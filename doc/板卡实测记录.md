# 板卡实测记录

2026-09-16，开发板用板载 Type-C 线接入本机后的实测结果。只从资料推出、没有实际测到的内容单独标注。

## 1. USB 枚举

| 项 | 实测 |
| --- | --- |
| 芯片 | FTDI FT4232H，VID `0403`，PID `6011` |
| USB 描述串 | `Quad RS232-HS`，是 FTDI 出厂默认值，EEPROM 里没有写板名 |
| 序列号 | 设备实例路径为 `5&2C0399E&0&9`，是按接入位置生成的，说明 EEPROM 里没有序列号 |
| 接入位置 | 根集线器 Port_#0009 |
| 驱动 | 接入时四个接口都是 FTDI VCP 2.12.36.20（服务 `FTDIBUS`）；同日 Interface 1 换成 libusbK，其余三个不变 |

本机没有 COM8。四个接口与串口号的对应关系，由设备管理器中接口与串口设备的父子关系查出；板上用途取自原理图（设计说明第 13 页，U5 FT4232HL）：

| 接口 | FT4232 通道 | 串口号 | 板上用途 | 驱动 |
| --- | --- | --- | --- | --- |
| Interface 0 | A（ADBUS0~7） | COM9 | 未连接，8 个脚全部悬空 | 不用动 |
| Interface 1 | B（BDBUS0~3） | COM10（换驱动后消失） | JTAG：TCK、TDI、TDO、TMS，各串 33Ω | 已用 zadig 换成 libusbK 3.1.0.0（`oem300.inf`），Efinity Programmer 和 OpenOCD 通过它访问 |
| Interface 2 | C（CDBUS0/1） | COM11 | UART：CDBUS0 接 `UART_TX_3V3`，CDBUS1 接 `UART_RX_3V3`，两根线上各有一个指示灯（D15、D16） | 保持 FTDI 驱动，作串口用 |
| Interface 3 | D（DDBUS0~7） | COM12 | 未连接 | 不用动 |

由此得到三点：

- 板上没有单独的 SPI 下载通道。Efinix 官方 Ti60F225 开发套件用 Interface 0 烧 Flash，这块板不一样，Flash 只能在 Programmer 里选 `SPI Active using JTAG Bridge` 烧写，设计说明第 85~86 页也是这样做的。
- 资料目录 `02_.../驱动安装及说明/` 下的 `XL_YLS_DL_*` 驱动包是外接下载器 YLS_DL 用的，写的是 FT2232 的 PID `6010`，与板载 FT4232H 的 `6011` 不符，不要装。那个目录里的 `zadig-2.8.exe` 可以用。
- 设计说明第 87 页让 OpenOCD 配置写 `ftdi channel 0`，但原理图上通道 A 是悬空的，两者矛盾。以原理图和本仓 `sdk/bsp/efinix/EfxSapphireSoc/openocd/ftdi_ti.cfg` 的 `channel 1` 为准；上板时如果 OpenOCD 连不上，再核对这一点。

## 2. 串口

- FPGA 侧：`system_uart_0_io_rxd` 在 GPIOL_02（R4），`system_uart_0_io_txd` 在 GPIOR_28（R14），3.3V LVCMOS。`fpga/ddr_demo_ti60/ddr_demo_ti60.peri.xml` 与设计说明第 34 页一致。
- 实测：COM9~COM12 同时以 115200、8N1 打开，DTR/RTS 不置位，只收不发，监听 8 秒，四个口都收到 0 字节。
- 这只能说明这 8 秒内板子没有往串口输出。板上 Flash 里现在是什么设计、SoC 是否在运行，都还不知道。官方示例只在启动时打印，要在按复位或重新上电的同时监听 COM11 才能判断。

## 3. JTAG 与 OpenOCD 配置

- `ftdi_ti.cfg` 中 `vid_pid 0x0403 0x6011`、`channel 1`，与上表的 JTAG 通道一致。
- 新版 IDE 使用的配置分支里 `ftdi device_desc` 一行是注释掉的，不按描述串匹配，所以 EEPROM 保持默认的 `Quad RS232-HS` 也不影响。旧版 IDE 分支里仍写着 `ftdi_device_desc "Titanium Ti60F225 Development Kit"`，用不上。

## 6. 命令行上板流程

2026-09-16 用这套命令跑通了官方比特流加 memTest，全程不开 GUI。

### 6.1 加载比特流（JTAG，掉电丢失，不改 Flash）

```
C:\Efinity\2026.1\pgm\bin\ftdi_pgm.bat -m jtag -u ftdi://0x0403:0x6011:0:ff/1 E:\Workspace\Efinix\Main\bit\official\ddr_demo_ti60.bit
```

JTAG 模式要的是 `.bit`，不是 `.hex`（`ftdi_program.py` 第 3119 行）。6MHz 下用时 3 秒，输出里有 `Device ID read from JTAG: 0x10660A79`。

### 6.2 编译软件

BSP 是 2025.2 生成的，所以用 WSL 里的 gcc 8.3.0 编译：

```
wsl.exe -e bash -c 'X=/home/glorinz/opt/xpack-riscv-none-embed-gcc-8.3.0-2.3/bin/riscv-none-embed-; cd /mnt/e/Workspace/Efinix/Main/sdk/software/standalone/application/memTest && make BSP=efinix/EfxSapphireSoc RISCV_BIN=$X OBJDIR=<输出目录>'
```

- 要写 `wsl.exe -e`。不带 `-e` 时，命令会先经过 WSL 默认 shell 再解析一遍，`$X` 在那一层就展开成空，make 于是退回用 x86 的 `gcc`，报 `unrecognized argument in option '-mabi=ilp32'`。
- 输出目录不要用 WSL 的 `/tmp`：同一天两次调用之间，`/tmp` 下的产物消失过一次。

### 6.3 加载并运行程序（OpenOCD）

OpenOCD 在 `C:\Efinity\efinity-riscv-ide-2026.1\openocd\bin\openocd.exe`。`debug_ti.cfg` 从当前目录往上最多找 4 级 `cpu0.yaml`，文件在 `sdk/` 下，所以要在应用目录里启动：

```
cd E:\Workspace\Efinix\Main\sdk\software\standalone\application\memTest
openocd.exe -f <sdk>/bsp/efinix/EfxSapphireSoc/openocd/ftdi_ti.cfg -f <sdk>/bsp/efinix/EfxSapphireSoc/openocd/debug_ti.cfg ^
  -c "reset halt" -c "load_image <memTest.bin> 0x1000 bin" -c "resume 0x1000" -c "sleep 30000" -c "halt" -c "reg pc" -c "shutdown"
```

结果：`reset halt` 后 PC 为 `0xf9000000`，也就是 bootloader 所在的片上 RAM；30 秒后停机，PC 为 `0x10a0`，是 `start.S` 中 `main` 返回后的 `mainDone` 死循环。COM11 收到：

```
***Starting Memory Test*** 
Data matched .. Test PASSED
***Succesfully Ran Demo*** 
```

踩到的三个问题：

| 现象 | 原因 | 做法 |
| --- | --- | --- |
| 不先 `reset halt`，直接 `load_image` 再 `resume 0x1000`：PC 停在 `0x8`，串口 0 字节。用 `dump_image` 读回的内存与 bin 的 SHA256 却一致；把 a0、a1 清零也一样 | 推测是指令缓存：FPGA 配置完后 bootloader 已经把 Flash 里的未知内容拷到 `0x1000` 并执行过，这些旧指令还留在 CPU 的 4KB 指令缓存里，而 JTAG 写 DDR 不经过这个缓存。加上 `reset halt` 就正常了，但没有做能区分「缓存」与「其他 CPU 状态」的实验 | 加载程序前一律 `reset halt`，IDE 的 launch 配置也是先复位（`doFirstReset`/`doSecondReset`） |
| `verify_image` 报 `Target fpga_spinal.cpu0 doesn't support checksum_memory`，OpenOCD 在这一步退出，后面的命令都不执行 | vexriscv 目标没有实现目标端校验和 | 用 `dump_image <文件> 0x1000 <长度>` 读回，在主机上比较 SHA256 |
| `step` 之后 PC 从 `0x1000` 变成 `0xc`，下一条命令报 `Target not halted` | 当时没有先复位，是否与上面第一条同因没有查 | 需要单步时改用 GDB，或先复位后再试 |

### 7.4 bootSizeTest：512KB bootloader 从 Flash 引导

`sdk/software/standalone/application/bootSizeTest/` 用来检查 bootloader 从 Flash 拷贝的长度：

- 程序带一个 300,000 字节的数据块（`src/blob.S`）。第 i 个字为 `i × 2654435761 + 0x5A5A5A5A` 的低 32 位，内容随位置变化。
- 启动后打印数据块整体和最后 4KB 的 CRC32。算法与 zlib 相同。

gcc 8.3.0 编译结果与 PC 侧期望值：

| 项 | 值 |
| --- | --- |
| bin 大小 | 301,882 字节（大于 124KB 的 126,976） |
| 数据块 | 起于 `0x00001750`，长 300,000 字节 |
| 最后 4KB | 起于 `0x00049b30`，远超 124KB 的拷贝边界 `0x00020000` |
| `crc_all` | `0x47df83a8` |
| `crc_tail` | `0x78c8c48f` |

数据块第 0、1、74999 个字已与公式逐个核对。程序或工具链改变后，期望值要重新计算。

上板过程（2026-09-16）：

1. 把程序写入 Flash `0x380000`，写入后单独读回，与 hex 文件 SHA256 一致（第 8 节）。
2. 对照组：JTAG 加载官方比特流（124KB bootloader），10 秒后读 COM11。
3. 实验组：接着 JTAG 加载 Main 比特流（512KB bootloader），10 秒后读 COM11。

对照组放在前面，是因为 FPGA 重配置期间 DDR3 可能保留上一次的内容（未验证）。如果先跑 512KB 版本，数据块尾部会残留正确数据，对照组可能假通过。

| 比特流 | bootloader | 打印的 `image` | `crc_all` | `crc_tail` | 结论 |
| --- | --- | --: | --- | --- | --- |
| 官方 `bit/official/ddr_demo_ti60.bit` | 124KB | 301884 | `0xca93125f` | `0x3e3489a4` | 两个都不符，符合预期：只拷了前 124KB |
| Main `outflow/ddr_demo_ti60.bit` | 512KB | 301884 | `0x47df83a8` | `0x78c8c48f` | 两个都与期望一致，**通过** |

- 对照组也能正常打印：代码和字符串都在镜像的前 124KB 里，缺的只是数据块后段。
- 打印的 `image` 比 bin 多 2 字节，因为 `_edata` 在 `.data` 之后按 4 字节对齐。
- 单线 SPI 拷贝 512KB 的实际用时没有测量，加载比特流后 10 秒内输出已经完整。

## 8. Flash

### 8.1 芯片与出厂内容

- JTAG Bridge 读到 JEDEC ID `0xEF6017`，芯片是 **Winbond W25Q64**，8MiB，按 4KB 扇区擦除（写 294KiB 时擦除 296KiB）。
- 写入前整片读出，内容如下：
  - `0x000000`~`0x0C74E2` 是一个比特流。文件头为 `Version: 2025.2.288.4.15`、`Project: _Prj_v4\10_Ti60f225_sc431hai2hdmi_demo\Ti60f225_sc431hai2hdmi_v3`，即资料包里的摄像头转 HDMI 例程，其中没有 SoC。这解释了第 2 节上电后串口没有输出。
  - 其余全部为 `0xFF`，`0x380000` 起的程序区是空的。
- 备份在 `bit/flash_backup/flash_20260916_W25Q64_before_bootSizeTest.hex`。格式为每字节一行文本，24MB，不进 git。连续读两次，文件 SHA256 相同（`ACF6181F8FEEB797…`）。

### 8.2 命令

JTAG Bridge 分两步：先用 JTAG 把 FPGA 配置成 Flash 烧写器，再通过它读写 Flash。

```
set U=ftdi://0x0403:0x6011:0:ff/1
ftdi_pgm.bat -m jtag -u %U% C:\Efinity\2026.1\pgm\fli\titanium\u10660A79.bit
ftdi_pgm.bat -m jtag_bridge --jtag_bridge_mode read --address 0x0 --num_bytes 0x800000 -o <备份.hex> -u %U% <不存在的文件.hex>
ftdi_pgm.bat -m jtag_bridge --jtag_bridge_mode all --verify_method hostx1 --address 0x380000 -u %U% <程序.hex>
```

- `u10660A79.bit` 按 JTAG ID 命名，是 Efinity 自带的桥接镜像（`efx_hw_manager.py` 第 1041 行从 `pgm/fli/` 列出）。
- `--jtag_bridge_mode` 的默认值是 `all`，即擦除加写入（`ftdi_program.py` 第 3189~3192 行）。读 Flash 时必须显式写 `read`。
- 即使是读，也必须给一个输入文件，且扩展名必须是 `.hex`（第 3123 行）。给一个不存在的路径，万一模式写错，也只会因为打不开文件而失败，不会写入。
- 读出的文件与 Programmer 的 hex 格式相同，可以原样写回。
- 写入地址必须在扇区边界上；擦除长度按扇区向上取整，只擦写入的那一段（第 2478~2498 行）。
- 不是比特流的数据也能写：解析文件头失败只打印警告（第 2336~2337 行）。
- 程序 bin 转 hex：每字节一行，两位大写十六进制，LF 换行，与官方 `.hex` 相同。目前用 WSL 中的 python 转换，并做了回环校验，还没有写成脚本。
- 用时：整片读取 31~33 秒；bootSizeTest 擦除 2 秒、写入 1 秒、读回校验 1 秒。

### 8.3 当前状态

- `0x000000` 起仍是出厂的摄像头例程，上电时加载的是它，不是 Main。
- `0x380000`~`0x3C9B39` 是 bootSizeTest。
- 恢复出厂内容：用 8.2 节的写入命令把备份文件写回 `0x0`。
