# 赛题二总体设计：Sprite 渲染加速系统

方案稿 v0.1，2026-09-16。本文所有带「估算」的数字都还没有上板实测，第 7 节列出了替换它们的实验。已核实的事实都注明了出处。

---

## 0. 目标与指标

### 0.1 赛题到底比什么

选题指南第 7~9 页（`Efinix/01_赛题指南/易灵思FPGA 创新设计赛道选题指南.pdf`）高阶挑战第 3 条原文：

> 在 RISC-V 上运行一个具有极高同屏元素数量的游戏 Demo（如《吸血鬼幸存者》的简化版或类似《东方 Project》的弹幕射击游戏）。在开启硬件加速（Alpha 混合 + Color Keying）的情况下，挑战保持 60 FPS 稳定运行时的同屏活动元素（Sprite）数量极限。

所以核心指标是：**开启 Alpha 与 Color Key、稳定 60 FPS 的前提下，同屏活动 Sprite 的最大数量**，下文记作 `N_max`。「弹幕数量」是它在弹幕游戏里的具体形态。

其余要求是门槛项，必须做到，但不决定排名：

| 类别 | 要求 |
| --- | --- |
| 基础 1 | 引擎解析指令（操作类型、源地址、目的地址、宽、高），支持块拷贝与纯色填充，HDMI 输出至少 640×480@60 |
| 基础 2 | 加速器经总线直接访问内存，合理使用突发与内部 FIFO |
| 基础 3 | C 驱动配置寄存器，双缓冲防撕裂；Demo 在屏幕上实时对比软件渲染与硬件渲染的帧率 |
| 高阶 1 | 硬件 Alpha 混合，用 DSP 计算 `fg*a + bg*(1-a)` |
| 高阶 2 | Color Key，跳过透明色像素 |
| 高阶 3 | 高负载游戏 Demo，冲 `N_max` |

### 0.2 我们自己要定死的口径

赛题没有规定「稳定」和「活动元素」怎么数，演示和报告里必须自己先写清楚，否则数字没有说服力：

- 稳定 60 FPS：连续 60 秒内没有一帧的渲染超过 16.67 ms，也就是不掉帧；同时报告帧时间的最大值和 99 分位。
- 活动元素：每帧实际提交给引擎、至少有一个像素落在屏幕内的 Sprite 绘制命令数。背景、HUD 底图不计入。
- `N_max` 由程序自动搜索：逐步加弹幕，直到出现掉帧再回退，结果显示在屏幕上并打到串口。

### 0.3 设计总原则

赛题要的是专用加速器，不是通用计算平台。和龙芯 NPU 那套「补齐计算原语全面性」的思路相反，这里只做对 `N_max` 和画面效果有直接贡献的东西：

- 不做浮点、不做通用 uop 虚拟机、不做 3D、不做实时旋转缩放。旋转和动画预先渲染成图集里的多帧。
- 硬件预算集中投在三件事上：减少每个 Sprite 的 DDR3 访问次数、把小纹理放进片上存储、多像素并行的混合通路。
- 架构上分层，接口带版本号和能力寄存器，新增一种混合模式或数据源只动一个模块。

### 1.2 裁剪清单

**关键结论：逻辑和 DSP 都不紧，片上 RAM 才是稀缺资源（总共 2.56 Mbit）。裁剪只有省 RAM 的那几条值得花时间，其余顺手做。**

1. **DDR 跨时钟 FIFO（17 块 RAM，占全片 6.6%）是冗余的。** 顶层把 SoC 的 `io_systemClk` 和 `io_memoryClk` 都接到同一个 `user_clk`（`rtl/ddr3_example_top.v` 第 390、395 行），跨时钟 FIFO 两端是同一个时钟。但 Sapphire 手册（UG-RISCV-SAPPHIRE v6.0，Cache/Memory 页）写明「External Memory Clock Domain：Unified System Clock」**只在 Lite 版可选**，当前配置（含 FPU、自定义指令等 Standard 专属项，`settings.json` 里 `DDRCLK_DOMAIN="1"`）走的是专用内存时钟。两条路：
   - 保留 Standard，接受这 17 块；
   - 换 Lite 版并选 Unified System Clock。Lite 没有 FPU、自定义指令、压缩指令，这些我们都用不上；乘除法和桶形移位器在 Lite 里要手动打开。需要实验 E1 比较 CoreMark 和 RAM 占用后再定。
2. **Efinity 调试核（1 块 RAM、944 LUT）。** 开发期保留，发布构建去掉 `Efinity_Debug` 宏和调试配置。建议做成构建开关，不要手删。
3. **I2C0。** 在 SoC IP 里关掉，省约 170 FF、220 LUT。
4. **外部 AXI 主机口 `io_ddrMasters_0`（32 位）。** 加速器如果按 3.3 节走 `Axi_Mux` 接入 DDR3，就用不到 SoC 内部这个口，可在 IP 里关掉，连带省一部分仲裁和位宽转换逻辑（具体数字要重新生成后看报告）。
5. **`axiA` 16MB 从口窗口。** 控制寄存器放 APB Slave 0（64KB）足够，关掉。
6. **工程文件列表清理。** `rtl/memory_test/` 与 `src/Axi_Mux.v` 在列表里但没有例化。`memory_test` 删掉；`Axi_Mux.v` 留着，3.3 节要用。
7. **不要动的。** `settings.json` 里 `BARREL_SHIFTER="1'b0"`、`MULDIV_EXT="1'b0"` 看起来像关了，但手册注明这两项是 Lite 专属，Standard 里默认开启，不是性能隐患。

裁剪能省下的逻辑合计约 1.5K LUT，对这块 60K 的芯片意义不大；能省下的 RAM 是 1 块（调试核）加可能的 17 块（换 Lite）。

### 1.3 要加回来的

| 项 | 原因 |
| --- | --- |
| 按键 KEY0~3 接进 SoC | 游戏输入。管脚 C4、P14、N14、A3，都在 3.3V bank（设计说明第 33 页）。开 GPIO1 或把 GPIO0 加宽 |
| 用户中断 A 接引擎 | 场同步、命令表执行完、错误三种中断。`USER_0_INTR` 已开，中断号 16 |
| 缓存加大（待定） | 游戏逻辑的数据（几千个弹幕的数组）远大于 4KB 数据缓存。手册允许 1~32KB，每加倍大约多 8 块 RAM，需要实验 E8 看收益 |
| bootloader 程序区扩大 | 原来应用只有 124KB（`LDSize=124`，`USER_SOFTWARE_SIZE=0x1F000`），装不下游戏。2026-09-16 已改为 Flash 镜像 512KB、程序区 4092K，并直接替换了片上 RAM 初始文件，不必重新生成 SoC；做法与检查见 `README.md`「Bootloader 与程序区」，尚未上板 |

### 1.4 计算卸载的路线

| 阶段 | CPU 做 | 硬件做 | 墙在哪 |
| --- | --- | --- | --- |
| 软件基线 | 游戏逻辑 + 逐像素绘制 | 扫描输出 | CPU 访存带宽 |
| P1 直通 BitBlt | 游戏逻辑 + 生成命令表 | 按命令逐个在 DDR3 上搬运与混合 | 每个 Sprite 几十次 DDR 事务 |
| P3 条带合成 | 同上 + 按行分桶 | 在片上条带缓冲里合成，整行读写 DDR3 | CPU 生成命令的速度 |
| P4（可选）弹幕运动卸载 | 发射、碰撞判定结果处理、规则 | 按参数更新弹幕位置、直接生成绘制 | 硬件合成算力 |

第 3.1 节给出每一步墙的估算。

## 2. 资源划分

### 2.1 DDR3 地址空间（256MB）

**已核实的事实**

- 板上 DDR3 256MB，控制器 AXI 地址 28 位，正好覆盖 `0x0000_0000`~`0x0FFF_FFFF`（`rtl/ddr3_controller/ddr3_parameter.vh`）。
- CPU 看到的 DDR 窗口从 `0x0000_1000` 开始，窗口大小 `0xE000_0000`（`sdk/.../soc.h`）。
- 顶层把 SoC 的 32 位地址直接接到控制器 28 位地址上。所以 256MB 以内 CPU 地址与 AXI 物理地址大概率相同，超出后会回绕别名。**这一点要实验 E2 上板确认**，确认之前驱动里不要假设。

**分区**

| 区 | 地址范围 | 大小 | 内容 | 读 / 写方 |
| --- | --- | --: | --- | --- |
| 保留 | `0x0000_0000`–`0x0000_0FFF` | 4KB | CPU 窗口之外 | 不用 |
| 程序 | `0x0000_1000`–`0x003F_FFFF` | 约 4MB | 代码、数据、堆、栈 | CPU |
| 命令表 A/B | `0x0040_0000`–`0x005F_FFFF` | 2MB | 两张命令表各 1MB，每张最多 32768 条 32 字节命令 | CPU 写，引擎读 |
| 共享数据池 | `0x0060_0000`–`0x00FF_FFFF` | 10MB | P4 弹幕参数表、其他需要与引擎共享的数据 | CPU / 引擎 |
| 素材 | `0x0100_0000`–`0x01FF_FFFF` | 16MB | 纹理图集、背景、字库，启动时从 Flash 装入 | CPU 写一次，引擎读 |
| 帧缓冲 0 | `0x0200_0000`–`0x023F_FFFF` | 4MB | 见下 | 引擎或软件渲染写，扫描输出读 |
| 帧缓冲 1 | `0x0240_0000`–`0x027F_FFFF` | 4MB | 同上 | 同上 |
| 离屏层 | `0x0280_0000`–`0x02FF_FFFF` | 8MB | 背景预合成、调试抓帧 | 引擎 |
| 预留 | `0x0300_0000`–`0x0FFF_FFFF` | 208MB | — | — |

**帧缓冲的行跨取 4096 字节**，也就是每一行在内存里占一个完整的 4KB 页，每行最多 1024 个 32 位像素：

- 一行的读写正好是一次突发，**永远不会跨 4KB 边界**。AXI4 禁止突发跨 4KB，这是龙芯工程 MTX 搬运层踩过的协议坑（`Loongarch_NPU_SoC/Main/rtl/ip/mtx/doc/mtx.md` 第 5 节）。行跨取 4096 后，这个问题在数据布局上就消失了，不再需要额外的边界检查。
- 地址计算只剩移位：`addr = base + (y << 12) + (x << 2)`。
- 代价是一帧占 480×4KB = 1.875MB，比紧凑存放多 0.7MB，256MB 里不值一提。
- 640 个像素 = 160 个 128 位 beat，一次突发放得下（AXI 上限 256 beat）。但控制器参数里有 `BURST_MODE="8"`，控制器 AXI 部分是加密的，看不出它是否限制了突发长度，**实验 E4 必须先测**。搬运层把最大突发长度做成参数，测完再定。

**像素格式**：帧缓冲 XRGB8888，纹理 ARGB8888（预乘 alpha，见 3.5）。选 32 位而不是 RGB565 的理由是一个 128 位 beat 正好 4 个像素，搬运和并行混合都按 4 像素对齐，逻辑最简单；带宽代价见 3.1，不是瓶颈。

**命令表双份**：CPU 在第 N 帧填命令表 A 的同时，引擎还在执行第 N−1 帧的命令表 B。两者流水并行，吞吐翻倍，代价是画面延迟多一帧。

**Cache 一致性**：引擎直接改 DDR，CPU 的数据缓存可能留着旧值。约定共享区单向使用：命令表和素材 CPU 只写不读回，帧缓冲 CPU 只在软件渲染模式下写。状态一律走寄存器。实验 E3 验证这条约定。

### 2.2 Flash（8MB）

| 区 | 地址 | 大小 | 内容 |
| --- | --- | --: | --- |
| 比特流 | `0x000000`–`0x1FFFFF` | 2MB | 当前比特流约 636KB：`bit/official/ddr_demo_ti60.bit` 文件大小 1.95MB，但它是每行一个字节的十六进制文本，共 651,444 行 |
| 空闲 | `0x200000`–`0x37FFFF` | 1.5MB | 素材溢出区 |
| 应用 | `0x380000`–`0x3FFFFF` | 512KB | bootloader 从这里拷程序，地址 `0x380000` 由 bootloader 决定 |
| 素材包 | `0x400000`–`0x7FFFFF` | 4MB | 带目录头的图集、背景、字库 |

两个约束：

- 4MB 素材放不下几张全屏图（640×480 ARGB8888 一张 1.2MB）。背景用图块拼、或者调色板加 RLE 压缩。
- 装载时间。手册写 bootloader 拷 124KB 约 300ms，照此单线 SPI 拷 4MB 约 10 秒。bootloader 支持双线与四线读取，但顶层只连了 SPI0 的 `data_0/1`，`data_2/3` 悬空，`peri.xml` 也只分配了两根数据线，所以现在只能试双线（`spiFlash_f2m_dual`）；四线要先改顶层与接口设计，并核对板上 Flash 的 IO2/IO3 是否接到 FPGA。实验 E6 测单线与双线的速度。

### 2.3 片上 RAM 预算（256 块，每块 10Kbit）

块数按 `位数 / 10240` 向上取整估算。Efinity 实际映射受深宽比影响，v1 摄像头工程里 1024 深×128 宽的 FIFO 实测 13 块，与公式一致。

| 用途 | 规格 | 块数 | 备注 |
| --- | --- | --: | --- |
| DDR3 控制器 | 固定 | 22 | |
| CPU 缓存 | 4KB + 4KB | 16 | 实验 E8 后可能加大 |
| 片上 RAM、UART、SPI、DDR 桥 | 固定 | 10 | |
| DDR 跨时钟 FIFO | 固定 | 17 | 换 Lite 后为 0 |
| **现有小计** | | **65** | 去掉调试核后 |
| 扫描输出异步 FIFO | 128 位 × 512 深（约 3 行） | 7 | 跨 100MHz → 25.2MHz |
| 引擎 DDR 读缓冲 | 128 位 × 256 深 | 4 | |
| 引擎 DDR 写缓冲 | 128 位 × 256 深 | 4 | |
| 命令缓冲 | 256 条 × 256 位 | 7 | 从 DDR 命令表批量读入 |
| 条带缓冲（P3） | 640 × 16 行 × 32 位 | 32 | 条带 8 行则 16 块 |
| 热纹理缓存（P3） | 128×128 ARGB8888 一页 | 52 | 放 64 帧 16×16 的弹幕和粒子 |
| OSD 字库 | 96 字 × 8×16 点阵 | 2 | 硬件叠加帧率和计数 |
| **新增小计** | | **108** | |
| **合计** | | **173（67.6%）** | 余 83 块。换 Lite 为 156 块 |

原则：**富余的 RAM 优先给热纹理缓存和条带缓冲**。3.1 节会算出，这两样直接决定每个 Sprite 要不要访问 DDR3，是 `N_max` 的主要杠杆。

### 2.4 DSP 预算（160 块）

每块 DSP 在 dual 模式下有一个 11×10 和一个 8×8 乘法器（Ti60 数据手册 DSP Block 一节）。

| 用途 | 数量 |
| --- | --: |
| CPU 乘法 | 4 |
| 混合通路：每像素 3 个通道乘法，每条通路一次处理 4 像素 | 每条通路 12 个乘法，约 6~12 块 |
| 着色（tint，可选） | 同上再加一份 |
| 扫描输出全局淡入淡出 | 3 个乘法 |
| **合计（2 条通路、带着色）** | **约 50 块以内** |

DSP 不是约束，不需要为省 DSP 用移位加法近似。

### 2.5 时钟与复位

- 引擎挂 `user_clk`（100MHz），与 SoC、DDR3 控制器的 AXI 同一个时钟域。控制器 `ASYN_AXI_CLK=0`，所以引擎到 DDR3 不需要跨时钟。
- 唯一的跨时钟点是扫描输出：100MHz 读 DDR3，经异步 FIFO 送 25.2MHz 像素域。
- 场同步从像素域同步到 100MHz 后，给引擎做缓冲切换、给 CPU 发中断。前后缓冲的切换请求在像素域的场消隐期锁存，保证不撕裂。
- `core_clk` 来自 PLL_TL0，DDR3 的 400MHz 来自 PLL_TR0，二者同源于 25MHz 晶振（`peri.xml`）。这是官方原样，不动。

## 3. 加速器设计

### 3.1 先算账：墙在哪

每帧可用的时间是 16.67ms，按 100MHz 算约 166 万个时钟周期。

**DDR3 带宽不是墙。** 控制器每 10ns 最多交换一个 128 位 beat（x16 颗粒解串到 128 位，DDR3 控制器手册 v2.1），理论上限每秒 1 亿 beat。640×480@60 的扫描输出每秒只要 461 万 beat，占 4.6%；整帧读背景加整帧写回再占 9.2%。实际吞吐会低于理论值，E4 实测，但数量级上有富余。

**真正的墙是事务次数。** 一次 AXI 突发除了传数据，还有地址握手、控制器排队、写响应等固定开销，记为 `t_tx`（周期数，未知，E4 测）。龙芯工程 GEMM 已经实测过同类问题：搬运占了 87%~91% 的时间，计算只占零头（`Loongarch_NPU_SoC/Main/rtl/ip/gemm/doc/gemm.md` 11.1 节）。所以设计的第一目标是减少每个 Sprite 的事务数。

下面用 `t_tx = 20` 个周期作为假设，比较三种架构画一个 16×16 带 Alpha 的 Sprite 的代价。结论对 `t_tx` 的取值不敏感，只有绝对数字会变。

| 架构 | 每个 Sprite 的 DDR 事务 | 每个 Sprite 的周期（估算） | 每帧固定开销（估算） | `N_max` 硬件侧上限（估算） |
| --- | --- | --: | --: | --: |
| A. 直通 BitBlt：逐行读纹理、读目标、写目标 | 16 行 × 3 = 48 次 | 约 1400 | 背景整帧拷贝约 17 万 | 约 1000 |
| B. 条带合成，纹理在 DDR3 | 每行读 1 次纹理 = 16 次 | 约 600 | 整帧读写背景约 17 万 | 约 2500 |
| C. 条带合成，纹理在片上缓存 | 0 次 | 约 70（4 像素并行） | 同上 | 约 2 万 |

架构 C 的硬件上限远超 CPU 能喂的量。CPU 这一侧的估算：Sapphire 手册给出 1.16 DMIPS/MHz，按 100MHz 约 116 DMIPS；每个弹幕的更新、碰撞和写 32 字节命令算 100 条指令左右，5000 个弹幕就要约 50 万条指令、5ms 量级。**所以做完 C 之后，墙会移到 CPU 生成命令上**，这就是 P4 弹幕运动卸载存在的理由。E8 实测每弹幕的 CPU 开销。

### 3.2 总体结构

```
           RISC-V（Sapphire）
             │ APB（寄存器）          │ AXI 128 位（程序、命令表、素材）
             ▼                        ▼
      ┌──────────────┐          ┌──────────┐
      │  前端 CSR    │          │ Axi_Mux  │── DDR3 控制器 ── DDR3 256MB
      │ 命令表门铃   │          │ 3 进 1 出│
      │ 中断/计数器  │          └──────────┘
      └──────┬───────┘             ▲     ▲
             ▼                     │     │
      ┌──────────────┐   S1 引擎   │     │ S2 扫描输出（优先级最高）
      │ 中端         │─────────────┘     │
      │ 命令解码     │                   │
      │ 几何/裁剪    │           ┌───────┴──────┐
      │ 行/条带迭代  │           │ 扫描读出     │
      └──────┬───────┘           │ 异步 FIFO    │
             ▼                   │ 时序/OSD/淡出│
      ┌──────────────┐           │ DVI 编码     │── HDMI
      │ 像素流水线   │           └──────────────┘
      │ 取数→色键→   │
      │ 乘→加→写     │
      └──────┬───────┘
             ▼
      ┌──────────────────────────────┐
      │ 后端：三个地址空间            │
      │ DDR（搬运层）/ TEX 纹理缓存 / BAND 条带缓冲 │
      └──────────────────────────────┘
```

分层直接借用龙芯工程 MTX 的思路（`mtx.md` 第 2 节）：前端是各自的软件接口，中端把「搬什么形状」展开成连续段，后端只管「怎么在 AXI 上搬完」。区别在于这里多了一个像素流水线，而且后端有三个地址空间。

### 3.3 总线接入

用官方工程里现成但没例化的 `fpga/ddr_demo_ti60/src/Axi_Mux.v`，不用 tinyml 工程的 `axi_interconnect_beta`：

| | `Axi_Mux.v` | `axi_interconnect_beta` |
| --- | --- | --- |
| 源码 | 明文，可以仿真、可以改 | 加密 |
| 端口 | 2~8 个主机进、1 个出（宏 `X2`~`X8`） | `S_COUNT` 参数 |

接法：S0 接 SoC 的 `io_ddrA`（128 位），S1 接引擎，S2 接扫描输出，出口接 DDR3 控制器。

扫描输出是实时流，不能靠先到先得（`mtx.md` 第 13 节已经写过这个教训）。用优先级模式把扫描输出排最高，FIFO 深度留 3 行。最坏情况下扫描要等一个 256 beat 的突发做完，约 2.6 微秒，而像素域消耗一行要 25 微秒，余量充足。实验 E5 在满负载下验证 FIFO 不欠载。

### 3.4 命令与软件接口

**表面（surface）表。** 所有「地址」都经过表面表间接寻址，驱动先登记表面，命令里只写表面号和坐标。这样硬件能统一做裁剪和越界检查，也满足赛题「源地址、目的地址」的要求：源地址 = 源表面基址 + 源坐标换算。

| 字段 | 宽度 | 含义 |
| --- | --: | --- |
| `base` | 32 | 基址，DDR 物理地址或片上缓存偏移 |
| `stride_log2` | 5 | 行跨取的 log2，帧缓冲为 12 |
| `width` / `height` | 各 16 | 尺寸，用于裁剪 |
| `space` | 2 | 0 DDR，1 TEX 纹理缓存，2 BAND 条带缓冲 |
| `format` | 4 | XRGB8888、ARGB8888 预乘、8 位索引 + 调色板 |

**命令记录固定 32 字节（8 个字）。** 记录长度必须是 2 的幂，硬件才能用移位算第 k 条的地址，这是 VSE gather 踩过的坑（`Engineering/_raw/Temp/VSE-Alpha混合入门.md` 6.2 节）。

| 字 | 位 | 字段 |
| --- | --- | --- |
| w0 | [7:0] | 操作码：0 NOP，1 FILL，2 BLIT，3 SET_CLIP，4 BAND，0xFF END |
| | [11:8] | 混合方程编号（3.5） |
| | [12] | 色键使能 |
| | [13] | 着色使能 |
| | [19:16] | 源表面号 |
| | [23:20] | 目的表面号 |
| | [31:24] | 常数 alpha |
| w1 | [15:0] / [31:16] | 源 x / 源 y |
| w2 | [15:0] / [31:16] | 目的 x / 目的 y，有符号，允许部分出屏 |
| w3 | [15:0] / [31:16] | 宽 / 高 |
| w4 | | FILL 的颜色或着色颜色 |
| w5 | | 色键颜色 |
| w6 | | 预留：翻转标志、帧号 |
| w7 | | 序号，调试与错误定位用 |

**纹理上传也是一条 BLIT**：目的表面的 `space` 设为 TEX，就把 DDR3 里的纹理拷进片上缓存，不需要另开一套上传接口。

**寄存器（APB Slave 0，基址 `0xF810_0000`）**

| 偏移 | 名称 | 说明 |
| --- | --- | --- |
| `0x000` | `ID` | 固定魔数 + 版本号 |
| `0x004` | `CAPS` | 能力位：色键、alpha、条带模式、TEX 大小、通路数 |
| `0x008` | `CTRL` | 使能、软复位、模式（直通 / 条带） |
| `0x00C` | `STATUS` | 忙、错误码、当前命令序号 |
| `0x010` / `0x014` | `IRQ_EN` / `IRQ_STAT` | 场同步、命令表完成、错误 |
| `0x020` / `0x024` / `0x028` | `LIST_BASE` / `LIST_COUNT` / `DOORBELL` | 提交命令表 |
| `0x030` / `0x034` | `FRONT` / `SWAP_REQ` | 前缓冲表面号，切换请求在场消隐生效 |
| `0x040`~`0x0BF` | `SURF[0..15]` | 表面表，每个 8 个字 |
| `0x100`~`0x13F` | `PERF_*` | 计数器，场同步时快照 |
| `0x200`~`0x27F` | `OSD_TEXT` | 硬件叠加的字符 |
| `0x300`~`0x3FF` | `PALETTE` | 8 位索引格式的调色板 |

**计数器按「能对账」设计**，龙芯 GEMM 的计数器口径一节就是为了这个（`gemm.md` 4.1 节）：`CMD`、`PIXEL`、`KEY_SKIP`、`RD_BURST`、`WR_BURST`、`RD_BEAT`、`WR_BEAT`、`WAIT_DDR`（等 ready 的周期数）、`BUSY`、`FRAME_DROP`。约束关系要成立，例如 `RD_BEAT` 等于各读突发长度之和；对不上就说明有漏计，不能拿去分析性能。

### 3.5 像素流水线

**混合方程统一成一张表，不为每种效果写一条通路。** 纹理一律存预乘 alpha（素材工具转换时乘好），混合写成：

```
out = src × Fs + dst × Fd       每个通道，结果饱和到 255
```

| 编号 | 名称 | Fs | Fd | 用途 |
| --: | --- | --- | --- | --- |
| 0 | COPY | 1 | 0 | 背景、不透明图块 |
| 1 | ALPHA | 1 | 1 − a_src | 半透明弹幕、UI 面板（预乘） |
| 2 | ADD | 1 | 1 | 发光、爆炸、激光 |
| 3 | CONST | c | 1 − c | 整体淡入淡出、受击闪烁 |
| 4 | MUL（预留） | dst | 0 | 阴影、暗化 |

- 预乘之后 ALPHA 每通道只剩 1 个乘法。赛题公式 `fg*a + bg*(1-a)` 与预乘形式在数学上等价（`fg_pm = fg*a`）；报告里要写清这层换算，并保留一个「非预乘」开关，演示时可以直接对照赛题公式。
- 除以 255 用精确舍入：`q = (x + 128 + ((x + 128) >> 8)) >> 8`，对 0~65025 的乘积与四舍五入结果一致。仿真里做全量穷举验证。
- 色键独立于混合方程：源像素等于色键颜色时不写目的像素。赛题明确要求色键，即使 alpha 为 0 的像素也能起到同样效果，也要单独实现。
- 新增一种效果只加表中一行，不改流水线结构。

**流水线分 5 级，每级一次处理 4 个像素（一个 128 位 beat）**

```
级 0  取数     src 字、dst 字（直通模式从 DDR 读缓冲取，条带模式从 BAND 取）
级 1  判定     色键比较，选 Fs / Fd
级 2  乘       DSP，输出寄存
级 3  加与舍入 饱和、÷255
级 4  写回     写缓冲 / BAND；色键命中的像素保持原值
```

吞吐每周期 4 像素。条带模式下数据全在片上，可以复制多条通路按 x 区间并行；直通模式受 DDR3 事务限制，多条通路没有收益。

### 3.6 两种执行模式

**直通模式（P1，满足基础要求）**：命令逐条执行，目的就是 DDR3 帧缓冲。适合大块拷贝和填充，例如整帧背景、大图切换，这时一次突发 160 beat，事务开销被摊薄。

**条带模式（P3，冲 `N_max`）**：借鉴移动 GPU 的分块延迟渲染（tile-based deferred rendering），把屏幕按 16 行一条切开：

1. CPU 生成命令时按条带分桶，每条带一个命令子表。高度不超过 16 的 Sprite 最多落在 2 条带里，分桶是 O(N)。同一条带内保持提交顺序，也就保持了绘制顺序。
2. 引擎逐条带处理：从 DDR3 读背景的 16 行进 BAND（16 次突发），执行该条带的全部命令（纹理来自 TEX 或 DDR3），把 16 行写回后缓冲（16 次突发）。
3. 每帧固定 960 次突发，与 Sprite 数量无关。Sprite 数量只受像素流水线算力限制。

两种模式共用同一套命令格式、同一个像素流水线，区别只在目的地址空间和迭代顺序。

### 3.7 双缓冲与帧节拍

1. 引擎按场同步中断工作。CPU 在帧 N 生成命令表 A，同时引擎渲染帧 N−1 的命令表 B 到后缓冲。
2. 引擎渲染完置 `IRQ_STAT.list_done`，CPU 写 `SWAP_REQ`。
3. 切换在下一个场消隐锁存。如果引擎在场消隐前没画完，这一帧保持前缓冲，`FRAME_DROP` 加一。
4. 软件渲染模式下同一套切换机制照用，只是后缓冲由 CPU 写。

### 3.8 软件执行器：同一份命令表，两个执行者

赛题要求实时对比软件与硬件帧率。最有说服力的对比是：**同一个游戏、同一份命令表，一次交给 C 语言写的软件执行器画，一次交给硬件画**。这个软件执行器还有第二个用途：它就是硬件的金标准。

- 板上：同一帧命令表软硬各跑一次，比较后缓冲 CRC，作为逐像素一致的上板判据。
- PC 上：软件执行器编进 PC 版游戏，开发游戏和做计算统计都不需要板子。
- 仿真：软件执行器输出的帧作为硬件测试台的期望值。

硬件实现与软件执行器之间的语义差异（舍入、裁剪边界、色键和混合的先后）必须在 3.5 节的表里写死，两边照同一份规格实现。

### 3.9 与龙芯工程的对照

| 龙芯工程做法 | 本设计 | 理由 |
| --- | --- | --- |
| VSE：通用 uop 程序表达任意运算 | 固定流水线 + 混合方程表 | 2D 游戏的像素运算只有五六种，可编程的每像素调度开销换不来收益 |
| GEMM：FP32 全程浮点 | 8 位定点 | 像素本来就是 8 位 |
| MTX：描述符 → 连续段 → 突发 | 保留这三层 | 已经证明清晰，可以照搬思路 |
| MTX：4KB 边界与最大突发长度两条限长 | 帧缓冲行跨 4096 消掉第一条，第二条参数化等 E4 | 协议要求 |
| MTX：超时后排空，不直接回空闲 | 保留 | 共享 DDR3 上跑着 CPU 的程序，把总线挂死等于死机 |
| GEMM：计数器能对账 | 保留 | 性能分析的前提 |

## 4. 软件设计

### 4.1 做一个游戏是不是异想天开

不是。赛题要的是「简化版」，弹幕射击的机制本身很简单：

- 弹幕只有位置和速度，每帧加一次；
- 弹型用参数方程生成（圆环、螺旋、自机狙、扇形、随机雨），几行代码一种；
- 碰撞只需要判「自机与敌弹」和「自机子弹与敌机」，自机判定点是一个小圆，O(N) 就够；
- 没有物理引擎、没有寻路、没有网络。

纯 C 大约 2000~3000 行能完成一个可玩的关卡。真正难的是让它在 116 DMIPS、无 FPU 的 CPU 上跑到几千个弹幕，这正是本设计要解决的问题。

### 4.4 软件分层

```
game/        游戏逻辑：实体池、弹型、碰撞、关卡脚本           与平台无关
render/      显示列表：命令记录、条带分桶、表面管理             与平台无关
exec_sw/     软件执行器：按 3.5 节规格逐像素执行命令表           与平台无关，也是金标准
hal/         平台层
  board/     引擎驱动、场同步中断、按键、UART、定时器、素材装载
  pc/        SDL2 窗口、键盘、计时
tools/       素材工具：PNG → 预乘 ARGB 图集 + 索引头；素材包打包进 Flash 镜像
```

实现约束：

- 无 FPU：坐标用 Q12.4 定点，角度用 1024 项的正弦表。
- 实体用结构体数组拆成的并列数组（SoA），一次循环只碰需要的字段，对 4KB 数据缓存友好。
- 不在每个弹幕上调用函数指针；弹型在发射时算好参数，更新循环只做加法。
- 离屏弹幕立即回收，实体池固定大小，不用 `malloc`。
- 同一份 `game/`、`render/`、`exec_sw/` 在 PC 和板子上编译，PC 版先跑通再上板。
- 程序放 `sdk/software/standalone/` 下，沿用官方 makefile（`riscv-none-embed-gcc`）。

### 4.5 计算类型统计

**这一节的数字是按场景参数推算的模型，不是实测。** 实测靠 4.6 节的计数器，PC 版游戏做出来后先在 PC 上跑出第一版真实统计。

场景 S1：游戏区 400×480，Boss 弹幕段的典型一帧。

| 运算类别 | 对象 | 个数 | 单个尺寸 | 像素数 | 每像素运算 |
| --- | --- | --: | --- | --: | --- |
| COPY 不透明 | 滚动背景 | 1 | 400×480 | 192,000 | 读 + 写 |
| COPY 不透明 | HUD 底图 | 1 | 240×480 | 115,200 | 读 + 写；可优化为只在分数变化区重画 |
| COPY + 色键 | 敌机 | 20 | 32×32 | 20,480 | 读 + 比较 + 写 |
| COPY + 色键 | 自机 | 1 | 32×32 | 1,024 | 同上 |
| COPY + 色键 | HUD 文字 | 60 | 8×16 | 7,680 | 同上 |
| ALPHA（预乘） | 敌弹 | 2,000 | 12×12 | 288,000 | 读源 + 读目的 + 3 乘 + 3 加 + 舍入 |
| ADD | 自机子弹 | 40 | 8×16 | 5,120 | 读源 + 读目的 + 3 饱和加 |
| ADD | 爆炸与粒子 | 200 | 16×16 | 51,200 | 同上 |
| CONST | 受击闪白 | 0~1 | 400×480 | 0~192,000 | 3 乘，偶发 |
| FILL | 血条、边框 | 若干 | — | 约 2,000 | 写 |
| **合计** | | **约 2,320 个 Sprite** | | **约 68 万像素（约 2.2 倍屏幕）** | |

从表里读出的结论：

1. **按个数，86% 是小尺寸的 ALPHA 敌弹，而且只用少数几种纹理**。热纹理缓存加条带模式正是为它们准备的。
2. **按像素，COPY 占 45%、ALPHA 占 42%**。COPY 集中在两张大图上，走长突发很便宜；ALPHA 分散在几千个小矩形里，事务开销才是大头。
3. **乘法**：每帧约 86 万次 8 位乘法，全部来自 ALPHA。流水线每周期 4 像素、12 个乘法，约 7.2 万个周期、0.72ms 就能做完，算力不是问题。
4. **FILL 几乎可以忽略**，但它是赛题基础要求，必须有。
5. **CPU 侧**每帧要更新 2,000 个弹幕、写约 74KB 命令表（2,320 × 32 字节）。`N` 冲到上万时，这部分会先撑不住（3.1 节）。

场景 S2（压力测试）只把敌弹数 `N` 当变量，其余同 S1。每加 1,000 个 12×12 弹幕，多 14.4 万像素、43.2 万次乘法、3.2 万字节命令。

### 4.6 统计埋点

软件执行器和硬件引擎用同一套统计口径，才能逐项对比：

| 统计项 | 软件执行器 | 硬件 |
| --- | --- | --- |
| 每类运算的命令数、像素数、色键跳过像素数 | 计数变量 | `PERF_CMD` / `PERF_PIXEL` / `PERF_KEY_SKIP` |
| DDR 突发数、beat 数、等待周期 | — | `PERF_RD_BURST` 等 |
| 游戏逻辑耗时、生成命令耗时 | CLINT 定时器打点 | 同左 |
| 渲染耗时 | 软件执行器前后打点 | 门铃到 `list_done` 中断的时间 |
| 帧时间分布、掉帧数 | 串口输出直方图 | `PERF_FRAME_DROP` |

统计结果每秒经串口输出一行 CSV，PC 上汇总画图，直接进报告。

## 6. 容易漏掉的规划项

1. **验证策略。** DDR3 控制器、SoC、`axi_interconnect_beta` 都是加密的，iverilog 仿不了整机。分三层：
   - 引擎单元仿真：自写 AXI 从机模型，必须带随机反压、可配的突发长度上限和响应延迟。龙芯工程的教训是测试台里的从机比真从机强，等于没验。
   - 金标准：软件执行器输出的帧，逐像素比较。
   - 上板：同帧软硬件 CRC 对比，经串口报告。每条判据按 SOP 先注错见红。
   - `Axi_Mux.v` 是明文，扫描输出优先级可以在仿真里先验证。
2. **错误通路。** 突发超时、`RRESP`/`BRESP` 非 OKAY、命令越界，都要置粘滞错误位和序号、发中断，超时后排空再回空闲（3.9 节）。别等出事了才补，龙芯工程 MTX 就是事后才发现错误上报整条是死的。
3. **时序。** 像素流水线每级寄存；DSP 输出寄存；按手册建议，高频下布局布线用 TIMING_1。每次加模块看 WNS/WHS 有没有被挤。
4. **素材流水线。** PNG 到预乘图集的工具、素材包格式（目录头 + 数据）、Flash 镜像合成（比特流 + 程序 + 素材）、启动装载与校验，都要在 M3 之前做完。
5. **规则风险。** P4 把弹幕运动交给硬件，可能被认为不是「在 RISC-V 上运行游戏」。建议：规则、发射、碰撞结果处理始终在 CPU；硬件只做运动学和绘制；保留纯 CPU 运动模式作对照，报告里写明两种模式各自的 `N_max`。
6. **分辨率余量。** 行跨 4096 最多支持 1024 宽。以后想上 1280×720 要改为 8192 跨，同时换 PLL（74.25MHz），扫描带宽约乘 3。现在只把行跨做成参数。
7. **开发环境与硬件。** 开发板 2026-09-16 已接到本机（枚举情况见 `doc/板卡实测记录.md`）；同日装了 Efinity 2026.1 与 RISC-V IDE 2026.1，工程从 2025.2 迁过去要升级 SoC IP 并同步软件包（见 `README.md`「使用」）；PC 版游戏和引擎单元仿真不依赖工具，可以先做。
8. **交付物。** 源码、报告、演示视频（赛题一的宣讲里鼓励 B 站风格短视频，赛题二可以照做）。提交截止时间资料里没找到，以官方通知为准。
