# 开工前准备情况

2026-09-16。这份文件回答三个问题：现在的工程占了多少资源、还有哪些浪费可以卸载、引擎要接进来还差什么。数字来自当天重构后的那次编译与上板，命令和过程在 `板卡实测记录.md`。

## 1. 结论

硬件基线已经全部上板验证过：SoC 跑得起来、DDR3 读写正确、HDMI 出画、程序能从 Flash 引导、APB 寄存器通路可读写。仓库也按目录分好层、每层有 README。

还没做的是两类：**SoC 内部的裁剪**（要重新生成 IP，第 3 节）和**引擎的接入点**（第 4 节）。两者都不阻塞开工，但第 4 节里 E2、E4 两个实验决定架构参数，建议排在写引擎代码之前。

## 2. 当前占用与时序

Efinity 2026.1 编译 `fpga/gfx2d_ti60`，四步 PASS，用时 77 秒。

| 项 | 用量 | 占比 |
| --- | --: | --: |
| XLR | 14517 / 60800 | 23.9% |
| 片上 RAM 块 | 65 / 256 | 25.4% |
| DSP | 4 / 160 | 2.5% |
| 全局时钟 | 10 / 32 | 31.3% |

分模块（数量级，取自布局报告的层次统计）：

| 模块 | XLR | RAM 块 | 说明 |
| --- | --: | --: | --- |
| `u_soc` | 约 8700 | 43 | CPU 约 3300/16 块，DDR 跨时钟 FIFO 17 块，其余是外设与总线 |
| `u_ddr3` | 约 5400 | 22 | DDR3 控制器，RAM 全在 PHY |
| `u_hdmi_tx` | 322 | 0 | 彩条 + TMDS 编码 |
| `u_apb_probe` | 54 | 0 | APB 探针寄存器 |

时序（约束在 `fpga/gfx2d_ti60/sdc/gfx2d_ti60.sdc`）：

| 时钟 | 约束 | setup slack | hold slack |
| --- | --: | --: | --: |
| `core_clk` 100MHz | 10.000 ns | 3.516 | 0.026 |
| `sdram_clk` 400MHz | 2.500 ns | 0.506 | 0.052 |
| `rx_cal_clk` | 2.500 ns | 0.489 | 0.032 |
| `tx_cal_clk` | 2.500 ns | 0.322 | 0.099 |
| `tx_cal_clk_90edge` | 2.500 ns | 0.458 | 0.072 |
| `hdmi_tx_slow_clk` 25.2MHz | 39.683 ns | 36.212 | 0.094 |
| `jtag_inst1_TCK` | 100.000 ns | 94.870 | 0.097 |

- 没有负 slack。`core_clk` 还能提到 150MHz 以上。
- **hold 余量只有几十皮秒**，`core_clk` 是 0.026 ns。官方原始工程也是这个数，属于这个设计的常态，但意味着以后每加一个模块都要看 hold，不能只看 setup。

告警：约束告警 0 条（重构前 174 条），位宽截断告警 2 条且都在厂商加密文件 `phy_ctl.v` 里，我们自己的代码 0 条。

## 3. 资源浪费的卸载

| 项 | 省下 | 状态 | 做法 |
| --- | --- | --- | --- |
| 自动插入的逻辑分析仪 `la0` | 944 XLR + 1 块 RAM | **已做** | 工程 xml 的 `auto_instantiation` 改 `off` |
| 外部 AXI 主机口 `io_ddrMasters_0` 的位宽转换与仲裁 | 约 600 XLR + 5 块 RAM | **已做** | 顶层不给这个口接时钟，逻辑被优化掉。彻底删掉要重新生成 IP |
| 死文件：`memory_test`、`rtl/common`、5 个 debug 残留 | 不占资源 | **已做** | 已删除，见 git 历史 |
| I2C0 | 约 350 XLR | 未做 | SoC IP 里关掉，要重新生成 |
| `axiA` 16MB 从口窗口 | 约 20 XLR + 一部分地址解码 | 未做 | 同上。控制寄存器走 APB 就够 |
| DDR 跨时钟 FIFO | **17 块 RAM** | 未做 | 只有 Lite 版 SoC 能选统一时钟，要先做实验 E1 比较性能 |

已经省下的相对官方基线约 1.5K XLR 和 6 块 RAM。剩下能省的里面，唯一值得花力气的是那 17 块 RAM，占全片 6.6%。

**稀缺的是片上 RAM，不是逻辑**：全片只有 2.56 Mbit（256 块）。现在用了 65 块，设计文档 2.3 节给引擎的预算是 108 块，合计 173 块（67.6%），能放得下。

## 5. 未决问题

这些会影响架构参数或正确性，做引擎之前要有结论（编号与设计文档第 7 节一致）：

| 编号 | 问题 | 为什么重要 |
| --- | --- | --- |
| E2 | CPU 地址与 DDR3 物理地址是否恒等；SoC 发出的 AXI ID 会不会超过 4 位 | 顶层把 32 位地址截成 28 位、8 位 ID 截成 4 位。地址超 256MB 会回绕，ID 超 15 会让响应对不上 |
| E4 | 控制器能接受的最大突发长度、每次事务的固定开销 | 设计文档 3.1 节的全部估算都建立在这上面 |
| E3 | 数据缓存与引擎写 DDR 的一致性 | 决定共享区是否必须单向使用 |
| E1 | Standard 与 Lite 版 SoC 的性能与 RAM 差距 | 决定能不能省那 17 块 RAM |
| E5 | 满负载时扫描输出 FIFO 会不会欠载 | 决定 `Axi_Mux` 的仲裁模式与 FIFO 深度 |
| E6 | 单线与双线 SPI 的装载速度 | 决定素材包大小上限 |

另外两条要一直盯着：hold 余量只有 0.026 ns；DDR3 控制器、SoC 都是加密 RTL，整机没法仿真，所以每一层都要有自己的判据。

## 6. 建议的下一步

1. 先做 E2 和 E4。这两个实验只需要现有比特流加一个小程序，但决定帧缓冲布局与搬运层参数。
2. 再做 M1 显示：扫描输出从 DDR3 取像素、双缓冲、场同步中断，软件先用 CPU 画方块验证通路。
3. 然后才是引擎本体（M2 直通 BitBlt）。

里程碑的完整定义在 `赛题二总体设计.md` 第 8 节。
