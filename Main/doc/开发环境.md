# 开发环境与操作

本文件是这个仓库里唯一记录与具体机器相关的内容的地方：要装哪些工具、从哪里获取、
每一步操作的命令是什么。其余文档一律不写绝对路径，需要时引用本文件的占位符。

第 0 节是标准工作流程，说明一次改动从写 RTL 到上板验收按什么顺序走、每一步看什么判据；
第 1 节起是各步骤的工具与命令细节，第 0 节按节号引用它们。

## 0 标准工作流程

命令默认在 `Main/` 下执行。

```
  0.1 开工前      Todo 条目先写判据，再写代码
       |
  0.2 写 RTL      rtl/ 下改代码，同步工程源文件列表、peri.xml、sdc、地址表
       |
  0.3 仿真        sim/<模块>/run.sh：正常用例 PASS，注错用例 FAIL；全部仿真回归
       |              不符合预期 -> 回到 0.2
  0.4 编译比特流  efx_run.bat，依次看：四步 PASS、时序、资源、告警、接口
       |              负 slack、新增告警、接口对不上 -> 回到 0.2
  0.5 编译软件    sw/apps/<类>/<程序>/ 下 make，登记期望输出
       |
  0.6 上板        加载 .bit -> 打开串口 -> OpenOCD 加载程序 -> 新判据 + 回归表
       |              不一致 -> 先排除加载步骤，再回到 0.2 或 0.5
  0.7 收尾        路径还原与检查、文档与 Todo 状态、提交
```

0.8 节给出「改了什么、要重跑哪几步」的对照表，不是每次改动都要走完全程。

### 0.1 开工前

- 在 `../../Engineering/Todo/` 建条目，结构见该目录 README。**判据在写代码之前写好**：
  仿真怎样算过、上板看哪一行输出、对照组是什么。
- 会进网表的改动攒成一批、一次编译。每次编译都会重新布局，
  余量本来就薄的 hold 可能被挤成负数（当前最薄的是 `core_clk` 与 `rx_cal_clk`，都是 0.026 ns）。
- 需要重新生成 SoC IP 的改动（GPIO 位数、中断、缓存、外设开关、程序区大小）单独成批、单独提交。
  生成前先提交或备份，生成用 `tools/soc/ipm_gen_soc.py`，生成后按 `sdk/README.md` 的步骤同步软件包、逐条恢复登记项。

### 0.2 写 RTL

| 要做的事 | 位置 | 漏掉的后果 |
| --- | --- | --- |
| 自写代码放 `rtl/top/`、`rtl/bus/` 或新建子目录；`rtl/vendor/` 与 `rtl/hdmi/` 里的官方文件不改 | 在 `rtl/README.md` 登记文件、来源、是否进工程 | 厂商文件被改后无法与原件核对 |
| 文件开头写 `` `default_nettype none ``，结尾恢复 `` `default_nettype wire `` | 每个自写 `.v` | 未声明的信号被当成 1 位线，总线被静默截断（platform 第 01 章 4.4 节）；不恢复会影响后面编译的厂商文件，工程是单编译单元 |
| 新文件加进工程源文件列表 | `fpga/gfx2d_ti60/gfx2d_ti60.xml` 的 `<efx:design_file>` | 仿真能过，综合时缺模块 |
| 改顶层端口 | 同步 `fpga/gfx2d_ti60/gfx2d_ti60.peri.xml` | **不报错**，只在布局报告的 Missing Interface Pins 里多出一行 |
| 改 PLL 参数 | 同步 `fpga/gfx2d_ti60/sdc/gfx2d_ti60.sdc` | 时序按旧周期分析，slack 不可信 |
| 占用新的 APB 地址段、DDR 区域或中断号 | `README.md` 的地址映射表；DDR 分区见 `赛题二总体设计.md` 2.1 节 | 两个模块译码到同一段地址 |
| 新增 `.vh` | 源文件里按相对路径 `` `include ``，仿真脚本的 iverilog 加 `-I` | 综合能过而仿真找不到文件，或反过来 |

### 0.3 仿真

- 每个自写模块一个 `sim/<模块>/` 目录，`run.sh` 照 `sim/apb_probe/run.sh` 的结构写：
  测试台结束时打印一行 `RESULT: PASS` 或 `RESULT: FAIL`，脚本逐个用例比对期望，
  全部符合才打印 `SIM OK`，否则退出码非零。
- **至少一个注错用例**：用宏（`-DINJECT_xxx`）把一处改错，期望 FAIL。
  注错要对准这个模块最可能出错的地方，例如位宽、边界、超时，而不是一个必然崩溃的错误。
  注错用例 PASS 说明判据没有检查到这一项，判据要先修好。
- 访问 AXI 的模块用 `sim/axi_probe/axi_ram_model.v` 作从机，保持随机反压（参数 `STALL`）打开；
  用到 `Axi_Mux` 的要带厂商原语模型，见第 10 节。
- 先跑新用例，再按第 10 节把所有仿真跑一遍。新增的仿真目录要补进第 10 节的命令、`sim/README.md` 的表
  和 `README.md`「约定」里的提交前判据。
- DDR3 控制器与 SoC 的 CPU 运算模块是加密的，整机仿不了。
  凡是依赖它们的行为（控制器的实际反压、CPU 缓存、启动流程），判据放到 0.6 节上板去做。

### 0.4 编译比特流

命令见第 5 节，约一分半。跑完按下表顺序检查，任何一项不过都回到 0.2：

| 顺序 | 检查项 | 看哪里 | 判据 |
| --- | --- | --- | --- |
| 1 | 四步跑完 | 命令行输出；`fpga/gfx2d_ti60/outflow/gfx2d_ti60.bit` 的修改时间 | map、interface、pnr、pgm 全部 PASS，`.bit` 是这次生成的 |
| 2 | 时序 | `outflow/gfx2d_ti60.timing.rpt` 第 2 节 Clock Relationship Summary | Setup 与 Hold 两张表每个时钟的 slack 都为正；hold 与上一版逐行对比并记录 |
| 3 | 资源 | `outflow/gfx2d_ti60.place.rpt` 的 `XLRs`、`Memory Blocks`、`DSP Blocks` 三行；按模块拆分看 `gfx2d_ti60.hier_util.rpt` | 与 `README.md`「现在的状态」登记的上一版对比，增量能用本次改动解释清楚 |
| 4 | 约束 | `outflow/gfx2d_ti60.log` | 出现 `SDC file 'sdc/gfx2d_ti60.sdc' parsed successfully`，且没有指向约束的 WARNING |
| 5 | 告警 | `outflow/gfx2d_ti60.warn.log` | 见下 |
| 6 | 接口 | `outflow/gfx2d_ti60.place.rpt` 开头的 Missing Interface Pins | 只允许现有 6 项：`jtag_inst1_DRCK`、`jtag_inst1_TMS`、`jtag_inst1_RESET`、`jtag_inst1_RUNTEST`、`jtag_inst1_UPDATE`、`hdmi_pll_fb`。多出的就是顶层端口与 `peri.xml` 没对上 |

告警的看法：

- `warn.log` 是**追加写入**的，只看最后一个 `Efinity Synthesis Started` 之后的部分。
- 自写代码（`rtl/top/`、`rtl/bus/` 与今后新增的目录）的位宽截断告警（含 `truncated`）必须为 0。
- 其余新增告警逐条看过，确认无害的写进对应 TechReports 章节。
  已知无害的有：`rtl/vendor/` 里的截断（`phy_ctl.v`、`Axi_Mux.v` 第 2277 行），
  顶层 `jtag_inst1_*` 未连接，SoC 网表里 `urandom` 系统函数不支持、
  指令缓存 `lineLoader_address` 悬空（2026-09-19 起 `io_ddrMasters_0` 已从 IP 里关掉，那条告警不再出现）。

`gfx2d_ti60.log` 在布局之后会打出若干 `may not meet ... the hold (min) timing requirement` 的负 slack，
那是布线之前的估计，布线阶段会做 hold 修复，时序一律以 `timing.rpt` 为准。

### 0.5 编译软件

程序分两类，构建方式不同：

- **走项目分层的程序**（`sw/apps/game/gfx2dGame/` 与以后的应用）：照 `sw/apps/game/gfx2dGame/` 建目录，
  源码放 `src/`，makefile 只写 `APP`、`APP_SRCS`、`LIBS` 三行再 `include ../mk/$(PLATFORM).mk`。
  平台由 `PLATFORM` 选，默认 `target`（板上），`PLATFORM=host` 是 PC 版。
  纯算法进 `sw/lib/`，平台相关的进 `sw/bsp/`，应用只写应用——分层由各层的头文件路径保证。
  命令与产物的完整说明见 `sw/README.md`。
- **七个诊断程序**（`sw/apps/test/` 下的 `bootSizeTest/`、`cacheCoherencyTest/`、`keyTest/`，`sw/apps/probe/` 下的 `ddrAliasTest/`、`ddrBurstProbe/`、
  `cacheMechTest/`、`cacheMinTest/`）：仍沿用官方 makefile 体系，复制 `makefile` 改 `PROJ_NAME` 即可，`STANDALONE` 往上四级。应用按用途放 `apps/game/`、`apps/test/`、`apps/probe/`，分类见 `sw/README.md`。
- 外设与 APB 基址用 `sdk/bsp/efinix/EfxSapphireSoc/include/soc.h` 里的宏（如 `IO_APB_SLAVE_0_INPUT`），
  自定义寄存器的偏移写在程序里，并与 RTL 文件头的寄存器表一致。
- 编译命令见第 7 节，产物是 `build/<程序>.bin`。
- 判据写成串口上能逐行比对的输出：每项一行 `ok` 或 `fail`，最后打印失败计数与 `done`，
  不依赖肉眼判断数值是否合理。
- 在 `sw/README.md` 登记期望输出、bin 大小和编译用的工具链版本。
- 改了 bootloader 或链接脚本，按第 9 节的五步同步。**项目自己的链接脚本是 `sw/bsp/ti60/linker/gfx2d.ld`**，
  它不在 sdk 里，改它不需要重新生成片上 RAM 初始文件。

### 0.6 上板

顺序固定：

1. `ftdi_pgm.bat --scan_usb` 读到器件 ID `0x10660A79`（第 4 节）。拔插后串口号可能变化，一并确认。
2. JTAG 加载 `.bit`（第 6 节）。掉电丢失，不改 Flash。板子每次上电都要做这一步：Flash 里是出厂比特流，
   没有本工程的 SoC，跳过这一步时 OpenOCD 能认到 TAP，`reset halt` 却报 `timed out while waiting for target halted`。
3. 打开串口 `<COM>`，115200 8N1。**先开串口再加载程序**：串口没打开期间板子发出的数据会被直接丢弃，
   驱动不缓存，之后再打开也读不回来。2026-09-17 实测，用不清缓冲的 Win32 原生打开方式和 .NET `SerialPort` 两种方式：
   程序在串口关闭时跑完，之后打开读到 0 字节；在输出过程中打开，只收到打开之后的部分，第一行从半行开始。
4. 在 `Main\sdk\bsp` 下启动 OpenOCD，`reset halt`、`load_image`、`resume 0x1000`（第 6 节）。
   **推荐用 `tools/board/board_run.py`**，它把第 2~4 步合成一条命令，保证先开串口、加载前复位，
   并且只在每一步都有正面证据时退出码才为 0。用法见 `tools/board/README.md`；
   它要用 Efinity 自带的 Python 跑，并设 `PYTHONHOME=<EFINITY>\python311`。
5. 先做一次**调试通路连通性检查**：连续开两次 OpenOCD 会话，各读一次 PC，两次都要
   `Target successfully examined`。再往下走回归表。
6. 先收新判据的输出，再跑下面的回归表。

第 5 步是 2026-09-17 加的。E1 的构型对比里遇到过一种故障：比特流能烧、JTAG TAP 能认、
`load_image` 能下，**只有读 CPU 寄存器会失败或挂住**，而回归表是按功能列的，
一条都拦不住它，白跑了半天才发现。两次读 PC 很便宜，能在第一时间把这种情况挑出来。
`tools/board/board_run.py --check-only` 就是这一项；回归表里不加载程序的两项（APB 探针、按键读数）用它的 `--cmd`。

回归表（以当前比特流为准，新增功能验收后把它的判据补进来）：

| 项 | 怎么跑 | 期望 |
| --- | --- | --- |
| 调试通路 | 连续两次 OpenOCD 会话各读一次 PC | 两次都 `Target successfully examined` |
| memTest | `sdk/software/standalone/application/memTest`，编译与加载同上 | 串口打印 `Test PASSED` |
| APB 探针 | 不加载程序，OpenOCD 直接读写，命令见第 6 节 | ID `0x47465832`、VERSION 1、SCRATCH 写入的图案读回一致、`0xF810_8008` 读回 0 |
| `sw/apps/probe/ddrAliasTest` | 编译加载 | 与 `sw/README.md` 登记的输出一致，`fail 0` |
| `sw/apps/probe/ddrBurstProbe` | 编译加载，`resume` 后数秒内输出完毕 | `fail 0` 与 `done`，各行 `ok`；IDENT 三行（探针 / guard，要求 VERSION 2 / 扫描替身）、SHARE 三行、TRI 读写各五行、INJECT 五行，期望值见 `sw/README.md` |
| `sw/apps/test/cacheCoherencyTest` | 编译加载，正常版、`INJECT=1` 注错版、`INJECT=2` 注错自检版各一次 | 正常版 `fail 0`；注错版 `fail 0` 且 A3 两行加 B、C 共四行 `FAIL (inject)`；注错自检版 `fail 4` 且同四行 `NOT_RED (inject)` |
| `sw/apps/probe/cacheMechTest` | 编译加载 | `fail 0` 与 `done`，T1~T10 每组 `ok`，各组数值与 `sw/README.md` 登记的一致 |
| `sw/apps/probe/cacheMinTest` | 仅作现象可复现，改了缓存相关的 SoC 配置时跑 | `fail 0` 与 `done`；`S3 CACHE_NOEVICT` 一行按设计报 FAIL，不作结论 |
| HDMI | 接显示器 | 八色竖条 |
| 按键 | 不加载程序时 OpenOCD `mdw 0xf8016000` 读 GPIO1；动过 GPIO1、按键管脚或 `peri.xml` 时再跑 `sw/apps/test/keyTest`，30 秒内把 KEY0~3 逐个按一下 | 空闲读数 `0x0000000f`；`keyTest` 的 `fail 0` 与 `done`，四个键各有一次 down 与 up |
| `sw/apps/test/bootSizeTest` | 仅在改 bootloader、链接脚本或 Flash 布局时跑，写 Flash `0x380000` 后复位（第 8、9 节） | 两个 CRC 与 `sw/README.md` 一致；官方 124KB 比特流作对照组必须不一致。**对照组先跑**：DDR 里残留上一次 512KB 启动拷进去的完整镜像时，对照组会假通过；已经先跑了实验组的，先用 OpenOCD 把 `0x20000` 起的数据块尾段清零（`mww 0x00020000 0 0xC000`）再跑对照组 |

- 结果与预期不一致时，先排除加载步骤：加载前没有 `reset halt`、
  加载的是旧的 `.bit` 或 `.bin`（比对修改时间或 SHA256）、串口号不对。再查第 12 节故障对照，最后才回去改代码。
- 串口原始输出保存下来，贴进 TechReports 对应章节，不要只写「通过」。
- 只有需要掉电保留时才写 Flash（第 8 节），写之前先整片备份。

### 0.7 收尾与提交

1. 路径还原并检查，见第 3 节：`--restore` 之后 `--check` 必须通过。
2. 核对 `README.md`「约定」里的提交前判据：全部仿真符合预期、编译四步 PASS 且无负 slack、`--check` 通过。
3. 文档分工：当前状态写进 `README.md` 与各目录 README；
   过程、数据、踩坑和原因写进 `../../Engineering/TechReports/`；
   Todo 条目改成「待验收」，用户验收之后才删除。
4. 编译与仿真产物（`outflow/`、`work_*/`、`build/`）不入库。

### 0.8 改了什么，要重跑什么

| 改动 | 仿真 | 编译比特流 | 编译软件 | 上板 |
| --- | --- | --- | --- | --- |
| 自写 RTL 模块内部 | 该模块，再全部回归 | 要 | 不要 | 新判据与回归表 |
| 顶层端口或 PLL | 受影响的模块 | 要，重点看时序与接口两项 | 不要 | 回归表全部 |
| 只改 `sw/` 下的程序 | 不要 | 不要 | 该程序 | 该程序 |
| bootloader 或链接脚本 | 不要 | 要，bootloader 在比特流里 | 全部重编 | 第 9 节两条判据与回归表 |
| 重新生成 SoC IP | 全部 | 要 | 全部重编，期望值重新计算 | 回归表全部，含 `bootSizeTest` |
| 只改文档 | 不要 | 不要 | 不要 | 不要，只跑 `--check` |

| WSL（Ubuntu） | 任意 | Windows 功能 | 跑仿真与软件编译 |
| iverilog、python3 | 任意 | WSL 的包管理器 | 仿真、bin 转 hex |
| xPack riscv-none-elf-gcc | 13.4.0-1，Linux x64 版装进 WSL | https://github.com/xpack-dev-tools/riscv-none-elf-gcc-xpack/releases | 编译 `sdk/` 与 `sw/` 下的程序。与 IDE 2026.1 自带的是同一版本，IDE 里那份是 Windows 版，WSL 用不了 |
| PC 侧依赖 | 见下 | WSL 的包管理器 | `sw` 的 PC 目标（SW1 起）：显示、键盘与 32 位主机测试 |

PC 目标（`make PLATFORM=host`）另外要三样，都在 WSL 里装：

```
wsl -u root -e apt-get install -y libsdl2-dev gcc-multilib
```

- `libsdl2-dev`：`bsp/host` 的窗口与键盘，`mk/host.mk` 用 `sdl2-config` 取编译与链接参数。
  2026-09-21 起本机是 2.32.10，`SDL_GetPerformanceFrequency` 给 1e9（SW4 的 4.1 节）。
- `gcc-multilib`：`lib/test/` 要另编一份 `-m32`（板上是 ILP32，PC 是 LP64，
  两边输出必须逐字节相同），没装时 `gcc -m32` 报找不到 `crti.o`。
- **窗口能不能开**取决于 WSLg：`echo $DISPLAY` 应给 `:0`、`echo $WAYLAND_DISPLAY` 应给一个 socket 名。
  两个都为空时 SDL 会退到 `offscreen` 驱动继续跑（实测，不是报错退出），
  拿不到窗口就按无窗跑：`SDL_VIDEODRIVER=dummy <程序>`。
  **有窗与无窗是同一个二进制**，只换驱动，判据要求两条 CRC 序列逐行相同（SW4 的 2.5 节）。
- `sudo` 要交互输入密码，在非交互的调用里会卡住，用 `wsl -u root -e` 绕过。

两条版本上的约束：

- `sdk/` 是 efx_soc 3.4.0（Efinity 2026.1）生成的（2026-09-19），它的 makefile 用 `riscv-none-elf-` 前缀，
  `-march` 带 `_zicsr_zifencei`，要 gcc 12 以上。此前的 3.3.0 软件包用 `riscv-none-embed-` 前缀，
  只能用 8.3.0 编；8.3.0 编不了现在这套，13.4 也编不了旧的那套，两者跟着 `sdk/` 的版本走。
  WSL 里旧的 8.3.0（`~/opt/xpack-riscv-none-embed-gcc-8.3.0-2.3`）可以留着，现行流程不再用它。
- Ubuntu 仓库里的 `riscv64-unknown-elf-gcc` 缺 C 库头文件，编不了这套程序。

## 4 下载器与端口

板上是一颗 FT4232H，VID `0403`、PID `6011`，四个通道的用途取自开发板原理图：

| 通道 | 板上用途 | 驱动 |
| --- | --- | --- |
| ch0 | 八个脚全部悬空 | 不用动 |
| ch1 | JTAG：TCK、TDI、TDO、TMS | **换成 libusbK** |
| ch2 | UART：与 SoC 的 UART0 相连，115200 8N1 | 保持 FTDI 虚拟串口驱动 |
| ch3 | 未连接 | 不用动 |

只给 ch1 换驱动，用 zadig 选 Interface 1，类型选 libusbK。换完之后：

```
<EFINITY>\pgm\bin\ftdi_pgm.bat --scan_usb
```

应当读到器件 ID `0x10660A79`、IR 长度 5，`--list_usb` 在通道 1 给出 `<JTAG>`。
换驱动之前这两条命令都报 `No USB target detected`。

三点容易踩：

- 板上没有独立的 SPI 下载通道，写 Flash 只能走 JTAG Bridge，见第 8 节。
- 官方设计说明里 OpenOCD 配置写的是 `ftdi channel 0`，与原理图矛盾，
  以 `sdk/bsp/efinix/EfxSapphireSoc/openocd/ftdi_ti.cfg` 里的 `channel 1` 为准。
- 板卡资料包里的 `XL_YLS_DL_*` 驱动是给外接下载器用的，inf 里写的是 FT2232 的 PID `6010`，
  与板载的 `6011` 不符，装了不起作用。其中的 zadig 可以用。
- 板子拔插之后串口号可能变化，操作前先用 `--scan_usb` 与设备管理器确认。

## 6 加载与调试

加载比特流（掉电丢失，不改 Flash）：

```
<EFINITY>\pgm\bin\ftdi_pgm.bat -m jtag -u <JTAG> fpga\gfx2d_ti60\outflow\gfx2d_ti60.bit
```

这个模式要的是 `.bit`，不是 `.hex`。6MHz 下约 3 秒。

OpenOCD 在 `<IDE>\openocd\bin\openocd.exe`。

**`cpu0.yaml` 的查找范围。** `sdk/.../openocd/debug.cfg` 与 `debug_ti.cfg` 都设
`max_levels 3`，也就是从当前目录往上**最多查 3 级**（`../`、`../../`、`../../../`，
加上当前目录一共 4 个位置）。而 `cpu0.yaml` 在 `Main/sdk/` 下，
官方示例 `sdk/software/standalone/<程序>/` 往上三级正好是 `sdk/`；
本项目的 `sw/apps/<类>/<程序>/` 要往上 4 级到 `Main/` 再进 `sdk/`，`cpu0.yaml` 不在它的上级链路上，往上查多少级都找不到，
所以会报 `cpu.yaml not found within 3 levels` 并初始化失败。

两条可用路径：

- **在 `Main\sdk\bsp` 下启动**（往上 2 级就是 `sdk/`），跑官方示例足够；
- 换用 [`../tools/board/gfx2d_debug.cfg`](../tools/board/gfx2d_debug.cfg) 的思路，
  走两份 cfg 里的 `LEGACY_IDE` 分支，由环境变量 `workspace_loc` 直接给出目录。
  注意 `ftdi_ti.cfg` 第 1 行会 `set LEGACY_IDE 0`，覆盖环境变量，
  所以要在加载它之前设回 1。

**`irlen` 两处不一致。** `debug.cfg` 写的是 `jtag newtap ... -irlen 4`，
`debug_ti.cfg` 写的是 `5`。这块板的 IR 宽度是 5（`ftdi_pgm.bat --scan_usb` 报
`ir_width 5`），用 `debug.cfg` 会报
`IR capture error at bit 4, saw 0x25 not 0x..3`，连不上 CPU。**本板用 `debug_ti.cfg`。**

这两条 2026-09-17 在 E1 的上板过程中实测确认，过程见技术报告 platform 第 04 章 4.3 节。
需要现成可用的配置与一条命令走完的上板流程，用
`tools/board/board_run.py`（它自带一份改好的 cfg）。

加载并运行一个程序：

```
cd <REPO>\Main\sdk\bsp
openocd.exe -f efinix\EfxSapphireSoc\openocd\ftdi_ti.cfg ^
            -f efinix\EfxSapphireSoc\openocd\debug_ti.cfg ^
  -c "reset halt" -c "load_image <REPO>/Main/sw/apps/test/bootSizeTest/build/bootSizeTest.bin 0x1000 bin" ^
  -c "resume 0x1000" -c "shutdown"
```

`load_image` 的路径用正斜杠，OpenOCD 的 Tcl 解析会把反斜杠当转义符。
不要在 OpenOCD 里用 `sleep` 等程序跑完：它会占住 OpenOCD 的解释器，
进程不退、脚本挂住；要看输出就照 0.6 节的顺序先开串口再 `resume`。

不写程序也可以直接读写外设寄存器，例如验证 APB 通路：

```
  -c "reset halt"
  -c "mdw 0xf8100000 3"
  -c "mww 0xf8100008 0xa5a55a5a" -c "mdw 0xf8100008"
  -c "mdw 0xf8108008"
```

调试通路上有三条限制：

- **加载程序前必须 `reset halt`。** 不复位直接 `resume` 时 PC 会停在 `0x8`，串口无输出，
  而读回的内存与文件一致。原因见技术报告 platform 系列第 01 章 4.3 节。
- `verify_image` 不可用，目标端没有实现 `checksum_memory`，且失败后 OpenOCD 会直接退出，
  后面的命令都不执行。改用 `dump_image <文件> <地址> <长度>` 读回主机比对哈希。
- `step` 在未复位时会让 PC 跑飞并报 `Target not halted`，需要单步时改用 GDB。

```

wsl -e bash -c 'RISCV_BIN=<RISCV_BIN> bash Main/tools/check/check_sw_layers.sh'
```


**六个诊断程序**（`bootSizeTest`、`ddrAliasTest`、`ddrBurstProbe`、`cache*Test`）
与官方示例仍用同一套官方 makefile：

```
wsl -e bash -c 'cd sw/apps/test/bootSizeTest && make BSP=efinix/EfxSapphireSoc RISCV_BIN=<RISCV_BIN> OBJDIR=build'
```

- `wsl.exe` 会把当前的 Windows 目录映射进去，所以在仓库里任意位置调用都不必写 `/mnt/` 路径。
- 必须写 `wsl -e`。不带 `-e` 时命令会先经过一层默认 shell 再解析一遍，

  `unrecognized argument in option '-mabi=ilp32'`。
- `OBJDIR` 默认是程序目录下的 `build/`，已在 `.gitignore` 里。
  不要指到 WSL 的 `/tmp`，那里的产物可能在两次调用之间消失。

## 8 读写 Flash

板上 Flash 是 Winbond W25Q64，8MiB，4KB 扇区，JEDEC ID `0xEF6017`。
分区规划见 `赛题二总体设计.md` 2.2 节：`0x000000` 起是比特流，`0x380000` 起是程序。

写之前先把整片读出来备份。JTAG Bridge 分两步，先把 FPGA 配置成一个 Flash 烧写器，
再通过它读写：

```
set U=<JTAG>
set PGM=<EFINITY>\pgm\bin\ftdi_pgm.bat

%PGM% -m jtag -u %U% <EFINITY>\pgm\fli\titanium\u10660A79.bit

%PGM% -m jtag_bridge --jtag_bridge_mode read --address 0x0 --num_bytes 0x800000 ^
      -o <备份.hex> -u %U% <一个不存在的文件.hex>

%PGM% -m jtag_bridge --jtag_bridge_mode all --verify_method hostx1 --address 0x380000 ^
      -u %U% <程序.hex>
```

- `u10660A79.bit` 按器件的 JTAG ID 命名，是 Efinity 自带的桥接镜像。
- `--jtag_bridge_mode` 的默认值是 `all`，即擦除加写入。**读 Flash 时必须显式写 `read`**。
- 即使是读，也必须给一个输入文件，且扩展名必须是 `.hex`。
  给一个不存在的路径，万一模式写错也只会因为打不开文件而失败，不会写入。
- 写入地址必须落在扇区边界上，擦除长度按扇区向上取整，只擦写入的那一段。
- 这个模式只接受每字节一行的 hex 文本，不接受裸 bin，转换用 `tools/board/bin2hex.py`。
- 读出的文件与 Programmer 的 hex 格式相同，可以原样写回，用于恢复。
- 用时参考：整片读取 31 到 33 秒；写 294KiB 时擦除 2 秒、写入 1 秒、读回校验 1 秒。

## 9 改 bootloader 之后要同步什么

bootloader 以初始内容的形式烧在比特流里，源码在 `sdk/software/standalone/bootloader/`。
改了它的源码或 `bootloaderConfig.h`（例如拷贝长度 `USER_SOFTWARE_SIZE`）之后，
下面五步缺一不可，只改源码不会有任何效果。

1. 重新编译 bootloader，用第 7 节的命令，`BSP` 与工具链前缀相同。
2. 把新的 bin 转成片上 RAM 的初始内容。`binGen.py` 要求环境变量 `EFINITY_HOME`，
   产物落在当前目录的 `rom/` 下：

   ```
   wsl -e bash -c 'cd sdk/tool && EFINITY_HOME=<EFINITY> python3 binGen.py \
     -b bootloader/bootloader_512K.bin -c EfxSapphireSoc -s 4096 -f 0'
   ```

3. 用产物替换 SoC IP 里的 8 个初始文件，
   `fpga/gfx2d_ti60/ip/soc/` 与 `fpga/gfx2d_ti60/ip/soc/source/hardware/netlist/` 下各 4 个，
   文件名形如 `EfxSapphireSoc.v_toplevel_system_ramA_logic_ram_symbol<N>.bin`。
4. 更新 `sdk/tool/bootloader/` 下的 bin 与 hex，它们是上板校验时的比对基准。
5. 程序区长度跟着改时，同步 `sdk/bsp/efinix/EfxSapphireSoc/linker/` 下的
   `default.ld` 与 `freertos.ld`，以及 SoC IP 配置里的 `LDSize`。

判据两条，都要做：

- 重新编译比特流并加载，`reset halt` 之后用 `dump_image` 读回片上 RAM `0xF9000000` 起
  bootloader 的长度，SHA256 与 `sdk/tool/bootloader/` 下的 bin 一致，
  说明新 bootloader 确实进了比特流；
- 跑 `sw/apps/test/bootSizeTest`，两个 CRC 与主机侧算出的期望值一致，
  并用官方 124KB 比特流作对照组，对照组必须不一致。
  没有对照组时无法区分「新长度生效」与「程序恰好短到旧长度也够」。

## 10 跑仿真

```
wsl -e bash -c 'bash sim/hdmi/run.sh'
wsl -e bash -c 'bash sim/apb_probe/run.sh'
wsl -e bash -c 'EFINITY_HOME=/mnt/<EFINITY 的盘符与路径> bash sim/axi_probe/run.sh'
wsl -e bash -c 'EFINITY_HOME=/mnt/<EFINITY 的盘符与路径> bash sim/axi_mux_guard/run.sh'
```

每个脚本都包含注错用例，全部用例都符合预期才输出 `SIM OK`。前两个不依赖 Efinity；
`axi_probe` 与 `axi_mux_guard` 的 `Axi_Mux` 例化了厂商原语 `EFX_SRL8`，要从
`<EFINITY>/sim_models/verilog/efx_srl8.v` 取仿真模型，
所以要用 `EFINITY_HOME` 指向 Efinity 安装目录在 WSL 里的路径（`C:\` 在 WSL 里是 `/mnt/c/`）。
这个原语的输出取反、地址反向，不能用自己写的移位寄存器代替，原因见 platform 第 03 章 3.2 节研究 5。
`axi_mux_guard` 的全链路用例用 `RD_QUEUE=4`、`ADDR_STALL_MAX=4`，写方向另有 `WR_QUEUE=4` 一组（见 `sim/axi_mux_guard/run.sh`），
它测的是 E5 2.2 节的保护口径，末行 `SIM OK: 17/17 checks as expected`。
判据表与实测值写在 `Engineering/Todo/hw/E5-Axi_Mux优先级与扫描FIFO水位.md`，过程与解释在 platform 第 06 章。
从机 `axi_ram_model.v` 的协议报警 `MODEL: wlast mismatch` 会计入 `wlast_err`，全链路用例要求它为 0。

## 12 故障对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `No USB target detected` | ch1 上还是 FTDI 虚拟串口驱动，或者换成了别的通道 | 用 zadig 给 Interface 1 装 libusbK，见第 4 节 |
| 编译在 map 之后报 `No such file: ...work_dbg\debug_top.v` | 工程开了调试核自动插入 | `auto_instantiation` 改 `off`，见第 5 节 |
| 程序不运行，PC 停在 `0x8`，串口无输出 | 加载前没有复位 | 一律先 `reset halt`，见第 6 节 |
| `Target ... doesn't support checksum_memory` | 目标端没有实现校验和 | 改用 `dump_image` 比哈希 |
| make 报 `unrecognized argument in option '-mabi=ilp32'` | 调 WSL 时漏了 `-e`，变量被外层 shell 吃掉 | 见第 7 节 |
| 串口一直没有输出 | 板上 Flash 里可能是出厂的演示比特流，其中没有 SoC | 先 JTAG 加载本工程的比特流再看 |
| OpenOCD 报 `Target successfully examined` 之后 `reset halt` 报 `timed out while waiting for target halted` | 同上，板子上电后还没加载本工程的比特流 | JTAG 加载 `.bit` 之后重试，见 0.6 节第 2 步 |
| `cpu.yaml not found within 3 levels`，`target ... init failed` | OpenOCD 的启动目录往上找不到 `Main/sdk/cpu0.yaml` | 在 `Main\sdk\bsp` 下启动，见第 6 节 |
| `sdl2-config: command not found` 或 `mk/host.mk` 报 `sdl2-config 不可用` | WSL 里没装 SDL2 开发包 | `wsl -u root -e apt-get install -y libsdl2-dev`，见第 2 节 |
| `gcc -m32` 报找不到 `crti.o` | 没装 multilib，`lib/test/` 的 32 位那一份编不了 | `wsl -u root -e apt-get install -y gcc-multilib`，见第 2 节 |
| PC 版起不来，`SDL_Init` 失败 | WSLg 没起来，`$DISPLAY` 与 `$WAYLAND_DISPLAY` 都是空的 | `wsl --update` 之后重开终端，检查方法见第 2 节 |
| 板子上 `make INJECT=...` 之后产物与正常版逐位一样 | 同一个 `OBJDIR` 里只重链没重编 | 已由 `mk/*.mk` 的编译选项标记文件处理；自己指定了 `OBJDIR` 时换一个目录或先 `make clean` |
