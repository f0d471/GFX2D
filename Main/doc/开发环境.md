# 开发环境与操作

本文件是这个仓库里唯一记录与具体机器相关的内容的地方：要装哪些工具、从哪里获取、
每一步操作的命令是什么。其余文档一律不写绝对路径，需要时引用本文件的占位符。

## 1 路径占位符

| 占位符 | 含义 |
| --- | --- |
| `<REPO>` | 本仓库根目录 |
| `<EFINITY>` | Efinity 安装目录 |
| `<IDE>` | Efinity RISC-V 嵌入式 IDE 安装目录 |
| `<RISCV_BIN>` | RISC-V 交叉工具链的前缀，含目录与 `riscv-none-embed-` 这一段 |
| `<JTAG>` | 下载器的 URL，形如 `ftdi://0x0403:0x6011:0:ff/1` |
| `<COM>` | 板上 UART 对应的串口号 |

第 11 节给出一组参考取值。每台机器的取值不同，除第 11 节外不要把实际路径写进任何文档或脚本。

## 2 需要装的工具

| 工具 | 版本要求 | 获取方式 | 用途 |
| --- | --- | --- | --- |
| Efinity | 当前工程用 2026.1 编译。2025.2 及以前打不开本工程 | https://www.elitestek.com/efinity/ 注册后下载，教育邮箱可直接申请 | 综合、布局布线、生成比特流、烧写 |
| Efinity RISC-V 嵌入式 IDE | 与 Efinity 同版本 | 同一下载页 | OpenOCD、GDB、Eclipse 工程 |
| Oracle JRE 8 | 8u3xx | 板卡资料包内附，或 Oracle 官网 | 生成与升级 Sapphire SoC IP |
| libusbK 驱动 | 3.1.0.0 | zadig（板卡资料包内附） | 让 Efinity Programmer 与 OpenOCD 访问板载 JTAG |
| WSL（Ubuntu） | 任意 | Windows 功能 | 跑仿真与软件编译 |
| iverilog、python3 | 任意 | WSL 的包管理器 | 仿真、bin 转 hex |
| xPack riscv-none-embed-gcc | 8.3.0 | https://github.com/xpack-dev-tools/riscv-none-embed-gcc-xpack/releases | 编译 `sdk/` 与 `sw/` 下的程序 |

两条版本上的约束：

- `sdk/` 是 efx_soc 3.3.0（Efinity 2025.2）生成的，它的 makefile 用 `riscv-none-embed-` 前缀。
  IDE 2026.1 自带的是 `riscv-none-elf-gcc` 13.4.0，编这套 BSP 会报缺 `zicsr`，
  所以单独装 8.3.0。升级 SoC IP 并同步新软件包之后可以改用 IDE 自带的工具链。
- Ubuntu 仓库里的 `riscv64-unknown-elf-gcc` 缺 C 库头文件，编不了这套程序。

## 3 克隆之后要做的一件事

有五个文件是厂商工具生成的，里面必须写绝对路径，
仓库里存的是占位符形式，在 `Main/` 下执行一次展开：

```
wsl -e python3 tools/localize_paths.py --apply
```

提交之前还原成占位符，避免把本机路径提交上去：

```
wsl -e python3 tools/localize_paths.py --restore
```

`--check` 扫描整个仓库，发现任何机器专属的绝对路径就以非零退出码结束，可以挂在提交前检查里。
详见 `../tools/README.md`。

## 4 下载器与端口

板上是一颗 FT4232H，VID `0403`、PID `6011`，四个通道的用途取自开发板原理图：

| 通道 | 板上用途 | 驱动 |
| --- | --- | --- |
| ch0 | 八个脚全部悬空 | 不用动 |
| ch1 | JTAG：TCK、TDI、TDO、TMS | **换成 libusbK** |
| ch2 | UART：与 SoC 的 UART0 相连，115200 8N1 | 保持 FTDI 虚拟串口驱动 |
| ch3 | 未连接 | 不用动 |

只给 ch1 换驱动，用 zadig 选 Interface 1，类型选 libusbK。换完之后：

```
<EFINITY>\pgm\bin\ftdi_pgm.bat --scan_usb
```

应当读到器件 ID `0x10660A79`、IR 长度 5，`--list_usb` 在通道 1 给出 `<JTAG>`。
换驱动之前这两条命令都报 `No USB target detected`。

三点容易踩：

- 板上没有独立的 SPI 下载通道，写 Flash 只能走 JTAG Bridge，见第 8 节。
- 官方设计说明里 OpenOCD 配置写的是 `ftdi channel 0`，与原理图矛盾，
  以 `sdk/bsp/efinix/EfxSapphireSoc/openocd/ftdi_ti.cfg` 里的 `channel 1` 为准。
- 板卡资料包里的 `XL_YLS_DL_*` 驱动是给外接下载器用的，inf 里写的是 FT2232 的 PID `6010`，
  与板载的 `6011` 不符，装了不起作用。其中的 zadig 可以用。
- 板子拔插之后串口号可能变化，操作前先用 `--scan_usb` 与设备管理器确认。

## 5 编译硬件

```
call <EFINITY>\bin\setup.bat
cd <REPO>\Main\fpga\gfx2d_ti60
efx_run.bat gfx2d_ti60.xml
```

map、interface、pnr、pgm 四步，不需要许可证，不需要开 GUI。
产物在 `outflow/`：`.bit` 用于 JTAG 加载，`.hex` 用于写 Flash。

工程 xml 里 `<efx:debugger>` 的 `auto_instantiation` 是 `off`。
改成 `on` 会让命令行编译在 map 之后中断，因为自动插入调试核这一步要求
`work_dbg/debug_top.v` 事先存在，而这个文件只有 GUI 的 Debug Wizard 会生成。
需要逻辑分析仪时，先在 GUI 里生成一次再回到命令行。

## 6 加载与调试

加载比特流（掉电丢失，不改 Flash）：

```
<EFINITY>\pgm\bin\ftdi_pgm.bat -m jtag -u <JTAG> fpga\gfx2d_ti60\outflow\gfx2d_ti60.bit
```

这个模式要的是 `.bit`，不是 `.hex`。6MHz 下约 3 秒。

OpenOCD 在 `<IDE>\openocd\bin\openocd.exe`。它的 `debug_ti.cfg` 依次检查当前目录的
`../cpu0.yaml`、`../../cpu0.yaml`、`../../../cpu0.yaml`、`../../../../cpu0.yaml`，
而这个文件在 `Main/sdk/` 下。官方示例 `sdk/software/standalone/<程序>/` 往上三级正好是 `sdk/`，
本项目的 `sw/<程序>/` 往上找不到它，会报 `cpu.yaml not found within 3 levels` 并初始化失败。
所以**统一在 `Main\sdk\bsp` 下启动**（上一级就是 `sdk/`），程序文件写完整路径。
加载并运行一个程序：

```
cd <REPO>\Main\sdk\bsp
openocd.exe -f efinix\EfxSapphireSoc\openocd\ftdi_ti.cfg ^
            -f efinix\EfxSapphireSoc\openocd\debug_ti.cfg ^
  -c "reset halt" -c "load_image <REPO>/Main/sw/bootSizeTest/build/bootSizeTest.bin 0x1000 bin" ^
  -c "resume 0x1000" -c "sleep 10000" -c "halt" -c "reg pc" -c "shutdown"
```

`load_image` 的路径用正斜杠，OpenOCD 的 Tcl 解析会把反斜杠当转义符。

不写程序也可以直接读写外设寄存器，例如验证 APB 通路：

```
  -c "reset halt"
  -c "mdw 0xf8100000 3"
  -c "mww 0xf8100008 0xa5a55a5a" -c "mdw 0xf8100008"
  -c "mdw 0xf8108008"
```

调试通路上有三条限制：

- **加载程序前必须 `reset halt`。** 不复位直接 `resume` 时 PC 会停在 `0x8`，串口无输出，
  而读回的内存与文件一致。原因见技术报告 platform 系列第 01 章 4.3 节。
- `verify_image` 不可用，目标端没有实现 `checksum_memory`，且失败后 OpenOCD 会直接退出，
  后面的命令都不执行。改用 `dump_image <文件> <地址> <长度>` 读回主机比对哈希。
- `step` 在未复位时会让 PC 跑飞并报 `Target not halted`，需要单步时改用 GDB。

## 7 编译软件

`sdk/software/standalone/` 下的官方示例与 `sw/` 下本项目的程序用同一套 makefile：

```
wsl -e bash -c 'cd sw/bootSizeTest && make BSP=efinix/EfxSapphireSoc RISCV_BIN=<RISCV_BIN> OBJDIR=build'
```

- `wsl.exe` 会把当前的 Windows 目录映射进去，所以在仓库里任意位置调用都不必写 `/mnt/` 路径。
- 必须写 `wsl -e`。不带 `-e` 时命令会先经过一层默认 shell 再解析一遍，
  `$` 开头的变量在那一层就被展开成空，make 会退回用主机的 gcc，报
  `unrecognized argument in option '-mabi=ilp32'`。
- `OBJDIR` 默认是程序目录下的 `build/`，已在 `.gitignore` 里。
  不要指到 WSL 的 `/tmp`，那里的产物可能在两次调用之间消失。

## 8 读写 Flash

板上 Flash 是 Winbond W25Q64，8MiB，4KB 扇区，JEDEC ID `0xEF6017`。
分区规划见 `赛题二总体设计.md` 2.2 节：`0x000000` 起是比特流，`0x380000` 起是程序。

写之前先把整片读出来备份。JTAG Bridge 分两步，先把 FPGA 配置成一个 Flash 烧写器，
再通过它读写：

```
set U=<JTAG>
set PGM=<EFINITY>\pgm\bin\ftdi_pgm.bat

%PGM% -m jtag -u %U% <EFINITY>\pgm\fli\titanium\u10660A79.bit

%PGM% -m jtag_bridge --jtag_bridge_mode read --address 0x0 --num_bytes 0x800000 ^
      -o <备份.hex> -u %U% <一个不存在的文件.hex>

%PGM% -m jtag_bridge --jtag_bridge_mode all --verify_method hostx1 --address 0x380000 ^
      -u %U% <程序.hex>
```

- `u10660A79.bit` 按器件的 JTAG ID 命名，是 Efinity 自带的桥接镜像。
- `--jtag_bridge_mode` 的默认值是 `all`，即擦除加写入。**读 Flash 时必须显式写 `read`**。
- 即使是读，也必须给一个输入文件，且扩展名必须是 `.hex`。
  给一个不存在的路径，万一模式写错也只会因为打不开文件而失败，不会写入。
- 写入地址必须落在扇区边界上，擦除长度按扇区向上取整，只擦写入的那一段。
- 这个模式只接受每字节一行的 hex 文本，不接受裸 bin，转换用 `tools/bin2hex.py`。
- 读出的文件与 Programmer 的 hex 格式相同，可以原样写回，用于恢复。
- 用时参考：整片读取 31 到 33 秒；写 294KiB 时擦除 2 秒、写入 1 秒、读回校验 1 秒。

## 9 改 bootloader 之后要同步什么

bootloader 以初始内容的形式烧在比特流里，源码在 `sdk/software/standalone/bootloader/`。
改了它的源码或 `bootloaderConfig.h`（例如拷贝长度 `USER_SOFTWARE_SIZE`）之后，
下面五步缺一不可，只改源码不会有任何效果。

1. 重新编译 bootloader，用第 7 节的命令，`BSP` 与工具链前缀相同。
2. 把新的 bin 转成片上 RAM 的初始内容。`binGen.py` 要求环境变量 `EFINITY_HOME`，
   产物落在当前目录的 `rom/` 下：

   ```
   wsl -e bash -c 'cd sdk/tool && EFINITY_HOME=<EFINITY> python3 binGen.py \
     -b bootloader/bootloader_512K.bin -c EfxSapphireSoc -s 4096 -f 0'
   ```

3. 用产物替换 SoC IP 里的 8 个初始文件，
   `fpga/gfx2d_ti60/ip/soc/` 与 `fpga/gfx2d_ti60/ip/soc/source/hardware/netlist/` 下各 4 个，
   文件名形如 `EfxSapphireSoc.v_toplevel_system_ramA_logic_ram_symbol<N>.bin`。
4. 更新 `sdk/tool/bootloader/` 下的 bin 与 hex，它们是上板校验时的比对基准。
5. 程序区长度跟着改时，同步 `sdk/bsp/efinix/EfxSapphireSoc/linker/` 下的
   `default.ld` 与 `freertos.ld`，以及 SoC IP 配置里的 `LDSize`。

判据两条，都要做：

- 重新编译比特流并加载，`reset halt` 之后用 `dump_image` 读回片上 RAM `0xF9000000` 起
  bootloader 的长度，SHA256 与 `sdk/tool/bootloader/` 下的 bin 一致，
  说明新 bootloader 确实进了比特流；
- 跑 `sw/bootSizeTest`，两个 CRC 与主机侧算出的期望值一致，
  并用官方 124KB 比特流作对照组，对照组必须不一致。
  没有对照组时无法区分「新长度生效」与「程序恰好短到旧长度也够」。

## 10 跑仿真

```
wsl -e bash -c 'bash sim/hdmi/run.sh'
wsl -e bash -c 'bash sim/apb_probe/run.sh'
wsl -e bash -c 'EFINITY_HOME=/mnt/<EFINITY 的盘符与路径> bash sim/axi_probe/run.sh'
```

每个脚本都包含注错用例，全部用例都符合预期才输出 `SIM OK`。前两个不依赖 Efinity；
`axi_probe` 仿真的 `Axi_Mux` 例化了厂商原语 `EFX_SRL8`，要从 `<EFINITY>/sim_models/verilog/efx_srl8.v` 取仿真模型，
所以要用 `EFINITY_HOME` 指向 Efinity 安装目录在 WSL 里的路径（`C:\` 在 WSL 里是 `/mnt/c/`）。
这个原语的输出取反、地址反向，不能用自己写的移位寄存器代替，原因见 platform 第 03 章 3.2 节研究 5。

下面是产出当前这批结果的那台机器上的取值，供填写第 1 节的占位符时参照。

| 占位符 | 参考取值 |

## 12 故障对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `No USB target detected` | ch1 上还是 FTDI 虚拟串口驱动，或者换成了别的通道 | 用 zadig 给 Interface 1 装 libusbK，见第 4 节 |
| 编译在 map 之后报 `No such file: ...work_dbg\debug_top.v` | 工程开了调试核自动插入 | `auto_instantiation` 改 `off`，见第 5 节 |
| 程序不运行，PC 停在 `0x8`，串口无输出 | 加载前没有复位 | 一律先 `reset halt`，见第 6 节 |
| `Target ... doesn't support checksum_memory` | 目标端没有实现校验和 | 改用 `dump_image` 比哈希 |
| make 报 `unrecognized argument in option '-mabi=ilp32'` | 调 WSL 时漏了 `-e`，变量被外层 shell 吃掉 | 见第 7 节 |
| 串口一直没有输出 | 板上 Flash 里可能是出厂的演示比特流，其中没有 SoC | 先 JTAG 加载本工程的比特流再看 |
| `cpu.yaml not found within 3 levels`，`target ... init failed` | OpenOCD 的启动目录往上找不到 `Main/sdk/cpu0.yaml` | 在 `Main\sdk\bsp` 下启动，见第 6 节 |
