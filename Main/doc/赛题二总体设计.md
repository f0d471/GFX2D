## 0. 目标与指标

### 0.1 赛题到底比什么

选题指南第 7~9 页（`Efinix/01_赛题指南/易灵思FPGA 创新设计赛道选题指南.pdf`）高阶挑战第 3 条原文：

> 在 RISC-V 上运行一个具有极高同屏元素数量的游戏 Demo（如《吸血鬼幸存者》的简化版或类似《东方 Project》的弹幕射击游戏）。在开启硬件加速（Alpha 混合 + Color Keying）的情况下，挑战保持 60 FPS 稳定运行时的同屏活动元素（Sprite）数量极限。

所以核心指标是：**开启 Alpha 与 Color Key、稳定 60 FPS 的前提下，同屏活动 Sprite 的最大数量**，下文记作 `N_max`。「弹幕数量」是它在弹幕游戏里的具体形态。

其余要求是门槛项，必须做到，但不决定排名：

| 类别 | 要求 |
| --- | --- |
| 基础 1 | 引擎解析指令（操作类型、源地址、目的地址、宽、高），支持块拷贝与纯色填充，HDMI 输出至少 640×480@60 |
| 基础 2 | 加速器经总线直接访问内存，合理使用突发与内部 FIFO |
| 基础 3 | C 驱动配置寄存器，双缓冲防撕裂；Demo 在屏幕上实时对比软件渲染与硬件渲染的帧率 |
| 高阶 1 | 硬件 Alpha 混合，用 DSP 计算 `fg*a + bg*(1-a)` |
| 高阶 2 | Color Key，跳过透明色像素 |
| 高阶 3 | 高负载游戏 Demo，冲 `N_max` |

### 0.2 本方案自己定死的口径

赛题没有规定「稳定」和「活动元素」怎么数，演示和报告里必须自己先写清楚，否则数字没有说服力：

- 稳定 60 FPS：连续 60 秒内没有一帧的渲染超过 16.67 ms，也就是不掉帧；同时报告帧时间的最大值和 99 分位。
- 活动元素：每帧实际提交给引擎、至少有一个像素落在屏幕内的 Sprite 绘制命令数。背景、HUD 底图不计入。
- `N_max` 由程序自动搜索：逐步加弹幕，直到出现掉帧再回退，结果显示在屏幕上并打到串口。
  搜索先倍增再二分，候选值上再跑 60 秒确认（`Engineering/TechReports/sw/07-演示模式与统计埋点.md` 3.5 节）。
- 负载弹：游戏里实际画的小圆弹，16×16、预乘 ALPHA、带光晕；另报一档 8×8 作对照。报告的是活动元素数，另列敌弹数。

以上口径于 2026-09-25 确认（SW8 的 K1、K2）。

### 0.3 设计总原则

赛题要的是专用加速器。这里只做对 `N_max` 和画面效果有直接贡献的东西，不追求计算原语的全面性：

- 不做浮点、不做通用 uop 虚拟机、不做 3D、不做实时旋转缩放。旋转和动画预先渲染成图集里的多帧。
- 硬件预算集中投在三件事上：减少每个 Sprite 的 DDR3 访问次数、把小纹理放进片上存储、多像素并行的混合通路。
- 架构上分层，接口带版本号和能力寄存器，新增一种混合模式或数据源只动一个模块。

### 1.2 裁剪清单

**关键结论：逻辑和 DSP 都不紧，片上 RAM 才是稀缺资源（总共 2.56 Mbit）。裁剪只有省 RAM 的那几条值得花时间，其余顺手做。**

1. **DDR 跨时钟 FIFO（17 块 RAM，占全片 6.6%）是冗余的。** 顶层把 SoC 的 `io_systemClk` 和 `io_memoryClk` 都接到 `core_clk`（`rtl/top/gfx2d_top.v` 的 `u_soc` 例化），跨时钟 FIFO 两端是同一个时钟。但 Sapphire 手册（UG-RISCV-SAPPHIRE v6.0，Cache/Memory 页）写明「External Memory Clock Domain：Unified System Clock」**只在 Lite 版可选**，当前配置（含 FPU、自定义指令等 Standard 专属项，`settings.json` 里 `DDRCLK_DOMAIN="1"`）走的是专用内存时钟。两条路：
   - 保留 Standard，接受这 17 块；
   - 换 Lite 版并选 Unified System Clock。Lite 没有 FPU、自定义指令、压缩指令，本设计都用不上；乘除法和桶形移位器在 Lite 里要手动打开。需要实验 E1 比较 CoreMark 和 RAM 占用后再定。

   > 订正（2026-09-19）：E1 已定**保留 Standard，接受这 17 块**（统一时钟下调试通路不可用），见 platform 第 04 章。
2. **自动插入的逻辑分析仪 `la0`（1 块 RAM、944 LUT）。** 2026-09-16 已关闭：命令行编译生成不了它依赖的 `work_dbg/debug_top.v`。要抓波形时在 GUI 里生成一次再编译，见 `../../Engineering/TechReports/platform/01-从零搭起可上板的硬件基线.md` 4.2 节。
3. **I2C0。** 在 SoC IP 里关掉，省约 170 FF、220 LUT。

   > 订正（2026-09-19）：改为**保留**，留给摄像头配置传感器，见 `../../Engineering/TechReports/platform/07-SoC-IP定型与工具链升级.md` 3.1 节。
4. **外部 AXI 主机口 `io_ddrMasters_0`（32 位）。** 加速器如果按 3.3 节走 `Axi_Mux` 接入 DDR3，就用不到 SoC 内部这个口，可在 IP 里关掉，连带省一部分仲裁和位宽转换逻辑（具体数字要重新生成后看报告）。
5. **`axiA` 16MB 从口窗口。** 控制寄存器放 APB Slave 0（64KB）足够，关掉。

   > 订正（2026-09-19）：第 4、5 条已随 SoC IP 定型做掉（efx_soc 3.4.0 重新生成），见 platform 第 07 章。
6. **工程文件列表清理。** 2026-09-16 已做：`rtl/memory_test/` 整个删除；`Axi_Mux.v` 移到 `rtl/vendor/axi_mux/`。2026-09-17 实验 E4 已把它加回源文件列表并例化（3.3 节）。
7. **不要动的。** `settings.json` 里 `BARREL_SHIFTER="1'b0"`、`MULDIV_EXT="1'b0"` 看起来像关了，但手册注明这两项是 Lite 专属，Standard 里默认开启，不是性能隐患。

裁剪能省下的逻辑合计约 1.5K LUT，对这块 60K 的芯片意义不大；能省下的 RAM 是 1 块（调试核）加可能的 17 块（换 Lite）。

## 2. 资源划分

### 2.1 DDR3 地址空间（256MB）

**已核实的事实**

- 板上 DDR3 256MB，控制器 AXI 地址 28 位，正好覆盖 `0x0000_0000`~`0x0FFF_FFFF`（`rtl/vendor/ddr3_controller/ddr3_parameter.vh`）。
- CPU 看到的 DDR 窗口从 `0x0000_1000` 开始，窗口大小 `0xE000_0000`（`sdk/.../soc.h`）。
- SoC 送出的地址与 CPU 地址按位相同，顶层只把低 28 位接给控制器。2026-09-16 上板实测（实验 E2，`sw/apps/probe/ddrAliasTest`）：低 28 位每一位都参与寻址，高 4 位被丢弃，回绕周期 256MB。**`0x0000_1000`~`0x0FFF_FFFF` 内 CPU 地址就是控制器地址**，驱动下发给引擎的指针不需要换算；`0x1000_0000` 以上全是别名，不使用。颗粒最低 4KB 只能经 `0x1000_0000` 起的别名访问，保留不用。过程见 `../../Engineering/TechReports/platform/02-DDR地址译码与AXI-ID实测.md`。
- SoC 发出的 AXI ID 恒为 0（CPU 一路的 ID 在 IP 里接常量，外部主机口未启用），顶层截成 4 位是安全的。`io_ddrMasters_0` 一旦启用，它的 ID 最高位是 1，截断后响应会回错主机，所以不要启用它。
- CPU 数据缓存是 1 路直接映射、64 行 x 64 字节，行号取地址 [11:6]、标签取 [31:12]（`sw/apps/probe/cacheMechTest` 的 T4 逐位实测）。读会把整行装进缓存，只写不装行，写之后读一次会装行（T2）；装进来的行在 IO 访问、别的行的访问与任意长的空转之后都还在（T7~T9）。经别的地址（别名，或另一个 AXI 主机）改写 DDR 时，缓存里已有的副本不会失效（`sw/apps/test/cacheCoherencyTest`）。本构型**没有写缓冲**，CPU 的写返回时已经落到 DDR（T3、T6，网表里是 `dBus_Bridge_withoutWriteBuffer`）。过程见 `../../Engineering/TechReports/platform/05-CPU数据缓存与第二个主机写入的一致性.md`。

**分区**

| 区 | 地址范围 | 大小 | 内容 | 读 / 写方 |
| --- | --- | --: | --- | --- |
| 保留 | `0x0000_0000`–`0x0000_0FFF` | 4KB | CPU 窗口之外；DDR3 控制器上电校准在最低 64 字节写测试图样（E4 实测） | 不用 |
| 程序 | `0x0000_1000`–`0x003F_FFFF` | 约 4MB | 代码、数据、堆、栈 | CPU |
| 命令表 A/B | `0x0040_0000`–`0x005F_FFFF` | 2MB | 两张命令表各 1MB，每张最多 32768 条 32 字节命令 | CPU 写，引擎读 |
| 共享数据池 | `0x0060_0000`–`0x00FF_FFFF` | 10MB | P4 弹幕参数表、其他需要与引擎共享的数据 | CPU / 引擎 |
| 素材 | `0x0100_0000`–`0x01FF_FFFF` | 16MB | 纹理图集、背景、字库，启动时从 Flash 装入 | CPU 写一次，引擎读 |
| 帧缓冲 0 | `0x0200_0000`–`0x023F_FFFF` | 4MB | 见下 | 引擎或软件渲染写，扫描输出读 |
| 帧缓冲 1 | `0x0240_0000`–`0x027F_FFFF` | 4MB | 同上 | 同上 |
| 离屏层 | `0x0280_0000`–`0x02FF_FFFF` | 8MB | 背景预合成、调试抓帧 | 引擎 |
| 预留 | `0x0300_0000`–`0x0FFF_FFFF` | 208MB | — | — |

**帧缓冲的行跨取 4096 字节**，也就是每一行在内存里占一个完整的 4KB 页，每行最多 1024 个 32 位像素：

- 一行的读写正好是一次突发，**永远不会跨 4KB 边界**。AXI4 禁止突发跨 4KB，这是协议条文，越界时从机行为未定义。行跨取 4096 后，这个问题在数据布局上就消失了，不再需要额外的边界检查。
- 地址计算只剩移位：`addr = base + (y << 12) + (x << 2)`。
- 代价是一帧占 480×4KB = 1.875MB，比紧凑存放多 0.7MB，256MB 里不值一提。
- 640 个像素 = 160 个 128 位拍，一次突发放得下。2026-09-17 实验 E4 实测控制器接受 256 拍的突发，读写都无错；`BURST_MODE="8"` 指一个 AXI 拍对应颗粒上 8 个 16 位字，与 AXI 突发长度无关。搬运层仍把最大突发长度做成参数。

**像素格式**：帧缓冲 XRGB8888，纹理 ARGB8888（预乘 alpha，见 3.5）。选 32 位而不是 RGB565 的理由是一个 128 位 beat 正好 4 个像素，搬运和并行混合都按 4 像素对齐，逻辑最简单；带宽代价见 3.1，不是瓶颈。

**命令表双份**：CPU 在第 N 帧填命令表 A 的同时，引擎还在执行第 N−1 帧的命令表 B。两者流水并行，吞吐翻倍，代价是画面延迟多一帧。

**Cache 一致性**：引擎直接改 DDR，CPU 的数据缓存会留着旧值（实验 E3 实测，[`platform 第 05 章`](../../Engineering/TechReports/platform/05-CPU数据缓存与第二个主机写入的一致性.md)）。状态一律走寄存器。共享区的约定是**读回前必须失效**，命令表读回校验、素材复核、调试时读帧缓冲都允许，条件三条：

1. 失效必须在引擎对这一区域的写入**完成之后**（完成中断或状态寄存器确认之后），读回期间引擎不再写这一区域。先失效、再读、再让外部主机写，读到的仍是旧值（E3 机理实验 T5，8/8）。
2. 失效调用包成带 `"memory"` clobber 的函数，且不要直接排在条件分支之后。这颗 CPU 上紧跟在跳走的分支之后的失效指令即使没执行也会清缓存（T10）；结果仍正确，但多付一次重新装行的代价。
3. CPU 在软件渲染模式下写帧缓冲不受影响；切回硬件渲染之前对帧缓冲区失效一次。

代价实测（1 tick = 10 ns = 1 个 `core_clk` 周期）：失效指令本身，全清约 67 个周期、单地址约 4 个周期；失效之后每一行第一次被访问要重新装入，约 69 个周期。所以「全清之后程序接着跑」的实际开销约 135 个周期起（全清加栈所在一行），每多用到一行加约 69。**估算**：CPU 读回一整帧 640×480 XRGB8888（19200 行）仅装行约 132 万个周期、约 13 ms，同帧 CRC 对比（3.8 节）适合作逐帧调试手段，不适合每帧常开。

| 比特流 | `0x000000`–`0x1FFFFF` | 2MB | 当前比特流约 636KB：`bit/official/ddr_demo_ti60.bit` 文件大小 1.95MB，但它是每行一个字节的十六进制文本，共 651,444 行 |

| 应用 | `0x380000`–`0x3FFFFF` | 512KB | bootloader 从这里拷程序，地址 `0x380000` 由 bootloader 决定 |
| 素材包 | `0x400000`–`0x7FFFFF` | 4MB | 带目录头的图集、背景、字库 |

两个约束：

- 4 MiB 素材分区放不下 3~4 张独立的全屏原图。虽然 640×480×4 的紧凑像素只有
  1,228,800 字节，v1 表面的行跨必须是 2 的幂，640 宽要按每行 4096 字节存放，
  一张实际占 1,966,080 字节（1.875 MiB）。
  **首版素材方案**：保留多张大图快速切换的可见效果，
  用可复用图块/图集或程序生成的不同背景合成；不要求在素材包中存 3~4 张独立整图，
  也不为此引入 INDEX8 或 RLE。若以后改变路线，再单独评估容量、装载时间与格式。
- 装载时间。手册写 bootloader 拷 124KB 约 300ms，照此单线 SPI 拷 4MB 约 10 秒。bootloader 支持双线与四线读取，但顶层只连了 SPI0 的 `data_0/1`，`data_2/3` 悬空，`peri.xml` 也只分配了两根数据线，所以现在只能试双线（`spiFlash_f2m_dual`）；四线要先改顶层与接口设计，并核对板上 Flash 的 IO2/IO3 是否接到 FPGA。实验 E6 测单线与双线的速度。

### 2.4 DSP 预算（160 块）

每块 DSP 在 dual 模式下有一个 11×10 和一个 8×8 乘法器（Ti60 数据手册 DSP Block 一节）。

| 用途 | 数量 |
| --- | --: |
| CPU 乘法 | 4 |
| 混合通路：每像素 3 个通道乘法，每条通路一次处理 4 像素 | 每条通路 12 个乘法，约 6~12 块 |
| 着色（tint，后续 profile） | 同上再加一份 |
| 扫描输出全局淡入淡出 | 3 个乘法 |
| **合计（2 条通路、带着色）** | **约 50 块以内** |

DSP 不是约束，不需要为省 DSP 用移位加法近似。

### 2.5 时钟与复位

- 引擎挂 `user_clk`（100MHz），与 SoC、DDR3 控制器的 AXI 同一个时钟域。控制器 `ASYN_AXI_CLK=0`，所以引擎到 DDR3 不需要跨时钟。
- 唯一的跨时钟点是扫描输出：100MHz 读 DDR3，经异步 FIFO 送 25.2MHz 像素域。
- 场同步从像素域同步到 100MHz 后，给引擎做缓冲切换、给 CPU 发中断。前后缓冲的切换请求在像素域的场消隐期锁存，保证不撕裂。
- `core_clk` 来自 PLL_TL0，DDR3 的 400MHz 来自 PLL_TR0，二者同源于 25MHz 晶振（`peri.xml`）。这是官方原样，不动。

## 3. 加速器设计

### 3.1 先算账：墙在哪

每帧可用的时间是 16.67ms，按 100MHz 算约 166 万个时钟周期。

**E4 实测（2026-09-17，`sw/apps/probe/ddrBurstProbe`，经 `Axi_Mux` 的第二个主机，突发对齐 4KB）**：突发上限 256 拍，读写都可用；每笔事务周期数 `T(N) = t_tx + k·N`，写 `t_tx = 7.25`、`k = 1.183`，读 `t_tx = 27.41`、`k = 1.086`（N 为拍数，一拍 128 位）。过程与原始数据见 `../../Engineering/TechReports/platform/03-DDR3上的第二个主机与突发预算.md`。

**DDR3 带宽不是墙。** 实测持续吞吐每周期 0.85（写）~0.92（读）拍，即每秒 8500 万~9200 万拍。640×480@60 的扫描输出每秒 461 万拍；按每行 256 拍一次突发读，一帧 300 笔、约 9.2 万个周期，每秒占 5.5%。整帧读背景加整帧写回约占 11.1%。数量级上有富余。

> 订正（2026-09-17）：本段原写「控制器每 10ns 最多交换一个 128 位 beat（DDR3 控制器手册 v2.1），理论上限每秒 1 亿 beat，扫描占 4.6%，读写背景占 9.2%」。手册描述的是 Efinix 自己的 DDR3 核，与板上 Elitestek 的 `ddr3_top` 不是同一个实现，不能当作本板的依据；数字已换成 E4 实测。

**真正的墙是事务次数。** 一次 AXI 突发除了传数据，还有地址握手、控制器排队、写响应等固定开销，记为 `t_tx`。实测读事务的固定开销（约 27 个周期）是写的近 4 倍，每笔只读 1 拍时要 29 个周期，是 256 拍突发里每拍开销的 24 倍。所以设计的第一目标是减少每个 Sprite 的事务数，读方向尤其要避免小块读。

> 订正（2026-09-17）：本节原来还引用「同类加速器上实测过搬运占 87% 至 91% 的时间」作为参照。这个数字出自其他项目，本仓库里没有出处可查，删除。

下面的表仍是按 `t_tx = 20` 个周期的假设估算的，**尚未用实测值重算**（读 27.4、写 7.3）。三种架构的相对排序不受影响，绝对数字待引擎设计定型时重算。

| 架构 | 每个 Sprite 的 DDR 事务 | 每个 Sprite 的周期（估算） | 每帧固定开销（估算） | `N_max` 硬件侧上限（估算） |
| --- | --- | --: | --: | --: |
| A. 直通 BitBlt：逐行读纹理、读目标、写目标 | 16 行 × 3 = 48 次 | 约 1400 | 背景整帧拷贝约 17 万 | 约 1000 |
| B. 条带合成，纹理在 DDR3 | 每行读 1 次纹理 = 16 次 | 约 600 | 整帧读写背景约 17 万 | 约 2500 |

表中的架构 C 上限与 CPU 侧负载都还是假设，不能据此断言瓶颈一定会移到 CPU。
Sapphire 的 1.16 DMIPS/MHz、100MHz 下约 116 DMIPS 不能直接换算本程序的每弹幕周期；
「更新、碰撞并写 32 字节命令约 100 条指令，5000 个约 5ms」是待测估算。
E8 先分别量运动更新与命令提交，并比较缓存配置；它不含碰撞和完整游戏循环，
P4 是否值得做还要等 SW8/SW9 的板上整帧分段与真实 `N_max`。
2026-09-25 复核时发现先前用于 E7/E8 解释的 `outflow` 比特流是 16KB/4 路，
与源码和 SoC 头文件所示的主线 4KB/1 路不一致。主线已从 4KB 源码重编并上板；
旧 16KB 比特流与资源、时序报告已留存。E7 在真实 4KB 主线上测得精确 S1 整表
80.46 M 周期，在 100MHz 下约 **805 ms**；两面 18 项输出 CRC32 与逐像素加和
均经独立复算一致。E8 新逐帧校验产物的 N=1000 合成负载 A/B/C 分别为
4KB 下 49.05/71.47/176.24、16KB 下 34.78/40.33/104.33 周期/弹幕/帧；
8KB 仅保留旧产物结果；不再要求补新版测量，2026-09-27 收尾结果见 platform 第 10 章 5.9。4KB 下 C 的 N=2000 约耗 3.51 ms/帧。

仅是不同探针口径的预算参照，不能当成真实游戏实测帧时。
生产构造层、碰撞和规则、硬件模式整帧分段还须在 SW9 同表实测；

### 3.2 总体结构

```
           RISC-V（Sapphire）
             │ APB（寄存器）          │ AXI 128 位 S2（程序、命令表、素材）
             ▼                        ▼
      ┌──────────────┐          ┌──────────┐
      │  前端 CSR    │          │ Axi_Mux  │── DDR3 控制器 ── DDR3 256MB
      │ 命令表门铃   │          │ 3 进 1 出│
      │ 中断/计数器  │          └──────────┘
      └──────┬───────┘             ▲     ▲
             ▼                     │     │
      ┌──────────────┐   S1 引擎   │     │ S0 扫描输出（实时流）
      │ 中端         │─────────────┘     │
      │ 命令解码     │                   │
      │ 几何/裁剪    │           ┌───────┴──────┐
      │ 行/条带迭代  │           │ 扫描读出     │
      └──────┬───────┘           │ 异步 FIFO    │
             ▼                   │ 时序/OSD/淡出│
      ┌──────────────┐           │ DVI 编码     │── HDMI
      │ 像素流水线   │           └──────────────┘
      │ 取数→色键→   │
      │ 乘→加→写     │
      └──────┬───────┘
             ▼
      ┌──────────────────────────────┐
      │ 后端：三个地址空间            │
      │ DDR（搬运层）/ TEX 纹理缓存 / BAND 条带缓冲 │
      └──────────────────────────────┘
```

分层沿用搬运硬件常见的三段划分：前端是各自的软件接口，中端把「搬什么形状」展开成连续段，后端只管「怎么在 AXI 上搬完」。区别在于这里多了一个像素流水线，而且后端有三个地址空间。

### 3.3 总线接入

用官方工程目录里的 `rtl/vendor/axi_mux/Axi_Mux.v`，不用 tinyml 工程的 `axi_interconnect_beta`。
**当前实现（2026-09-21 起）**：`Axi_Mux.v` 第 43 行用 `` `define X3 ``，实例 `u_axi_mux` 的
S0 接扫描输出 `u_display`、S1 接渲染引擎 `u_engine`（引擎 P1 B6 接入；此前由探针主机 `axi_probe_master` 占位，已随 D6/D22 撤下）、S2 接 SoC 的 `io_ddrA`；
仲裁方式、三通道掩码与 SoC 防饿死保护由永久模块 `u_mux_guard` 给出（APB `0xF810_F000~0xF810_FFFF`）。
2.1~2.3 已于 2026-09-19 上板验证；S0 的扫描替身 `scanout_stub` 已于 2026-09-21 换成真实 `display`
（同一个 `0xF810_E000` 窗口），替换之后 2.3 节那批量复测仍在同一量级（第 06 章 5.4 节）。
2.4 的真实扫描 FIFO 压力矩阵与深度定值也已完成（2026-09-21），E5 于 2026-09-24 整体验收；
过程与实测值见 [platform 第 06 章](../../Engineering/TechReports/platform/06-Axi_Mux三端口仲裁与SoC防饿死保护.md)
与 [第 08 章](../../Engineering/TechReports/platform/08-扫描FIFO的压力矩阵与深度定值.md)。

| | `Axi_Mux.v` | `axi_interconnect_beta` |
| --- | --- | --- |
| 源码 | 明文，可以仿真；资料包里没有任何官方设计例化过它。本设计保留原仲裁状态机，不修改第三方逻辑 | 加密 |
| 端口 | 2~8 个主机进、1 个出（宏 `X2`~`X8`） | `S_COUNT` 参数 |
| 数据宽度 | 参数，默认 128 | 参数 |
| 仲裁 | 地址握手后重新仲裁，数据按信息 FIFO 的授权顺序返回。`Cfg_Arb_Type`：0 轮询、1 厂商所谓“优先级”；该模式不是普通严格优先级，实际序列见下。`Cfg_Cnl_Mask` 可屏蔽新授权 | 未知 |
| 缺陷 | 没有 `BRESP` 端口，顶层把控制器的 `bresp` 并接给各主机 | 未知 |

扫描输出是实时流，不能只靠先到先得。E4 实测：轮询下另一个主机持续发 256 拍突发时，
发短事务的 CPU 速度降到 51.5%。E5 确认的 X3 目标分配为：

| 端口 | 主机 | 正式契约 |
| --- | --- | --- |
| S0 | 扫描输出 | 只读；最多一笔在途 |
| S1 | 2D 引擎（B6 起），接入前曾由 `axi_probe_master` 替代，该模块已撤下 | 读、写各最多一笔在途，参数 `MAX_INFLIGHT=1` |
| S2 | Sapphire SoC | 由永久 guard 监测地址等待并防饿死 |

2026-09-19 直接仿真 `Axi_Mux_Addr_Ctrl` 得到实际授权序列：三路持续请求时 S0、S1 交替，
S2 饿死；只有 S1、S2 持续请求时 S1 独占。原因是地址握手后的第一个空闲周期里，刚完成的通道
仍在 `Act_Cnl_List` 中，被下一轮搜索排除。因而本设计保留厂商多路器但不依赖“严格优先级”假设，
用三层措施形成边界：扫描与引擎的一笔在途契约；永久 `axi_mux_guard`；真实 FIFO 水位与欠载计数。

`axi_mux_guard` 独占 APB Slave 0 的 `0xF810_F000~0xF810_FFFF`，上电默认优先级模式、三通道全开、
guard 开启、`AGE_LIMIT=64`。它分别锁存 SoC 的 AR、AW 超龄状态，只要任一方向在等待就从新授权中
暂时屏蔽 S1；S0、S2 永不被 guard 屏蔽。掩码不能撤销已经取得的地址授权，所以 64 只是触发阈值，
不是绝对等待上界。整机仿真按实测口径验收：引擎遵守一笔在途时 S2 地址等待不超过 414 个周期
（读 301、写 311），引擎激进发地址时不超过 700（读 590、写 607）；加密 DDR3 控制器的板上结果只报告实测最大值。
guard 只在读方向有对照证据（关掉后读等待升到 889）。写方向上保护开、关的仿真结果逐项相同：
写数据 256 拍把地址通道压成「一个授权挂着等下游」，掩码几乎没有生效的时机。
所以**写方向的等待只靠引擎的一笔在途契约约束**，引擎写通道必须等 `bvalid` 握手之后才发下一笔地址。
过程见 `Engineering/TechReports/platform/06-Axi_Mux三端口仲裁与SoC防饿死保护.md`。

FIFO 初始按 3 行预留（128 位 × 512 深，占 6 块片上 RAM）。E4 实测一笔 256 拍读约 307~311 个周期
（约 3.1 微秒），而可见 640 像素消耗约 25.4 微秒，这只说明量级有余量，不构成实时性证明。
**2026-09-21 定值**：用 `sw/apps/probe/displayFifoProbe` 在 `idle`、S1 满负载读、S1 满负载写
三种负载下各收 120 场连续快照（量的是帧缓冲模式下前 476 行的读侧保守水位），最低水位分别是
**347 / 331 / 327 拍**，触底次数与欠载拍数都是 0、每场弹出 76800 拍、场末残留 0 —— 都远高于
一行 160 拍的下界，所以 M2 阶段**保持 512 拍**。深度不能按水位差值线性外推：改浅会同时改变
发行节奏与场末排水窗口。256 / 1024 都算新设计，必须重算 `MEASURE_LINES` 并重跑 `sim/display`、
Efinity 时序与整套板测。这一组数只是「探针负载模型下的平台基线」——探针造不出真实引擎的
读改写与读写切换开销，引擎接入 S1 之后要在最重的 FILL/BLIT/ALPHA 命令表下按同一判据复跑。

> 订正（2026-09-17）：本节原写「S1 接引擎，S2 接扫描输出，用优先级模式把扫描输出排最高」，与 `Axi_Mux` 优先级模式只能让 S0 最高相矛盾；原写「等一个 256 beat 突发约 2.6 微秒」是按每拍 1 个周期估算的，已换成 E4 实测。原文还引用了另一个项目的文件 `mtx.md`，本仓库里不存在，删除。
>
> 订正（2026-09-19）：前一次订正仍把厂商的“优先级模式”解读成严格优先级。E5 的三端口
> 仿真推翻了这一解读，现改为记录实际授权序列，并用一笔在途、guard 与 FIFO 实测共同保证实时性。
>
> 订正（2026-09-19，第二轮）：原写仿真按 `AGE_LIMIT + ADDR_STALL_MAX + 4` 验收，整机仿真证明该算式不成立
> （已授权的排队事务不受掩码影响），改为上面的实测口径；并补上写方向的结论。
>
> 订正（2026-09-21）：S0 的扫描替身 `scanout_stub` 换成真实扫描输出 `display`；2.4 的真实 FIFO
> 压力矩阵与深度定值完成，**维持 512 拍**，依据（独立复现修复后三组 120 场最低水位 347 / 331 / 327 拍）与
> 适用边界（探针负载模型、引擎接入后须复测）见上面的段落与 platform 第 08 章。

### 3.4 命令与软件接口

**表面（surface）表。** 所有「地址」都经过表面表间接寻址，驱动先登记表面，命令里只写表面号和坐标。这样硬件能统一做裁剪和越界检查，也满足赛题「源地址、目的地址」的要求：源地址 = 源表面基址 + 源坐标换算。

| 字段 | 宽度 | 含义 |
| --- | --: | --- |
| `base` | 32 | 基址，DDR 物理地址或片上缓存偏移 |
| `stride_log2` | 5 | 行跨取的 log2，帧缓冲为 12 |
| `width` / `height` | 各 16 | 尺寸，用于裁剪 |
| `space` | 2 | 0 DDR，1 TEX 纹理缓存，2 BAND 条带缓冲 |
| `format` | 4 | 0 XRGB8888、1 ARGB8888_PREMULT、2 ARGB8888_STRAIGHT、3 INDEX8 |
| `valid` | 1 | 该槽位已登记；软复位清零，驱动最后置 1 |

v1 的有效描述符要求：基址 4 字节对齐，宽高非 0，`2 <= stride_log2 <= 31`，
`width × 4 <= 2^stride_log2`，最后一个像素的地址计算不溢出 32 位，
控制字里 `stride_log2`/`space`/`format`/`valid` 之外的位为 0，即
`(ctrl & 0x7fff0ce0) == 0`（三段为 [7:5]、[11:10]、[30:16]；违反时按 `BAD_SURFACE` 报错，
2026-09-20 与 spec 第 02 章对账时补齐）。不同表面号不得指向互相重叠的存储区域。
地址按 `base + (y << stride_log2) + (x << 2)` 算。

每项固定 3 个字、步长 12 字节：+0x0 是 `base`；+0x4 的低/高半字是 `width/height`；
+0x8 的 [4:0] 是 `stride_log2`、[9:8] 是 `space`、[15:12] 是 `format`、[31] 是 `valid`，
其余位必须为 0。16 项正好占 `0x040~0x0FF`。

**命令记录固定 32 字节（8 个字）。** 记录长度必须是 2 的幂，硬件才能用移位算第 k 条的地址，这是 VSE gather 踩过的坑（`Engineering/_raw/Temp/VSE-Alpha混合入门.md` 6.2 节）。

| 字 | 位 | 字段 |
| --- | --- | --- |
| w0 | [7:0] | 操作码：0 NOP，1 FILL，2 BLIT，3 SET_CLIP，4 BAND，0xFF END |
| | [11:8] | 混合方程编号（3.5） |
| | [12] | 色键使能 |
| | [13] | 着色使能（v1 不支持，必须为 0） |
| | [19:16] | 源表面号 |
| | [23:20] | 目的表面号 |
| | [31:24] | 常数 alpha |
| w1 | [15:0] / [31:16] | 源 x / 源 y |
| w2 | [15:0] / [31:16] | 目的 x / 目的 y，有符号，允许部分出屏 |
| w3 | [15:0] / [31:16] | 宽 / 高 |
| w4 | | FILL 的常量源像素；BLIT 在 v1 必须为 0 |
| w5 | | 色键颜色 |
| w6 | | 预留：翻转标志、帧号；v1 必须为 0 |
| w7 | | 调试标签；构造层默认填命令表零基索引 |

**命令 ABI v1 是 DDR 直通 profile。** 只支持 NOP、FILL、BLIT、SET_CLIP、END，源表面可以是
XRGB8888、ARGB8888_PREMULT 或 ARGB8888_STRAIGHT，目的只能是 XRGB8888，`space` 只能为 DDR。
BAND、TEX、INDEX8、tint 与 w6 都留给后续 profile；置入 v1 命令时按下面的错误模型停止。
原计划的「BLIT 上传 TEX」仍是后续方向，启用前要同时定义 ARGB 目的的 alpha 写回语义。

**v1-TEX 能力 profile（引擎 P3 的 G1，2026-10-07 定案 D57/D63）。** 在 v1 之上只放开一项：
BLIT 的**源**表面允许 `space=1`（TEX，片上 16 KiB scratchpad），目的仍只能是 DDR；
`space=2`（BAND）与 3 仍按 `BAD_SPACE` 拒绝，BAND/INDEX8/tint/w6 继续无效，
CAPS 的 [6] TEX 相应从 0 改为 1，其余能力位不变；32 字节命令记录不变，ABI v2 实例列表仍归 G3。
TEX 表面的 `base` 解释为 TEX 窗口内的字节偏移；它在 v1 六条结构要求之外再加两条，
违反报 `BAD_SURFACE`，仍在 space/format 两步之前：`base` 按 16 字节对齐；
`base + height × 2^stride_log2 <= 0x4000`（扩展位宽求值，完整行跨含 padding）。
「ARGB 目的 alpha 写回」继续搁置：本 profile 只做 TEX 源，不做 BLIT-to-TEX。

FILL 的 w4 按方程解释：ALPHA 要求 `R/G/B <= A`，按预乘 ARGB 解释；ALPHA_STRAIGHT

XRGB 在两种 alpha 方程中的有效 `a` 都是 255。

同一表面号的 BLIT 源、目的矩形按未裁剪的半开区间检查，非空且相交就报 `OVERLAP`；
不同表面号不得别名。零宽或零高只表示「没有矩形」：它跳过逐像素、重叠检查与后续执行，
**前面的检查一步不少**（零面积且格式错配仍报 `BAD_FORMAT`，2026-09-20 与 spec 第 02 章对账时写清）。

**结束与错误。** `LIST_COUNT` 是硬边界，END 是提前结束符；两者先到者成功结束，COUNT 为 0
或耗尽时没有 END 也属于成功。检查顺序固定为：取记录、操作码、字段、方程、源表面、目的表面、
space、format、FILL 预乘约束、BLIT 重叠。`space` 与 `format` 各是一步、覆盖源与目的两个表面
（源在前），所以「源格式非法 + 目的 space 非 DDR」报 `BAD_SPACE`；`FETCH` 时记录没读到，
`ERROR_TAG` 读 0。软件执行器把命令来源建模为 `readable_count` 条可读记录，索引超界不得解引用，
而是返回 `FETCH`（三处 2026-09-20 前期研究与复核写清，见 spec 第 02 章规范条款 §5）。错误码为：

| --: | --- | --- |
| 0 | OK | 成功 |
| 1 | BAD_OPCODE | BAND 或未知操作码 |
| 2 | BAD_FIELD | 保留位、未用字段、tint 或 w6 非零 |
| 3 | BAD_EQUATION | 方程号 6~15 |
| 4 | BAD_SURFACE | 未登记或描述符非法 |
| 5 | BAD_SPACE | 引用了该 profile 不允许的空间（v1 的一切非 DDR；v1-TEX 的 TEX 目的、BAND、space=3） |
| 6 | BAD_FORMAT | 格式不支持、目的不是 XRGB，或方程与源格式不匹配 |
| 7 | OVERLAP | 同一表面的 BLIT 矩形重叠 |

| 9 | FETCH | 命令记录读取失败 |
| 10 | BUS_READ | 像素数据读回的响应非 OKAY（硬件独有） |
| 11 | BUS_WRITE | 像素数据写响应非 OKAY（硬件独有） |

首错停止：失败命令没有像素或状态副作用，此前结果不回滚，后续记录不读取；错误前成功执行的
SET_CLIP 状态保留。10~12 三种总线类错误例外：失败命令可能已写了部分行，不回滚，读错的那一行不写，
之后的命令仍没有像素副作用。硬件锁存错误码与 `ERROR_INDEX`；非 FETCH 错误的 `ERROR_TAG=w7`，
FETCH 的 `ERROR_TAG=0`。软件执行器返回同一三元组。
新一次被接受的 DOORBELL 清除旧错误定位。完整依据与一致性用例见
[spec 第 02 章](../../Engineering/TechReports/spec/02-命令语义.md)。

**计数器按「能对账」设计**：`CMD`、`PIXEL`、`KEY_SKIP`、`RD_BURST`、`WR_BURST`、`RD_BEAT`、`WR_BEAT`、`WAIT_DDR`（等 ready 的周期数）、`BUSY`。
掉帧不在引擎里计，由 SW8 用场数减切换数算（[engine 第 00 章](../../Engineering/TechReports/engine/00-P1路线与层间契约.md)第三节 I8）。约束关系要成立，例如 `RD_BEAT` 等于各读突发长度之和；对不上就说明有漏计，不能拿去分析性能。

### 3.5 像素流水线

**混合方程统一成一张表，不为每种效果写一条通路。** 主路径的纹理存预乘 alpha；为赛题原式的
对照路径另有显式 ARGB8888_STRAIGHT 格式。混合写成：

```
out = src × Fs + dst × Fd       每个通道，结果饱和到 255
```

| 编号 | 名称 | Fs | Fd | 用途 |
| --: | --- | --- | --- | --- |
| 0 | COPY | 1 | 0 | 背景、不透明图块 |
| 1 | ALPHA | 1 | 1 − a_src | 半透明弹幕、UI 面板（预乘） |
| 2 | ADD | 1 | 1 | 发光、爆炸、激光 |
| 3 | CONST | c | 1 − c | 整体淡入淡出、受击闪烁 |
| 4 | MUL | dst | 0 | 阴影、暗化 |
| 5 | ALPHA_STRAIGHT | a_src | 1 − a_src | 赛题非预乘公式的对照路径 |

- 预乘之后 ALPHA 每通道只剩 1 个乘法。赛题公式 `fg*a + bg*(1-a)` 与预乘形式在数学上等价（`fg_pm = fg*a`）；报告里要写清这层换算。方程 5 明确使用 ARGB8888_STRAIGHT 源，演示时直接对照赛题公式，不再让同一个格式随方程改变含义。
- 色键独立于混合方程：源像素等于色键颜色时不写目的像素。赛题明确要求色键，即使 alpha 为 0 的像素也能起到同样效果，也要单独实现。
- 新增一种效果只加表中一行，不改流水线结构。

**逐像素规格（定稿 2026-09-18）。** 软件执行器与硬件实现同一份规格，两边的逐像素结果必须一致，这是 3.8 节同帧 CRC 判据成立的前提。下面七条把「混成一个通道的数值」写到可以直接实现的程度，配套的穷举校验在 `../tools/check/check_round255.c`（主机上编译运行，不依赖板子）。推导、原始输出与订正过程见 [`spec 第 01 章`](../../Engineering/TechReports/spec/01-逐像素规格.md)。

*1 方程表完整性。* 上表 6 行即 v1 全部。COPY 用 (1, 0)、ADD 用 (1, 1)、MUL 用 (dst, 0)，ALPHA 用 (1, 1−a)、ALPHA_STRAIGHT 用 (a, 1−a)、CONST 用 (c, 1−c)。

*2 通道混合的计算域与舍入。* 每个通道按下面的顺序算：

```
x   = src[c] * Fs + dst[c] * Fd           Fs、Fd 以 255 为满量程的整数表示
out = min(255, (t + (t >> 8)) >> 8)       t = x + 128
```

**表里的 `1` 是归一化值，实现里是 `255`。** 预乘 ALPHA 实现为 `src_pm × 255 + dst × (255 − a)`。照字面把 `Fs = 1` 代进去，源色权重从 255 掉到 1，8421376 组里有 8355712 组结果错误。

与实现有关的结论（`check_round255.c` 的 (a)、(b) 两节）：

- `(t + (t >> 8)) >> 8` 在 `x = 0..65025` 上与 `round(x / 255)` 的 half-up 精确商逐值一致。两项之和的上限是 `130050`，在 `x = 0..130050` 上裸快速式有 253 处不符（首个 `x = 65663`，快速式得 257、精确商 258），算完商后 `min(255, …)` 就全部一致。
- **中间量不能模截断到 16 位**：`t & 0xFFFF` 在全域有 64643 处不符（`x = 130050` 时得 253）。保留 17 位（`130178 < 2^17`），或者把 `t` **饱和**到 16 位（`min(65535, t)`，全域 0 处不符），都正确；用 18 位或 DSP 原生端口宽度是实现选择。舍入与最后的 clamp 可以分在两个流水级。

*3 舍入与饱和的顺序。* 采用「两项乘积先相加，再做一次 ÷255 舍入，最后饱和」（记作 V），即上面那条式子；另一种写法是「两项各自 ÷255 舍入之后再相加饱和」（记作 U）。按方程逐个代入穷举：

| 方程 | Fs、Fd（255 满量程） | 代入后的通道算式 | U 与 V 不一致的组数 |
| --- | --- | --- | --- |
| COPY | 255, 0 | `src × 255` | 0 / 256 |
| ALPHA（预乘） | 255, 255−a | `src_pm × 255 + dst × (255−a)`，`src_pm ≤ a` | 0 / 8421376 |
| ALPHA（非预乘开关） | a, 255−a | `src × a + dst × (255−a)` | 4121020 / 16777216（24.56%） |
| ADD | 255, 255 | `src_pm × 255 + dst × 255` | 0 / 65536 |
| CONST | c, 255−c | `src × c + dst × (255−c)` | 4121020 / 16777216（24.56%） |
| MUL | dst, 0 | `src × dst` | 0 / 65536 |

需要定序的是 CONST 与非预乘 ALPHA。CONST 的最小反例：`c = 1`、`src = 1`、`dst = 128`，精确值 `32513 / 255 ≈ 127.502`，V 得 128、U 得 127。整屏淡入淡出会让它作用到每一个像素。预乘 ALPHA 与顺序无关，因为第一项系数是 255 的整数倍，除以 255 不产生舍入。

本设计选 V：它等于把混合的数学定义算完之后只量化一次，对六种写法是同一套公式。

**预乘的代价。** 预乘在素材侧已经量化过一次（`src_pm = round(s·a/255)`），混合时再量化一次。以非预乘源色的实数混合为基准，预乘路径有 4121020 / 16777216 组与理想舍入不同，最大偏差 254/255；非预乘路径（V）0 组不同，最大偏差 127/255（`check_round255.c` 的 (d) 节）。仍选预乘为主用形式，理由是每帧路径上省一个乘法，素材侧那次量化只做一次；偏差要在素材工具里记着。

> 订正（2026-09-18）：本节先后改过三处。一，原表把预乘 ALPHA 与 CONST 合成一档、称都与顺序有关，那个 4121020 属于 CONST 与非预乘 ALPHA；二，原文称「把中间量饱和到 16 位连 `x = 0` 也会改坏、32640 处不符、模截断 97283 处」，那是穷举工具把 `+128` 加了两次的假象，正确数字是饱和 0 处、模截断 64643 处；三，原文称预乘「让 ALPHA 比非预乘少一次量化」，实际是多一次。过程见 [`spec 第 01 章`](../../Engineering/TechReports/spec/01-逐像素规格.md) 第四节。

*4 混合的通道范围与色键。* **混合只作用于 R、G、B 三个通道。** 源像素的 alpha 只用于
ALPHA / ALPHA_STRAIGHT 的系数和色键比较；它不参与目的像素的运算，也不被写入。
XRGB 源在两种 alpha 方程里的有效 alpha 是 255。**写入 XRGB8888 帧缓冲时 `[31:24]` 必须强制为 0**——否则 COPY 一个 ARGB 源时软件会把 alpha 一起搬过去、硬件清零，两侧后缓冲不同，同帧 CRC 直接不一致。

色键的比较对象是**源表面的 32 位存储字**：XRGB 源的比较值高字节为 0，ARGB 源的比较值包含 alpha。命令里的色键颜色（w5）按同一格式给出，驱动填的时候要与源表面的 `format` 一致。判断写成伪代码，避免「通过之后执行混合」这种正反问都能读的措辞：

```
key_enable = w0[12]
key_word   = w5                          按源表面的 format 解释
src_word   = 源表面 (src_x, src_y) 处的 32 位字

if (key_enable && src_word == key_word)
    skip_write;                          目的像素完全不变，不读也不写
else
    blend_and_write;                     按方程算 R/G/B，写回时高字节按上面的规则处理
```

PREMULT 纹理存预乘后的字，STRAIGHT 纹理存未预乘的字；色键总是比较当前表面实际存储的那一个字。
同一素材若要做两条 alpha 路径的对照，素材包显式存两份，不让硬件猜格式。

*5 坐标、裁剪与 SET_CLIP。* 字段的位宽与符号：

| 字段 | 位宽 | 符号 | 范围 |
| --- | --- | --- | --- |
| 目的 `dst_x`、`dst_y`（w2 两个半字） | 各 16 | 有符号 | `−32768 ~ 32767` |
| 宽 `w`、高 `h`（w3 两个半字） | 各 16 | 无符号 | `0 ~ 65535` |
| 源 `src_x`、`src_y`（w1 两个半字） | 各 16 | 有符号 | `−32768 ~ 32767` |

**中间量一律用 32 位有符号算。** `dst_x + w` 的最大值是 `32767 + 65535 = 98302`，超出 16 位但远在 32 位内，所以规格完整接受命令字段的全部范围，不设额外限制。（本节原先写过「`dst_x + w` 必须能放进 17 位有符号」，那是错的：`w ≤ 65535` 推不出 `dst_x + w ≤ 65535`，已删除。）

执行顺序，空宽高先判，避免 `w − 1` 在无符号下溢：

```
1  if (w == 0 || h == 0)                   整条命令跳过
2  dx1 = dst_x + w − 1, dy1 = dst_y + h − 1      32 位有符号
3  x0 = max(0, dst_x, clip_x0, surf_x0)          四者取最大
   x1 = min(639, dx1, clip_x1, surf_x1)          四者取最小（y 同理）
4  if (x1 < x0 || y1 < y0)                 整条命令跳过
5  逐像素：sx = src_x + (px − dst_x)，越界只跳过该像素
```

裁剪取四者的交集：命令的目的矩形、游戏区 `[0,639] × [0,479]`、`SET_CLIP` 框，以及**目的表面自身的 `[0, width−1] × [0, height−1]`**。取闭区间。

**`SET_CLIP` 的语义：**

| 项 | 规定 |
| --- | --- |
| 矩形来源 | w1 的源 x / 源 y 作左上角，w3 的宽 / 高作尺寸。**其余字必须为 0**，非 0 按 `BAD_FIELD` 报错（2026-09-20 订正：原文写「其余字忽略」，与 spec 第 02 章规范条款 §3“标成 0 的字段必须为 0”冲突；字段合法性以第 02 章为准） |
| 区间 | 闭区间 |
| 复位值 | 上电与软复位后为整个游戏区 `[0,639] × [0,479]`，等价于不裁剪 |
| 生效范围 | **持续生效**，直到下一条 `SET_CLIP` 或软复位；新 `SET_CLIP` **替换**旧框，不与旧框求交，只影响它之后提交的命令 |
| 与游戏区的关系 | 只能把可见范围限制在游戏区内，不能扩到游戏区外；“只能缩小”是相对游戏区，不是相对上一个裁剪框；矩形超出游戏区时按游戏区截断 |
| 空矩形 | 宽或高为 0 表示全部裁掉，之后的命令全部跳过，直到下一条非空 `SET_CLIP` |
| 命令表边界 | 状态在帧之间**不自动复位**；驱动若需要每帧从全屏开始，要在表头显式发一条 |

「持续生效」与「不随帧复位」要一起读：同一个 `LIST_BASE` 被两帧复用、第二帧表头没有 `SET_CLIP` 时，第二帧会继承第一帧末尾的裁剪框。这是有意选择（省一条命令），驱动必须知道。

*6 alpha 为 0 的像素。* ALPHA 方程下 `a = 0` 的像素**照常写目的像素**，写入值与目的原值相同。统一走写回路径，硬件与软件都不按 alpha 值做分支，结果的正确性只由公式保证。读写避让可以做，条件是输出逐像素相同：COPY 且源不透明时跳过读目的、色键命中时跳过写目的、`a = 0` 时跳过写目的都属于这一类。

*7 字节序与内存布局。* RISC-V 小端。帧缓冲的像素字取值是 `0x00RRGGBB`，纹理的预乘像素字取值是 `0xAARRGGBB`（top 8 位在帧缓冲里是 0、在纹理里是 alpha）。小端下的字节位置：

| 格式 | 字节 0 | 字节 1 | 字节 2 | 字节 3 |
| --- | --- | --- | --- | --- |
| 帧缓冲 XRGB8888 | B | G | R | 0 |
| 纹理 ARGB8888_PREMULT | B | G | R | A |
| 纹理 ARGB8888_STRAIGHT | B | G | R | A |

一个 128 位拍正好 4 个像素，拍内偏移 0、4、8、12 依次是 4 个像素的字节 0（B 通道）。行跨取 4096 字节，`addr = base + (y << 12) + (x << 2)`（2.1 节）。

**扫描输出接帧缓冲不需要做字节重排。** 上表说的是字节在内存里的位置，不是字内的位段，两者别混。
一拍的 `[31:0]` 就是像素字 `0x00RRGGBB`（AXI 与 RISC-V 同为小端），所以 `[23:16]` 是 R、`[15:8]` 是 G、`[7:0]` 是 B；
而 `rtl/hdmi/hdmi_tx.v` 给编码器的是 `blue_din = vid_rgb[7:0]`、`green_din = vid_rgb[15:8]`、红取 `[23:16]`。
两边位段完全同序，扫描输出只需要把拍内的 4 个像素按低位在前的顺序拆开，不做任何字节交换。
彩条模块是厂商代码（`rtl/hdmi/`），不改；拆像素这一步放扫描输出一侧。

8 位索引加调色板的格式本设计保留定义但不实现，E7 与直通模式都不涉及。

**流水线分 5 级，每级一次处理 4 个像素（一个 128 位 beat）**

```
级 0  取数     src 字、dst 字（直通模式从 DDR 读缓冲取，条带模式从 BAND 取）
级 1  判定     色键比较，选 Fs / Fd
级 2  乘       DSP，输出寄存
级 3  加与舍入 饱和、÷255
级 4  写回     写缓冲 / BAND；色键命中的像素保持原值
```

吞吐每周期 4 像素。条带模式下数据全在片上，可以复制多条通路按 x 区间并行；直通模式受 DDR3 事务限制，多条通路没有收益。

### 3.6 两种执行模式

**直通模式（P1，满足基础要求）**：命令逐条执行，目的就是 DDR3 帧缓冲。适合大块拷贝和填充，例如整帧背景、大图切换，这时一次突发 160 beat，事务开销被摊薄。

**条带模式（P3，冲 `N_max`）**：借鉴移动 GPU 的分块延迟渲染（tile-based deferred rendering），把屏幕按 16 行一条切开：

1. CPU 生成命令时按条带分桶，每条带一个命令子表。高度不超过 16 的 Sprite 最多落在 2 条带里，分桶是 O(N)。同一条带内保持提交顺序，也就保持了绘制顺序。
2. 引擎逐条带处理：从 DDR3 读背景的 16 行进 BAND（16 次突发），执行该条带的全部命令（纹理来自 TEX 或 DDR3），把 16 行写回后缓冲（16 次突发）。
3. 每帧固定 960 次突发，与 Sprite 数量无关。Sprite 数量只受像素流水线算力限制。

两种模式共用同一套命令格式、同一个像素流水线，区别只在目的地址空间和迭代顺序。

### 3.7 双缓冲与帧节拍

1. 引擎按场同步中断工作。CPU 在帧 N 生成命令表 A，同时引擎渲染帧 N−1 的命令表 B 到后缓冲。
2. 引擎渲染完置 `IRQ_STAT.list_done`，CPU 写 `SWAP_REQ`。
3. 切换在下一个场消隐锁存。如果引擎在场消隐前没画完，这一帧保持前缓冲，这一场记为掉帧（SW8 用场数减切换数算）。
4. 软件渲染模式下同一套切换机制照用，只是后缓冲由 CPU 写。

### 3.8 软件执行器：同一份命令表，两个执行者

赛题要求实时对比软件与硬件帧率。最有说服力的对比是：**同一个游戏、同一份命令表，一次交给 C 语言写的软件执行器画，一次交给硬件画**。这个软件执行器还有第二个用途：它就是硬件的金标准。

- 板上：同一帧命令表软硬各跑一次，比较后缓冲 CRC，作为逐像素一致的上板判据。CPU 读后缓冲算 CRC 之前，按 2.1 节「Cache 一致性」的三条条件失效；加一条注错，跳过这次失效时 CRC 必须不一致。整帧读回约 13 ms（2.1 节估算），按需开启。
- PC 上：软件执行器编进 PC 版游戏，开发游戏和做计算统计都不需要板子。
- 仿真：软件执行器输出的帧作为硬件测试台的期望值。

硬件实现与软件执行器之间的语义差异（舍入、裁剪边界、色键和混合的先后）必须在 3.5 节的表里写死，两边照同一份规格实现。

### 3.9 与通用加速器做法的对照

下面几条是同类加速器上的常见做法，逐条说明本设计取还是不取。

| 常见做法 | 本设计 | 理由 |
| --- | --- | --- |
| 用通用微操作程序表达任意逐元素运算 | 固定流水线加一张混合方程表 | 2D 游戏的像素运算只有五六种，可编程带来的每像素调度开销换不来收益 |
| 算术全程走浮点 | 8 位定点 | 像素本来就是 8 位 |
| 搬运分成描述符、连续段、突发三层 | 保留这三层 | 分层之后上层只描述形状，协议细节收在最底层一份实现里 |
| 底层同时守 4KB 边界与最大突发长度两条限长 | 帧缓冲行跨取 4096 消掉第一条，第二条参数化，等 E4 定值 | 协议要求，且最大突发长度由从机能力决定 |
| 事务超时后排空，不直接回空闲 | 保留 | DDR3 上同时跑着 CPU 的程序，把总线挂死等于死机 |
| GEMM：计数器能对账 | 保留 | 性能分析的前提 |

## 4. 软件设计

### 4.1 做一个游戏是不是异想天开

不是。赛题要的是「简化版」，弹幕射击的机制本身很简单：

- 弹幕只有位置和速度，每帧加一次；
- 弹型用参数方程生成（圆环、螺旋、自机狙、扇形、随机雨），几行代码一种；
- 碰撞只需要判「自机与敌弹」和「自机子弹与敌机」，自机判定点是一个小圆，O(N) 就够；
- 没有物理引擎、没有寻路、没有网络。

纯 C 大约 2000~3000 行能完成一个可玩的关卡。真正难的是让它在 116 DMIPS、无 FPU 的 CPU 上跑到几千个弹幕，这正是本设计要解决的问题。

### 4.4 软件分层

**定稿 2026-09-19（SW1 实现时回改）。** 分层由编译结构保证，不靠约定：每一层只看得到自己该看得到的头文件。
`sdk/` 是 SoC IP 的生成物、重新生成时整体被覆盖，所以**只读**；项目自己的一侧是叠在它上面的板级层：

```
Main/sw/
  mk/           两套构建：target.mk 板上（xPack gcc + sdk 的 BSP）、host.mk PC（WSL gcc + SDL2）
  bsp/          项目板级层，叠在只读的 sdk 之上
    include/    board.h（板级接口）、memmap.h（DDR 分区的偏移与大小，见 2.1 节）
    ti60/       板上实现 + linker/gfx2d.ld（项目链接脚本，栈 64KB）
    host/       PC 实现：SDL2 窗口与键盘，DDR 分区用一块内存模拟
  lib/          纯 C，两边都编，不依赖任何平台
    core/       定点、CRC32、xorshift32、正弦表、轻量格式化输出
    gfx/        命令表构造、软件执行器（3.8 节，SW3 落地）
    test/       主机侧单元测试
  apps/         应用，按用途分三类：game/（游戏与演示）、test/（回归判据）、probe/（探针与 benchmark）
    game/gfx2dGame/  游戏逻辑（实体池、弹型、碰撞、关卡脚本）与 main.c
  tools 一侧    素材工具：PNG → 预乘 ARGB 图集 + 索引头；素材包打包进 Flash 镜像
```

依赖方向只有一个：应用 → `lib/` 与 `bsp/include/board.h`；`board.h` 由 `bsp/ti60` 或 `bsp/host` 实现。
编 `lib/` 时只有 `-Isw/lib`，看不到 `board.h`；编应用时没有 sdk 的头文件路径。
PC 在这套结构里就是「另一块板子」，与 Zephyr 的 `native_sim` 同一种做法。

实现约束：

- 无 FPU：位置与速度用 int32、低 8 位为小数的定点（原定 Q12.4 的速度分辨率只有 1/16 像素/帧，
  慢速圆环飞几百帧会明显变形，数值实验见 `Engineering/TechReports/sw/06-游戏本体.md` 3.2 节）；
  角度用 16 位二进制角，查 1024 项的正弦表，atan2 只在发射时用。
- 实体布局首版先用结构体数组（AoS），并把池访问集中封装以便替换。
  E8 同逻辑合成负载的 4KB 档测得 AoS 49.05、SoA 71.47 周期/弹幕/帧；
  16KB 档 SoA 的劣势缩到约 16%，仍未反超。真实游戏还包含压缩、碰撞和构造层，
  最终布局由 SW7/SW9 的完整帧分段决定。
- 不在每个弹幕上调用函数指针；弹型在发射时算好参数，更新循环只做加法。
- 离屏弹幕立即回收，实体池固定大小，不用 `malloc`（`bsp/host` 分配模拟内存不受这条限制）。
- 同一份 `lib/` 与应用在 PC 和板子上编译，PC 版先跑通再上板；应用里不出现 `#ifdef` 平台判断。
- 程序放 `Main/sw/` 下，用项目的两套构建（`sw/mk/target.mk`、`sw/mk/host.mk`），不放进 `sdk/`。
- 分层是可判定的：`Main/tools/check/check_sw_layers.sh` 逐条验证（越界 include 编不过、同名目标文件、
  软浮点符号、`sdk/` 无改动）。落地与踩坑见 [`Engineering/TechReports/sw/01-软件平台分层与双目标构建.md`](../../Engineering/TechReports/sw/01-软件平台分层与双目标构建.md)。

### 4.5 计算类型统计

**这一节的数字是按场景参数推算的模型，不是实测。** 实测靠 4.6 节的计数器，PC 版游戏做出来后先在 PC 上跑出第一版真实统计。
第一版实测（PC，2026-09-28）已出：S1 规模（模式 3 固定旋钮 1744，约 2040 颗 16×16 敌弹）每帧 872,384 像素，COPY 38.8%、ALPHA 61.2%、ADD 0，命令 2,248 条；与本表的逐项对照与差异解释在 [`../../Engineering/TechReports/sw/07-演示模式与统计埋点.md`](../../Engineering/TechReports/sw/07-演示模式与统计埋点.md) 3.12 节。差额主要来自弹的尺寸（本表按 12×12，K2 定案用 16×16）。

场景 S1：游戏区 400×480，Boss 弹幕段的典型一帧。

| 运算类别 | 对象 | 个数 | 单个尺寸 | 像素数 | 每像素运算 |
| --- | --- | --: | --- | --: | --- |
| COPY 不透明 | 滚动背景 | 1 | 400×480 | 192,000 | 读 + 写 |
| COPY 不透明 | HUD 底图 | 1 | 240×480 | 115,200 | 读 + 写；可优化为只在分数变化区重画 |
| COPY + 色键 | 敌机 | 20 | 32×32 | 20,480 | 读 + 比较 + 写 |
| COPY + 色键 | 自机 | 1 | 32×32 | 1,024 | 同上 |
| COPY + 色键 | HUD 文字 | 60 | 8×16 | 7,680 | 同上 |
| ALPHA（预乘） | 敌弹 | 2,000 | 12×12 | 288,000 | 读源 + 读目的 + 3 乘 + 3 加 + 舍入 |
| ADD | 自机子弹 | 40 | 8×16 | 5,120 | 读源 + 读目的 + 3 饱和加 |
| ADD | 爆炸与粒子 | 200 | 16×16 | 51,200 | 同上 |
| CONST | 受击闪白 | 0~1 | 400×480 | 0~192,000 | 3 乘，偶发 |
| FILL | 血条、边框 | 若干 | — | 约 2,000 | 写 |
| **合计** | | **约 2,320 个 Sprite** | | **约 68 万像素（约 2.2 倍屏幕）** | |

从表里读出的结论：

1. **按个数，86% 是小尺寸的 ALPHA 敌弹，而且只用少数几种纹理**。热纹理缓存加条带模式正是为它们准备的。
2. **按像素，COPY 占 45%、ALPHA 占 42%**。COPY 集中在两张大图上，走长突发很便宜；ALPHA 分散在几千个小矩形里，事务开销才是大头。
3. **乘法**：每帧约 86 万次 8 位乘法，全部来自 ALPHA。流水线每周期 4 像素、12 个乘法，约 7.2 万个周期、0.72ms 就能做完，算力不是问题。
4. **FILL 几乎可以忽略**，但它是赛题基础要求，必须有。
5. **CPU 侧**每帧要更新 2,000 个弹幕、写约 74KB 命令表（2,320 × 32 字节）。`N` 冲到上万时，这部分会先撑不住（3.1 节）。

场景 S2（压力测试）只把敌弹数 `N` 当变量，其余同 S1。每加 1,000 个 12×12 弹幕，多 14.4 万像素、43.2 万次乘法、3.2 万字节命令。

## 6. 容易漏掉的规划项

1. **验证策略。** DDR3 控制器与 `axi_interconnect_beta` 是加密的，SoC 网表里也有两个 CPU 运算模块（`EfxCPUSp1`、`EfxCPUSp2`）加密，iverilog 仿不了整机。分三层：
   - 引擎单元仿真：自写 AXI 从机模型，必须带随机反压、可配的突发长度上限和响应延迟。一条同类工程的教训是：测试台里的从机比真从机强，等于没验。
   - 金标准：软件执行器输出的帧，逐像素比较。
   - 上板：同帧软硬件 CRC 对比，经串口报告。每条判据按 SOP 先注错见红。
   - `Axi_Mux.v` 是明文，实际授权序列、在途契约与 `axi_mux_guard` 可先在仿真里验证；真实 FIFO 水位仍须上板测。
2. **错误通路。** 突发超时、`RRESP`/`BRESP` 非 OKAY、命令越界，都要置粘滞错误位和序号、发中断，超时后排空再回空闲（3.9 节）。别等出事了才补。同类工程上出现过错误上报整条通路是死的、事后才发现的情况。
3. **时序。** 像素流水线每级寄存；DSP 输出寄存；按手册建议，高频下布局布线用 TIMING_1。每次加模块看 WNS/WHS 有没有被挤。
4. **素材流水线。** PNG 到预乘图集的工具、素材包格式（目录头 + 数据）、Flash 镜像合成（比特流 + 程序 + 素材）、启动装载与校验，都要在 M3 之前做完。
5. **规则风险。** P4 把弹幕运动交给硬件，可能被认为不是「在 RISC-V 上运行游戏」。建议：规则、发射、碰撞结果处理始终在 CPU；硬件只做运动学和绘制；保留纯 CPU 运动模式作对照，报告里写明两种模式各自的 `N_max`。
6. **分辨率余量。** 行跨 4096 最多支持 1024 宽。以后想上 1280×720 要改为 8192 跨，同时换 PLL（74.25MHz），扫描带宽约乘 3。现在只把行跨做成参数。
7. **开发环境与硬件。** 工具链清单与全部操作命令见 `开发环境.md`。工程由 2025.2 生成、用 2026.1 编译，升级 SoC IP 时要同步软件包并恢复 `sdk/` 的登记项，见 `../sdk/README.md`「重新生成 SoC IP 时」。PC 版游戏和引擎单元仿真不依赖这套工具，可以先做。
8. **交付物。** 源码、报告、演示视频（赛题一的宣讲里鼓励 B 站风格短视频，赛题二可以照做）。提交截止时间资料里没找到，以官方通知为准。
