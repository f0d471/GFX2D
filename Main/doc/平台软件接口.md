# 平台软件接口与职责契约

## 1 范围与职责

应用只表达内容、规则、场景与资源需求。公开平台 API 提供显示、输入、单调时间、
只读资源与持久化服务；应用不操作寄存器、设备地址、缓存行、IRQ、TEX 或交换寄存器。
宽高、像素格式、pitch 属于正常图像接口，允许应用查询，不允许假定固定物理布局。
低层 gfx ABI 保留给图形运行时与诊断消费者；不把它强行伪装成通用游戏 SDK。

| 层 | 允许依赖 | 禁止依赖 |
|---|---|---|
| 公开 API 消费者 | api/、标准 C、自己的内容 | bsp/、sdk/、其他应用私有目录 |
| 纯库 | lib/、标准 C | BSP、操作系统、SDL |
| 服务/图形运行时 | api、lib、BSP 服务 | 游戏规则、应用注册表 |
| 平台/固件适配 | BSP、OS、服务 | 敌机/关卡/场景实现 |
| 内容适配 | 应用框架、图形运行时、自己的资源 | 厂商头、寄存器写入 |

目录与信任边界必须由真实编译命令和负向包含检查执行。保留的旧判据入口是低层
诊断消费者，不能把其允许的设备接口扩散到新 SDK 应用。

## 2 必需技术债编号

| 编号 | 契约 |
|---|---|
| A01 | 通用应用生命周期头不包含 stg/R4；内容能力和恢复由注入回调提供 |
| A02 | 引擎提交/等待/恢复的通用 renderer 离开游戏目录，两个入口共用 |
| A03 | 新 SDK 使用带代次的帧句柄；不公开命令表和物理表面表 |
| A04 | 通用资源机制与具体素材描述分离，内容保留自己的槽位/热集策略 |
| A05 | 两个独立 SDK 示例，仅用公开头，公共底层不因第二个消费者改变 |
| A06 | 引擎等待允许 RTOS 阻塞协作；裸机保持受控轮询 |
| A07 | 所有声明为时间的上界读取单调计时，不用轮询次数冒充秒 |
| A08 | 输入采集/解码移出任务临界区，单次字节处理有预算 |
| A09 | 输入动作/组合策略离开板级事实接口，旧键位数值与线协议兼容 |
| A10 | 单实例服务有明确所有者；通用框架使用不含具体游戏的配置 |
| A11 | 产品 scheduler/config 与平台时间适配归固件/系统，不扩散至内容 |
| A12 | 新等待返回完成/超时/退出/设备错误，旧 void 包装仅为兼容入口 |
| A13 | 产品与旧判据共用机制，原确定性/CRC 不通过更新 golden 掩盖 |
| A14 | SDK 构建与独立例子不链接现有游戏，禁止平台条件宏进入 SDK 消费者 |

## 3 显示、输入、时间与资源

帧状态为 FREE→ACQUIRED→PENDING→FREE。只有 ACQUIRED 帧可映射写入；提交失败不
转移所有权，提交成功后调用者停止访问；完成确认后释放，旧句柄因代次变化失效。
只允许一个 pending 呈现，忙态明确返回；关闭或设备错误不登记虚假的呈现完成。
服务负责在首次获取和交换之间维护扫描面所有权，应用无需知道 FB0/1。

输入提供状态和按下/松开事件；板级采集仍有 GPIO/串口实现。产品动作由独立输入
映射策略产生。BSP仅返回分开的物理/远程样本，输入服务组合与映射；BSP不反向
调用产品策略。单调时间以毫秒表示，截止时间采用无符号差值或足够宽的计数。
资源读取始终带长度与边界，错误不会假装读满。

## 4 应用框架

应用声明稳定 ID、名称、enter/frame/leave；框架持有不透明用户指针和服务回调。
进入成功后才提交活动状态；退出必须完成资源交接。进入/绘制/退出失败先停止活动
应用，再确认底层恢复、完成局部清理并进入菜单。恢复失败保持 fault，可显式重试。
能力判断、后端/场景遥测属于内容提供的查询；框架不硬编码 R4 ID 的设备依赖。

## 5 产品服务机制与边界

P01：持久化记录包含版本、序号、长度、CRC；双槽提交，损坏/中断写后仍可读取最后
有效版本。PC 后端真实执行文件读写并注入中断阶段；目标后端没有获准分区时明确
NOT_SUPPORTED，禁止占用现有程序/素材区域。机制通过不等于 Flash 掉电板测通过。

P02：健康服务登记关键执行者与期限；独立检查实际进展，区分启动宽限、健康、停滞
和恢复。保存错误与恢复次数；硬件 watchdog 接线/复位策略必须另有板端证据。

P03：固件镜像验证包含长度、版本、目标兼容标识与负载 CRC，拒绝截断、越界与错配。
验证和选择策略使用独立 PC 反例。既有 bootloader/Flash 布局本轮不切换，不改生成 SDK；
运行时 boot 集成、双槽 Flash 容量与断电更新是明确的后续硬件工作。

实体控制器、音频等依目标产品立项；本轮不能凭 PC 输入或静音后端宣称外设已实现。

## 6 验收范围

`platform-sdk`覆盖PC正常/故障、64/32位、sanitizer、公开头隔离和独立消费者；原有
菜单/内容及确定性由直接消费者检查。PC耗时不能生成板端性能结论。

`sw16-board`在Windows使用既有B7快照，以JTAG装载新编译软件；核对引擎、公开SDK的
完整DDR帧CRC/JTAG抽样/实际交换计数、RTOS五应用与故障恢复，以及R4完整板端判据。
物理检查不复用旧设备状态，正常结束或失败均恢复正常菜单并释放串口。
该入口不重建RTL或修改硬件ABI；验收使用acceptance，quick不能代替完整节拍。

Flash上电启动、目标持久化/断电更新、硬件watchdog、实体控制器与HDMI人工观感均是
单独边界，JTAG运行不替代这些结论。真实IRQ运行与时钟进展也不等于已测得最坏IRQ时延。

## 7 底层维护阅读顺序

1. `sw/api/platform.h`：应用可见的最小契约与所有权。
2. `sw/services/platform/platform.c`：获取、映射、提交、完成与故障状态。
3. `sw/bsp/include/board.h`与`gfx_engine.h`：设备服务、提交与完成的区别。
4. `sw/bsp/ti60/board.c`、`board_irq.c`、`gfx_engine.c`：真实寄存器、计时、缓存与IRQ。
5. `sw/services/gfx`与`sw/lib/gfx`：通用执行、资源租约、ABI及软件参考。
6. `sw/runtime`、`sw/system`、`sw/rtos`与`sw/firmware`：生命周期、OS集成和组合根。
7. `sw/lib/core/record`、`firmware_image`与`health`：持久化、校验及监督的纯机制。

无需阅读敌机/关卡/UI实现即可维护这些接口。仍需了解内容的资源预算与时间要求。
新SDK当前用于独立固件/显示所有者，初始化要求端口定义的启动状态；不支持与旧
底层显示入口并行或对仍运行的扫描器热接管。现有Myriad兼容端口不是通用引擎兼容层。
SDK板端检查以重新配置位流后的启动状态初始化；实际Flash启动与扫描器热接管仍需
独立设计及判据，不能从PC模型或冷启动JTAG运行推导。
