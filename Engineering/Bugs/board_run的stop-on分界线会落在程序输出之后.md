# `board_run.py` 的 `--stop-on` 分界线会落到程序输出之后，把通过的运行报成失败

状态：**未修复。** 只影响上板工具的退出码，不影响任何 RTL、比特流或程序；
串口日志本身是完整的，`fail 0` 照常在里面。回归表按退出码判读时会得到假红，
所以**看到 `ERROR: N 秒内没有收到 'fail '` 时要翻一下日志**，不要当成程序失败。
不阻塞任何工作点。

## 1 症状

2026-09-21 在扫描输出快照缺陷的复验里，同一条命令跑同一个程序，退出码在 0 和 1 之间漂。
失败那次的输出（`--seconds 200`，程序实际只跑约 20 秒）：

```
   7018 bytes written at address 0x00001000
   downloaded 7018 bytes in 0.365347s (18.759 KiB/s)
...
T10 ok
T11 n=1000 ticks empty=8017 all=75080 addr=12076 two_hits=9084 two_misses=147955
T6 ok
fail 0
done

# --- 程序已加载，以下才是它的输出 ---

# closed 22:56:29, 1160 bytes
```

分界线落在**整份输出之后**，而 `--stop-on` 只在分界线之后匹配，于是主线程报
`ERROR: 200 秒内没有收到 'fail '`、退出码 1，尽管 `fail 0` 与 `done` 都已经收到了。

## 2 复现

比特流：`fpga/gfx2d_ti60/outflow/gfx2d_ti60.bit`（任意一版都行，与比特流无关）。
程序：`sw/apps/probe/cacheMechTest`、`sw/apps/probe/ddrAliasTest` 都复现过。

```
board_run.py --bin <程序.bin> --stop-on "fail " --seconds 200
```

不是每次都发生，连跑几次会看到退出码在 0 和 1 之间变。
判读方法：看日志里 `# --- 程序已加载` 这一行的位置——正常在程序横幅之前，出问题时落在 `done` 之后。

## 3 影响面

只影响 `tools/board/board_run.py` 的退出码与那一行 `ERROR`，日志内容与板上行为都是对的。
回归表里所有用 `--bin` + `--stop-on` 的项都可能中招（实测 `cacheMechTest`、`ddrAliasTest`），
`--cmd`、`--check-only` 两条路径不走这段逻辑，不受影响。

## 4 定位过程

- 先排除程序本身：日志里 `T1`~`T11` 每组 `ok`、`T6 ok`、`fail 0`、`done` 齐全，与登记的期望值一致。
- 再排除采集时长：把 `--seconds` 从 60 加到 200 之后仍然复现，而程序只跑约 20 秒；
  日志末尾的 `# closed` 时间戳显示采集确实跑满了整个窗口。
- 分界线的位置是直接证据：它由 `serial_worker` 在观察到 `armed` 置位的那一刻写进日志，
  落在 `done` 之后就说明 `armed` 是在程序跑完之后才被置位的。

## 5 根因

`main()` 里 `armed.set()` 排在 `run_openocd(load_cmds)` **返回之后**，
而 `run_openocd` 用 `subprocess.run` 等 OpenOCD 进程整个退出。
`load_cmds` 的最后一条是 `shutdown`，正常情况下 OpenOCD 在 `resume` 之后一两秒内退出，
分界线就落在正确的位置；但它的退出并不总是这么快，慢到程序已经打完的时候，
分界线就落到了整份输出之后。

也就是说，分界线标的是「OpenOCD 进程退出」而不是「`resume` 执行完」，
这两件事之间的间隔不受控制。匹配窗口的起点因此可能晚于新程序的全部输出。

## 6 修法与验证判据

还没有修。两个方向，各有取舍，要先想清楚再动：

- **让 `armed` 在 `resume` 之后立刻置位**，不等进程退出。要改成边读 OpenOCD 输出边判断
  （例如看到 `resume` 对应的输出行就置位），比现在的 `subprocess.run` 复杂；
  好处是分界线标的就是它应该标的那件事。
- **改成按内容分界**而不是按时刻：加载之前先记下已收到的字节数，
  新程序的横幅（每个程序开头都打自己的名字）出现在那之后才算数。
  实现简单，但要求每个程序都打横幅，等于加一条新约定。

**不能**退回成「不设分界线」：那正是 2026-09-21 记进 `tools/board/README.md` 第 5 条的假绿——
烧完比特流板子会从 Flash 自启动，上一份固化的程序同样打 `fail 0` 与 `done`，
直接匹配会在新程序一行都没输出的时候报成功。这条缺陷是那次修复的反面，
修它的时候两个方向都要用判据钉住。

验证判据（修完要同时成立）：

1. 正常路径：连跑 `cacheMechTest` 与 `ddrAliasTest` 各 5 次，退出码全 0，
   日志里 `# --- 程序已加载` 都在程序横幅之前。
2. 假绿路径：**不加载程序**、只烧比特流让 Flash 里的 `bootSizeTest` 自启动，
   用 `--stop-on done` 跑，必须报失败——现在这条是靠分界线成立的，不能改丢。

## 7 判据缺口

工具自己没有判据。`tools/board/README.md` 只写了退出码 0 的四项正面证据，
没有反过来要求「退出码 1 时确实没有收到那段文本」，所以假红没有任何东西拦得住。
第 6 节的两条判据就是补这个缺口：一条守正常路径，一条守它当初要防的假绿路径。
