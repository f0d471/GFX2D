# Engineering

工程的跨时间文档：每一步为什么这么做、对仓库做了什么、做完之后是什么样。

与其它文档的分界是体裁，不是主题。仓库里其余的 README 和 `doc/` 下的文件登记**当前状态**，
看一眼就知道现在是什么样；本目录记录**过程**，回答为什么变成这样。
同一件事在两边出现属于正常。

## 目录

| 目录 | 收录范围 | 维护方式 |
| --- | --- | --- |
| [TechReports/](TechReports/) | 每个工作点的开发过程 | 一个主题一个系列，完成一个工作点增加一章，写完定稿 |
| [Todo/](Todo/) | 未完成事项的 spec 与开发日志 | 完成后删除文件，内容并入 TechReports |
| [Bugs/](Bugs/) | 未修复的在产缺陷 | 修复后删除文件，内容并入 TechReports |

当前实现是什么样，由 [`../Main/rtl/README.md`](../Main/rtl/README.md) 等目录 README
与各模块的文件头说明，本目录不重复。

## 流转规则

1. 开工前在 `Todo/` 建立文件，写明要解决什么、如何切分、判据是什么。
2. 开工后同一文件继续记录，用作开发日志。
3. 过程中出现修不掉的问题，在 `Bugs/` 另开一条，注明现有判据为什么没有覆盖到它。
4. 工作点完成并上板通过后，在 `TechReports/` 对应系列增加一章，小工作点补进已有章节。
   需要前期研究或实验取样的，研究过程、取样数据和对它们的解释写进这一章，开发日志里只留流水。
5. 同步更新受影响目录的 README，让它们继续反映当前状态。把 `Todo/` 中该文件的状态改为「待验收」。
6. **用户验收之后**才删除 `Todo/` 中该文件。验收前开发日志保留，作为对照 TechReports 的原始流水。

## 与 doc/ 的分工

| 位置 | 回答什么 | 体裁 |
| --- | --- | --- |
| [`../Main/doc/赛题二总体设计.md`](../Main/doc/赛题二总体设计.md) | 打算怎么做，指标口径与资源划分 | 方案 |
| [`../Main/doc/开发环境.md`](../Main/doc/开发环境.md) | 工具怎么装、每一步操作的命令是什么 | 手册 |
| 各目录的 `README.md` | 这个目录下有什么，能不能改，现在到哪一步了 | 登记 |
| `TechReports/` | 因果链：为什么是这几步、改了哪里、改完是什么样 | 记述 |

过程性的内容不留在 `doc/` 和 README 里。开发日志进 `Todo/`，完成之后并进 `TechReports/`，
`doc/` 与 README 只留结论。

## 约束

- `Todo/` 与 `Bugs/` 只收未完成项，不保留已完成条目的记录。
- `TechReports/` 定稿后不追加章节来更正旧章。结论被后续实测推翻时回原章订正，
  在订正处写明日期与推翻它的那次实测。
- `Bugs/` 的每一条都要回答现有判据为什么没有覆盖到该缺陷。
- 不写绝对路径。需要引用工具安装位置时用 [`../Main/doc/开发环境.md`](../Main/doc/开发环境.md)
  第 1 节的占位符。
- 各目录的写作规范见其自身的 README。
