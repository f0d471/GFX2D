**01 · P1：定时器寻址错误，且硬件诊断依据错误**

位置：`Main/sw/rtos/rtos_irq.c:103`、`Main/sw/apps/console/src/FreeRTOSConfig.h:67`。

- 配置和 SDK 给出的 mtime 地址是 `0xf8b00000 + 0xbff8 = 0xf8b0bff8`；初始化函数实际使用 `0x0f8bbff8`，少一个十六进制位。
- 本轮构建的反汇编也确实从错误地址加载，排除了只改注释/未进入实际 BIN 的可能。
- 板上同次读取：正确地址为 `68efd536 00000004`，错误地址为 `fbf7ef77 f6f7fb6f`，比较寄存器读回为 0。
- 隔离诊断使用正确地址时，100Hz 档两秒收到 199 次中断，1kHz 档两秒收到 1998 次中断，异常中断均为 0；比较寄存器读回依然为 0。

结论：比较寄存器读回 0 不能作为 timer 不工作的证据。当前 B7 硬件已经能产生毫秒量级的 machine timer 中断，原“必须先改 SoC 才能用毫秒 tick”的前提不成立。这里没有证明完整 FreeRTOS 1kHz 移植已经通过；应先修正软件地址、使用同源地址定义，再重新验证端口。诊断代码、汇编、原始日志分别见 `timer_probe/`、`build_console/console-O2-perf.asm`、`clock-address-readback.log`、`timer-audit.serial.log`、`timer-audit-1k.serial.log`。

另一个静态问题：即使地址正确，`mtime + 0x7fffffff` 在 100MHz 下也只是约 21.47 秒以后，不能称为永久屏蔽。若选择场中断 tick，应明确屏蔽 machine timer 或设置有定义的长期策略。

**02 · P1：enter 失败后仍执行失败应用**

位置：`Main/sw/apps/console/src/appfw.c:178`。

`switch_to()` 先离开旧应用并写 `s_active = next`，随后调用 `enter()`；失败仅写一行日志，不回滚、不退到安全菜单，也不禁止后续 `frame()`。实际 runner 源码宿主故障探针输出：

```
FAILED_ENTER active_is_failed=1 failed_app_frame_calls=1
```

资源、素材或引擎准备失败时，后续帧可能使用未准备好的表面/状态。这是已复现的状态机问题；本轮没有在板上故意制造 DMA 内存破坏。修复应使“进入成功”成为活动状态的前置条件，并定义失败后的排空、清理与恢复路径。

**03 · P1：错误返回没有贯穿应用生命周期**

位置：`appfw.h:35`、`shell.c:184` 与 `shell.c:247`、`app_game.c:63`、`app_game.c:88`、`app_about.c:142`。

- `frame` 和 `leave` 都是 void，框架无法据返回值阻止下一次执行或切换。
- 菜单把构建/渲染/呈现错误累加到 `bad`，最终 `(void)bad`；渲染失败后仍可能请求显示该帧。
- 游戏退出/切后端忽略 flush 失败，继续重置状态或重配后端；关于页也吞掉构建与部分呈现错误。
- `rt->fails` 没有成为框架恢复或结束判据。

风险：故障被藏成黑屏、旧画面或错误资源交接；在排空失败时继续重配可能破坏在途事务的资源所有权。这是静态确认的错误路径，未将其写成已经发生的板上数据破坏。应统一 enter/frame/leave 的结果、失败状态和资源排空策略。

**04 · P1：RTOS 任务的进展依赖渲染实现**

位置：`appfw.c:262`、`appfw.c:325`、`board.c:326`、`r4_render.c:754`。

游戏/三维路径仍包含忙轮询，runner 持续就绪，monitor 提高到优先级 4 才避开饿死。注释明确低优先级任务会饿死；因此后续增加相机、存储等任务时，合理的低优先级后台任务也不能保证运行。菜单/关于页已经有等待帧信号量的路径，所以不是每个页面每时每刻都忙轮询。

tick 又依赖场中断；场中断被屏蔽或显示控制异常时，输入与监控的 Delay 也失去推进。这里不是说“拔 HDMI 线就会停 tick”，本轮没有做这种物理实验。应把 RTOS 独立时间基准、渲染节拍和输入/导航响应分开，并让等待驱动提供可阻塞、可超时的实现。

**06 · P2：两个运行框架造成产品能力分叉**

位置：`console/makefile:3`、`apps_registry.c:15`、`gfx2dGame/main.c:1039`。

PC/旧板端入口拥有基础 Demo、2D 游戏、压力测试、三维四模式；console 只有菜单、弹幕、三维、系统信息，未适配基础 Demo 与压力测试。PC 本轮 60 帧合成键实跑仍能进入四模式，因此“旧功能进不去”不是旧实现被删，而是新框架漏接。

PC 使用桌面 OS、板端使用 FreeRTOS 本身合理；产品菜单、应用列表和导航另写两套并非必要。应共享平台无关的应用管理/导航逻辑，由宿主循环和板端 runner 分别驱动。

**07 · P2：菜单把自己当成可启动内容**

位置：`apps_registry.c:15`、`shell.c:99`、`appfw.c:269`。

菜单直接枚举 `[menu, stg, r4, about]`，默认选中第 0 项 menu；按确认请求当前应用，被 runner 的相同应用过滤掉，因此默认确认看起来没有反应。数字 1 也只请求菜单自身。应用注册顺序同时决定显示顺序和快捷键，插入/排序会改变按键含义。

应将系统入口与可启动内容分开，并给应用稳定 ID、显示名称、可见/可用状态、快捷命令等显式元数据。

**08 · P2：数字键和系统导航没有统一语义**

| 场景 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| PC / 原 gfx2dGame | 基础 Demo | 2D 游戏 | 压力测试 | 三维；三维内切场景 |
| console 菜单 | 菜单自身 | 弹幕 | 三维 | 转发成 1+2+3，作为 HOME 组合 |
| console 弹幕 | 不切应用 | 不切应用 | 不切应用 | 满足保持条件后回菜单 |

位置：`main.c:1460`、`shell.c:104`、`app_game.c:120`、`app_r4.c:85`、`input_forward.py:49`。

本轮板测在弹幕里发送 1 和 3 均未离开弹幕；发送 4 对应组合后才回菜单。应先在系统层识别“启动某应用/返回/确认”，消费对应事件，再把剩余按键交给应用。不能靠每个应用自己避让系统组合。

**09 · P2：启动键被新应用再次使用**

位置：`appfw.c:43`、`shell.c:110`、`app_r4.c:79`。

输入在切换中继续累积，新应用的前一帧键值被清零，启动时的 MODE3 随后又被视为 R4 内的场景切换沿。

本轮同一源码/BIN 的板上对照：

- 数字 3 进入：先 `r4 enter`，接着 `r4 leave frames/late 0 0`，再次进入；后续 R4STAT 的 scene=1，是茶杯。
- 方向选择＋确认进入：没有这次额外重进，scene=0，是走廊，持续 30 FPS。
- 宿主实际 app_r4.c 探针：`scene_after_number3=1 restart_requested=1`。

两条路径显示不同内容，不能把茶杯的 12～14 FPS 与走廊的 30 FPS 当成 RTOS 性能退化对比。应在切换边界消费启动事件，并规定按键释放/继承策略。

**10 · P2：HOME 的时间语义随应用改变**

位置：`appfw.c:262`、`app_r4.c:89`、`chord.c:14`。

chord 的 8 次计数发生在 runner 迭代中。R4 发现完整 HOME 组合后直接 return，不渲染、不等待，于是 runner 可空转凑满 8 次。实际源码宿主探针为：

```
HOME_CLOCK board_fields_during_hold=0 r4_rendered_frames=0 returned_to_menu=1
```

相反，SW 渲染每次应用帧约需近一秒，HOME 就会迟迟达不到 8 次。本轮后端往返中 SW 的原始统计约 2 FPS（窗口计数），可见渲染速度确实影响这一路径。纯计数器的 11 项通过无法覆盖这种集成错误。

应使用统一时间基准定义保持时长，并让导航响应不依赖应用完成了多少次渲染。

**11 · P2：当前实体按键不足以操作游戏机前端**

位置：`Main/sw/bsp/ti60/board.c:204`、`shell.c:104`。

板载 KEY0～3 仅映射左/下/上/右；菜单确认要求 BOMB，HOME 要求 MODE1|MODE2|MODE3。现有板载四键没有生成这些动作的路径。因而当前前端尚不能凭这四键完成“选应用→进入→返回”的独立操作闭环，需要 PC 转发或另行接入的手柄。这里来自完整软件映射核查，本轮没有声称已经验证外接独立手柄。

应明确实体四键、PC 键盘、手柄都能生成的确认/返回/导航动作，必要时版本化扩展输入协议。

**12 · P2：关于页的返回操作未实现**

位置：`app_about.c:5`、`:84`。

文件声明 BOMB/HOME 退出，但 frame 完全忽略 keys，只能依赖框架 HOME。本轮板测从 about 按 BOMB、1 都未返回，直到 HOME 才离开。应实现并显示统一 BACK 动作，而不是页面注释与实际行为各一套。

**13 · P2：控制面板没有消费 console 的状态协议**

位置：`Main/tools/board/game_control.py:38`、`:156`。

当前解析器认识旧 CSV、mode enter、R4STAT，不认识 console enter/leave、menu fps、stg fps。本轮把真实板测日志送入实际 BoardState：

- 03 号日志最终已回 menu，面板仍为 `mode=r3d, fps=30`。
- 再送入 05 号日志（最终仍是 menu），面板仍为 `mode=r3d`。

面板的“3D / 茶杯 [4]”仍发送旧 0x380，在 console 中实际属于 HOME。模式、后端与动作不匹配会造成操作无效和误导状态显示。应建立版本化状态/命令协议，面板按固件声明的应用和能力生成控件。

**14 · P2：共享运行时尚未成为唯一实现**

位置：`gfx2dGame/main.c:151`、`apps/common/stg_runtime.c:83`、`console/makefile:20`；已有待办 `Engineering/Todo/sw/启动序列去重.md`。

boot/素材/TEX/后端管理仍有两份；console 通过路径和通配列表编译旧游戏内部源码，缺少稳定的应用级接口。原 main 还带注错、影子对拍和 mode 感知能力，不能简单删除替换。新增应用若继续复制适配器和启动段，维护与验证负担会继续增长。

应先盘点并合并这些能力，再让两个入口共用；资源所有者与切换排空契约要由框架协调。

**15 · P2：PERF 同时决定日志与实际执行能力**

位置：`console/makefile:14`、`renderer.c:234`、`stg_modes.c:179`。

SW9_PERF 同时影响引擎流水启用、逐帧 CRC/普查以及产物类型。console 必须强制 PERF=1 才获得预期的执行路径，既有联调已经踩过“打开/关闭性能档，实际游戏路径与帧率发生巨大变化”的问题。

日志/对拍强度与渲染后端/流水策略应为独立配置，诊断版本也应能明确验证正在运行哪条后端路径。

**16 · P3：统计单位与文档仍有可见误导**

位置：`app_about.c:100`、`shell.c:207`、`app_game.c:158`、`appfw.c:9`、`Engineering/Todo/README.md:49`。

- UPTIME MS 直接显示 tick 数，当前 60Hz 下不是毫秒。
- 菜单/游戏把超过一秒窗口中的 swap 次数直接标成 FPS，不按实际窗口时长归一，所以日志可能写 61 FPS；不应直接当作精确 61Hz 运行结论。
- appfw 文件头仍写 monitor 优先级 1，实现已经为 4；Todo 总索引仍写 RTOS 进行中，单项已待检阅。
- 菜单页脚每次进入把选择复位为 0（菜单自身），原先选择不保留，进一步放大“返回后确认没反应”的体验。

**建议的目标机制与修复顺序**

1. 先修定时器地址/独立 tick、应用失败状态机、排空和帧失败的处理，并补能抓住这些缺陷的反例。
2. 建立共享应用管理器：PC 与板端默认进入同一菜单，开发/测试入口可显式指定应用；宿主循环和 FreeRTOS runner 仅负责驱动方式。
3. 固定应用 ID：1 基础 2D 演示、2 弹幕游戏、3 压力测试、4 三维。菜单与系统信息属于系统页面，不挤占内容快捷键。
4. 系统先处理启动/确认/返回/HOME；应用只收到剩余业务输入。三维场景、L1/L2、后端分别用明确动作，不复用全局启动键。
5. 补齐四种输入来源的可达映射、共享启动能力、当前控制面板协议；最后补全 PC 菜单测试、真实应用出帧与连续切换/故障恢复判据。

不需要为了 PC 与板端入口一致而让 PC 跑 FreeRTOS。需要共享的是产品应用模型、导航语义和生命周期，而平台驱动、任务调度和显示实现保留各自实现。
