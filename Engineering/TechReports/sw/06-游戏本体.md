# 06 游戏本体

本章记的是 gfx2d 项目的游戏：一个跑在 RISC-V 软核（Efinix Ti60 FPGA 上的 Sapphire SoC，100 MHz）上的竖版弹幕射击，名字叫 MYRIAD。
它有两重用途：赛题高阶要求 3 的「同屏元素极多的游戏 Demo」，以及 `N_max`（开着 Alpha 与色键、稳定 60 FPS 时同屏活动 Sprite 数的极限）的负载来源。
游戏只经命令表出画面，PC 上由软件执行器画进内存、SDL2 窗口显示，板上换成硬件引擎或同一个执行器（本系列第 02、03 章）。
本章覆盖 SW7 的 A~D 四批：数值基础、实体池、批量提交、弹型与发射器、碰撞、组帧、自机与规则、敌机与关卡、素材、HUD、
游戏的判据入口，以及 D 批的工具辅助通关录像与 S1 规模。模式框架、`N_max` 搜索与统计在第 07 章。
配图一张：[`fig/06-游戏一帧的通路.svg`](fig/06-游戏一帧的通路.svg)。

## 一、动机

第 05 章的基础 Demo 证明了「应用每帧生成命令表、交给执行器、呈现后缓冲」这条通路在 PC 与板上逐位等价，
但它的负载是赛题基础要求 3 原话里的方块与整屏图，只有一种元素、没有规则。高阶要求 3 要的是游戏，而且指标 `N_max` 数的是同屏活动元素，
所以游戏本身就是压力测试的负载：它每帧推进几千个实体、生成几千条命令，负载的形状决定了 `N_max` 能测出什么。

这个定位带来三条约束，决定了后面的每一步：

1. **性能约束直接落在每帧几千次的循环上。** 设计文档 4.4 节的「发射时算好参数、更新只做加法、不在每个弹幕上调函数指针、离屏立即回收、不用 `malloc`」
   都作用在这些循环里。E8（platform 第 10 章）在 4KB 缓存上量出 AoS 的纯更新约 49 周期/弹幕/帧，
   更新并写一条合法命令记录约 176 周期；2000 颗弹光更新就是一帧预算（1,666,667 周期）的 6%~21%，循环里多一次除法或一次间接调用都看得出来。
2. **确定性。** 同一种子加同一段输入，PC 与板子的每一帧命令表与整帧 CRC 必须相同（SW1~SW9 总览的约束 3），
   SW9 的板上对账、D 批的录像回放、SW8 的自动驾驶都建立在这一条上。所以一帧的顺序、每一处取整、随机数的取数次序都是契约，要写成可以照抄的规则。
3. **规则由独立实现核对。** 弹型的轨迹、碰撞的边界这类「看起来对」的东西，用同一份代码生成期望值等于没有判据（SW3 的教训，第 02 章 4.3 节）。
   所以数值规则要写到另一个人用另一种语言照着写也能逐位对上的程度。

为什么自己写而不移植：资料包里没有游戏（设计文档 4.2 节）；看过的开源弹幕游戏里，Taisei 用浮点复数坐标、每颗弹上挂回调与协程，
rRootage、Noiz2sa 靠 BulletML 的 XML 解析器，Butano Fighter 建在 GBA 的硬件精灵上，每一个要改的部分都比留下的多。
所以按模块借鉴（3.1 节），自己写约三千行纯 C。

## 二、为什么是这几步

SW7 与第 07 章的 SW8 一起分四批做，每批结束时都有一个能独立判定的状态：

| 批 | SW7 这一侧 | 结束时能看到什么 |
| --- | --- | --- |
| A 基础件 | 数值基础（定点、二进制角、正弦表、atan2）；实体池；批量提交接口 | 主机测试全过，还没有画面 |
| B 弹幕场 | 弹型与发射器；静止自机的碰撞；用占位图按池组帧 | PC 窗口里五种弹型；弹型轨迹与独立实现逐帧一致 |
| C 可玩 | 自机与规则；敌机、Boss 与关卡；正式素材；HUD 与游戏的判据入口 | 从开始打到 Boss 结束；判据入口两遍逐字节相同 |
| D 收尾 | 工具辅助的通关录像与回放入口；S1 规模 | 录像回放打到 `CLEAR`；约 2000 颗弹的一帧在 PC 上正常显示 |

顺序由依赖决定，少一步后面的判据就写不出来：

- 弹型判据要一份独立实现（Python）逐帧对 C 的轨迹，前提是定点、角度取整、正弦表、atan2 的每一条规则先成文，所以数值基础在最前。
- 发射器往池里追加实体，碰撞与组帧遍历池，所以池在发射器之前；组帧一帧要发几千条同模板的 BLIT，逐条走 `gfx_blit()` 的十步检查太贵，
  批量接口 `gfx_blit_run()` 与池同一批做，B 批组帧时直接用。
- 自机、敌机与关卡要一个「一帧的顺序」把输入、两类碰撞、炸弹、死亡与粒子排进来；这个契约建在 B 批弹幕场的四步之上。
- 通关录像要求整局确定、规则完整，只能在 C 批之后。

## 三、每一步做了什么

### 3.1 前期研究：检索与借鉴

开工前先找开源实现与文献（2026-09-24）。整套移植不划算（第一节），按模块借鉴：

| 来源 | 借了什么 | 没借什么 |
| --- | --- | --- |
| Taisei Project（C11，MIT）`src/projectile.h` | 敌弹、自机弹、粒子是同一种实体的三类；碰撞尺寸与显示尺寸分开存；每颗弹只擦一次 | 浮点复数坐标、每颗弹上的回调与协程、OpenGL 着色器 |
| Butano Fighter（GBA，zlib）关卡与敌弹 | 关卡是一张常量事件表；移动事件是「速度增量加持续帧数」；Boss 单独一类 | C++ 模板与硬件精灵；敌弹奇偶分组（等碰撞成为瓶颈再用） |
| BulletML 参考手册 | `fire` 的方向四种取法与 `repeat`、`wait`；五种弹型都是这几个原语的参数组合 | XML 与解析器；每帧改速度的指令（违反「更新只做加法」） |
| 东方红魔乡的 ECL 时间轴（社区逆向文档与 thtk） | 关卡时间轴是按帧号排序的指令表 | 字节码解释器 |
| Fabian《Data-Oriented Design》 | 「存活」由在不在表里表示，一遍只碰还活着的行 | 行在多张表之间迁移 |
| Tonc 附录 B、Coranac《Off on a tangent》 | 正弦表按 2 的幂分一周、Q1.14 幅度；atan2 的八分象限归约、一次除法、五项多项式 | — |
| Doom `tables.h` | 二进制角（BAM），余弦取正弦表偏移四分之一周 | 8192 项的表长 |
| 东方系列判定尺寸（社区实测） | 自机判定直径约 5 像素；大弹的判定与图像之比小于小弹；游戏区 384×448 与本项目 400×480 接近 | — |
| Shawn Hargreaves 的预乘 Alpha | 预乘图里 alpha 为 0、RGB 不为 0 的像素就是加法：光晕与弹芯画在同一张图、同一条 ALPHA 命令里 | — |

游戏类型按四项比过（每个元素的 CPU 代价、像素数、开发量、板上四个键够不够）：竖版弹幕射击每颗弹发射后只做加法、碰撞只查自机一个点，
类幸存者每个敌人每帧要转向、敌人之间要互相推开、武器对敌人是多对多碰撞，同样的引擎下 `N_max` 会小几倍。
决策 G1~G4（2026-09-25）按推荐定案：竖版弹幕、以 Boss 战为主（约 30 秒杂兵段加四张符卡，终符的密度随时间上升、直接当压力测试的负载）；
霓虹几何主题（深色底、滚动网格、四色发光弹、线框机体，素材全部脚本生成）；四个按键当方向、对立方向同按留作系统键；游戏名 MYRIAD。

### 3.2 前期研究：定点精度

设计文档 4.4 节原写位置与速度用 Q12.4（低 4 位小数）。在 WSL 的 python3 里做了一次数值实验：一次圆环齐射 n 发，
角度量化到 1024 项正弦表，速度分量按 4 位或 8 位小数截断，飞 T 帧后与理想圆比：

| 发数 | 速度（像素/帧） | 帧数 | 小数位 | 最大位置偏差（像素） | 半径范围（理想） |
| --: | --: | --: | --: | --: | --- |
| 32 | 0.5 | 600 | 4 | 41.95 | 265.2~335.4（300） |
| 32 | 0.5 | 600 | 8 | 2.89 | 298.3~302.3（300） |
| 48 | 1.0 | 240 | 4 | 19.75 | 221.5~254.6（240） |
| 48 | 1.0 | 240 | 8 | 1.67 | 239.0~240.8（240） |
| 24 | 3.0 | 80 | 4 | 6.65 | 233.3~244.4（240） |
| 24 | 3.0 | 80 | 8 | 1.23 | 239.7~240.2（240） |

速度分量的截断误差最多一个最低位，飞 T 帧就累积 T 倍：4 位小数时一个最低位是 1/16 像素/帧，600 帧累积 37.5 像素，与第一行的 41.95 同一量级。
误差随速度变慢而变大，恰好落在弹幕游戏最常用的慢速圆环上，截断改四舍五入也只能减半。所以改成 **Q.8**（int32、低 8 位小数），
更新仍是两次加法；E8 的实体本来就是 int32，只是小数位不同。

### 3.3 开工前的反向核对

每一批开工前都拿判据反过来问：「用 spec 写下的接口与规则，这条判据能不能表达出来，两份独立实现会不会写出两种结果」。
四轮共查出 44 处（前期复核 10、A 批 6、B 批 11、C 批 17），定法写进 spec 再写代码。几处决定性的：

- **atan2 的输入会溢出**（A 批）：原判据只测 `[-512, 511]` 的整数，游戏传进来的是两点坐标之差，Q.8 下约 ±11 万，
  照原文直接归约 `(y << 15) / x` 与 `x + y` 都会越出 int32。
- **一帧的顺序与「第 k 帧的状态」没写**（B 批）：弹型判据逐帧比坐标，先后差一步就整体错开一帧。
- **随机雨的取数次序没写**（B 批）：一个场一个 `xorshift32`，按发射器顺序、每发先取 x 再取速度，Python 照抄同一个次序才能对上。
- **组帧的发出缓冲**（B 批）：按池容量一次开够要 16384 × 16 字节 = 256 KB，是板上 4 KB 数据缓存的 64 倍；改成游标分段，缓冲 2 KB。
- **敌机不能进池**（C 批）：一个敌机要带血量、移动事件表的游标与 1~4 个发射器，20 字节的实体放不下；稳定压缩又会移动实体，发射器按下标找宿主会指错。
- **终符的「密度随时间上升」与常量发射记录冲突**（C 批）：定为令牌门控（3.11 节）。

### 3.4 数值基础

代码在 `lib/core/fixmath.{h,c}` 与由 `Main/tools/check/gen_sin_tab.py` 生成的 `lib/core/sin_tab.c`（两者都入库，检查脚本重新生成逐字节比）。
下面每一条取整规则都是契约，弹型的 Python 独立实现照同一条写：

- Q.8 定点；屏幕坐标取 `x >> 8`（两个目标都是 gcc，有符号右移是算术右移，向负无穷取整）。
- 二进制角 uint16，65536 为一周，加减自然回绕；角 `a` 对应方向 `(cos a, sin a)`，屏幕 y 向下，所以角度增大是顺时针。
- 正弦表 1024 项加 256 项尾巴，Q1.14，生成时按绝对值四舍五入再补符号（表严格奇对称），不用 Python 的银行家舍入 `round()`。
- 查表下标 `((a + 32) >> 6) & 1023`，取最近的一格；直接 `a >> 6` 会让所有角度往同一个方向偏，最多 63 BAM。
- 速度分量 `(speed × sin_tab[idx]) >> 14`，算术右移。
- `fx_atan2(y, x)` 照 Coranac 的 `atan2Tonc`：八分象限归约、一次除法、五项多项式；换成 16 位 BAM 只改两处（八分之一周 0x2000、末步 `(dphi + 2) >> 2`）。
  另补两条：**先缩放再归约**（x、y 同时算术右移直到都落在 [-32767, 32767]，判断不取绝对值，`INT32_MIN` 也走得通）；`fx_atan2(0, 0)` 返回 0。

主机测试 `lib/test/test_fixmath.c` 拿双精度的 `sin`、`atan2` 当参考（双精度只出现在测试里）：

| 组 | 判据 | 实测 |
| --- | --- | --- |
| F2 | 正弦表对双精度的最大误差 ≤ 1 LSB | 0.499 LSB |
| F3 | 任意 BAM 查表误差 ≤ 51 LSB（半格 32 BAM × 最大斜率 π/2 加 0.5） | 50.734 LSB |
| F4 | atan2 在 `[-512, 511]²` 穷举，最大误差 < 64 BAM | 1.400 BAM（1,048,575 点） |
| F5 | atan2 大范围：Q.8 随机 ±2^17、全 int32 随机、int32 边界 | 1.847、1.991、0.999 BAM |
| F6 | 慢速圆环 32 发、0.5 像素/帧、600 帧 | 最大偏差 2.889 像素，与 3.2 节 Q.8 那一行一致 |
| F7 | 表上每一格的 `(cos, sin)` 经 atan2 取回 | 与这一格差 1 BAM：表、速度分量、atan2 三者的方向约定一致 |

注错：下标直接 `>> 6` 让 F3 到 99.429 LSB；速度只留 Q12.4 让 F6 到 41.954 像素（与 3.2 节同一个数）；去掉缩放让 F5 到 16371.910 BAM，
UBSan 报 `y << 15` 与 `INT32_MIN` 取负的溢出。atan2 的五个系数在云上会话里只能从搜索引擎的索引摘要核对（原文页面出网被拒），
后来在参考机上打开原文逐项对过（`OCTANTIFY` 宏、`BRAD_PI`、`fixShift = 15`、五个系数与末步），与 `fixmath.c` 一致；
穷举的最大误差 1.400 BAM 折成原文单位是 0.7，与原文「几乎所有点在 ±0.5 以内」一致。

### 3.5 实体池

`apps/game/gfx2dGame/src/game/stg_pool.{h,c}`。四个池（敌弹 16384、自机弹 256、敌机 64、粒子 2048）用同一种 20 字节的实体：
`x, y, vx, vy`（int32，Q.8，`x, y` 是中心）、`sprite`、`flags`（弹种、已擦弹、不可消除、已标记移除）。布局先用 AoS（E8 的同一合成负载 AoS 快于 SoA），
字段只在这一个文件里读写，将来换 SoA 只改这里。

回收照 Fabian 的 Existential Processing：更新、出界判定与稳定压缩在同一遍里做完，读指针从 0 走到 n，写指针只在实体存活时前进；
碰撞命中与炸弹消弹只打标志，下一遍压缩时移除。所以存活实体的相对顺序不变（绘制顺序稳定），没有空闲链表，一遍移除的个数恒等于出界数加被标记数。
出界边界是游戏区四周外扩最大弹图的半宽（10 像素），自机弹池单给 12 像素，半开区间。

测试放在应用目录（`apps/game/gfx2dGame/test/`）：池是应用代码，`lib/test` 只有 `-Isw/lib`、看不到它。
`check_sw7_game.sh` 照 `mk/host.mk` 的 `test` 目标的选项（用 `make --eval` 取出，判据与被测构建同一组参数）直接编两份：64 位挂 ASan/UBSan、`-m32` 各一份，
两份输出逐字节比；只链 `lib/` 与 `stg_*.c`，不链 bsp，这本身就证明游戏逻辑不依赖平台。随机 300 轮对独立期望（发射 21,946、出界 4,235、标记 16,826、池满 1,412）全对。

两个注错说明了判据要看内容而不只是数个数：`STG_POOL_SWAP`（移除改成与末尾交换）让顺序那一行与内容比对见红，
**「移除数 = 出界 + 标记」那两行仍是 ok**。

板上构建时 `stg_pool_step` 的循环体经 `objdump` 核过：存活实体只有 6 次读、5 次写、两次加法与四次比较，没有调用、除法与间接跳转（见 4.1 节）。

### 3.6 批量提交

`lib/gfx` 加 `gfx_blit_run()`：同一源表面、同一方程、同一色键、同一宽高的一串 BLIT，先按模板做一次完整校验，之后每条只填坐标与 `w7`，
**结果与逐条 `gfx_blit()` 逐字节相同**（整个缓冲区、`used`、`rejected`、`overflow`、`first_error`、`ended` 与成功条数）。等价要守住三处：
模板校验放在每次调用的开头（表面表可能在两次调用之间被改写）；源表面等于目的表面时每条退回完整的十步检查（第十步「同一表面上两矩形不重叠」依赖每条自己的坐标）；
逐条记账的先后照抄 `gfx_blit()`。随机 1000 组覆盖合法模板与六类非法模板、逐条坐标越界、中途表满、已经 END 的表、源等于目的且重叠，全对；
另 200 组在两次调用之间改写表面表，88 组的后半段因此被拒，确实测到了「开头重查」。注错 `BLIT_RUN_NO_FALLBACK`（源等于目的时也只用模板结果）
让「源等于目的」那一行见红，说明随机输入真的走到了逐条回退。

### 3.7 弹型与发射器，以及独立实现的期望文件

一种弹型是一条发射记录（BulletML `fire` 与 `repeat` 的子集：发数、方向模式 ABS/AIM/SEQ、首角与角距、首速与速度差、旋转、间隔与次数、弹种、
随机雨的 x 与速度范围），五种弹型（圆环、螺旋、自机狙、扇形、随机雨）是同一个发射函数的五组参数。发射时算好 `vx, vy`，此后只做加法。
非圆形弹的朝向靠图集里预渲染的 16 个方向帧，帧号 `first + (((angle + 2048) >> 12) & 15)`，`& 15` 让接近一周的角度回到第 0 帧。

一帧的顺序定为：① 每个池一遍更新（上一帧打的标记在这里移除）；② 发射器按数组顺序处理，到点在宿主当前的位置齐射，新弹追加在池尾、出生那一帧不移动，
处理完一个发射器它的宿主再移动；③ 碰撞；④ 组帧。第 k 帧的状态是第 ③ 步之后的池。

期望文件 `test/stg_patterns.txt`（五种弹型各从空场跑 120 帧，另加五个发射器同场的合并段，742 行）由 `Main/tools/check/gen_stg_patterns.py` 生成：
只用标准库，只照 spec 的文字写，自己算正弦表、自己写 atan2 的缩放与归约、自己写 `xorshift32`，不读 C 的源码与生成物；
每段先打一行参数（参数抄错时直接报「参数不一致」，省得从一串 CRC 不符里倒推原因），每帧一行池的 CRC。**C 与 Python 第一次对比就全部一致**。
一致之后用三个注错反证比对看得见差别：`SEQ` 不累加让螺旋段第 1 帧、`AIM` 的 atan2 参数对调让自机狙段第 0 帧、随机雨先取速度再取 x 让随机雨段第 0 帧各自见红，
比对脚本打出两边的整帧与第一颗不同的弹，定位不用另外调试。

### 3.8 碰撞

`stg_pool_collide()`：圆对圆、全整数，**命中定义为 `dx² + dy² < (r1 + r2)²`，严格小于，恰好相切不算**。先做轴向粗筛
（阈值是擦弹半径加弹的判定半径，最大 20 像素），通过粗筛的坐标差小于 64 像素，平方不会溢出；粗筛写成一次无符号比较
（`|d| < T` 等价于 `0 <= d + T - 1 < 2T - 1`）。受击关掉时（压力测试的钩子，也是无敌）不计命中、不打标记、擦弹照算，
压力测试的碰撞开销因此与游戏里相同。

边界用例：半径和恰好 1536（6 像素）不命中、差 1/256 像素命中；勾股数 3-4-5 恰好相切与再近 1/256 像素；坐标差接近游戏区尺寸时粗筛生效。
随机 200 轮 × 2000 颗对 64 位、不粗筛的朴素参考，命中数、擦弹数与每颗的标志全同。随机样本一半落在整像素网格上，恰好相切的情况出现 294 次，
「严格小于」在随机样本里也有反例可抓。注错 `COLLIDE_NO_CULL`（去掉粗筛）让大坐标差那一行见红，UBSan 报 `107519 * 107519` 溢出。

### 3.9 按池发出与组帧

`stg_pool_draw()` 按弹种筛出实体，算目的与源左上角，目的矩形与当前裁剪框相交才写进调用方给的数组；数组写满就停，读到哪里记在游标里，
下一次接着扫。组帧按弹种循环、每满 128 条调一次 `gfx_blit_run()`，缓冲 2 KB。活动元素就是这样发出去的 Sprite 命令条数（设计文档 0.2 节的口径），
按池分开计。每个池另记一个弹种位图（`stg_pool_step` 顺手或进存活实体的弹种），组帧只遍历有的弹种：C 批的弹种表有 14 项，
压力测试只用到 1 项，不这样做就有 13 遍空扫。

判据：分段扫与一次扫逐条相同，都等于独立重数（64 位、半开区间直接按定义写）；六段各 300 帧逐帧组帧，拒绝为 0，普查的 ALPHA 条数等于发出的敌弹数。
B 批的画面入口 `-DSTG_FIELD=1|2|3`（演示、判据、`N_max` 搜索）在 PC 上用截帧（`bsp/host` 的 `GFX2D_SNAPSHOT`，只在 PC 的 bsp 里）看过五种弹型。

### 3.10 自机与规则

C 批的核心是游戏一帧的顺序（`stg_game_step(g, keys)`），录像回放的 CRC 与自动驾驶的确定性都靠它：

```
  1 输入与阶段切换  标题满 120 帧开局、CLEAR 满 180 帧回标题；对立方向当该轴不动；炸弹键取按下沿
  2 四个池各一遍    粒子池再走一遍寿命；背景推进一帧
  3 自机            移动（高速 4、低速 2 像素/帧，斜向每轴 ×181/256），然后自动射击（每 4 帧两束）
  4 事件表          取出本帧到期的事件；Boss 的按时间切换（进场满 74 帧、间隙满、超时）
  5 敌机与 Boss     按槽位顺序：发射器到点齐射，再走一步，再判出界；Boss 排在最后
  6 碰撞            先自机弹对敌机与 Boss（一颗弹只打第一个目标），再自机判定点对敌弹
  7 结算            击毁与符卡血量耗尽；无敌倒计时先减一，再处理本帧的受击与炸弹；HI-SCORE；局的结束
```

第 k 帧的状态指第 k 帧第 7 步之后。几处顺序是实现时由判据逼出来的：阶段切换放在第 1 步，所以标题恰好 120 帧（放在第 7 步只剩 119）；
无敌倒计时先减一再处理受击，所以设下之后恰好 120 帧不受击（测试用「下一次受击在第 121 帧」卡住）；受击与手动炸弹落在同一帧只放一次炸弹；
HI-SCORE 在局的结束之前取 max（残机用完那一帧也可能擦弹得分）。

受击规则：还有炸弹就改成放炸弹、不扣残机（**自动炸弹在所有平台都生效**，否则同一份录像在 PC 与板上走出两种结局）；
没有炸弹就扣残机、闪白一帧（游戏区叠一条 CONST FILL）、无敌 120 帧、炸弹补回 3。炸弹给可消除的敌弹打标记并原位生成火花，无敌至少 180 帧。
回标题时随机数按进入游戏时的种子重新播种，所以同样的输入每一局走出同样的状态。

app 测试 R 组 28 行：移动（八方向、斜向对称、贴边夹住）、射击节奏、受击与无敌、自动炸弹、手动炸弹的按下沿、炸弹消 3000 颗时火花 2048 个与粒子溢出 952、
得分规则由测试另算。自机弹对敌机的随机样本起初只有 6 对恰好相切（见 4.6 节），改法之后 1781 对。

### 3.11 敌机、Boss 与关卡

敌机放在 64 个槽的固定槽位表（`stg_enemy.c`），每槽带血量、移动事件表的游标与 1~4 个发射器；出界用 32 像素外扩，出生点在外扩之内。
关卡是两张常量表，没有按关卡写死的分支（`stg_stage.c`）：

- **杂兵段是按帧号的事件表**（28 条：出敌、清弹、进 Boss），帧号从开局算起，最后一条是进 Boss；
- **Boss 段是符卡表**（四张：名字、血量、超时、开场间隙、1~6 个发射器与锚点）。符卡在血量耗尽或超时时结束，清掉可消除的敌弹，
  进下一张的间隙（间隙里 Boss 不受伤）或 `CLEAR`。

终符「密度随时间上升」用**令牌门控**实现：旋钮 K 是「每 125 帧允许发出的弹数」，每帧 `acc += K`，满 125 发一枚令牌，
令牌够下一个发射器一次齐射就让它齐射（轮转），令牌上限是这一帧新增的加 48，不跨帧囤积。稳态的发弹速率就是 K/125 颗/帧，稳态弹数随 K 线性增长。
游戏里 `K = 600 + (t × 3) >> 2`（t 是符卡开始后的帧数，超时 2400 帧时到 2400）；压力测试里 K 由 `N_max` 搜索设（第 07 章），
同一张符卡同时服务游戏与压力测试。

受击关掉、自机不射击时一局的各段开始帧由 spec 的常量另算，与实跑逐项相同：

| 段 | 开始帧 | 算法 |
| --- | --: | --- |
| 标题 | 0 | |
| 杂兵段 | 120 | 标题 120 帧 |
| Boss 进场 | 1860 | 120 + 进 Boss 的事件帧 1740 |
| 符卡一 | 1934 | + 进场 74 |
| 符卡二 | 3734 | + 超时 1800 |
| 符卡三 | 5624 | + 间隙 90 + 超时 1800 |
| 终符 | 7514 | + 间隙 90 + 超时 1800 |
| `CLEAR` | 10004 | + 间隙 90 + 超时 2400 |
| 回标题 | 10184 | + 180 |

旋钮 200、400、800、1600、3200 时稳态敌弹数 233、471、939、1880、3761，单调、近似正比；七次改档之后旧弹全部出界最多 282 帧，
不超过第 07 章按符卡参数推出的 `SETTLE_MIN` = 300。注错 `CARD_TIMEOUT_GT`（超时晚一帧）让各段开始帧见红，`GATE_NO_ACC`（累加器不跨帧）让门控那一行见红。

### 3.12 素材

`Main/tools/assets/gen_stg_neon.py` 按坐标算出 12 张 PNG（圆弹、小圆弹、米弹各四色，自机弹、火花、自机与两种敌机的线框、Boss、星点、标题、大号数字、图标、青色字库），
不用随机数与字体文件，生成的 PNG 入库，检查脚本重新生成比像素（不比 PNG 字节：压缩流随 Pillow 与 zlib 的版本变，打包只读像素）。
发光弹用预乘 ALPHA，光晕与弹芯一条命令画完；自机弹与火花用 ADD；线框机体用 COPY 加色键。素材包由 8 项 2,142,784 字节变为 20 项 2,840,320 字节
（4 MiB Flash 分区的 67.7%）。火花图集画成 4 列 × 5 行（寿命的低 2 位闪烁、高位变暗），按池发出的循环不用改。
Boss 原定 12 帧，因为素材包变大会让 SW5 的一条坏包判据失效，减成 6 帧（4.7 节）。

HUD 字库原是 SW5 自绘的，C 批截帧时发现数字难认（4.8 节），2026-09-28 换成开源的 Spleen 8x16（BSD-2-Clause）：
上游 BDF 与许可原样入库，`gen_font_txt.py` 转成原格式的字库文本，消费方都不用改；标题去掉中文副标题，只留 MYRIAD。

### 3.13 HUD 与游戏的判据入口

整帧组帧 `stg_game_compose`：`SET_CLIP` 游戏区 → 背景 89 条（整区 FILL、横竖网格线 28 条、60 个色键星点）→ 敌机 → Boss → 自机 → 判定点 →
自机弹（ADD）→ 敌弹（ALPHA，按弹种）→ 粒子（ADD）→ 标题图或 `CLEAR` → 闪白 → `SET_CLIP` 全屏 → HUD → END。整帧每个像素都被写到，
所以整帧 CRC 与上一帧无关。HUD 在右侧 240×480，文字绘制从 SW6 的 HUD 抽成共用函数 `stg_text`，SW6 的判据日志逐字节不变。

判据入口 `-DSTG_FIELD=4`：无窗口、不读实时按键，输入是固定的按键脚本（`xorshift32` 定种子，每 30 帧换一个方向、偶尔低速、第 900 帧按一次炸弹），
受击默认关掉；逐帧打一行计数与整帧 CRC，每帧自查普查的各方程条数与组帧按类记下的相符。HUD 的实时量（SW FPS）在判据里一律 `--`，
注错 `STG_LIVE_HUD` 让它显示实测值，两遍日志必须不同。一局约一万帧，PC 上按 60 Hz 等场要三分钟，所以 `bsp/host` 认 `GFX2D_UNPACED=1` 让呈现不等场，
`board.h` 不改。两遍日志逐字节相同（10,198 行），终符末敌弹 2618 颗、活动元素最多 2590。

### 3.14 工具辅助的通关录像

第 3 节「可玩」原要求一段人工通关录像；2026-09-28 定案改为工具辅助。自动驾驶（第 07 章）只活到第 3 张符卡，人工通关要有人坐下来打，
而判据要证明的是「能从开始打到 Boss 结束，且同一份录像每次回放的 CRC 相同」。

搜索器 `Main/tools/check/gen_stg_clear.c` 只链 `lib/` 与游戏代码，逐帧调 `stg_game_step`（同一个种子、受击打开）。开工前量了两件事：
PC 上一帧游戏逻辑约 1 微秒（自动驾驶一局 5291 帧共 6 毫秒），所以每一步都能在真实的模拟上试很多种按法；
自动驾驶那一局在杂兵段就中弹 4 次，全程 12 次，外推式的躲弹不够。

规则：每 4 帧一块、块内按住同一个按键位图，候选 18 个（九个方向各分高低速）；每个候选走完这一块，块内中弹的淘汰，
再从块末推演 64 帧，两种走法（每块块首问一次自动驾驶、或继续按住这个候选）取活得久的，活得最久的提交。两种推演都逐块定键，
推演活下来的路线在搜索里真的走得出来。走不下去（候选全部块内中弹或已禁用）时回退：退 d 块、把那一块提交过的按键记进禁用表，
同一个失败前沿上 d 按 1、1、2、2、4、4……加倍到 64 块；同一个前沿失败满 14 次，就在当前这一块允许中弹（由自动炸弹或扣残机抵掉，不能导致残机用完）。
全部是整数与固定顺序，同一份游戏代码两次搜出同一串按键。这套规则经过三版（4.9、4.10 节），第三版在参考机上 4 分 59 秒搜完：

### 3.15 回放入口与 S1 规模

回放入口 `-DSTG_FIELD=4 -DSTG_JUDGE_REPLAY=1`：输入换成录像、受击打开，其余与游戏判据入口相同（整帧组帧、普查自查、执行、整帧 CRC）。
录像在构建时经 `replay2c.py` 转成 C 数组（`REPLAYS` 加 `stg_clear`），板上构建同样编得进去，SW9 前半的逐帧对账可以直接用它。
进入 `CLEAR` 时打 `clear` 行、末尾打 `end` 行，格式与搜索器的摘要相同。回放两遍整份日志逐字节相同（9208 帧，PC 上每遍约 41 秒），
`seg`、`clear`、`end` 与搜索器逐行相同：搜索器只跑游戏逻辑，回放入口多了组帧、普查、执行与 CRC，两者一致说明组帧与执行没有反过来影响游戏状态。
注错 `REPLAY_KEY` 把第 200~203 帧的按键换成别的方向，逐帧日志恰好从第 200 帧起不同，那一局在第 5633 帧残机用完：
回放对输入逐帧敏感，所以「两遍 CRC 相同」确实在检查东西。

S1 规模（设计文档 4.5 节：Boss 弹幕段、2000 颗敌弹）用第 07 章模式 3 的固定旋钮 `-DGFX2D_PRESS_KNOB=1744` 造出（1744 是 16×16 搜索的结果旋钮）。
PC 上按 60 Hz 跑 30 秒，第 10 秒以后 20 个抽样帧的敌弹 2015~2048 颗、命令 2225~2258 条、像素 867,526~875,918，溢出 0，60 帧/秒零掉帧。
第 900 帧的截帧目视：约两千颗 16×16 青色圆弹从 Boss 处放射铺开，HUD 显示活动元素 2027、敌弹 2051、段名 `SIM K 1744`，裁剪、字库与图标都正常。

## 四、遇到的问题

### 4.1 更新循环里的结构体被存到了栈上

**第一现场**：`stg_pool_step` 第一版写成 `stg_ent e = ent[r]; ...; ent[w] = e;`，板上构建（gcc 13.4，`-O2`）的反汇编里，
每个存活实体比预期多 5 条 `sw ... (sp)` 与对应的读回。

**解读**：`e` 是 20 字节的局部结构体，gcc 把它整体在栈上存了一份再拷回，每颗弹多 5 次存储。这一段正是 `N_max` 要量的更新循环。

**定位**：对照源码，读写只发生在 `e` 的整体赋值上；改成先把字段读进标量局部变量、逐个写回之后，这 5 条存储消失。

**根因与修法**：整体赋值让编译器保留了结构体的内存形态。改成标量之后循环体只剩 6 次读（`flags` 与 `sprite` 各一次半字读）、
5 次写（`sprite` 与 `flags` 拼成一个字写回）、两次加法与四次比较。主机测试只看结果，看不到指令条数，所以后来的 G11 反汇编检查把这类循环都纳入。

### 4.2 头文件保护宏撞了常量名

**第一现场**：加 `stg_field.h` 之后编译报 `STG_FIELD_H` 重定义。

**解读与定位**：`stg_field.h` 的保护宏写成 `STG_FIELD_H`，与 `stg_pool.h` 里游戏区高度的常量 `STG_FIELD_H`（480）同名。

**根因与修法**：保护宏改成 `GFX2D_STG_FIELD_H`。SW6 的 `sw6_cfg.h` 踩过同一个坑（第 05 章 4.1 节），保护宏要带项目前缀。

### 4.3 尺寸为 0 的弹种照样被发出

**第一现场**：W2（随机池，分段扫与一次扫都要等于独立重数）第一版见红，C 侧多发出了若干条。

**解读**：多出来的都是弹种表里未用的项（宽高为 0）。宽为 0 时相交区间退化成 `[x0 + 1, x1]`，目的左上角落在里面的都判成「可见」。

**定位**：组帧只遍历尺寸非 0 的弹种，所以画面不受影响；函数自身的口径错了。独立重数按定义写（宽为 0 就没有像素），所以抓得到。

**根因与修法**：尺寸不大于 0 时什么也不发、游标直接到池尾。原来的手算用例都用真实弹种，覆盖不到这一类。

### 4.4 日志行尾的 `\r` 让判据全部假红

**第一现场**：G10 第一版 `grep '^fail 0$'` 找不到、横幅比较不等，而日志里肉眼看得见 `fail 0`。

**解读与定位**：`board_puts()` 在 PC 上也照板上串口打 `\r\n`，`$` 前面还有一个 `\r`。

**根因与修法**：先 `tr -d '\r'` 再比，与 `check_sw6_demo.sh` 的 `norm()` 同一做法。第 03 章 4.6 节记过同一类问题，新脚本没有照抄那一步。

### 4.5 反汇编判据把立即数的符号注释当成了除法库调用

**第一现场**：SW8 的模式框架合进来之后，G11 报 `stg_pool_step` 有违规指令：

```
addi s0,s0,-1 # ffff <__udivdi3+0xab>
```

**解读**：`addi s0,s0,-1` 本身合法；objdump 给立即数 0xffff 配上了最近的符号 `__udivdi3`（新代码让它挪到了 0xff54 附近），
G11 按整行匹配 `<__udiv`，把注释当成了调用。同一个原因让注错 `STG_LOOP_DIV` 的「见红」看见的也是这条注释，注进去的 `div` 反而没被当作证据。

**定位**：比较注错版与正常版的反汇编，两边都有这条注释，只有注错版多一条 `div`。

**根因与修法**：除法与取模按助记符查（`div`、`divu`、`rem`、`remu`），除法库只在跳转与调用指令的操作数里找。改完之后注错查到的是 `div a4,t3,a4`。
判据自己的缺陷，产品代码没有变；原判据只在一种链接布局下验证过，布局一变就暴露。

### 4.6 随机样本几乎碰不到「恰好相切」

**第一现场**：R9（自机弹对敌机，随机样本对 64 位朴素参考）300 轮只出现 6 对恰好相切。

**解读**：整像素网格上随机撒点，恰好落在圆上的机会很小，「严格小于」这条边界在随机样本里几乎没有反例，判据等于没测它。

**根因与修法**：四分之一的弹直接放在某个目标的相切处或再近 1/256 像素（轴向；半径和是 5 的倍数时按 3-4-5 放），相切增加到 1781 对，
注错 `PHIT_LE`（`<` 改 `<=`）让这一行见红。B 批的 X7 已经用过「一半落在整像素网格上」的做法，C 批新写的测试没有沿用。

### 4.7 素材包变大让 SW5 的一条坏包判据改报别的错

**第一现场**：C3 第一版照 spec 画了 12 帧的 Boss，`check_sw5_assets.sh` 的 S5f 见红：期望 `12 out_of_bounds`，实际报 `11 overlap`。

**解读**：S5f 造「条目越出包末端」的坏包，是把第 0 项（1,966,080 字节的整屏图）的起点写死成 1 MiB。包总长 3,135,232 字节时，
1 MiB + 1,966,080 没有越过包末端，这一项落进别的条目里，报的是重叠。

**定位**：只有包总长不超过 3,014,656 字节时，写死的 1 MiB 才越界。

**根因与修法**：当时 SW5 的文件不在 C 批的改动范围内，所以减素材：Boss 改成 6 帧（每帧 10 度，组帧时每 8 帧换一帧，转速不变），
包总长 2,840,320 字节，余量 174,336。S5f 的构造本身在 SW5 验收时改成按包的总长算起点（第 04 章），与包的大小无关。
这一条判据的构造依赖被测对象的大小，写的时候没有意识到。

### 4.8 HUD 的数字难认

**第一现场**：C 批在参考机上截帧目视，HUD 的分数与数值难认：`0` 是一个实心块中间一个点，`1` 像下划线。

**解读**：`Main/assets/font/ascii8x16.txt` 的文件头写「大写与数字顶在第 3 行」，`0`、`1`、`4`、`6`、`9` 等字形却从第 5、6 行起，残缺。
青色字库与大号数字照它渲染，一起受影响。字库自 SW5 起没有改过，问题早于 C 批；SW6 的 HUD 判据按字符逐个与字库比对，比的是「画得和字库一样」，
字库本身画错了它看不出来。

**根因与修法**：2026-09-27 定案换成现成的开源点阵字体。候选（自绘版、Spleen 8x16、Terminus 16 与粗体、X11 misc-fixed、VGA 16）在同一段 HUD 文字上渲染比较，
选 Spleen（笔画粗、数字规整，BSD-2-Clause 只要求保留版权声明）。换字库改了 HUD 的像素，SW6 两份期望日志以旧日志为底、只换随字形变的字段，
由 Python 按新字库独立重画 HUD 的 `hcrc` 全部对上，作为新期望值的独立证据。作品文档要附 Spleen 的版权声明。

### 4.9 搜索器推演改的是当前状态

**第一现场**：搜索器第一版跑出 `err 超过 20000 帧还没回到标题`。加调试输出之后：

```
dbg frame 7001 nb 1720 seg 6 phase 1 ebul 766 best 48 boss 3 t 402 hp 536
dbg frame 7502 nb 1816 seg 1 phase 1 ebul 13 best 48 boss 0 t 0 hp 512
```

**解读**：第 7001 帧还在终符（段 6），500 帧后段号回到杂兵段（段 1），中间只有约 120 帧不在搜索的块里，正好是标题的长度：
残机用完回到了标题，又开了一局。而规则是「块内中弹的候选淘汰」，按规则不可能用完残机。

**定位**：提交的块是从块首存档按同一个按键重走的，结果却与评估时不同，说明存档或评估改了不该改的状态。
`stg_game` 里四个池的 `ent` 指向同一个结构体里的存储（`stg_pools`），`memcpy` 出来的副本仍指着原件，推演一动就改了当前状态的池。

**根因与修法**：存档改成 `snap_copy`：拷完把四个 `ent` 改回副本自己的存储；其余指针都指常量表，照拷即可。搜索器最后按录像从头重跑一遍打摘要，
拷贝要是还有漏的，重跑的摘要就与搜索时不同；判据入口的回放又从另一条路径（含组帧与执行）重跑一遍。游戏代码里从来没有拷贝过整个游戏状态，
所以这个指针布局以前没有人需要关心。

### 4.10 深度优先回退爆炸，终符后段零中弹无解

**第一现场**：修好拷贝之后，第二版十分钟没跑完；换成「禁用表加回退距离递增」之后报 `err 块 1812 退不回去（存档环最早是块 1812）`。

**解读**：第二版在失败点附近把 18 个候选挨个试遍，失败向前传播时是 18 的幂次。第三版的失败点在第 1812~1940 块，
约第 7370~7880 帧，是终符；回退一路退到了存档环的边上。

**定位**：终符的门控 `K = 600 + (t × 3) >> 2`，拖到超时前是每 125 帧 2400 颗（约 19 颗/帧），零中弹可能根本无解；
而「可玩」要的是打到 Boss 结束、不丢局，炸弹本来就是游戏的一部分。

**根因与修法**：回退距离按同一前沿上的失败次数加倍（总工作量有上界）；同一个前沿失败满 14 次就允许这一块中弹（不能导致残机用完）。
第三版 5 分钟搜完，录像里中弹 4 次。第一版的深度优先写法在短的测试段上跑得通，规模一上来才暴露。
