# 24 凝时板端首验与串口十五位

2026-11-05审查订正：本章“3.53FPS、2.8倍归一化加速”对应的表达式
`INT64_C(1)<<42/len`先除后移，多数向量变零；原始日志R4STAT实际只发射约162条，
并非完整人形的1250条。此前数字不作为等画面加速结论。同时submit计时已包含rast，
二者不能再相加成35ms光栅下限。因此“即使geom为零也达不到30Hz”的结论撤回。
完整画面基线、修复、优化与新板测见[第25章](25-凝时板端缺陷与帧率优化.md)。
以下保留首轮实验过程，性能结论以上述订正和第25章为准。

2026-11-05，SH3 板上验收第一轮：HALTTIME（目录 id 7、快捷键 6）适配 B7 板并启动成功，

512 条装不下凝时满池 1279 条。

## 1 上板路径与两处缺陷

固件 build_console.py --app-profile full：425930 字节（512KiB 预算内）、RAM 92.00%、
3d_symbols=64、catalog hash 63b3e413…；素材 pak 未动（头内 CRC 0xA8624648 与
assets.h 一致），只重烧程序分区 0x380000（写前整片备份
Main/bit/flash-backup-20261105-before-sh.hex，程序分区逐字节对账 2dbe8633…）。

第一处缺陷：`PLATFORM_KEY_APP6 = 1u<<14` 在固件里接好了（input.h、
board_input_compat.h、navigate），但串口键包协议只有 14 位（lo7+hi7），
APP6 永远过不去；`--input-script` 与 `packet()` 都按 0x3FFF 拒收。
修复按同步字节选跨距：历史包 `ff 7f lo7 hi7 CRC7(14 位)` 逐字节不变；
APP6 包走 `ff 7e lo7 hi8 CRC7(15 位)`——0x7e 在旧解码器里是一张非法
legacy 包，会被安全丢弃。跨距由第二个同步字节选定、不靠试解：一个包只对应
一个 CRC，单比特载荷错误保持确定性检出（初版"两个跨距都试"会把错包以
~1/128 概率蹭过另一个跨距的校验，被 input64 的单比特翻转判据当场打红，
已废弃）。15 位包的 hi 字节可带 bit7，解码器仅在 ff 7e 的待收 hi 状态
无条件收下，其余状态 bit7 字节一律作新包头（截断帧靠它立即重同步，
resync 用例保持原语义）。`--input-script` 上限 0x3FFF→0x7FFF。
三方对拍（新包↔新解码器 32768 全跑、旧包↔新解码器 16384 全跑、
bit14=0 帧逐字节同）见 evidence/wire-roundtrip.log；test_input.c 增补
15 位穷举段（16384 值 × 15 位翻转）；板上实测注入 0x4000 一次进应用。

第二处缺陷：凝时满池实测 1279 条记录（宿主 900 帧扫，SHDBG 探针），板端
R4_REC_MAX=512（共享池 64KiB 主表）首帧即溢（r4 err records 4294967295）。
共享池 10MiB 只用了前 128KiB：主表扩到 1536 条（192KiB）、bin 32KiB→128KiB、
深度后移到 0x50000，合计 320KiB，仍在 2D arena（0x400000 起）之前；
submit 参数 tri_alloc 同步改为 R4_REC_MAX×128（原来钉死 65536，
第二条记录超界被引擎拒收：r4 err submit rc 4294967291 count 1250）。

## 2 节拍实测与归因

R4PERF（190 拍窗口）：p50 27,379,369 周期（273.8ms/帧），late 190/190，
fps_milli 3530。R4TIME 分解（10ns 周期）：

```text
cyc_logic      27,436      0.27ms
cyc_geom   25,393,693    253.9ms   ← 瓶颈
cyc_bin      168,852      1.7ms
cyc_hud         665
cyc_submit  1,769,912     17.7ms
rast_cycles 1,551,031     15.5ms
```

瓶颈在 sh_world_emit 的逐顶点程序化蒙皮：每敌 7+5+2×(5+3)+2×5+3+2 环 ×
8~12 边 ≈ 334 顶点，每顶点 sh_material 两次 sh_normalize（变除数 64 位除法
各 3 次，RV32 走 libgcc 软除法）+ isqrt ×3。第一刀已收：
sh_normalize 改一次倒数（inv=(1<<42)/len，误差 <1/64 LSB，宿主/板端同码），
cyc_geom 70.5M→25.4M（2.8×），帧时间 734ms→274ms（1.33→3.53 FPS），
宿主 R4TIME 同步 132k→37k。

## 3 停刀点：30 Hz 在本硅片上够不着

余下分解：geom 254ms + 光栅管线（bin 1.7 + submit 17.7 + rast 15.5）≈35ms。
就算 geom 降到零，1250 三角形的光栅底也在预算（33.3ms）边上；三维走廊自己的
板上回归（20 FPS，11-01 起挂账待定）同一堵墙。继续砍 CPU 需要改外观或换烘焙：

- 逐环材质（每环一个颜色替代每顶点）：材料调用 ~12×，外观变facet条带；
- 敌机网格改烘焙（SH1 原设计"烘焙每面常量"）：对齐走廊/山脊管线，改动最大；
- 顶点/边数缩减：直接改形状。

三条都改变用户在 PC 上定过的观感，SH3 判据（对照 SW19/SW20 固定 30Hz 零迟到）
在本场景三角形数下无解，需要拍板后再动。
