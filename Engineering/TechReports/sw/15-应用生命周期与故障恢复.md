# 15 应用生命周期与故障恢复

2026-10-28～29的应用运行时设计和修复。对象为`Main/sw/runtime/appfw.c`及公开运行时头，
host与FreeRTOS端口驱动同一管理器，内核集成见 [FreeRTOS](13-FreeRTOS移植与中断调度.md)。

## 1 边界与应用模型

管理器本身不包含FreeRTOS、SDL或游戏头。菜单、注册表、能力、准备、恢复、导航和不透明user
由组合根注入；菜单是系统页，不能列成默认可启动内容。稳定ID不等于数组位置，
默认历史ID1/2/3/4对应演示、弹幕、压力、三维，新集合以catalog为准。

系统启动与BACK先于业务输入处理。启动/确认键按住时消费到释放，避免泄漏成新应用首条热键；
方向可以继承，三维内部重进也保留热键状态。早期HOME按8个渲染帧计数，低帧率时含义不稳定，
最终改为显式BACK按下沿。

## 2 状态提交与资源归还

| 事件 | 约束 |
| --- | --- |
| enter成功 | 才提交活动应用 |
| enter失败 | 不调用失败对象的frame，清理后恢复菜单 |
| frame失败 | 不present失败帧，记录错误 |
| leave | 先完成引擎物理排空，再回收表面/TEX和应用资源 |
| 完成状态未知 | 确认复位/排空；失败保持fault，不假清软件状态 |
| 恢复请求 | 明确成功后才能绘制新表面；错误与恢复计数保留 |

回调区分完成、内部切换和错误。真实完成帧、呈现、丢日志和错误进入状态协议。
板端与宿主只负责驱动初始化、step、shutdown，不各自维护一套应用状态机。
输入编码与面板协议见 [UART与状态协议](21-UART输入与状态协议.md)。

## 3 旧消费者与通用服务

旧gfx2dGame保留开发/判据用途，产品默认console；二者共享图形和资源机制，
但内容清单、模型与UI仍在应用适配，不能整段改名后声称为通用服务。
早期stg_runtime吸收了两份启动、表面、TEX、后端和三维钩子；其INJECT_TEX_CRC、G1/G4影子
和mode感知判据不能在抽取时丢失。最终职责见 [平台SDK](16-平台SDK与资源所有权.md)。

PIPELINE控制执行策略，DIAGNOSTIC控制逐帧CRC；异步写帧与同步逐帧CRC组合被构建拒绝。
PERF不能决定产品是否具备流水能力。旧消费者未显式选择新策略时保持旧语义。

旧三模式切换曾用只停5帧的激励，池内无弹，漏清池变异也通过；改为待60帧后切走，
151次进入中100次检出不符。该记录说明生命周期检查必须真正占用资源，不把旧三模式数量固化为新管理器能力。

## 4 验证对象

管理器故障单测覆盖enter/frame/leave、返回、输入消费、排空失败和恢复；64/32位与sanitizer
检查相同实现。收集器拒绝零帧、冻结tick、渲染错误和无后台进展，产品程序实际完成并呈现后才计数。
不能只凭旧BIN存在跳过make，也不能以进程存在或菜单横幅替代应用出帧。

以下是当时系统整合回归，包含直接消费者与旧负载，不宣称本模块独立执行了新的整轮验收。
