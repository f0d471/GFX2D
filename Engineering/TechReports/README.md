# TechReports

记录每个工作点的开发过程。一个主题一个系列，第一篇讲从零到一的骨架，
之后每完成一个工作点增加一章。

## 记录单元

一章记录一个工作点，由事件、行为、结果三部分构成，三者齐备才算记完。

| 部分 | 内容 | 举例 |
| --- | --- | --- |
| 事件 | 触发这次改动的观测 | 编译报错、串口静默、上板无输出、资源占用异常 |
| 行为 | 针对事件做了什么 | 改代码、改工程配置、加判据、换实现 |
| 结果 | 行为带来的可测量变化 | XLR 与片上 RAM 块数、setup/hold slack、上板判据的通过项 |

不做重点摘要。被排除的方案、走错的判断、失败的尝试都要写进对应章节。

需要前期研究或实验取样的工作点（读手册、读厂商网表或第三方源码、设计实验、上板取样），
研究过程本身是章节的主体，写在「三、每一步做了什么」里：查了什么、原文或原始数据是什么、
读出了什么结论、结论可信到什么程度（实测、代码证据还是推测）。每个数据都要跟一段解释，
说明它意味着什么、排除了什么。Todo 的开发日志只留时间流水，不能代替这里的记述。

## 章节结构

每章按以下六节组织，节序固定。

### 一、动机

从上一章的结论接起，把因果链逐环写完，不跳环。每一环回答为什么不是另一种选择。

### 二、为什么是这几步

先完整列出这个工作点拆成哪几步，再从对象自身的性质推出为什么正好是这几步。
读者读完应能得到两条信息：这个工作点的总工作量，以及为什么少一步都不成立。

### 三、每一步做了什么

一步一节，每节回答两个问题：这一步解决什么问题，用什么办法解决。

- 描述写在行为级：改了仓库的哪个文件、哪个字段，数据从哪里流到哪里。
- 办法分两类，写明属于哪一类：常规做法一句话带过；特定手段写明是什么、为什么需要、代价是什么。
- 能画图的一律画图，规范见下一节。

### 四、遇到的问题

一个问题按四段写，本节篇幅不设上限。

| 段 | 内容 | 约束 |
| --- | --- | --- |
| 第一现场 | 当时的错误输出 | 只贴输出。原始记录丢失时按当时的描述还原，并注明哪些是反推的 |
| 解读 | 逐行说明该输出的含义 | 说明哪个字段是关键、该数值指向什么结论、排除了哪些可能 |
| 定位 | 从现象到根因的路径 | 写明试过什么、排除什么、依据是什么，包含判断错误的那一次 |
| 根因与修法 | 改了什么、为什么这样改有效 | 结尾补一句：原判据为什么没有覆盖到它 |

### 五、结果

上板或编译的实测数字，与改动前对比。写明测量方法、测量对象、已知误差来源。
没有实测的数字标明是估算或推测。

### 六、还欠什么

本工作点留下的账，指向 [`../Todo/`](../Todo/) 的条目。没有则写没有。

## 配图规范

三类图，用途不同，形式也不同。

| 类型 | 用途 | 形式 | 位置 |
| --- | --- | --- | --- |
| 架构图 | 一个阶段结束时整个系统由哪些部分组成、怎么连 | SVG | `<系列>/fig/<章号>-<名称>.svg`，正文用相对路径引用 |
| 结构图 | 某个部分改动前后的内部结构，以及改动点在哪 | ASCII | 正文代码块 |
| 流程图 | 某个操作或过程的步骤、分支与失败出口 | ASCII | 正文代码块 |

架构图的要求：

- 白底，无渐变、无阴影、无装饰性圆角。线宽与线型承载语义（总线宽度、接口类型、是否已接入），
  颜色只承载一种语义，图内必须有图例说明这两项。
- 每个框的名字用代码里的实例名或模块名，不用只在图里存在的叫法。
- 已生成而未接入的接口用灰色虚线画出来，不留空白。读者要能从图上看出下一刀接在哪。
- 最小字号 9 px，文字不出框，连线不穿框。
- 图内只写接口与参数（位宽、频率、地址），实测数字放正文表格。
- 每章的架构图画的是该章结束时的状态，不改旧章的图。
- 提交前渲染一次确认没有重叠。任何能跑无头模式的浏览器都可以，例如：

```
<浏览器> --headless --disable-gpu --screenshot=<输出.png> --window-size=1240,920 file:///<图.svg>
```

ASCII 图的要求：

- 框线只用半角字符，标签可以用中文，同一列的框宽按最长标签对齐。
- 改动点用 `[改]`、`[新]`、`[删]` 标在框内或框右，并在图下逐条对应说明。
- 改动前后各画一张，两张的框位置尽量一致，便于逐框对照。

## 写法约束

读者是没有参与过本项目的工程师。

| 项 | 约束 |
| --- | --- |
| 开头 | 先写明这是什么芯片、要解决什么问题，再给数据；不以内部名词和数字开篇 |
| 专有名词 | 首次出现时当场解释一句 |
| 不确定的内容 | 注明是反推值还是未裁决 |
| 最终实现 | 只写定稿形态；中间版本写入「遇到的问题」 |
| 不写的内容 | 已推翻且无教学价值的方案、待办清单（属于 `Todo/`） |
| 对举句式 | 不用「不是 X，是 Y」，直接写 Y |
| 拟人动词 | 使用工程对象和可观测行为：判据覆盖缺陷、约束告警减少、hold 余量下降 |
| 加粗 | 限术语首次出现和硬性结论，不逐段加粗 |
| 表格 | 只放实测数据，不用于概念对比 |
| 符号 | 不用符号代替措辞，不用 emoji |
| 结尾 | 不复述全文，不列条数式小结 |
