# 引擎源码分目录与依赖守卫整改（2026-11-12 ~ 11-13）

两件事在同一个工作点里做：把 `Main/rtl/engine/` 的平铺源码按机制分目录，
以及把依赖守卫从「片段 + 空模块声明」改成「一个真模块」。前者只动路径，
后者改变了一个判据的性质（非法构型从能编过变成编不过）。

## 一、分组与依据

| 位置 | 文件 | 依据 |
| --- | --- | --- |
| `core/` | `engine_cmd.v`、`engine_regs.v`、`engine_mover.v`、`engine_geom.v`、`engine_pix.v`、`engine_blend.v` | 任何构型都编进来，对应控制层、事务层、几何层、计算阵列四章 |
| `core/` | `engine_config_guard.v` | 依赖守卫，见第四节；与构型无关 |
| `buffer/` | `engine_tex.v`、`engine_band.v` | 片上存储数据面，由 `GFX_HAS_TEX` 与 `GFX_HAS_BAND_HW` 整块开关 |
| `frontend/` | `engine_inst.v`、`engine_pb.v`、`engine_pb_dma.v`、`engine_bin.v`、`engine_bounds.v`、`engine_packet_check.v` | 绘制前端；`engine_bin` 例化 `inst`/`bounds`/`packet_check`，拆开就断 |
| `rast/` | `engine_r3.v`、`engine_rlst.v`、`engine_rast.v` | 三维；`r3` 例化 `rlst` 与 `rast` |
| `include/` | `engine_feature.vh`、`engine_regs_offsets.vh` | 两份生成头，随构型变 |
| 根 | `engine_top.v` | 顶层接线，例化 `gfx_config_guard` 一次 |

分组用的是特性宏边界而不是功能相似度：一个子目录里的模块要么整体在构型里、要么整体不在。
`engine_top.v` 留根，因为它是唯一看全部子模块的文件。

## 二、`include` 怎么解决

声明头离开 `.v` 所在目录后，靠搜索路径找 `include`：

- 主工程 `fpga/gfx2d_ti60/gfx2d_ti60.xml` 的 `<efx:synthesis>` 里
  `<efx:param name="include" value="../../rtl/engine/include" />`。
  `efx_run.py` 第 760~761 行把它翻成 `efx_map` 的 `I=`，本轮 map 命令行里可见
  `I=../../rtl/engine/include`。
- 六份独立综合工程补同一参数：`sim/engine/ctrl/syn/engine_top_syn.xml`、
  `frontend/syn_bin/engine_bin_syn.xml`、`frontend/syn_inst/engine_inst_syn.xml`、
  `geom/syn/engine_geom_syn.xml`、`pix/syn/engine_pix_syn.xml`、`pix/syn/probe_pix_syn.xml`。
- `check_r2_synthesis.py` 与 `research_engine_features.py` 把模板 XML 改成平铺目录时，
  删掉继承来的 `include` 参数，否则那个相对路径在新目录里不成立。
- 仿真侧统一 `-I rtl/engine/include`（14 个脚本与 6 个检查脚本，见第三节）。

生成树里，两份声明头写进 `rtl/engine/include/`，守卫模块写进 `rtl/engine/core/`；
构建结束后删掉树根的两份暂存副本——不删的话，按 CWD 找 include 的工具会读到树根那份，
把真正被编译的头遮住（这条坑在第四节实测踩到过）。

## 三、改动面

- 分目录那次：`Main/` 下 44 个文件按映射批量改路径，14 处变量拼接手改，
  6 处 `glob('*.v')` 改 `glob('**/*.v')`；工程源文件顺序逐条比对，与改前一致。
- 守卫那次：`engine_config_guard.v` 加进 10 处源列表（工程 XML、`FIXED_RTL`、

## 四、依赖守卫：从「空声明」到「真模块」

**原状**：`engine_config_guard.vh` 是例化片段，`engine_config_error_modules.vh` 把 9 个
`GFX_CONFIG_ERROR_*` 都定义成空模块。空模块让例化合法，所以非法组合并不会失败——
2026-11-13 实测：B5 源树里删掉 `` `define GFX_HAS_BAND_HW ``（保留 PB），
`iverilog -s engine_top` 退出码 **0**，一个字都没报。真正拦住非法清单的只有
`feature_build.build()` 在生成前拒绝。

**现在**：`rtl/engine/core/engine_config_guard.v` 是一个模块，不定义任何
`GFX_CONFIG_ERROR_*`。依赖不满足时它例化一个不存在的模块，iverilog、
`hierarchy -check` 与厂商综合（`blackbox-error=1`）都是硬失败，报错文本里带违规边的名字。
`engine_top.v` 里只留一行 `gfx_config_guard u_config_guard();`。

它与构型无关：`guard_module()` 不看 `config`，内容只由 `feature_config.GUARDS` 与
`EXCLUDES` 决定，所以不按构型生成，只在依赖表变化时重写，`--check` 校验仓库副本。

**两个踩到的坑**：

1. 守卫模块最初漏了 `` `include "engine_feature.vh" ``。宏没进来，所有 `ifdef` 为假，
   模块变成空壳，非法构型照样编过——是先写的反例判据把它暴露出来的。
2. 生成树根部曾保留 `engine_feature.vh` 的暂存副本。按 CWD 找 include 的编译
   （仿真脚本都从树根起）会读到那份旧副本，于是「改 include/ 里的宏」不影响编译结果。
   现在 `build()` 在填充完树之后删掉树根的两份副本。

**新判据**：`guard_compile_negative.sh` 已并入 `feature-contract`，两条：
合法 B5 必须编得过（对照，防止假通过）；同一棵树删掉 `GFX_HAS_BAND_HW` 后必须编不过，
且诊断里出现 `PB_REQUIRES_BAND_HW`。`guard_negative.sh` 保留原职：九条非法清单必须被
构建入口拒绝（判据是退出码、诊断与「不得留下产物目录」）。

## 六、留给后人的三条

- 两份声明头的唯一入口是 `rtl/engine/include/`；守卫是 `core/` 里的普通模块，
  不要再改回 `.vh` 片段或空模块声明——那样会让非法构型重新变得能编过。
- 加一个引擎 RTL 文件要同时看三处：工程 XML、`feature_build.FIXED_RTL`、
  以及显式列源文件的仿真脚本（用 glob 的检查脚本会自动带上）。
- 守卫的失败信息现在是工具给的 missing module / blackbox 报错，文本里带边名；
  想让它更干净，只能在「不定义错误模块」与「空模块声明」之间二选一，不能兼得。
