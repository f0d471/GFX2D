# 02 AXI 事务层：引擎唯一的 AXI 主机怎么搬数据

这一章讲易灵思 Titanium 系列 Ti60F225 上的一块 RTL：`rtl/engine/engine_mover.v`。
它做一件事——把一段 DDR3 里的数据搬进片上、再把一段搬回去，给 2D 渲染引擎用。
数据搬运本身不产生颜色，但它出错的代价在这一层最大：引擎挂在 AXI 多路器 `Axi_Mux`
的第一个主机口（S1）上，一笔事务断在半截，多路器会一直等它，扫描输出与 CPU 跟着停住，
只能重新加载比特流。

引擎 P1 分六批（B1~B6），本层是第二批。它上面接几何层的描述符与控制层的取数、排空请求，
旁边接计算阵列的读写流，下面经 `Axi_Mux` S1 接 DDR3 控制器。

## 一、动机

引擎画一行像素要搬三笔数据：读源行、读目的行、写目的行。引擎自己不做这件事，
CPU 更不做——让 CPU 去搬，一个字要花掉取指、译码、访存三段时间，而像素通路一拍吃 16 字节。
所以引擎自己带一条搬运通路，几何层算好地址与拍数丢给搬运层，搬运层把它变成总线上的突发。

搬运层要做四件事：把描述符变成合法的 AXI 突发、保证同一方向只有一笔在途、
按像素跳过不该写的字节、在引擎被复位或从机不响应时把在途的事务收干净。
前三件是赛题基础要求 2（突发与 FIFO）与高阶要求 2（色键）的落点，
第四件不做的话整机在 `reset halt` 之后只能靠重新烧比特流救。

这一层的位置也决定了它的接口最杂：向上要接受两条不同的读请求（几何层的像素读、
控制层的命令取数），向旁边要给计算阵列出一条读流、收一条写流，向控制层要报状态、
收排空请求与超时门限。把这些接口一次冻结下来，B3、B4、B5 才能各做各的。

从上到下的因果链：整机要在 DDR3 上跑弹幕游戏 → 引擎要把绘制搬到硬件 → 引擎按五层切开 →
搬运层是唯一碰总线的一层 → 它必须自己保证在途契约与收场动作 → 这一层的接口与约束
写进层间契约 I2、I3、I4、I7，后面三批照它接。

## 二、为什么是这几步

这个工作点拆成六步：前期研究、定案、写 RTL、单元仿真（含注错）、单独综合、写文档。
与 B1 相同的六步，但每一步的内容都更重，因为这一层有状态机、有总线、有上下游。

已经定下的东西有三件，本章不再论证。一是**用谁**：`rtl/vendor/verilog-axi/` 的两个核
（`axi_dma_rd.v`、`axi_dma_wr.v`），取上游归档前最后一个提交 `516bd5d`，MIT 许可，
源码一字不改（D3）。二是**每方向一笔在途**（D12）：放宽到两笔要先量加密的 DDR3 控制器
会不会提前接受地址，这件事没有数，要放宽得重做整个多主机仲裁的实验。三是**按像素跳过写
走 W 通道带内标记**（D16）：写核中间拍的 `wstrb` 恒为全 1、不看流的 `tkeep`，
所以「这个像素不写」只能在核外按位清。

没定的东西在实现一侧，共四项：两个核是黑盒，复位与超时时怎么收场；
附带信息（目标缓冲号、命令索引、来源）放哪；读侧两个请求方怎么仲裁；
以及这些事合起来写成一个什么样子的模块。四项里第一项决定后三项的形态——
收场动作只能在两个核的**流接口**上做，因为 `m_axi_rready` 在核内部，搬运层碰不到它。

六步各自解决一个问题，缺一不可：

- **前期研究**：把上面四项从「D3 的一句话」变成有数据的选项。D3 只说「用这两个核、
  源码不改」，没有一个字说复位时怎么办、超时怎么判、上下文放哪。照着这句话写不出代码。
- **定案**：把选项收成唯一解并编号（D29~D32），回写接口契约。
- **写 RTL**：把定案落成一个文件，两个核按参数配好、原样例化。
- **单元仿真**：证明它在协议上是对的。这一层的判据不能靠数据比对，
  因为数据对不对与协议合不合规是两件事；契约要按 valid 判、地址要按约束判、
  排空完成要在总线上看有没有断掉的突发。
- **单独综合**：测出资源与时序，与上游记录的两个核的规模对账。
- **文档**：把过程、数据与解释留下来。

判据里还有一条与其他批相同的硬要求：**注错必须见红**。
本层的五个注错各自打在一处机制上（读门控、写门控、带内掩码、排空、排空请求的「一次只完成一次」），
每一个都要红在它对应的判据上，不能是「随便什么错」。

## 三、每一步做了什么

### 3.1 两个核怎么配、怎么接

两个核都按同一组参数例化：`AXI_DATA_WIDTH = 128`、`AXI_ADDR_WIDTH = 32`、`AXI_ID_WIDTH = 4`、
`AXI_MAX_BURST_LEN = 192`、`AXIS_KEEP_ENABLE = 1`、`AXIS_LAST_ENABLE = 1`、
`AXIS_ID/DEST/USER_ENABLE = 0`、`LEN_WIDTH = 12`、`TAG_WIDTH = 4`、`ENABLE_SG = 0`、
`ENABLE_UNALIGNED = 0`。核的接口是「描述符进、流进出、状态从独立的状态口回来」。

三个已知行为决定了本层的写法，都在读源码时确认过：

- 写核中间拍的 `wstrb` 恒为全 1、不看流的 `tkeep`（`axi_dma_wr.v:555-557`），只有最后一拍看。
- 读核的状态脉冲在末拍**压进核内输出 FIFO**那一拍就出来（`axi_dma_rd.v:518-535`、`:662-669`），
  不是在它从流接口出去的那一拍。
- 写核发 AW 之前要等写流的第一拍：`axi_dma_wr.v:509` 是
  `m_axi_awvalid_next = s_axis_write_data_tvalid || !first_cycle_reg`。

两个核内部各有一个 32 深的输出 FIFO，深度写在模块体内的 `parameter` 里，
Efinity 当它是 localparam，不改源码缩不了。

**来源与入库核对。** 上游 [alexforencich/verilog-axi](https://github.com/alexforencich/verilog-axi) 已经归档，
后继项目 taxi 改用 CERN-OHL-S（强传染）许可，所以取归档前最后一个提交
`516bd5dadc3365b7f9e225d2af8fe0b8d804fe53`（2025-02-27）的 MIT 版本。两个核与上游的 `COPYING`
（入库改名 `LICENSE`）原样放进 `rtl/vendor/verilog-axi/`，三个文件的 git blob 与上游提交里的 blob 相同
（`axi_dma_rd.v` `9e01f9b`、`axi_dma_wr.v` `672910c`、`COPYING` `6923387`）。仓库的 `.gitattributes` 关掉了行尾转换，
入库的字节就是检出的字节。两个文件都是 Verilog-2001、不例化任何子模块，iverilog 12 用 `-g2005` 单独编译都通过
（`axi_dma_wr.v` 有五条 `@*` 敏感整个数组的告警，不影响功能）。

**核会自己把一个描述符拆成多笔，而且不等上一笔。** 描述符跨 4KB 或超过 `AXI_MAX_BURST_LEN` 拍时，
读核在上一笔地址握手之后就发下一笔、不等数据回完（`axi_dma_rd.v:362-404` 的 `AXI_STATE_START`），
写核拆出的第二笔 `awvalid` 也不等第一笔的写响应（`axi_dma_wr.v:509` 的 `!first_cycle_reg` 分支）。
3.8 节的整屏 FILL 注错用例在写方向量到 9120 个违例周期。所以在途契约不能交给核自己保证，定成两条规矩（D3）：
几何层保证每个描述符按 16 字节对齐、不跨 4KB、不超过 `AXI_MAX_BURST_LEN` 拍，核内永不拆分；
搬运层在上一个描述符完成之前不发下一个（「完成」的定义见 3.4 节）。
上游还有一个已知缺陷（issue #12）：`AXI_MAX_BURST_LEN × 16 >= 4096` 时 4KB 判断里的一个表达式恒真。
行最长 161 拍，所以取 `AXI_MAX_BURST_LEN = 192`，碰不到这个表达式；加上规矩 1，核内的 4KB 分支也走不到。

**在整机里综合的规模（前期研究，2026-09-26）。** 把 `Main/rtl` 与 `Main/fpga/gfx2d_ti60` 复制到仓库外，
顶层的 `u_axi_probe` 换成一个端口相同的综合探针（两个核、门控、带内掩码、深 256 与深 512 的 128 位行缓冲各一个、
4 个位置的像素旋转与色键比较，全部经 APB 可观测），`ENABLE_UNALIGNED` 取 0 与 1 各编一份。
Efinity 2026.1 的 map、interface、pnr、pgm 四步都 PASS，没有 error：

| 构型 | 整机 XLR | 片上 RAM | `u_rd` XLR / 块 | `u_wr` XLR / 块 | S1 上的模块合计 | `core_clk` setup (ns) | `core_clk` hold (ns) |
| --- | --: | --: | --: | --: | --: | --: | --: |
| 主线（探针主机） | 21935 | 71 | — | — | 1164 / 0 | 3.516 | 0.026 |
| `ENABLE_UNALIGNED = 0` | 22583 | 101 | 388.5 / 8 | 1126.5 / 8 | 2021 / 30 | 3.827 | 0.026 |
| `ENABLE_UNALIGNED = 1` | 24763 | 101 | 1404.5 / 8 | 1793.5 / 8 | 4063 / 30 | 3.648 | 0.026 |

- 每个核 8 块 RAM，全是内部 32 深的输出 FIFO：数据 128 位映射成 6 块 512×20 加 1 块 1024×8，
  `tkeep`/`wstrb` 16 位再 1 块。S1 上合计 30 块里另外 14 块是探针的两个 128 位行缓冲，深 256 与深 512 都是 7 块。
- 时序：`ENABLE_UNALIGNED = 0` 那份最差路径在 SoC 的 APB 响应（3.827 ns），S1 上的模块不在前列；
  `= 1` 那份最差路径是「512 深行缓冲读出 → 旋转与色键 → 写核字节移位器 → 写核输出 FIFO」，3.648 ns。
- 告警：两个核在 `= 0`/`= 1` 下各出 59/67 条，其中位宽截断 29/37 条、小存储映射成逻辑 5 条、
  「模块体内的 parameter 变成 localparam」25 条，都在厂商代码里，与 DDR 控制器那批告警同类。
- 复位：两个核的 `rst` 高有效、同步，只复位控制寄存器（数据寄存器不复位），没有收尾动作（3.2 节）。

这张表里两个核的 1515 XLR 是整机数，写核前面接着像素旋转与色键比较；只含本层的单独综合在 3.13 节，
写核的 XLR 与这里差 590（第五、六节）。

**`ENABLE_UNALIGNED` 取 0（D15）。** 首稿取 1，想让核自己处理非 16 字节对齐的地址。前期研究量到三处代价：
一是它会把非对齐地址直接发上总线（3.4 节的门控实验里 800 笔突发有 578 笔起始地址不按 16 字节对齐，
另一个种子 602 笔），DDR3 控制器没有验过这种地址；二是两个 16 位置的字节移位器（读核第 270 行、写核第 343~358 行），
两个核合计 3198 XLR 对 1515 XLR，多 1683；三是跨 4KB 拆行时仍然要做像素重排，省不掉 B4 的旋转器。
性能上两种取法的周期数完全相同（3.8 节）。所以取 0，非对齐由 B4 的像素旋转器处理。

### 3.2 排空：两个核不收尾，收场只能在流接口上做

引擎在事务中途被复位时，读方向迟到的 R 拍没人接，写方向的突发断在半截，
`Axi_Mux` 按信息 FIFO 的顺序一直等这一笔。两个核自己的复位是硬掐：读核把 `rready` 清 0
（`axi_dma_rd.v:612`），写核清空输出 FIFO 的读写指针（`:933-937`），都没有收尾动作。

参考了两个实现。龙芯仓 MTX 的两个事务引擎在超时之后走一个排空状态：
读方向保持接收准备、把在途数据吃到 `rlast`；写方向自己举 `wvalid`，
用字节使能全零的哑拍把欠总线的拍数补完，然后还要走一趟响应相收掉写响应
（`axi_wr_engine.v:82-153`、`:118-122`、`:185-218`）。iDMA 的后端把同一件事写成四行：
`dp_poison=1 / legalizer_flush=1 / w_dp_ready=1 / r_dp_ready=1`，
完成条件是数据通路全空，全程不复位任何子模块（`idma_error_handler.sv:355-367`）。

这两个参考的排空都写在引擎自己的 FSM 里，可以直接驱动 `m_axi_rready` 与 `m_axi_wvalid`。
本层的两个核是黑盒，`m_axi_rready` 在核内部，搬运层碰不到。所以本层的排空只能在流接口上做：

- **读方向**：搬运层把自己的 `s_axis_read_data_tready` 恒置 1 并把数据丢弃，直到 `tlast` 握手。
  核的输出 FIFO 是 32 深、半满节流（`axi_dma_rd.v:647,660`，对上游只开放 16 拍）；
  消费者恒 ready 时 FIFO 不会积起来，所以「恒 ready」足以让核把在途那一笔走完。
- **写方向**：搬运层自己按「描述符拍数 − 已送拍数」往核的写流里灌哑拍，
  四个像素的 X 字节最高位全打 1，经带内掩码就是 `wstrb = 0`；灌完再等状态。
  为此搬运层记住在途写描述符的总拍数与已送拍数，两个 12 位寄存器。

`drain_req` 做成电平请求、`drain_done` 做成单拍脉冲；排空态在两个方向都空闲时退出。
排空期间两个方向都不再收新提交，即使某个方向已经空了——否则刚排空的方向会被新描述符续上，
「两个方向都空闲」这个完成条件永远等不到。排空是幂等的：期间再来一次软复位只是让
`drain_req` 保持为高，状态机不动。

**一次请求只完成一次。** 控制层复位持续很久时，`drain_req` 可能就是复位电平本身，
在 `drain_done` 之后还要举很多拍。所以本层记一位「这次请求已经完成过」，`drain_req` 撤下才清：
完成之后请求还举着，不再重进排空、不再打 `drain_done`；而且 `drain_req` 举着的每一拍都不收新提交。
按电平重进的写法会在退出排空的那一拍放开门控，`drain_done` 每两拍打一次（第四节「排空请求按电平重进」）。

哑拍的最后一拍必须带 `tlast`。核在突发拍数用完而流上还没见到 `tlast` 时进
`STATE_DROP_DATA`（`axi_dma_wr.v:682-685`），一路丢流上的数据直到 `tlast`；
这期间写状态照常回来、门控放行下一个描述符，而核还没收完，**下一行的写流会被丢掉**。
这条约束对正常写流同样成立：B4 必须在每个写描述符的最后一拍给出 `tlast`。

反过来，流提前给 `tlast` 时核自己补尾：`STATE_FINISH_BURST`（`axi_dma_wr.v:701-732`）以 `wstrb = 0`、`wdata = 0`
把这一笔剩下的拍发完。所以排空其实只要一拍带 `tlast`、全打「不写」标记的哑拍，两个 12 位拍数寄存器可以省掉。
前期研究的原型副本把排空期的 `tlast` 恒置 1 验过：32 拍只送 8 拍后排空的用例与正常用例都通过，
补上的拍一个字节都没写。入库的 RTL 仍按「欠多少补多少」写（D29 原定案），这一条留作以后可选的简化。

### 3.3 超时：只报告不放弃，门限用板上实测定

两个核都没有超时逻辑：`DMA_ERROR_TIMEOUT` 在两个核里从未被赋值。
本层的语义是「只报告、不放弃」——某方向有描述符在途，且连续 `T` 个周期没有任何握手时，
打一拍 `tmo_evt` 并给出方向；搬运层不撤 valid、不动核，照常等状态回来。

门限 `T` 由控制层的寄存器给（I7），复位值取 4096 拍，100 MHz 下约 41 µs。
这个数来自板上实测。探针主机的 `TIMEOUT` 寄存器就是「有事务在途、连续这么多个周期没有任何握手即判超时」
（`rtl/bus/axi_probe_master.v` 第 15 行与第 268~277 行），与本层的超时同一个定义。
一个临时程序（不入库）在主线比特流上跑三端口满负载：扫描输出按水位取数，CPU 做 4 × 256 KiB 的拷贝，
S1 的探针以 192 拍突发（本层的 `AXI_MAX_BURST_LEN`）连续读或写 32768 笔。`TIMEOUT` 从 4096 往下扫
（4096、2048、1024、768、640、512、448、384、320、256、224、192），每档 3 轮，第一次超时即停：

| 方向 | 不超时的最低档 | 第一次超时 | 每轮周期数 | 同轮量到的其它端口 |
| --- | --: | --- | --: | --- |
| 读 | 224（3 轮全过） | 192，第 6141 笔报 `TIMEOUT`（`st=0x6`） | 约 826 万 | 扫描 `max_first` 78、`max_full` 244~254；S2 `max_wait_ar` 239~262、`max_wait_aw` 412~434 |
| 写 | 224（3 轮全过） | 192 那一轮打出 `RUN` 后串口再无输出 | 约 821 万 | 扫描 `max_first` 516~518、`max_full` 682~684；S2 `max_wait_ar` 420~427、`max_wait_aw` 435~436 |

写方向那一轮没有结果行，与探针超时后进 `S_HANG`、`valid` 不撤、写突发断在半截的行为一致
（`axi_probe_master.v` 第 29 行），但没有直接的超时行，所以写方向只取上界。
结论：这组负载下 S1 在 AXI 一侧最长的无握手空档读写都不超过 224 拍（读方向在 193~224 之间），
4096 留 18 倍以上。没有覆盖的：探针一次只跑一个方向、地址不递增，引擎读写同时在途时两者会互相挤，
B6 用真实引擎按同一口径复测。这次测量在 3.14 节独立复现过一次，两个门限档位相同。
每次上板前都重新烧比特流，实验结束后重新烧写并读回探针寄存器，`STATUS` 为 0、`TIMEOUT` 回到复位值 `0x0010_0000`。

定案初稿的依据不是这个数。初稿引的是「E5 量到 S1 地址等待最坏 607 周期、回归阈值 700，
由此最坏合法空档约 730 拍、4096 留 5.6 倍」；而 platform 第 06 章 5.2 节里的 590、607 是**仿真**中
CPU 替身（S2）在 S1 激进时的最大地址等待，700 是它的回归阈值，S1 自己的等待那一章没有量过。
复核时发现引错，才改做上面的板上测量。门限值没有变，依据换了。

**「握手」两侧都算。** 一开始只把本层一侧算作握手：描述符握手、读写流握手、状态脉冲。
定案的复核发现这与板上量法不是同一个口径——板上量的是 AXI 一侧。两者之间隔着核内 32 深
输出 FIFO：写方向最后一拍流进核之后，流一侧要等 FIFO 在 W 通道上排完、B 回来、状态出来
才有下一次握手，这一段是几段 AXI 空档之和；读方向从描述符握手到第一拍出流，
也跨过 AR 等待与首拍延迟两段。所以 224 拍框不住原来的定义。订正后的清零条件加上本方向
AXI 一侧的握手（读 AR、R；写 AW、W、B），只加不减，一个真正不响应的从机两侧都没有握手，照样报超时。
前期研究的原型加开关对照过：八个用例结果不变，计数器在正常用例里跑到的最大值从 5/4（读/写）降到 1/1，
换成定时从机（`RD_LAT=23 RD_BUB=12`）后读方向从 28 降到 24。判据里补了一条：
**正常与排空用例全程不得置超时位**。

合起来，计数器在四种情况下清零：复位、控制层清错误（`err_clr`）、该方向没有在途描述符、
该方向这一拍有任何握手（本层一侧的描述符、流、状态脉冲，加上 AXI 一侧的上述通道）。
计数到门限就停住；同一个描述符只报一次，中间有握手清零之后再次超时也不重报，
直到这个描述符完成或 `err_clr`。搬运层不撤 valid、不动核，等状态回来。

写方向另有一段两侧都没有握手的窗口：写核的 `awvalid` 要等写流的第一拍，
所以「写描述符握手 → 写流首拍」这一段的长短由 B3 发描述符的时机与 B4 的像素延迟决定，
不归总线。B3 定发出时机时要守住 `T`。

### 3.4 在途门控：读方向的「完成」不是状态脉冲

**门控在随机反压下的实测（前期研究，2026-09-26）。** 仓库外的搬运层骨架（两个核、描述符门控、带内掩码）
经真实 `Axi_Mux` 接一个 128 位、带 `wstrb`、1 MiB 的从机。测试台每次跑 400 个操作：从低 512 KiB 随机取源地址
（4 字节对齐）、1~640 个像素（每 7 个操作里有一个只有 1~6 个像素），截到不跨 4KB；目的在高 512 KiB，同样截断；
每个像素以约 3/8 的概率打「不写」标记，每 5 个操作里有一个全不打、一个全打。读、写两个方向并发：
写第 k 个操作时，读已经在取第 k+1 个。从机每个 ready/valid 以 3/8 的概率拉低；
`rndready` 两档让读流的消费者只有 1/4 的周期 ready。判据：读回的像素逐个对影子内存，
结束后目的区 131072 个字逐字对影子内存；每个描述符恰好一笔突发、不跨 4KB、`WLAST` 位置对；
契约按原文判，上一笔没结束时下一笔的 valid 拉高一个周期记一次违例。

- 五个正常配置全过，门控下两个方向的违例都是 0；去掉门控的两个注错版，读方向 2.8 万多个违例周期、写方向 8 千多个。
- **`max_inflight` 在注错版里仍然是 1。** 从机一次只收一个地址，第二个 `arvalid` 拉起来了也握不上手，
  按握手计数的在途笔数永远到不了 2。第一版测试台正是这样写的，两个去门控的注错版都报了 PASS；
  改成按 valid 判之后才见红。所以本层的在途判据一律按 valid 判，`max_inflight` 只作观测、不作判据。
- `rndready` 两档总周期从 3.3 万涨到 7.2 万、数据仍全对：消费者慢时读核在输出 FIFO 半满后拉低 `rready`。
  到了真总线上，`Axi_Mux` 按读地址的顺序回数据，S1 的 `rready` 一低，排在后面的扫描输出与 SoC 的读数据也跟着停，
  所以读流的消费者（B4 的行缓冲写口）必须恒 ready，读描述符只在目标行缓冲有整行空间时发出（D23）。
  本层的仿真把「读数据阶段 S1 的 `rready` 恒为 1」列成判据（3.11 节的 `rrb`）。
- `inj_tkeep_u1` 与 `unal_addr` 两列分别见 3.7 节与 3.1 节。

这组实验只证明了总线一侧：门控下总线上没有第二笔。下面这件事总线一侧看不出来。

D3 规矩 2 原文写「搬运层在上一个描述符的状态回来之前不发下一个，状态在数据全部交接之后才出」。
前半句对，后半句与读核的实际行为不符。

只例化一个读核与一个无反压的从机，一笔 4 拍读，消费侧按 `SINK_DLY` 做 1/(SINK_DLY+1) 的 ready，
记录四个时刻（单位：拍，相对于描述符握手）：

| `SINK_DLY` | AR | `rlast` | 状态脉冲 | 流末拍握手 | 状态 − `rlast` | 流末拍 − 状态 |
| --: | --: | --: | --: | --: | --: | --: |
| 0（恒 ready） | 2 | 7 | 8 | 9 | 1 | 1 |
| 1 | 2 | 7 | 8 | 13 | 1 | 5 |
| 3 | 2 | 7 | 8 | 19 | 1 | 11 |
| 15 | 2 | 7 | 8 | 63 | 1 | 55 |

状态脉冲在总线末拍收到后的第 1 拍就出来了，而末拍数据还要经核内的输出 FIFO
（`axi_dma_rd.v:635-645` 写入、`:672-679` 弹出）才在 `m_axis_read_data_tvalid` 上出现。
消费者越慢，两者差得越远，15 那一档差 55 拍。

后果落在上下文寄存器上：寄存器在下一个描述符握手那一拍改写，所以只看状态就放行的话，
上一个描述符的最后几拍会被算成下一个的。这是静默错数据，总线侧的判据抓不到——
去掉读门控的注错版在总线上量到 4 个违例周期，而像素读流上已经读到了命令取数区的字 `0x200`。

所以门控条件订正成：读方向要**状态脉冲已捕获且读流 `tlast` 已握手**，缺一不可；
写方向没有这个问题，写核的状态在 `bvalid` 之后才出（`axi_dma_wr.v:757-771`），
状态回来时本描述符的 W 拍早已全部交接完，所以只看状态。

### 3.5 上下文寄存器：附带信息放哪

要在描述符之外附带的有三样：目标缓冲号（读流上要给行缓冲）、命令索引（错误的归属）、
来源（这一笔是像素读还是命令取数，决定读流往哪边分发）。写方向另要存
I2 写描述符的「是否本命令最后一行」，控制层靠它判断一条命令的写回全部完成。

核本身能带的很有限。读向描述符口的 `tag` 只有 4 位，且核只把它送**状态口**
（`axi_dma_rd.v:340` 进、`:525` 出），不上数据流；描述符口的 `id`/`dest`/`user` 会搬到数据流上，
但在 `AXIS_ID/DEST/USER_ENABLE = 0` 时被强制置零（`:653-655`）。写向描述符口上只有
`addr`/`len`/`tag`，没有 `id`/`dest`/`user`。

三样都放搬运层自己的上下文寄存器，每个方向一组。理由是每方向只有一笔在途，一个寄存器就够；
而目标缓冲号要在数据流上陪跑整笔，命令索引只回状态口，两者挤同一个 4 位 `tag` 会互相顶掉。

上下文寄存器成立的前提就是 3.4 节那条时序订正：它不能在上一笔的读流还没交接完时被改写。
命令取数那一路的目标缓冲号没有意义，装入时固定写 0，免得上一笔的残值漏进状态口。

### 3.6 读侧仲裁与读流分发

命令取数与像素读共用一个读核，命令取数优先（D8）。做法是把两个请求方并到读核的描述符口前面：
在读核的描述符 `ready` 为高、且门控开着的那一拍组合仲裁，命令取数有请求就选它；
两个请求方各出一个 `ready`，像素读的 `ready` 再与「命令取数没有请求」相与。

读流的分发由上下文寄存器的来源位选：命令取数的拍子走命令缓冲口，像素读的走行缓冲口
并带上目标缓冲号。一条读流只可能属于一个请求方，因为一笔在途。

没有采用的两种分发：用核的 `tag` 查表——`tag` 4 位、只回状态口，做不成流上的实时选择；
在读流上带 `dest`——要打开 `AXIS_DEST_ENABLE`，而这个信息搬运层本来就有。

判据落在仿真 `normal` 用例里：两个请求方同时举手时，命令取数的地址必须先上总线
（按 `araddr` 的先后判）；两条读流各自的数据、缓冲号、命令索引都要对得上。

### 3.7 W 通道带内掩码

需要按像素不写的有三处：色键命中、行首行尾不属于本行的像素、排空时补的哑拍。
像素通路输出像素的 X 字节最高位置 1 表示「这个像素不写」；写核与 `Axi_Mux` 之间
按每个像素的这一位把该像素的 4 位 `wstrb` 清零，再把 X 字节清零后上总线。
四个像素是一段 `generate` 循环，核的源码一字不改。

没有走的三条路：改 `axi_dma_wr.v` 让中间拍也与 `tkeep` 相与（违反 D3，而且 `tkeep`
在核里还参与帧尾判断，第 358、571、838 行要重验）；把「不写」塞进流的 `tkeep`
（写核中间拍根本不看它）；色键 BLIT 也读目的、在像素通路里把命中的像素换回原值
（D7 第二行的读写避让就失效了，机体类每行约多 35 周期）。

第二条前期研究量过：3.4 节门控实验的 `inj_tkeep_u1` 把「不写」从带内标记改成在写流的 `tkeep` 上挖洞，
结束比对报 `22825 dst words differ, first at 0x00081188 got 00c7e87f want c7205dca`——
应当保持原值 `c7205dca` 的像素被写成了源像素 `00c7e87f`。

- 整屏 FILL 一行 126.0 周期，总览第 1 节的 125.6 是它的手算值。
- 硬件侧上限按总览第 1 节的算法：145 万 ÷ 1108 ≈ 1310 颗，与原估算的约 1300 一致。

**注错：一行跨 4KB。** 同一个测试台把整屏 FILL 的起点挪到 x = 700，每行 1600 字节跨过 4KB 边界，写核把它拆成两笔：

```text
UNAL=0 MODE=3 SRC_OFF=0 DST_OFF=0 FETCH_B=0 PIX_LAT=4 CMD_GAP=2: cmds=480 rows=480 reads=0 cycles=63360 per_cmd=132.0 per_row=132.0 viol=0/9120
```

写方向 9120 个违例周期：拆出的第二笔 `awvalid` 在第一笔写响应回来之前就拉起了。
这就是 3.1 节「核会自己拆、而且不等上一笔」的实测，也说明 D3 规矩 1（几何层保证不跨 4KB）对写核同样必要。

这个模型用的是前期研究的骨架，不是入库的 `engine_mover.v`：骨架的读门控只看状态（3.4 节订正之前的写法），
超时与排空也还没有。入库版本读方向多等一次 `tlast` 握手，按 3.4 节的表，消费者恒 ready 时
末拍握手比状态晚 1 拍，估计每笔读晚 1 拍、每颗多约 32 个周期（16 行 × 2 笔读，约 3%）。这是推算，没有在模型上重跑，
B6 按真实引擎复测时一起核对（第六节）。

**MTX 的收场动作。** 排空是 FSM 里的一个状态，写向 `StDrain = 3'd4`（`axi_wr_engine.v:82-86`），
出口只有两个：`w_fire && m_axi_wlast → StResp`、`tmo_hit → StIdle`（`:146-147`）。排空期的 W 通道由引擎自己举 valid：

```
axi_wr_engine.v:118  assign m_axi_wvalid = ((state == StData) & d_valid) | (state == StDrain);
axi_wr_engine.v:120  assign m_axi_wdata  = (state == StDrain) ? 32'b0 : d_data;
axi_wr_engine.v:122  assign m_axi_wstrb  = (state == StDrain) ? 4'b0000 : 4'b1111;
```

字节使能全零就是「哑拍一个字节都不写」的依据。排空之后还要走 `StResp` 把写响应收掉。
`abort_q` 在进排空那一拍置位、收新命令时清（`:186-187`），它拦住完成脉冲（`:212`），也拦住继续发下一条突发。
读向是镜像：`m_axi_rready` 在排空期恒 1（`axi_rd_engine.v:109`），数据一律丢弃（`:189-190`）。
两个方向进排空时让超时计数重新起算（`axi_wr_engine.v:215-216`，`axi_rd_engine.v:195-200`），
否则带着已经翻上去的计数器进排空，第一拍就判「排空也超时」——这一条在 MTX 里必要，因为它的排空超时会放弃；
本层排空不放弃，所以不需要。

**iDMA 的同一件事。** 排空态 `LEG_FLUSH` 的行为只有四行（`idma_error_handler.sv:355-367`）：
`dp_poison=1 / legalizer_flush=1 / w_dp_ready=1 / r_dp_ready=1`，完成条件是 `!dp_busy_i`（buffer 与读、写数据通路全空）。
写侧的 `dp_poison` 落到 `idma_axi_write.sv:203-212,220` 是 `w.data='0; w.strb='0`，而 `w_valid` 不受影响——
「beat 照发、字节使能全 0」两边是同一个动作。iDMA 全程不复位任何子模块
（`idma_dataflow_element.sv:43-44` 把 FIFO 的 `clr_i`/`flush_i` 硬接 0），用排空态收场。
不借鉴的两处：一是它没有超时，全 `src/` 匹配 `timeout|watchdog|TIMEOUT` 为 0，论文全文出现 0 次，
出错后停在 `WAIT` 等软件写 `idma_eh_req_i`，从机死了就永久停住；二是它的多笔在途前提
（`NumAxInFlight > 1` 是 elaboration 断言，`idma_backend.sv.tpl:1046-1049`），本层每方向一笔，那条 ABORT 降级分支在这里恒不成立。

`AxiRamRead`/`AxiRamWrite`（`test_axi_dma_rd.py:37`）。逐条读下来：

| 在途契约 | 上一笔没结束（读看 `rlast` 握手、写看 `bvalid` 握手）时下一笔的 `arvalid`/`awvalid` 拉高的周期数恒为 0（按 valid 判，不按握手计数，3.4 节）；**上一笔读流的 `tlast` 还没握手时下一个读描述符不得发出，且每条读流拍子带的目标缓冲号与命令索引必须属于产生它的那个描述符**；每笔地址 16 字节对齐、不跨 4KB、一个描述符恰好一笔；`WLAST` 与 `AWLEN` 对得上；读数据阶段 `rready` 恒为 1；随机反压下不死锁；去掉门控的注错版必须见红 |
| 写掩码（机制） | 带内标记的像素 `wstrb` 清零、X 字节清零后上总线；中间拍稀疏、首末拍、整行全跳过与排空哑拍都不写；带内掩码旁路的注错版必须见红 |

| 复位（仿真） | 读、写突发中途软复位与控制层复位各一例：排空完成、总线上没有断掉的突发（R 拍全部收完、`WLAST` 对账、写响应全部收到）、之后能再次提交；**排空期间不得接受新提交**；排空旁路的注错版必须见红；**请求完成之后继续举着时 `drain_done` 只打一次、请求撤下之前不得接受新提交，按电平重进的注错版必须见红** |
| 从机回归 | `sim/axi_probe/` 与 `sim/axi_mux_guard/` 的判据不变（`sim/display/` 也用同一个从机，一并回归）；**定时模式与前期研究校准用的从机逐拍相同（主机停拍不卡死、空拍位置、读首拍延迟），用自己的测试台验** |
| 单独综合 | XLR 与 RAM 和两个核在整机里的数（3.1 节）对账；**综合顶层必须观测被测的每一个输出位，先证明数字是本层的再对账** |

### 3.12 从机补四样与回归

`sim/axi_probe/axi_ram_model.v` 是四个仿真共用的从机。原来的它只有 4096 拍（64 KiB）取模、
没有 `wstrb` 端口、错误只由 `awlen/arlen > MAX_LEN` 决定、只有随机反压。
本批按 D13 补四样，四样都是新增参数、默认值返回原行为：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `MEM_WORDS` | 4096 | 存储字数，地址取模改用它；4 MiB 时取 262144 |
| `STRB_EN` | 0 | 0 按整字写（原行为）；1 按 `wstrb` 逐字节写 |
| `ERR_LO`/`ERR_HI` | `0xFFFF_FFFF`/`0` | 落在这个字节区间的突发回 `SLVERR`，默认值让判断恒为假 |
| `TIMED` | 0 | 0 随机反压（原行为）；1 定时模式，用 E4 的校准值 `RD_LAT=23 RD_BUB=12 WR_BUB=6 B_LAT=1` |

`wstrb` 是一个绕不开的新端口，而三个既有测试台不接它。所以它与 `STRB_EN` 相与：
默认配置下走原来那条整字写，`wstrb` 一个字节都不读，端口悬空也不影响。
定时模式的分支放在原来那条随机反压表达式之前、且默认时恒为假，
这样 `TIMED=0` 时 `stall(0)` 的调用次数与顺序与改前完全一样，随机序列不会错位。

回归的做法：仓库外的镜像里放一份改过的从机与三个套件的副本，
把从机换成仓内原版再跑一遍，两次的完整输出逐字节比对。三个套件、
包括每一个注错用例的报错条数，都逐字节相同。复核时又在提交 `1ea9fc3` 的干净工作树（原版从机）上
跑一遍三个套件，与工作区的输出逐字节比对，结论相同。

**定时模式在复核时修了三处。** 上面的回归只覆盖默认参数，`TIMED=1` 在仓库里没有任何用例。
把前期研究的校准测试台（探针主机经 `Axi_Mux` 打从机，3.8 节）换上仓内这一份从机重跑，
与校准用的那一版从机逐项对照，查出三处不同（过程见第四节「从机的定时模式」）：

1. 写方向按「已收拍数是 `WR_BUB` 的倍数」拉低 `wready`：主机恰好在那一拍不举 `wvalid` 时，
   拍数不再变化，`wready` 永远为 0，写通道卡死；主机不停时空拍又晚一拍。
   改成只在收满 `WR_BUB` 拍那次握手之后空一拍。
2. 进写数据态的第一拍收不了，比校准用的从机多一拍；定时模式下 AW 握手当拍就把 `wready` 置 1。
3. 读地址先入队、下一拍才出队，这一拍没算进 `RD_LAT`，首拍晚一拍；出队时改装 `RD_LAT − 1`。

三处都只在 `TIMED=1` 的分支里，默认参数的输出不变（上面的逐字节回归在修改之后重跑过）。
修好之后，校准测试台在 `RD_LAT/RD_BUB/WR_BUB/B_LAT = 23/12/6/1` 与 `23/12/5/3` 两组参数下的输出
与校准用的那一版从机逐字节相同，也就是 3.8 节记的写 9.02/12.02/26.02/306.06、
读 29.02/32.02/45.02/305.06 个周期。回归写成 `sim/engine/mover/tb_slave_timed.v`，进 `run.sh`。

### 3.13 单独综合

仓库外建了一个只含本层的 Efinity 2026.1 小工程，顶层自己造激励：LFSR 生成描述符，
一个常 ready 的 AXI 从机回数据与写响应，写流按描述符拍数供数并打「不写」标记，
每 256 拍拉一次 `drain_req` 把排空那条路也编进去。设备信息段与工程参数从主线的
`gfx2d_ti60.peri.xml`、`gfx2d_ti60.xml` 原样搬，时钟约束是 `create_clock -period 10.000 clk`。

单独综合的顶层要让综合删不掉被测的任何一位，照 B1 的做法（engine 第 01 章 3.8 节）：
一个 128 位 LFSR 给出从机的读数据、写流的数据与 `tkeep`、描述符的各字段；
被测的每一个输出（读流与命令取数流的数据、`tkeep`，W 通道的数据与 `wstrb`，AR/AW 的地址与长度，
状态、排空与超时）按位异或进一个 128 位观测寄存器，观测寄存器再回灌进 LFSR。
第一版顶层只观测了握手与状态这些控制位，两个核的输出 FIFO 被整块删掉，
量出来的规模不是本层的（第四节「单独综合的顶层没有观测数据位」）。

四步（map、interface、pnr、pgm）全 PASS，数据在第五节。

## 四、遇到的问题

### 读核的状态脉冲早于末拍握手，只看状态会静默错数据

**第一现场**

一笔 4 拍读，消费侧恒 ready，实测四个时刻（相对描述符握手，单位拍）：

```
t_desc=2 t_ar=4 t_rlast=9 t_st=10 t_tlast=11
AR-desc=2 RLAST-AR=5 ST-RLAST=1 TLAST-ST=1 TLAST-RLAST=2
RESULT: HAZARD (状态脉冲早于末拍握手 1 拍)
```

把消费侧做成每 4 拍、每 16 拍只 ready 一拍，同一个判据报的是
`TLAST-ST=5`、`TLAST-ST=55`。

**解读**

`t_st` 是读核状态脉冲那一拍，`t_tlast` 是末拍数据在流接口上被消费者收走那一拍。
`ST-RLAST=1` 说明状态在总线末拍收到的下一拍就出来了，这是核的写法决定的：
末拍被核内部接收那一拍生成状态、同拍压进输出 FIFO，而那一拍数据还要经 FIFO 弹栈
才出现在 `m_axis_read_data_tvalid` 上。消费者越慢，`TLAST-ST` 越大。

**定位**

先怀疑测试台的观测方式：把观察块从 `posedge` 换成 `negedge` 之后数字才稳定下来，
说明第一版读数被边沿抢了。稳定之后这个先后仍然存在，而且随消费者节拍单调变大，
指向核内部的 FIFO 而不是观测。

**根因与修法**

D3 规矩 2 的「状态在数据全部交接之后才出」对写核成立、对读核不成立。
读方向的门控改成「状态脉冲已捕获**且**读流 `tlast` 已握手」。
原判据为什么没有覆盖到它：总线侧的判据只看 `arvalid`/`awvalid`，
而这时总线上的上一笔确实已经收完（`rlast` 早就握手了），违例计数只有 4；
错的是流一侧的归属。注错版里总线侧几乎看不出问题，流上却已经错到另一个请求方的区域。

### 测试台把同一个描述符发了两遍

**第一现场**

原型跑第一个用例就挂住，统计里 `ar` 数远大于描述符数，写方向一次都没起来：

```
STAT rd_viol=0 wr_viol=0 rd_out=0 wr_out=0 ar=6666 aw=0
RESULT: FAIL (看门狗：仿真没有自己结束)
```

**解读**

`ar=6666` 说明读核被反复喂了描述符。`aw=0` 说明流程卡在第一个用例的读侧，
根本没走到写。

**定位**

驱动任务的写法是「举 `valid`，等 `ready` 拉高，再等下一个 `ready`」。
问题在第二个「等」：握手发生在第一个 `ready` 拉高的那一拍，而握手之后门控立刻把
`ready` 拉低；任务却还停在循环里等 `ready` 再拉高——那要等这一笔整个做完。
于是同一笔描述符被压在门口反复接受。

**根因与修法**

驱动任务改成按**握手计数**判定：「举 `valid` 前记下计数，等到计数变了就撤 `valid`」。
原判据为什么没有覆盖到它：这不是被测模块的缺陷，是激励自己的缺陷。
一条经验：外部命令一条都没动而 `ar` 数暴涨，先看激励是不是把同一笔发了多次。

### Axi_Mux 没有 BRESP 端口，写响应在仿真里悬空

**第一现场**

写 `SLVERR` 的用例里，从机确实回了非 OKAY，被测的状态口却报没有错：

```
DBG T=385000 wr_fire=0 core_st_v=0 core_err=0000 | st_v=0 err=0 cidx=11 bresp=zz bvalid=1
ERR 写响应 SLVERR 但状态里没有报错
```

**解读**

`bresp=zz` 是关键：写响应是**高阻**。核采到一个 z，自然不认为它非 OKAY，
状态里的错误位一直是 0。

**定位**

顺着 `m_axi_bresp` 往回查，它被接在 `Axi_Mux` 的端口上。查仓内 `Axi_Mux.v` 的端口表：
它有 AW/W/B 三个通道的 ID、VALID、READY，**没有 BRESP**。`rtl/README.md` 的 vendor 表
里已经登记过这件事：「没有 BRESP 端口，顶层把控制器的 bresp 并接给各主机」。
测试台照着「所有 AXI 信号都过 mux」写，把这条漏了。

**根因与修法**

测试台里把写响应直接从从机接给被测，与顶层做法一致。
原判据为什么没有覆盖到它：读方向的 `RRESP` 在 mux 上有端口、走通了，
写方向一路顺下来没被怀疑；而「高阻」在波形里长得像 0，只有打出来才看得见。

### 超时用例自己在主机与 mux 之间造闸门，把总线留在不自洽的状态

**第一现场**

超时用例解放之后那一笔永远做不完：

```
ERR 放开之后这一笔没有完成
ERR 超时用例收尾仍有在途读 1
STAT rd_out=1 tmo=1
```

跟踪打出来：`m_arvalid` 在被按住期间从 1 变成 0，而从机侧一次 AR 都没收到。

**解读**

`m_arvalid` 是主机的输出，它掉下去只有一个原因：主机认为握手已经发生。
而主机看到的 `m_arready` 来自 mux，mux 的 `S_AR_Ready` 是
`Act_Cnl_List & {ACN{M_A_Ready}}`——授权位与下游 ready 相与。看住下游的 ready，
主机这一侧就不该认为握手了。

**定位**

第一版的「按住」是在主机与 mux 之间造一个闸门：喂给 mux 的 `I_M_AR_READY` 接 0、
喂给从机的 `arvalid` 也接 0。这两个是**两件事**：mux 因为下游 ready 是 0 而不给主机授权，
但它自己的主机侧 `arvalid` 照常往上发；从机这边又被挡着看不到地址。
放开之后 mux 的内部信息 FIFO 与下游对不上，总线留在一个谁也不认的状态。

**根因与修法**

改成用从机自带的 `hold_ar`/`hold_aw`（模型里本来就有，用于「已授权之后的持续反压」）：
从机把 `arready` 按住，mux 看到的就是真正的下游不 ready，两侧自洽。
原判据为什么没有覆盖到它：这是激励的问题，不是被测的问题；
而且它只在这一个用例里出现，其他用例的闸门恒通过、看不出来。

### 写在途门控的判据，用「发一笔等一笔」的写法验不到

**第一现场**

去掉写门控的注错版一开始报了 PASS：

```
inject_nogate_wr: RESULT: PASS
```

**解读**

门控的作用是「上一笔的状态没回来之前，第二个写描述符不得被接受」。
而测试台原来的写法是每一笔写之后都 `wait_wr_status`——第二个描述符本来就在状态之后才举手，
门控有没有都看不出来。

**定位**

读方向没有这个问题，因为读流消费完（`tlast` 握手）与状态回来之间有一段，
测试台的读任务等的是流、不是状态，于是下一个描述符确实会在状态之前举手。
写方向少了这一段，必须专门造一次背靠背的举手。

**根因与修法**

在 `normal` 用例里补一段：发完一笔写之后立刻举第二个写描述符，只举 5 拍，看它会不会被接受。
第一版举了 400 拍，结果和门控放开那一拍抢同一个边沿（门控在 `wr_busy` 清零前一拍就放开），
变成时好时坏；改成只举 5 拍之后确定：门控下这 5 拍 `wr_ready` 恒 0，
注错版第一拍就被接受。原判据为什么没有覆盖到它：用例的写法把要验的性质绕过去了。

### 单独综合里一处多驱动

**第一现场**

Efinity 在 elaboration 阶段就报错：

```
[EFX-0010 VERI-ERROR] net 'm_bready' is constantly driven from multiple places (VDB-1000)
[EFX-0010 VERI-ERROR] found another driver here (VDB-1001)
[EFX-0021 ERROR] Elaboration of module 'b2_top_mover' failed.
```

**解读**

综合顶层的从机模型里写了 `assign m_bready = 1'b1;`，而被测的 `engine_mover` 这一端
`m_axi_bready` 是**输出**，它也在驱动同一根线。

**定位**

仿真里 iverilog 只在多驱动时报一条告警、不报错，所以这条错误是在综合阶段才第一次露出来。
顶层从机是照着「主机给的信号都自己造」写的，把 `bready` 也当成了要造的一路。

**根因与修法**

删掉那一行，让被测驱动。原判据为什么没有覆盖到它：仿真能跑，
综合才是第一现场；同类错误在 B1 那种纯组合模块里不会出现，这一批才第一次遇到。

以下三个问题是复核时查出来的。

### 排空请求按电平重进

**第一现场**

在 `drain` 用例里补一组：请求完成之后继续举 40 拍，同时一个像素读描述符全程举着。改之前的 RTL：

```
ERR 请求一直举着时 drain_done 打了 2 次，应为 1 次
ERR 排空请求还举着就接受了新的读描述符
```

**解读**

进排空的条件是 `drain_req && !draining`。完成那一拍 `draining` 清 0，下一拍请求还举着，
条件又成立。中间那一拍 `draining = 0`，门控是开的，举着的描述符被接受；
接着重进的排空又把它吃掉，再打一次 `drain_done`。

**定位**

原有三组排空激励都用同一个任务：看到 `drain_done` 半拍后就撤请求，
正好落在「退出」与「重进」之间，碰不到这一段。D29 的原文写的是「上升沿进排空态、`drain_done` 只发一次」，
前期研究的原型与入库 RTL 都按电平写了。控制层复位持续很久时，`drain_req` 可能就是复位电平本身，
这一段在真实使用里一定会出现。

**根因与修法**

记一位「这次请求已经完成过」，`drain_req` 撤下才清；请求举着的每一拍都不收新提交（3.2 节）。
旧写法留作注错位 4（`inject_drain_level`），必须见红。原判据为什么没有覆盖到它：
判据写了「排空期间不得接受新提交」，排空之后请求还没撤的那一段不在「排空期间」里，没有人写。

### 从机的定时模式

**第一现场**

从机的 `TIMED=1` 在仓库里没有任何用例。把前期研究的校准测试台换上仓内这一份从机，
与校准用的那一版从机对照（`RD_LAT/RD_BUB/WR_BUB/B_LAT = 23/12/5/3`）：

```
                校准用的从机          仓内从机
N=16   write    29.02                28.02
N=256  write    317.06               316.06
N=1    read     29.02 (first 28)     30.02 (first 29)
N=256  read     305.06               306.06
```

再写一个直连从机的小测试台，主机在第 6 拍握手之后停一拍：

```
ERR 主机在第 6 拍之后停一拍，写通道卡死（只写了 6 拍）
```

**解读**

写方向差在空拍的时机，读方向每一档都晚 1 拍。卡死那一条是真 bug：真实写核的输出 FIFO 一空，
W 通道就会停一拍。

**定位**

- 写方向：`wready <= !(wbub != 0 && wbub % WR_BUB == 0)`，`wbub` 只在握手时加一。
  拍数到了 `WR_BUB` 的倍数、而那一拍主机没举 `wvalid`，拍数就不再变，`wready` 永远是 0。
  校准用的从机多一个条件（`&& wready && wvalid`），只在那次握手之后空一拍。
- 写方向另一拍：校准用的从机在 AW 握手当拍就把 `wready` 置 1，仓内这一份要到写数据态才开始算。
  经过 `Axi_Mux` 时这一拍被遮住，直连时看得出来。
- 读方向：仓内从机的读地址先入队、下一拍才出队并装 `rwait`，校准用的那一版在握手当拍装。

**根因与修法**

照校准用的从机改（3.12 节），三处都只在 `TIMED=1` 的分支里，默认参数的输出逐字节不变。
回归写成 `tb_slave_timed.v`，期望值都是在校准用的从机上用同一个测试台量出来的；
改之前的从机在它上面三条全红。原判据为什么没有覆盖到它：从机回归的判据只写了
「默认参数下三个套件不变」，新增的定时模式没有自己的判据。

### 单独综合的顶层没有观测数据位

**第一现场**

第一版单独综合：两个核合计 706 XLR、0 块 RAM（`use-logic-for-small-mem = 0` 时 440 XLR、3 块），
与 3.1 节整机综合里两个核的 1515 XLR、16 块对不上。当时的记录把 0 块解释成
「32 深输出 FIFO 被映射成了逻辑」，并记为「无法归因」。

**解读**

两个核的输出 FIFO 各是 32 × 145 位（数据 128、`tkeep` 16、`tlast` 1）。映射成逻辑的话，
光存储就要 4640 个 FF；而报告里带 FF 的 XLR，`u_rd` 一共 95 个（纯 FF 37、LUT 加 FF 48、加法器加 FF 10），
`u_wr` 一共 144 个，装不下。
FIFO 不是变成了逻辑，是被删掉了。

**定位**

综合顶层的观测输出 `dout` 只异或了握手、`tlast`、状态这些控制位，
`rs_tdata`、`fs_tdata`、`m_axi_wdata`、`m_axi_wstrb`、AR/AW 地址一位都没有接出来；
从机回的读数据是 `{96'h0, lfsr}`，高 96 位恒为 0。FIFO 存的正是这些位，没有人看，综合就删了。

**根因与修法**

顶层改成 3.13 节的写法，每一个输出位都进反馈环。重跑之后两个核 897 XLR、**16 块 RAM**，
RAM 与 3.1 节的整机数逐块对上（每个核 8 块）。XLR 里 `u_rd` 361 对整机的 388.5，`u_wr` 536 对 1126.5：
写核差 590 XLR。3.1 节那次是整机编译，写核前面接着像素旋转与色键比较，整机优化会跨层次搬动逻辑，
那次的工程与报告已经不在，这一段差距本批无法归因，两个核的规模以本批单独综合为准、B6 整机编译再登记一次。
原判据为什么没有覆盖到它：「单独综合」一行只要求「登记数字并对账」，没有要求先证明数字是本层的——
一份被剪过的数也能「登记」。

下面一个问题是验收时查出来的。

### 两个核的入库副本是 CRLF 行尾，与上游不是逐字节相同

**第一现场**

从 GitHub 按提交 `516bd5d` 取原始文件，与 `rtl/vendor/verilog-axi/` 里的副本比：

```
axi_dma_rd.v ... differ: char 3, line 1
入库副本  30337 字节  md5 1fbed6e1…    上游  29645 字节  md5 d483e1b3…
入库副本  42326 字节  md5 676dd755…    上游  41384 字节  md5 c483b8ad…
```

**解读**

差的字节数正好是行数：`axi_dma_rd.v` 多 692 个、`axi_dma_wr.v` 多 942 个、`LICENSE` 多 19 个 `\r`。
去掉 `\r` 之后三个文件与上游逐字节相同。内容一个字没改，只是行尾从 LF 变成了 CRLF。

**定位**

副本取自研究工作区里的一份上游克隆。那份克隆在 Windows 上检出，全局 `core.autocrlf=true`，
索引里是 LF、工作区是 CRLF（`git ls-files --eol` 显示 `i/lf w/crlf`）。开发时核对的「与上游 MD5 相同」，
比的也是这份转换过的工作区文件，所以两边一起错、比对通过。本仓的 `.gitattributes` 是 `* -text`，
不做行尾转换，CRLF 会原样进库。

**根因与修法**

三个文件改用上游提交里的 blob（`git cat-file -p 516bd5d:rtl/axi_dma_rd.v` 等）重写，
现在它们的 git blob 与上游相同（3.1 节）。`sim/engine/mover/run.sh` 重跑仍是 15/15，行尾不影响功能。
原判据为什么没有覆盖到它：「与上游相同」拿的参照物本身被转换过；从 vendor 取第三方文件时，
参照物要取 git 对象（`git cat-file`、按提交的原始下载），不能取 Windows 上检出的工作区。

统计字段的含义：`rd_viol`/`wr_viol` 是按 valid 判的在途契约违例周期数，

`tmo` 是超时脉冲数。四个正常用例这七项里除 `tmo`（`timeout` 用例本来就该报一次）外全为 0。

### 从机回归

补过四样的从机换进仓库之后，三个套件的完整输出与换回原版逐字节相同：

```text
axi_probe     SIM OK: 5/5 cases as expected
axi_mux_guard SIM OK: 17/17 checks as expected
display       SIM OK
```

### 单独综合

同一份 RTL 在两种小存储策略下各综合一次，四步都 PASS。XLR 是器件占用，
RAM 是 `EFX_RAM10` 块数，时序是 `core_clk`（100 MHz）的余量：

| 构型 | `u_mover` XLR | 片上 RAM | `u_rd` XLR / 块 | `u_wr` XLR / 块 | setup (ns) | hold (ns) | 告警 |
| --- | --: | --: | --: | --: | --: | --: | --: |
| 与主线同参数（`use-logic-for-small-mem = 64`） | 1171.5 | 16 | 361 / 8 | 536 / 8 | 5.187 | 0.026 | 76 |
| `use-logic-for-small-mem = 0` | 898.5 | 19 | 258 / 9 | 366 / 10 | 5.206 | 0.027 | 71 |

XLR 与 RAM 取 Efinity 的 `hier_util` 报告；`u_mover` 一列是本层整块（两个核加仲裁、门控、排空、超时与掩码），
不含综合顶层自己的激励与观测逻辑。告警全部落在两个核与综合顶层上，`engine_mover.v` 自身 0 条。
最差 setup 路径从排空补拍的计数器 `wr_beats_sent` 到写核输出 FIFO 的写使能，14 级逻辑、4.467 ns。
hold 0.026 ns 与主线同量级，整机接入后在 B6 复测。

第一行是主线参数下的数：两个核合计 897 XLR、16 块 RAM，**RAM 与 3.1 节整机综合的 16 块逐块对上**
（每个核 8 块：输出 FIFO 的数据 128 位是 6 块 512×20 加 1 块 1024×8，`tkeep`/`wstrb` 1 块）。
XLR 里读核 361 对整机的 388.5，写核 536 对 1126.5。写核那 590 XLR 的差距来自 3.1 节那次的测法：
那次是整机编译，写核前面接着像素旋转与色键比较，整机优化会跨层次搬动逻辑；那次的工程与报告已经不在，
这一段本批无法归因。两个核的规模以本批这一行为准，B6 整机编译再登记一次。

复核之前这里登记的是 706 XLR、0 块，是第一版综合顶层把两个核的输出 FIFO 剪掉之后的数（第四节）。

### 上板验证

超时门限那一条独立重做了一次，读写两个方向各烧一次比特流。

读方向：`T` 从 4096 往下扫 11 档、每档 3 轮，32768 笔一笔不差。`T = 224` 三轮全过；
`T = 192` 在第 4472 笔报 `TIMEOUT`（`st = 0x6`）。同轮量到扫描输出 `max_first` 78、
`max_full` 244，guard 的 `max_wait_ar` 243、`max_wait_aw` 412，每轮约 8.2 M 周期。

写方向：同样的 11 档 × 3 轮，`T = 224` 三轮全过（`scan_first` 518、`scan_full` 684、
`guard_ar` 420~425、`guard_aw` 435~436，每轮约 8.2 M 周期）；`T = 192` 那一轮打出 `RUN` 之后
串口再无输出，与探针超时后进 `S_HANG`、`valid` 不撤、写突发断在半截的行为一致，
所以写方向只取上界。

两次都先重新烧写比特流，结束后重新烧写并读回探针寄存器，`STATUS` 为 0、`TIMEOUT` 回到复位值。
原始串口输出存在研究工作区的 `board/s1GapProbe/logs/`。

结论：这组负载下 S1 在 AXI 一侧最长的无握手空档读写都不超过 224 拍，`T = 4096` 的余量在 18 倍以上。
写方向那一组里扫描输出的 `max_full` 684 周期高于 E5 用 256 拍写量的 531，
按可见区 25.4 µs 消耗 160 拍折算约消耗扫描 FIFO 43 拍，相对第 08 章的最低水位 327 拍不构成风险；
B6 复测 E5 时写方向要把 192 拍这一档带上。

## 六、还欠什么

- **写核的 XLR 与整机数差 590。** RAM（16 块）与读核 XLR 都对上了，写核 536 对 1126.5 的差距
  来自 3.1 节那次整机编译，工程与报告已经不在，本批无法归因。两个核的规模以第五节为准，
  B6 的整机编译再登记一次，那时拿同一份报告与本批的数对照。记在
  [`../../Todo/hw/引擎P1-B6-顶层集成与上板.md`](../../Todo/hw/引擎P1-B6-顶层集成与上板.md)。
- **整机编译与进网表归 B6。** `engine_mover.v` 与 `rtl/vendor/verilog-axi/` 都还没有列进
  `fpga/gfx2d_ti60/gfx2d_ti60.xml`；B5 的 `engine_top.v` 例化它时三个文件一起加进去。
- **超时门限要在真实引擎负载下复算。** 上面的 224 拍是用探针跑的，探针一次只跑一个方向、
  地址不递增；引擎读写同时在途时两者会互相挤。B6 按同一口径复测。
- **三条接口约束要 B3、B4 守住**：每个描述符 16 字节对齐、不跨 4KB、不超过 192 拍；
  写流最后一拍必须给 `tlast`；写描述符握手到写流首拍之间不能长过门限 `T`。
  三条都写进了本批的判据与总览 2.4 节。
- **读、写两个方向在同一拍同时超时，`tmo_dir` 只能报写方向。** `tmo_evt` 是两个方向的「或」，
  `tmo_dir` 取写方向的事件；读方向那一次的「只报一次」标志照样置位，所以它不会再报。
  两个方向的计数各从自己最后一次握手起算，正好同一拍到门限的概率很低；`TIMEOUT` 是一个码值，
  丢的只是方向。B5 落寄存器时如果要方向，把两个方向各自的事件分开接出来。
- **D19 的码值与总线类错误的副作用**在 B5 完成时补进 spec 第 02 章的错误表（软件执行器不产生这几种）。
- **3.8 节的周期数是前期研究骨架上的**，入库版本读门控多等一次 `tlast`，估计每颗多约 32 周期，没有重跑；
  B6 的性能对账拿真实引擎与这里的 1092~1124 并列时一起核对。
