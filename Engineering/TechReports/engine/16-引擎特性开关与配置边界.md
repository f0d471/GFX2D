# 16 引擎生产特性开关与配置边界

本章记录引擎可选机制的正式开发与验证：把「框架加可选机制」从规格做成可构建的裁剪构型，
并给出七个代表档的同轮整机资源与时序。上一章（[15](15-引擎可选机制与配置边界.md)）是开工前的
前期研究；本章是生产实现，两者共用同一套机制标识，但配置定义以本章为准。

现行机制与接口写在 Main：
[`Main/rtl/engine/engine-manual.md`](../../../Main/rtl/engine/engine-manual.md) 第 7 节（开关、依赖、关闭态契约、能力位与默认后端）
与 [`Main/tools/check/feature_config.py`](../../../Main/tools/check/feature_config.py)（配置真源）。
本章只记过程、判据与原始读数。

## 一、动机

第 15 章把机制依赖、能力编码与工具链反例摸清，但生产 RTL 里一处特性开关都没有：
`engine_top` 无条件例化 TEX 与 PB，`engine_mover` 的 `ENABLE_BAND` 在顶层写死 1。
结果是「软件关掉候选」无法释放任何面积，后续任何需要在引擎内新增结构的改动都缺少空间。

本章要解决的是把开关**做出来**：宏进出编译输入、能力位随构型、源列表随构型排除模块，
并让关闭态有可判的契约，而不是「输入接常量、寄存器照留」。

## 二、为什么是这几步

顺序由依赖关系与判据强度共同决定。

**先把配置模型定死，再动 RTL。** 计数、依赖与 CAPS 是后面所有判据的输入；
模型错了，后面每个构型的产物都错。这一点在开发中真实发生过两次（见第五节）。

**切割按「文件级 → 常量化 → 状态机」由外向内。** 关一个机制先要让它对应的源文件
离开编译输入，其次才是模块内部的常量接法与状态机裁剪。把顺序倒过来会反复改同一个文件。

**判据分三层，缺一层就会漏。** 仿真 elaboration 证明「模块装得进去」，
厂商 map 证明「网表合法」，netlist 结构检查证明「关闭的机制真的不在网表里」。
三层各抓到过不同的问题，详见第五节。

**关闭态要写成契约，不能写成「不关心」。** 被裁掉的寄存器是保留地址还是取消映射、
不支持的 CTRL 位是忽略还是整次拒绝，这类选择一旦含糊，软件侧的行为就没有依据。

## 三、每一步做了什么

### 3.1 配置模型与计数

配置真源是 `Main/tools/check/feature_config.py`：五个结构位、三个像素位、一个交付标志。

| 位 | 宏 | 依赖 |
| --- | --- | --- |
| 结构 | `GFX_HAS_TEX` | 无 |
| 结构 | `GFX_HAS_BAND_HW` | 无 |
| 结构 | `GFX_HAS_STRIP` | `BAND_HW` |
| 结构 | `GFX_HAS_INST` | 无 |
| 结构 | `GFX_HAS_PB` | `BAND_HW` 与 `INST` |
| 像素 | `GFX_ALPHA` | 无 |
| 像素 | `GFX_EQ_EXT` | 无 |
| 像素 | `GFX_KEY` | 无 |
| 交付 | `GFX_DELIVERY` | 要求 `ALPHA` 与 `KEY` |

有三条依赖边，方向都是「机制指向它需要的硬件」：`PB → BAND_HW`、`PB → INST`、
`STRIP → BAND_HW`。合法配置是向下封闭集，穷举结果：
结构位 32 种输入中**合法 16、非法 16**；加上八种像素位与交付标志共 512 输入，
**合法 160（研究 128 + 交付 32）、非法 352**。
这组数由 `feature_config.py` 的 `_self_check()` 在导入时断言，改动依赖会在这里停住。

拆分依据是源码事实：`engine_pb.v` 第 190～192 行自行驱动 `band_start`/`band_flush`，
第 486～491 行的单包预检只认 `op==1/2/5`；命令层条带模式在 `engine_cmd.v` 显式拒绝实例包。
原先把条带硬件与命令层条带表合成一个开关，造出了一条并不存在的边「PB 依赖条带模式」。

### 3.2 构建入口

`Main/tools/check/feature_build.py` 按构型生成全部构建输入：

```text
特性清单（feature_config）
  +--> engine_feature.vh          宏的唯一定义处（存在式宏，关闭即不定义）
  +--> engine_config_guard.vh     依赖守卫片段
  +--> engine_config_error_modules.vh  守卫对侧声明
  +--> engine_regs_offsets.vh     按构型 CAPS（调 regs_gen 的生成函数）
  +--> gfx_regs.h                 同上，软件侧
  +--> gfx_feature.h              软件侧编译时预期能力
  +--> fpga/gfx2d_ti60/gfx2d_ti60.xml  源列表按构型排除模块
  +--> rtl/ 的完整副本            生成头与 engine_top.v 同目录，不需要额外 include 路径
```

寄存器偏移与位号的单一真源仍是 `regs_gen.py`：`gen_vh()`/`gen_h()` 接受 CAPS 覆盖值，
默认产物逐字节不变（`regs_gen --check` 通过）。CAPS 的语义边界写进生成模板：
能力位表示硬件具备什么，不表示默认走哪条后端。
`--sync` 把默认全功能构型的四份特性头写进 `rtl/engine/`、把 `gfx_feature.h` 写进 `sw/bsp/include/`；
`--check` 校验它们与默认构型一致。

工程 XML 的生成有两条硬约束，都踩过：**命名空间前缀必须是 `efx`**
（ElementTree 默认会改写成 `ns0:`，Interface Designer 直接拒绝），
**源文件顺序必须照抄模板**（工程是单编译单元，顺序参与编译，`engine_bin` 的映射对文本敏感）。

### 3.3 RTL 切割

九个自写文件按开关门控，禁用分支一律整块二选一，启用分支保持改动前的原文。

| 开关 | 主要切割点 |
| --- | --- |
| `TEX` | `engine_top` 的窗口声明、APB 第 4~7 页分选、mover 的 `tx_*` 端口、`u_tex` 例化；关闭时该页回到未映射页的常量应答 |
| `BAND_HW` | `engine_mover` 的条带数据面（宏未定义时整段常量进编译输入，`engine_band.v` 出源列表）、`engine_top` 的 `MOVER_BAND` 由宏派生 |
| `STRIP` | `engine_cmd` 的状态寄存器组、`band_y0` 与条带基址加、条带专属检查、`S_CFG`~`S_BWAIT` 十一个状态、局部 y 转换、表头取数路径 |
| `INST` | `engine_cmd` 的实例取数、FD/FS 流所有权、实例包字段检查、`S_INEXT`、`err_instance` 身份、`perf_instance`、收尾条件 |
| `PB` | `engine_top` 的两套通路二选一与 `u_pb`、`engine_regs` 的 PB 二选一与计数器、`engine_cmd` 的直投通路；五个文件整出源列表 |
| `ALPHA` / `EQ_EXT` | `engine_blend` 的方程臂；两者同关时 `default` 落到 COPY；`engine_cmd` 的 `eq_bad_c` 改成按开关取方程集 |
| `KEY` | `engine_pix` 的比较、三级延迟像、`no_write` 合并项与 `ws_key_lanes`；关闭时 `PERF[2]` 恒 0 |

`engine_regs` 里「哪种构型对应哪个能力位」由 CTRL 写逻辑落定：
无 `BAND_HW` 时 `ctrl_band` 固定 0，无 `PB` 时 `bin_mode` 固定 0，
所以写 CTRL 不支持位不会产生对应路径。

### 3.4 禁用契约

| 项 | 契约 |
| --- | --- |
| 保留寄存器 | 偏移与位号不变，读回 0 |
| 关闭机制对应的寄存器 | 从 `rd_mapped`/`wr_mapped` 摘掉：读报错、写拒绝 |
| CTRL 不支持位 | 写入该位的整次访问拒绝，且不改其它字段 |
| 无实例 | `ERROR_INSTANCE` 恒 `0xFFFFFFFF`，`PERF[9]` 恒 0 |
| 无 PB | `PERF[10..13]` 恒 0；INST 仍开时 `PERF[9]` 正常 |
| 无条带模式 | `CAPS` 不变（无专属位），判据只能取「无条带表取数」与「CTRL.BAND 被拒」 |

### 3.6 读数边界：构建目录与参数必须绑定

同一个工作点里对同一批构型跑过两轮整机综合（首轮 `feature-trees/`、
验收轮 `feature-accept/`），XLR 的跨轮差是 **−1059 ~ +1121（约 2~3%）**。
这两轮构建目录不同，尚未排除路径和工具环境差异，不能据此认定严格同输入存在随机波动：

| 档 | 首轮 XLR | 验收轮 XLR | 差 |
| --- | ---: | ---: | ---: |
| B0 | 36497 | 36386 | −111 |
| B1 | 38993 | 38432 | −561 |
| B2 | 39316 | 40091 | +775 |
| B3 | 43661 | 44782 | +1121 |
| B4 | 42039 | 40980 | −1059 |
| B5 | 61387（pnr FAIL） | 59652（PASS） | — |
| B6 | 38810 | 39424 | +614 |

RAM 与 DSP 两轮完全一致，setup/hold 都在正区间。可保留的边界有三条：

1. 资源读数绑定源码、构建目录、综合模式、时钟与实际产物；只说“同一轮”仍不足以保证可比。
2. 初版 B5 曾有通过构建，但该读数不证明后续修复版仍能放入器件。关闭态修复后，
   同一目录的 speed 两次均为 60838，真实超出 38；最终模式与资源由后续结果登记。
3. `engine_bin.v` 的正文排版确有综合影响，但这与“固定输入随机波动”是两种假设。
   不能把跨目录差值直接认定为后者。RTL 排版仍按验证流程重做综合。

### 3.7 板测

板测入口是 `check_board_smoke.py`，本机原先起不来：PATH 里没有独立 Windows Python，
只有 Efinity 内置的 `python311`，而它必须带 `PYTHONHOME` 才能启动
（少了它找不到 `encodings`），厂商布局工具又反过来要求 `PYTHONHOME` 未定义。
两个需求各自成立且方向相反。

解法不需要装任何东西：Efinity 的 `python311` **带 pyserial 与 winreg**，
而 `Main/tools/board/board_run.py` 的 `program_bitstream` 本来就自己从**子进程**环境里
摘掉 Efinity 变量（它记过厂商脚本在环境不齐时以 `Fatal Python error` 退出而**退出码仍为 0**）。
所以只要给本进程设 `PYTHONHOME`。新增 `Main/tools/board/python-efinity.cmd` 做这件事。

运行 `Main/sim/build/check-runs/20261015-225517-4ace73c4`：`BOARD PASS port=COM11`，
22 例 CRC 全对、`fail 0`、`done`。引擎侧逐项判据见 `logs/board/engine.log`，
其中 `TEX-CAPS ok` 与 **`CAPS-BACKEND-PAIR ok`** 都出现——
后者是本工作点新增的能力位与默认后端配对断言，
它的通过同时证明 `gfx_feature.h` 这条新输入在板上真的被消费到。
该标记已加进 `check_board_smoke.py` 的必需集合，否则这一行失败时检查仍会 PASS。

板测有条正当的前置判据：**位流不得早于 RTL／头文件／约束**。
本轮先被它拒绝一次（RTL 改动晚于位流），重综合本仓整机位流后通过；
重建读数 XLR 59652 / RAM 172 / DSP 23，与本工作点 B5 验收轮逐位一致。

`.cmd` 包装脚本有个必须记住的约束：**注释只能写 ASCII**。
cmd.exe 按 OEM 码页读 `.cmd`，中文注释会被解成乱码并当成命令执行。

### 3.8 裁剪位流上板

3.7 的板测用的是本仓默认（全功能）构型位流。裁剪构型另有一条更直接的判据：
**逐档部署位流，读运行中的硬件报告的能力位**。

判据不需要写任何测试程序。引擎控制寄存器挂在 APB 上，位流加载后 OpenOCD
直接 `mdw` 就能读（`Main/doc/开发环境.md` 的上板回归表就是这个做法）：
ID 在 `0xf8100000`、CAPS 在 `0xf8100004`。
[board_caps.sh](../../../Main/sim/engine/features/board_caps.sh) 逐档部署并断言
「ID 恒为 `47465801` 且 CAPS 与本构型 `config.json` 逐位相同」。

七档结果（实际硬件读回）：

| 档 | 期望 CAPS | 读回 CAPS | 结果 |
| --- | --- | --- | --- |
| B0 | 0000040f | 0000040f | PASS |
| B1 | 0000140f | 0000140f | PASS |
| B2 | 0000144f | 0000144f | PASS |
| B3 | 0000146f | 0000146f | PASS |
| B4 | 0000046f | 0000046f | PASS |
| B5 | 0000346f | 0000346f | PASS |
| B6 | 0000146f | 0000146f | PASS |

这条与 3.6 节的结构判据互补：结构判据读的是**综合网表**，
这条读的是**运行中的硬件**——关闭的机制在板上确实不在，而不只是在网表里不在。

B3 与 B6 的 CAPS 值相同（条带模式没有专属能力位，见 7.2 节的关闭态契约），
两档各自读回都等于期望值；CAPS 区分不了这两档，这一点在设计时已知，
区分它们的是 3.6 节的结构判据与行为判据。

初版验证完成后把当时的默认 B5 位流重新部署回板卡，读回 CAPS `0000346f`。
本次修复后的默认构型与最终部署状态见第五节。

按层次路径断言关闭的机制一次都不出现（`u_engine/u_tex`、`g_band`、
`u_engine/u_cmd/u_inst`、`u_engine/u_pb`），并能在两个方向上见红。
它在首轮与验收轮各自的源树上都跑过，两轮各七档 PASS，
读数登记在各自的 `netlist.json`。

### 3.10 关闭态功能复核与修复（2026-10-16）

切换基本档时，构建、网表与能力寄存器均通过，但第一张 BLIT 帧挂死。
先前的构型判据主要检查结构与寄存器访问，整帧及机制专项在默认全功能头下运行，
不能据此认定裁剪档的数据通路正确。以下复核在真实 engine_top 与随机反压 DDR 模型上进行，
另以构型位流执行功能板测；原验收结论保留当时的输入与范围。

#### 3.10.1 TEX 关闭后的共用读路

初始猜测是多笔描述符中 tlast 与命令取数所有权错拍。
既有波形显示，在约 1.915 us 切入第一笔像素读时，rd_ctx_cmd=0、rd_ctx_bg=0、
rd_drain_help=0、rs_tready=1，但 tx_busy=z、tx_data_blocks=x、core_rs_tready=x。
因此卡点先于正常末拍握手，不能由几何层的描述符索引或局部像素计数推断 DMA 已完成。
读核状态先到只使 rd_status_seen=1，rd_stream_done 仍为 0，门控继续挡住后续描述符。
当时悬着的描述符 rd_addr=0x00200100、bytes=0x100、beats=16、ARLEN=15 均正确，
cmd 已到 S_TERM；这些事实排除地址/长度配置错误，不能据此认定像素流已经收尾。

顶层在关闭 TEX 时省略了 mover 的整组端口连接，mover 本身仍保留这些输入与共用路由。
`iverilog -Wportbind` 明确报告九个悬空输入。修复在顶层无 TEX 分支补齐
tx_ready、tx_rs_tdata、tx_rs_tvalid、tx_rs_tlast、tx_rs_buf、tx_stat_valid、
tx_stat_cidx、tx_stat_buf 与 tx_busy 的空闲常量，没有放松读门控或修改 DMA 核。

```text
关闭 TEX 前：u_tex --tx_busy/流/状态--> mover 共用读路
关闭 TEX 后：常量 0 --[改：补齐九输入]--> mover 共用读路
                                         |
                              DDR tlast 握手后解除读门控
```

隔离对照中 B0 的 FILL 通过，B0/B1 的同一 BLIT 帧超时；
B2 虽然同样无条带硬件，但 TEX 存在，该帧通过。
仅补齐 TEX 输入的 B0 副本也通过，2652 周期、4096 像素、内存零差异。
影响面据此按 TEX=0 选择。此前 BAND_HW 出向网悬空是另一个关闭态连接缺陷，
已在前一提交补齐十条出向常量；两者都说明仅检查被裁模块是否消失仍不足够。

#### 3.10.2 拒绝写的原子性与 STRIP/PB 分工

寄存器层原来只在组合 PSLVERR 上拒绝不支持的 CTRL 位，时序写路径仍由 wr_ctrl 放行。
一次带 BAND/BIN 的拒绝写因而还能改变 EN、清 PERF 或举软复位。
修复把 ctrl_unsupported 纳入 wr_ctrl，拒绝访问的全部副作用同时被挡住。
被裁寄存器的时序写也按 wr_mapped 门控；无 PB 的四个保留参数读回零。

进一步检查发现，BAND_HW 只说明条带数据面存在，不能据它放行命令层条带模式。
现在 STRIP 存在时允许独立 BAND；只有 PB 而无 STRIP 时，只接受同次写入的 BAND|BIN。
LSTRIPS/STRIP_H/BAND_SURF 是两个生产者共用的配置，STRIP 或 PB 任一存在就应映射。
软件的条带提交确认实际 CTRL 读回为 EN|BAND 且 BIN 已清零，不能只检查 CAPS.BAND。
这种检查允许同一 BIN 在 STRIP 与 PB 专用数据面构型之间使用，拒绝访问保持原 CTRL 不变。

#### 3.10.3 PB 的实际控制选择器

与开关改造前的顶层比对，发现 PB 的十条条带控制二选一被改成了旧命令层直连。
PB 自己的 band_start/flush 虽然仍生成，却到不了 mover；PB 关闭 STRIP 时，共享配置
又被摘掉。寄存器冒烟与默认直通的板测没有激活 PB，不能覆盖这两个问题。
修复恢复按 pb_active 选择生产者的十条连接，并修正共享寄存器的保留条件。

新增构型功能台实际执行一条条带的 LOAD/EXEC/FLUSH，逐像素检查结果与行尾填充，
使 PB 不依赖 STRIP 的配置也必须完成真实绘制。补充构型 11011-111-d 的
独立综合与功能板测用于验证被七代表档漏掉的 PB 无 STRIP 路径。

#### 3.10.4 像素与构建入口的关闭态

无 KEY 的实现原先接受 key_enable，像素层却把比较链裁掉，命令被静默执行成普通 BLIT。
现在请求色键的 BLIT/实例包按 BAD_FIELD 拒绝，支持与不支持的方程则分别执行或返回
BAD_EQUATION。TEX 源关闭返回 BAD_SPACE，无实例的 op 0x05 返回 BAD_OPCODE。

配置名的第三段原来只在恰好为 d 时设置交付标志，拼错的后缀会静默变成研究构型；
现行入口拒绝其它后缀。生成守卫时也改为从清单取准确宏名，修正 ALPHA/KEY 被错误
拼成 GFX_HAS_ALPHA/GFX_HAS_KEY 的问题。守卫的空声明仍不能提供结构保证，
非法配置拒绝由构建入口承担，关闭机制的结构由厂商网表检查承担。

构型 elaboration 把悬空输入告警提升为失败；缺源树的契约脚本记录 INCOMPLETE；
套件汇总启用 pipefail，不能把上游失败与最后一行 PASS 合并成通过；
综合收集器遇到负时序或自写 RTL 位宽告警直接失败，并删除本次失败档的旧通过读数。
流程测试中的历史板测样本补齐现行能力配对标记，同时加入缺标记反例。
收口路径检查还发现套件汇总与旧七档综合脚本写死本机安装位置，改为沿用调用方环境；
旧综合入口把输出限制在 sim/build 内并拒绝构型目录链接，移除重复的递归删除；
11 项入口行为检查验证缺环境、错误输出、链接与失败传递，模拟编译器未触发综合或板测。

#### 3.10.5 验证范围

`feature-function` 已接入唯一清单，运行全部 160 个合法构型。
每个构型覆盖非对齐三行窗口、FILL、六方程、色键、DDR/TEX、实例与 PB 的有效路径或
关闭态错误三元组，逐像素比较目的与保护字，并检查拒绝 CTRL 写后的 EN/PERF 和再次提交。
首轮四个定向变异分别恢复 TEX 悬空、CTRL 副作用、错误 BAND 放行与关闭色键后的静默执行。
矩阵轮 20261016-171351-c32a855c 为 acceptance，五项 feature 检查通过，
160 构型及四个变异通过；它尚未覆盖以下后端切换与软复位场景。

七代表档的功能板测改用同一 featureTest BIN，外部检查器由独立方程计算 CRC，
逐案验证唯一性、错误三元组、保护字、加载边界与正常结束行。
TEX/PB 按运行时能力执行，能力不存在时记录明确范围，不能只读 CAPS 就算功能通过。
综合、专项及板测的最终结果与证据入口在第五、六节登记。

#### 3.10.6 连续后端切换、软复位与游戏能力判断

实例与 STRIP 加入同一板测 BIN 后，B0～B4 通过，B5 的 PB 绘制也通过，
紧接着的 STRIP 却返回 code=0、bad=0x2800：10240 个可见像素仍为初始保护值。
这是实际功能失败，不能因为收到 done 就判通过。
PB 完成后 pb_active 仍为上一门铃锁存的 1；新的 CTRL 已写成 BIN=0、BAND=1。
命令层在新门铃沿却按 band_mode && !pb_active 锁存，进入零长度直通表并提前完成。
修复改为按当前 bin_mode 选择请求，pb_active 继续仅承担在途事务所有权。
新增 PB→STRIP 的完整 LOAD/EXEC/FLUSH 对照，在未修复 RTL 上复现整面保护值不变。

B0 的 159 向量回归还检出无 PB 分支把 preserve_clip 接成 1，
导致软复位保留旧窗口。设置面外 clip 后，软复位再 BLIT 的 18 个像素全部未更新。
修复把无 PB 的 preserve_clip 接 0；PB 内部中止的保留条件保持原有表达式。
控制层向量恢复通过，新矩阵加入面外 clip→软复位→重新登记表面→BLIT 的真实消费者。
六个正式变异在原四个基础上增加恢复 preserve_clip=1 和恢复上一后端门控，均须见红。

生产 B0 游戏首轮的启动画面 CRC、240 帧、稳态 60 fps 与扫描诊断均正常，
但 run_modes 无条件调用 boot_tex，把无 TEX 能力计成装载失败并输出 fail 1。
修复先读取 CAPS；能力不存在时正常跳过热集，能力存在但装载或 CRC 失败仍计错。
原生产 HW/DDR 后端和 240 帧构建参数不变。

测试工具的两处错误也分别订正：新 SET_CLIP 反例最初误把右下角放进 w2，
按 ABI 改为 w1 起点、w3 尺寸后再复现软复位缺陷；板测解析器未接受 inst-absent
中的连字符，修正后用同一原始日志与十个负例验证，不借重新部署掩盖解析问题。

#### 3.10.7 全功能构建参数与编排

修复 PB 控制连接后，speed 模式在同目录复核两次均占 60838 XLR，超过器件 38 个。
固定 seed=1、placer_effort_level=2、原时钟与完整 RTL，按 Efinity 文档的 mode 选项比较：
area 为 62502、area2 为 60838，均未通过；speed2 为 60310/172/23，
core_clk setup/hold +0.240/+0.030 ns，全部时钟关系非负。
此组取样在连续后端/裁剪框修复之前，保留为参数选择证据，最终资源另表登记。
speed2 是厂商的更深逻辑优化模式，正式配置由 feature_config.synthesis_mode 统一生成：
全结构构型用 speed2，其余用 speed，并同步主工程模式与 config.json。
不同模式的资源差不再用来直接归因单机制成本。

七档编排外层原来仍有 1800 秒上限，内层较长预算不能阻止外层超时。
现按检查项设置预算，七档综合为 18000 秒；物理 board/feature-board/board-game
不自动复用。编译输入复用逐项比较 RTL/IP/约束/工程参数，忽略明确的 GUI 流程状态，

复制实验脚本曾保留通用检查键而使计划索引不同，编排据此拒绝归档；
对齐到实际已执行检查后才归档，原始 speed2 参数和结果没有改写。

## 四、遇到的问题

按发现顺序记录，每条都影响过后面的做法。

**计数错了两次。** 第一版把 KEY 与 ALPHA 当成互斥位，而方程集在两者全关时仍有 COPY 与 ADD；
第二版拆分结构位后只算了一条依赖的排除集，得 20 种。正确是 16 种。
修法不只是改数：把计数写进 `feature_config.py` 的导入期断言，并加一条
「必须不等于旧值 20」的反向断言，防止改动依赖时静默漂回。

**守卫恒成功。** 开发轮实测：把 `STRIP=1`、`BAND_HW=0` 的头手工塞进源树，elaboration 照样通过。
结论是守卫不是拦截点；拦截点是构建入口，结构保证要给 netlist 检查。

**`error` 指令挡不住。** Icarus 的预处理对 `` `error `` 只给警告、退出码仍为 0
（第 15 章已记）。守卫因此在三条工具链上都用命名缺失模块，不用 `` `error ``。

**命名空间前缀被改写。** 生成工程 XML 时没有注册 `efx` 前缀，ElementTree 输出 `ns0:`，
`map` 能过而 Interface Designer 报
`TypeError: can only concatenate str (not "NoneType") to str`——报错完全指不到原因。

**两处双重驱动，只有厂商工具能发现。** `bin_mode` 既由 `engine_regs` 的端口连接驱动、
又被 `engine_top` 的常量赋值驱动；`pw_ready` 是 `engine_mover` 的输出端口、也被接了常量。
两者都报 `constantly driven from multiple places`，而十个仿成套件全绿。
修法是把能力位约束放到**驱动侧**（`engine_regs` 的 CTRL 写逻辑），
以及删掉那条与端口冲突的常量。

**源文件顺序参与映射。** 第一版生成器按字典序排源文件，与模板顺序不同；
工程是单编译单元，顺序改变会影响厂商映射。改为照抄模板顺序后，
B5 的源列表与模板逐项相同。

**STRIP 没有专属能力位。** 判据不能靠 CAPS 区分它是否在构建里，
只能取「无条带表取数」与「CTRL.BAND 被拒」两项行为。

**一处 `if/else` 被 `ifdef` 拆散。** 给 `S_SWITCH` 的分支加条件编译时只包住了 `if`，
`else` 悬空，语法错误被报成 `Incomprehensible case expression`。
教训：给 if/else 加条件编译必须整条语句一起包。

**三处禁用契约违反。** 契约测试台一次抓出：条带寄存器在有 BAND_HW 但无 STRIP 的构型里
仍可写、同三个寄存器的读路径仍成立、CTRL 写不支持位没有整次拒绝。
修法分别是按 `GFX_HAS_STRIP` 门控 `wr_mapped` 与 `rd_mapped`、新增 `ctrl_unsupported`。

**一处命令编码契约违反：无 TEX 时 `space=1` 报错了码。** `engine_cmd.v` 原先的
`sp_src_bad` 只挡 `space==2/3`，而合约是「无 TEX 时 `space=1` 不再合法、报 `BAD_SPACE`」。
关掉 TEX 后 `space=1` 先被 `src_ok_c` 拒掉，落到 `BAD_SURFACE`。
改法：按 `GFX_HAS_TEX` 分档取 `sp_src_bad`，无 TEX 时源空间只允许 DDR(0)。
这类「契约写了一个码、实现给了另一个」的错误，只有把契约写成逐条判据才抓得住；
初版只修了实现；关闭态真实命令反例在 3.10 节的构型矩阵中补齐。

**工具解析陷阱。** 本机 iverilog 12 对「老式 task 带 integer 端口」与
「task 之后再放 reg/localparam 声明」都会误报语法错，且错误位置指向文件末尾
（`engine_pb.v:580`）而非真正位置，排查花了多轮。测试台因此改用宏断言、声明一律前置。

**仿成套件缺 include 路径。** 特性头进 RTL 后，九个套件里八个缺 `-I "$RTL/engine"`。
其中 `apb_probe/run.sh` 连 `RTL` 变量都没定义，加 `-I` 反而把脚本弄坏了（`set -u`）。
这条是改造的连带成本，登记在此以免下次重复。
