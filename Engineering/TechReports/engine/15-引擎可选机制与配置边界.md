# 15 引擎可选机制与配置边界

本章记录可选开关规格的前期审查、配置模型、工具链反例、隔离混合核实验与板卡基线。
范围是开工依据；没有实现生产特性开关，没有发布裁剪位流，也没有切换游戏默认后端。

## 一、动机

全功能硬件已经包含TEX、BAND、直通实例及PB，但日常游戏默认不走PB。
软件关闭候选无法释放RTL面积，后续开发需要能明确选择硬件构型。
原规格提出“永久框架+可选机制”的方向成立，问题集中在配置全集、能力编码、
资源归因、关闭态协议以及正式采用的边界。

采用六个代表档有利于控制完整构建次数；把六档当作合法配置全集会漏掉消费者。
面积档与性能档可以并存，谁成为生产默认由采用判据决定。

## 二、为什么是这几步

先从实际实例和握手确认依赖，再独立枚举能力编码；这两步不需要改变生产RTL。
随后验证编译期拒绝是否真的让工具失败，防止“日志有警告、退出码仍0”的假通过。
混合核可以在隔离目录保留真实数据通路，直接测量方程裁剪对乘法器的影响。
最后部署明确冻结的全功能位流，确认本机下载/调试与基线能力可用。
裁剪整机尚未存在，板卡基线不能替代未来裁剪位流的验证。

来源与借鉴边界：

- [Verilator语言扩展](https://verilator.org/guide/latest/extensions.html)说明其预处理扩展。
  工具支持不等于所有Verilog编译器都支持，因此本轮直接测试本机Icarus/Verilator/Yosys。
- [Yosys hierarchy文档](https://yosyshq.readthedocs.io/projects/yosys/en/0.44/cmd/hierarchy.html)
  给出hierarchy -check对未定义模块的检查。这里只借用编译拒绝机制，不移植模块代码。
- 仓内verilog-axi的参数检查、现有ENABLE_BAND分支和engine-manual协议
  提供本地接口参照。软件与RTL职责按已有分层保留，没有引入外部图形驱动。

## 三、每一步做了什么

### 3.1 源码边界与配置全集

engine_cmd包含直通engine_inst；engine_bin包含PB内部engine_inst。
PB驱动BAND的start/flush/ready/error，依赖BAND与INST。
v2命令层拒绝实例包，BAND因此不依赖INST。TEX是另一条源读支路。

按TEX/BAND/INST/PB顺序，16种输入中合法10种：

| 结构位 | CAPS（三像素位全开） | 代表档 |
| --- | --- | --- |
| 0000 | 0x0000040F | A0 |
| 0010 | 0x0000140F | 额外组合 |
| 0100 | 0x0000042F | 额外组合 |
| 0110 | 0x0000142F | A2 |
| 0111 | 0x0000342F | 额外组合 |
| 1000 | 0x0000044F | 额外组合 |
| 1010 | 0x0000144F | A1 |
| 1100 | 0x0000046F | A3 |
| 1110 | 0x0000146F | A4 |
| 1111 | 0x0000346F | A5 |

LANES=4贡献0x400；ALPHA两位、KEY、MUL贡献0xF。
因此全关结构位也不能得到原文0x2F。
全部七位与delivery标志共256输入：研究128中合法80、非法48；
交付128中合法20、非法108，合计合法100、非法156。
本轮Icarus对256个配置检查壳逐项elaboration，结果与独立有效性判定相符；
它验证配置守卫，不代表生产engine_top已经实现这256种输入。
本节的四结构位与组合计数已被3.7节替代，此处保留的是本轮实跑的那套输入。

### 3.2 编译守卫与宏反例

存在式宏GFX_HAS_PB即使定义为0，ifdef分支仍进入，实测打印DEFINED_IS_ON。
正式配置必须采用“开才定义”的语义，不能混用存在式与数值式开关。

原spec的error指令探针结果：

| 工具与动作 | 返回码 | 解释 |
| --- | ---: | --- |
| Icarus -E预处理 | 0 | 输出macro error undefined警告，未完成预期的预处理拒绝 |
| Verilator -E | 1 | 拒绝 |
| Yosys read_verilog | 1 | 拒绝 |

这里没有声称Icarus对任意带error的完整编译都成功；
结论是不能依赖该写法让所有工具在预处理阶段非零退出。

后备方案使用命名缺失模块，分别表示PB缺BAND、PB缺INST、
交付缺KEY、交付缺ALPHA；加一个全开正常对照。
Icarus覆盖全部输入，Verilator和Yosys各覆盖这五组。
正式构建还必须在生成头和源列表前检查清单；
厂商工程启用blackbox-error=1，并在实现轮补真实编译入口反例。
研究关闭态不自动补开ALPHA/KEY，交付拒绝条件按正向delivery判定。

### 3.3 资源归属复核

归档hier_util根为54236，u_engine为34284/101/19；
Main/README的60064是另一综合口径，不能在一张差额账里混减。
PB父项包括其内部实例核，扣除父项后再扣两处实例核会重复扣其中一处。
原式60064-434-5033-18588-2210即使照算也为33799，不是23799；
方法本身还混用了历史差与独立综合，因此两个推算值均不作为目标。

A1含直通INST，不能认作历史上尚无实例核的36443 TEX构型。
A4去PB但保留INST，也不能套早期41476条带构型。
层级表中父项包含子项；打包、单独map、place报告分别标阶段。
未来收益必须来自同源码、工具、阶段、约束的构型对照。
本轮未给出裁剪整机面积、时序或N_max预测数。

### 3.4 真实混合核的隔离实验

研究工具从现有engine_blend抽取方程臂，在本轮build目录生成四种隔离副本；
输入经寄存器动态驱动，不用常量eq让综合器提前抹去其它启用方程。
原混合公式、三拍流水及en保留；禁用方程的命令拒绝留给正式上层实现。

每种副本用独立整数参考式逐项比较，包含随机源/目的/alpha/常量与周期性停顿。
参考式直接计算src×Fs+dst×Fd，再作除255舍入/饱和，不复用被测base/m1/m2代入。
每种29997次检查，四种共119988次，0差异。

| 隔离核 | ALPHA | EQ_EXT | 合法方程 | map的EFX_DSP48实例 | EFX_RAM10实例 |
| --- | :-: | :-: | --- | ---: | ---: |
| full | 1 | 1 | 0/1/2/3/4/5 | 1 | 0 |
| no_alpha | 0 | 1 | 0/2/3/4 | 1 | 0 |
| no_ext | 1 | 0 | 0/1/2/5 | 1 | 0 |
| copy_add | 0 | 0 | 0/2 | 0 | 0 |

四种厂商map均PASS；计数来自实际映射网表中的Titanium原语实例。
该实验不是整机四步、不是pnr时序，也不是关闭Alpha就省12个DSP。
它直接推翻“Alpha是乘法器唯一理由”：CONST与MUL同样使用乘法器。

### 3.5 接口与软件消费者

审查发现原spec在以下地方会引入功能回归，修订后作为正式开发约束：

| 原问题 | 修订后的边界 |
| --- | --- |
| PB关闭时PERF[9..13]全0 | INST仍开时PERF[9]继续计实例；PB只拥有10..13 |
| 禁用寄存器统一读0 | ERROR_INSTANCE保留0xFFFFFFFF无实例哨兵 |

## 四、规格修订：条带拆分与能力语义

本节的两条修订发生在前期研究归档之后，是对规格的订正，不改变第三节已归档的实测结论。
修订尚未落到RTL、守卫清单与配置生成器，属正式开发的开工依据。

### 4.1 条带拆成硬件与控制两层

第三节的依赖图记作 PB 依赖 BAND 与 INST。复核源码后，PB 依赖的是**条带硬件**，
不是命令层的条带模式，原先把它写成一条边是因为一个开关装了两件事：

| 装在同一开关里的东西 | 消费者 |
| --- | --- |
| 条带RAM（engine_band.v）、mover的g_band/g_no_band两臂与17个端口、geom的band_enable/band_y0求交与rd_band/wr_band、band_start/flush/ready/loaded/error握手 | PB与命令层条带模式 |
| 命令层的S_CFG～S_BWAIT状态、bmode/cfg_phase/counts/table_base/strips_r、ABI v2条带表 | 只有命令层条带模式 |

依据是 PB 走的是命令层条带控制的旁路：engine_cmd.v 第639～642行在 external_mode 下
强制 bmode<=0、cfg_phase<=0；engine_pb.v 第190～192行自行驱动 band_start/band_flush，
第424/425/530/531行等 band 的 ready 并用 band_error_code 上报。
命令层的条带控制是一个完整状态块（engine_cmd.v 第1014～1073行，入口在第648行），
关闭后 bmode 恒0、该状态块进不去，而 band_* 握手口留给 PB。

拆分后开关与依赖：

```text
PB -----> BAND_HW
 |--------> INST

STRIP --> BAND_HW          TEX独立
```

| 开关 | 硬依赖 |
| --- | --- |
| GFX_HAS_TEX | 无 |
| GFX_HAS_BAND_HW | 无 |
| GFX_HAS_STRIP | BAND_HW |
| GFX_HAS_INST | 无 |
| GFX_HAS_PB | BAND_HW与INST |

三条边都是“机制指向它需要的硬件”，不再有“机制指向另一个机制”。

### 4.2 组合计数订正

结构位由4位增到5位。合法性有两条边：PB开要求BAND_HW与INST都开，STRIP开要求BAND_HW开。
**合法16种、非法16种**（本节早前版本按4位算得10/6，3.1节尚未拆分）。
像素位由3位独立组成8种：EQ_EXT与ALPHA各管自己的方程臂，都关时方程集落到COPY/ADD，
KEY只加色键比较不改方程集，因此没有互斥约束。

| 范围 | 合法 | 非法 | 合计 |
| --- | ---: | ---: | ---: |
| 研究（DELIVERY=0） | 16×8=128 | | 256 |
| 交付（DELIVERY=1，另要求ALPHA与KEY都为1） | 16×2=32 | | 256 |
| 合计 | **160** | **352** | 512 |

两条依赖各排除4种结构组合：PB开而BAND_HW或INST任缺的4种、STRIP开而BAND_HW缺的4种。

3.1节与其后表格里的“研究128中合法80、非法48；交付128中合法20、非法108，合计100/156”
不成立：它把KEY与ALPHA当成互斥位，而方程集在两者全关时仍有COPY与ADD。
总数由 `Main/tools/check/feature_config.py` 的 `_self_check()` 固化成断言，
改动 DEPENDS 或代表档时会在这里停住。
该计数未进入已归档的实跑输入（本轮跑的是按4位结构位生成的检查壳），
但它是正式开发要用的清单，须以本表为准。

### 4.3 准确CAPS

三个像素开关全开时取 0x400F 基值（LANES=4占CAPS[11:8]）。
位序 TEX/BAND_HW/STRIP/INST/PB 下的16种合法结构组合：

| 结构位 | CAPS | 结构位 | CAPS |
| --- | --- | --- | --- |
| 00000 | 0x0000040F | 10000 | 0x0000044F |
| 00010 | 0x0000140F | 10010 | 0x0000144F |
| 01000 | 0x0000042F | 11000 | 0x0000046F |
| 01010 | 0x0000142F | 11010 | 0x0000146F |
| 01011 | 0x0000342F | 11011 | 0x0000346F |
| 01100 | 0x0000042F | 11100 | 0x0000046F |
| 01110 | 0x0000142F | 11110 | 0x0000146F |
| 01111 | 0x0000342F | 11111 | 0x0000346F |

STRIP没有专属CAPS位，它不改变能力集合，只改变帧级控制由谁产生，
所以01000与01100同值、01010与01110同值、01011与01111同值、11010与11110同值。
因此**不能用CAPS判断STRIP是否在构建里**，
判据只能取“条带表取数是否发生”与“CTRL.BAND是否被接受”两项行为。
同理代表档里的B3与B6（差命令层条带控制）、B3与B5（差PB）各自CAPS同值而硬件不同：
PB增加的是同一能力的硬件执行者，STRIP改的是控制来源，两者都不进能力位。

3.3.3节列的旧六档CAPS不再作为构型定义：旧表把条带硬件与命令层条带表合成一位，
使其中三档各混着两件事，其中一档的0x2F还错取了更早文档的残值
（全关结构位时CAPS为0x400F，ALPHA两位、KEY、MUL贡献0xF已在3.1节记过）。

### 4.4 代表档改为消融序列

原A0～A5按“能力覆盖”选，混着多项差异，不能用来定位成本。
改为每步只加一个机制的消融序列：

| 档 | TEX | BAND_HW | STRIP | INST | PB | CAPS | 消融关系 |
| --- | :-: | :-: | :-: | :-: | :-: | --- | --- |
| B0 | 0 | 0 | 0 | 0 | 0 | 0x0000040F | 框架，只含COPY/ADD与色键 |
| B1 | 0 | 0 | 0 | 1 | 0 | 0x0000140F | B0加实例 |
| B2 | 1 | 0 | 0 | 1 | 0 | 0x0000144F | B1加TEX |
| B6 | 1 | 1 | 0 | 1 | 0 | 0x0000146F | B2加条带硬件 |
| B3 | 1 | 1 | 1 | 1 | 0 | 0x0000146F | B6加命令层条带控制 |
| B4 | 1 | 1 | 1 | 0 | 0 | 0x0000046F | B3去直通实例 |
| B5 | 1 | 1 | 1 | 1 | 1 | 0x0000346F | 全功能 |

历史构型与代表档的对应关系只作区间说明，历史构型的实例核有无未逐份存证：
2026-10-02的36009最接近B0，2026-10-08的36443最接近B2的TEX部分，
2026-10-09的41476介于B2与B3之间（帧级控制已并入、条带表未并入），
2026-10-09的60064等于B5的结构位。

### 4.5 能力位不等于默认后端

CAPS回答“这块硬件具备什么能力”，不回答“默认走哪条路”，两者必须分开登记。
禁止从CAPS的任何位推断默认后端：CAPS.BIN=1只表示硬件具备分桶能力，
与 GFX_FRONTEND_BIN=0、GFX2D_START_BACKEND 取2可以同时成立。

这条约束落三处：描述全功能构型时必须同时写出当时的默认后端取值，
不允许单独出现“全功能”而不带默认后端说明；regs_gen.py 生成CAPS的模板带一行语义声明，
使两份生成头自带该边界；engineTest 按构型检查时固定一组“硬件能力与默认后端”的配对，
断言默认后端为0时CAPS.BIN仍为1。
第三种改动的证据链与硬件构型变化完全不同，混起来会让性能数字失去归因。

### 4.6 对已归档内容的影响

不改变第三节的实测结果：256配置穷举、三工具守卫反例、混合核隔离map与冻结位流板测
都是按四结构位那套输入跑的，结论仍然成立。
本节修订的是**清单、依赖图、CAPS表与代表档**，它们尚未进入任何已跑通的构建。
第五节“还欠什么”里的生产特性清单、守卫、配置生成器与代表档整机四步，
按本节修订后的定义实施。



## 五、遇到的问题

首轮XML生成没有保持厂商模板的命名空间和节点顺序，efx_map在解析工程时失败。
生成器补齐xsi注册并将design_file放回模板顺序，改正Titanium原语名为EFX_DSP48/EFX_RAM10。
由于研究源码改变，重新建立运行目录；首轮失败输出留在忽略目录，
未用失败综合或旧板测替代最终轮必需项。
归档中的xml_generation_first_failure.log保留该次原始错误，另有release_identity.json
记录已登记部署位流与复现包manifest的比较；比较复用本轮身份，不再计算同一摘要。

原spec的数字和依赖结论分散在正文、表和日志，容易出现互相矛盾。
修订改用机制依赖、配置表、关闭态契约与实施次序四个明确入口；
历史被推翻结论集中说明，不再以脆弱行号作为接口定义。
