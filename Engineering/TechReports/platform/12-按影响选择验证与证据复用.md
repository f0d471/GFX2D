# 按影响选择验证与证据复用

## 一、动机

工作点扩展之后，提交前检查同时存在两种要求：Main README 列出全部仿真与整机编译，
开发环境手册又按软件、RTL 和文档划分验证范围。局部修改因此容易重复执行无关检查。
实例聚合检查的 legacy 重复调用 v2，分桶平台检查重复编跑库与应用的正常测试；
软件脚本跳过必需项后仍可能返回成功，固定输出目录又把复跑与归档证据混在一起。

本次调整检查编排、通过状态与证据流转，生产功能和默认绘制后端不在改造范围内。

## 二、为什么是这几步

1. 先统一影响范围与档位，否则脚本去重仍会被文档中的全量要求覆盖。
2. 再区分通过、失败、缺项与不适用，避免用减少执行项换取表面通过。
3. 公共正常测试同轮复用，专项断言与不同变异保留。
4. 新运行与历史证据隔离，用输入、参数和结果清单支持复核。
5. 最后验证编排反例、真实宿主／RTL 和代表性板测，分别记录各层证据。

## 三、每一步做了什么

### 3.1 唯一规则与清单

`Main/doc/验证流程.md` 维护影响表、quick／acceptance／release 的边界与状态定义；
`Main/tools/check/validate.py --list` 是可执行清单。Main README、开发环境手册、
Engineering 流转和仿真／工具说明改为引用这份规则。

```
改动文件 + 消费者
        |
        v
选择检查项与档位 --> 计划复核 --> 去重执行
                                   |
                                   v
                         PASS / FAIL / INCOMPLETE
                                   |
                                   v
                      输入复核 --> 同轮汇总 --> 一次归档
```

quick 保留正常、定向变异和代表性 RTL，排除录像重搜、生产模式完整 N_max 双进程搜索
与十分钟日志长跑。acceptance 保持选定专项的全量参数；release 另按冻结的交付清单
补齐实际候选回放、平台与板测，不从档位名称推导“所有功能都已验过”。

### 3.2 公共测试与聚合去重

`check_common.sh` 与 `check_host.sh` 统一库和应用的正常 64/32 位构建、sanitizer 与输出。
游戏和统计脚本读取同轮正常结果，仍执行各自的输出断言和变异构建。
应用二进制也保留在公共目录，弹型的轨迹消费者继续执行同一对象。

实例的显式 v2 与 legacy 内部 v2、分桶的显式 platform-hw 与 platform 内部硬件检查
使用同一检查键，输入与参数未变且本轮已有 PASS 时只执行一次。
TIMED 诊断开关改名 `--timed-profile`，公共 `--profile` 专用于选择验证档位。

### 3.3 状态与证据隔离

必需项未执行返回 INCOMPLETE／退出码 3；显式跳过录像重搜或日志长跑也属于缺项。
quick 按声明范围排除的长项记录 NOT_APPLICABLE 与原因。

`check_run.py` 在 `Main/sim/build/check-runs/<运行号>/` 保存所选依赖的身份、参数、状态与产物关联。
输入集合或内容变化会拒绝复用；未变文件复用已登记摘要，工具仅改时间戳时复核内容后刷新缓存。
工程 XML 的运行状态字段不属于设计输入，身份记录显式标明规范化范围；产物身份仍按完整字节登记。

固定归档中的 PASS 文本不能直接作为新轮结果。实例的当前汇总限定宿主／RTL，原完整
消费者转为显式历史复核，解除对手工综合 JSON 与旧板测日志的隐式依赖；分桶的 DDR 日志
单测补为可执行生产入口。正式汇总要求同轮正式组完成，quick 档拒绝完整验收汇总。
归档复制清单和日志，验证复制后的字节身份，构建目录不入库；历史快照不重判当前源码。

路径检查的 tracked 档直接读取 Git 清单，不再先扫描忽略目录；输入与产物的身份缓存跨轮
复用未变对象，保留时间戳的复制可强制重查。发现输入变化后将该轮标为失效，后续不能意外复用。

### 3.4 代表性板测

新板测入口扫描 JTAG，从当前 FT4232H C 接口定位 UART，检查位流新鲜度和时序，
部署后连开两次调试会话，重建 engineTest，再验证本次下载字节数、程序完成边界与引擎功能。
该检查不写 Flash，不给出新的 N_max 或全游戏性能结论。
物理检查每次实际执行，不自动复用设备状态；纯软件通过项仅在输入、参数与原始输出仍有效时复用。

## 四、遇到的问题

### 4.1 寄存器检查依赖工作目录

**第一现场**

```
regs_gen --check: 产物与真源不一致： rtl/engine/engine_regs_offsets.vh, sw/bsp/include/gfx_regs.h
```

**解读** 两份文件存在，但从仓库根调用时生成器按当前目录查找，误报内容不一致。

**定位** 原入口要求从 Main 下运行；统一检查入口以仓库根为工作目录。

**根因与修法** 路径改为从脚本定位 Main，生成文本和实际寄存器定义不变。
原判据只覆盖固定调用目录，没有覆盖统一入口的工作目录。

### 4.2 运行期间源码改变

**第一现场**

```
FAIL 检查输入已改变: Main/rtl/engine/engine_pix.v；请建立新的运行目录
```

**解读** 本轮检查没有继续把先前通过记录汇总为当前版本结果。

**定位** engine_pix 的注释位置在检查期间被外部调整，属于本次流程修改之外的变更。

**根因与修法** 保留外部修改并单列提交边界；源码稳定后登记新轮。
因 Synplify 对文本敏感，代表性板测前仍重新综合；词法等价不替代综合。

### 4.3 USB 重新枚举

**第一现场**

```
ERROR: No USB target detected, aborting!
```

**解读** FT4232H 存在，但 B 接口使用串口驱动，JTAG 不可访问。

**定位** 当前四接口枚举成串口，UART 号也与历史登记不同。

**根因与修法** B / Interface 1 恢复 libusbK 后重新扫描，识别到 0x10660a79。
UART 自动定位只采用当前存在的设备，排除注册表中保留的旧接口。
历史端口号和 TAP 识别均不能替代本次完整部署与功能采集。

### 4.4 横幅早于加载完成标记

**第一现场**

```
engineTest B6
ENG id ok
# --- 程序已加载，以下才是它的输出 ---
fill-screen 9cd34cb7 9cd34cb7 ok
```

**解读** CPU 在 OpenOCD 返回前已开始打印，横幅不一定在采集边界之后。

**定位** 22 组金标准、COUNT32、TEX 与压力结果均在边界之后，下载字节数与目标识别也完整；
错误来自新解析器对横幅位置的额外限制。

**根因与修法** 身份判定改为部署证据加边界后的完整功能集合，22 行独立对 golden.txt，
重复、缺行、CRC 差异、伪 done 与串口丢失均拒绝。补入横幅位于边界前的正例。

### 4.5 时序采集只记录同名时钟

**第一现场** 原采集器使用同一时钟名的正则回引用筛选报告行。

**解读** 当前位流的汇总表为同名时钟关系，但未来的跨时钟关系会被漏掉，无法据此保证完整覆盖。

**定位** 逐行对照报告表头及关系行，确认必须保留 launch 和 capture 两个字段。

**根因与修法** 采集全部关系，缺 setup／hold 数据或任意负 slack 均失败；补跨时钟负值反例。
修订后对已有报告离线复核，不重新综合未改变的设计输入。
