# 08 扫描 FIFO 的压力矩阵与深度定值

## 一、动机

本工程在易灵思钛金 Ti60F225 FPGA 上做 2D 渲染加速引擎。片内一颗 RISC-V 处理器（Sapphire SoC）跑 100MHz，
帧缓冲放在板上 256MB 的 DDR3 里，扫描输出把帧缓冲逐行读出来送 HDMI。

第 06 章把 DDR3 通路改成三端口：扫描输出接 S0，引擎（接入前由探针主机 `axi_probe_master` 替身）接 S1，
SoC 接 S2，并加一道老化屏蔽 `axi_mux_guard` 兜住 CPU 的地址等待。那一章的扫描侧用的是替身
`scanout_stub`，按固定行节拍发读，内部没有异步 FIFO。display 系列第 01 章在 2026-09-21 把替身换成真正的
扫描输出 `display`，占用同一个 `0xF810_E000` 窗口：取数侧 `display_fetch` 按水位发行一行 160 拍的读，
写入 `display_fifo`（128 位 × 512 深、跨 100MHz 与 25.2MHz 像素时钟的异步 FIFO），
像素侧 `display_out` 每 4 个像素弹出一拍、拆像素并输出。

水位指 FIFO 里当前存了多少个 128 位拍。发行条件是「空位不少于一行 160 拍才发下一行」，
512 深由这条策略推出来（约 3.2 行），占 6 块片上 RAM。FIFO 被读空时像素侧拿不到数据，
那一组 4 个像素输出黑色，画面上表现为一段内容错位，而这种错误在画面上分不出成因；
模块里因此带两个累计量，水位触底次数与没弹到的组数。水位在一个完整场里会不会进入危险区，
取决于 DDR3 控制器对扫描读的服务延迟，控制器是加密的，只能从板上量。

已有三组数字：display 第 01 章在无 S1 压力时读到 347 拍；E4 在轮询仲裁下量到另一个主机持续发
256 拍突发时 CPU 只剩 51.5% 的速度，第 06 章在三端口优先级加 guard 下量到约 62%，
扫描侧的首拍等待在满写负载下从 66 拍涨到 350 拍以上。
347 拍是无争用下的单场读数，回答不了「512 够不够」。要回答它，需要满负载下连续 120 场的水位序列，
以及每一场的完整性检查。

这一章做实验 E5 的第四节：用探针主机造纯读、纯写两种满负载，连续采 120 场的 FIFO 最低水位，
逐场判帧完整性、触底与欠载，据此给 FIFO 深度定值；同时把扫描输出接管替身之后 2.3 节那批量测的复算收口。
E5 前三节（端口重分配、防饿死措施、替身量测）在第 06 章。量测装置在系统里的位置见第 06 章的
`fig/06-系统架构.svg`，扫描输出内部的分块与连线见 display 第 01 章的 `fig/01-系统架构.svg`；
这一章不新增架构图，它没有改动 FPGA 侧的连接。

## 二、为什么是这几步

这一节的测量对象有三个性质，步骤按它们排：水位是**每场**的统计量，样本只有落在完整场上才有效；
压力源是 S1 上的探针主机，它在引擎接入后要撤走；板上的控制器与像素时钟是黑盒，只能通过寄存器观测。
由此拆成七步：

1. 逐条核对规格与 RTL，确认要读的每个寄存器、量程、单位与窗口在实现里成立；
2. 写测量程序 `displayFifoProbe`：三个场景、固定起点协议、连续 120 场、有界等待、失败留现场；
3. 先做无压力取样（JTAG 直接读寄存器），把三组场景的预期量级与协议边界钉住；
4. 三组各 120 场上板；
5. 独立复现审查：从完整烧写开始重跑，逐项对账，修掉会产生假证据或破坏失败现场的边界；
6. 回归行：把 `ddrBurstProbe` 适配真实扫描输出并复跑；
7. 定值落账：512 拍的结论与适用边界写进设计文档与程序说明。

第 1 步是后面所有数字的解释前提：计量窗口、单位或快照口径错一条，正确实现也会被自己的判据判失败。
第 3 步放在写程序之前，它能用最少的代码暴露协议层面的坑，例如跨域 `CLEAR` 的延迟与「弹数与 `SRC` 无关」
这一条。第 5 步单列，因为程序自己报 `fail 0` 只说明它按自己的判据跑完了，
说明不了这些判据的边界条件对；实际在那里找到四处会产生假证据的缺陷。
第 6 步是第 06 章留下的账：扫描输出接管替身之后，`ddrBurstProbe` 对扫描窗口的三个假设必然失效，
不补这一刀，E5 的回归行就是红的。

## 三、每一步做了什么

### 3.1 规格与 RTL 的逐条核对

E5 第四节要读 display、`axi_mux_guard`、`axi_probe_master` 三个 APB 窗口，权威寄存器表在
`rtl/display/display_fetch.v`、`rtl/bus/axi_mux_guard.v`、`rtl/bus/axi_probe_master.v` 三个文件头，
另有 `Engineering/Todo/hw/扫描输出.md` 2.2 节的同名表。核对方式是读 RTL 与源码行，
逐条落到具体行：

| 规格条目 | RTL 位置 | 核对结果 |
| --- | --- | --- |
| 最低水位计量窗口为前 476 行 | `display_out.v` 第 81 行 `MEASURE_LINES = V_ACTIVE - 4` | 成立；末 4 行是排水段 |
| `SNAP_MIN_LEVEL` 取读侧水位 | `display_out.v` 第 284 行用 `rd_level`（`rd_datacount_o`） | 成立；写指针同步滞后，读数是下界 |
| `FIFO_ZERO_HITS` 在窗口内计「由非 0 变 0」 | `display_out.v` 第 286~287 行，每拍维护 `level_was_zero` | 成立 |
| `FIFO_UNDERFLOW_BEATS` | `display_out.v` 第 280 行 `group_missed`：每个没弹到的 4 像素组记 1 | 单位是组，一组等于一个 128 位拍；不受行窗口限制 |
| 每场弹出 `FRAME_BEATS = 76800` | `display_out.v` 第 278 行按 `pop = rd_en` 计 | 成立；欠载时该值小于 76800 |
| `SNAP_END_LEVEL` 是场末清空前的残留 | `display_out.v` 第 334 行在场起始那一拍采 `rd_level` | 成立 |
| 六个 `SNAP_*` 属于同一场 | 像素侧在场起始整组锁存，toggle/ack 握手过域 | 成立；core 侧副本比像素侧滞后一场 |
| `SNAP_FRAME` 逐场加一 | `display_out.v` 第 273 行 | 成立；与 `FRAME_COUNT` 原点不同，只能各自求差 |
| `CTRL.CLEAR` 清两侧累计值 | `display_fetch.v` 第 562~565 行：core 侧脉冲、像素侧 toggle | 成立；像素侧要等下一场快照才看得出 |
| 探针每方向在途不超过一笔 | `axi_probe_master.v`：读等 `rlast`、写等 `b_fire` 才回 `S_NEXT` | 成立，与第 06 章措施一同源 |
| `COUNT` 是事务数、`LEN=255` 是 256 拍 | `axi_probe_master.v` 第 91、291 行 | 成立 |

核对结果里有两条会影响读数解释。其一，`FIFO_UNDERFLOW_BEATS` 计的是「组」，
一个组对应一个 128 位拍，报告里按拍写。其二，`SNAP_*` 是像素侧快照的副本，
写完 `CLEAR` 之后立刻读到的仍可能是上一场的值，必须等 `SNAP_FRAME` 前进一次才能把「读回 0」当作清零成功。

核对之后先用 JTAG 直接读寄存器取样（不加载程序，只读写 APB），四次会话把协议与量级钉住：

| 会话 | 配置与读回 |
| --- | --- |
| 空载基线 | 写 `CTRL=EN\|SRC\|CLEAR` 后 2 s：`SNAP_MIN=347`、`FRAME_BEATS=76800`、`SNAP_END_LEVEL=0`、触底与欠载 0、`MAX_FIRST=66`、`MAX_FULL=239`、`MAX_R_GAP=44`；再过 1 s，`FRAME_COUNT` 与 `SNAP_FRAME` 都加 61 |
| 清零协议 | `CTRL=2`（只开 `SRC`）300 ms 读到欠载 1 228 800 拍（16 场）；改 `CTRL=0` 后 50 ms 读到 1 382 400 拍（18 场，`SRC` 在场起始才生效，多记一场）；写 `CLEAR` 后立刻读仍是 1 382 400，再等 120 ms 才是 0 / 0 |
| 取数负载与 `SRC` 的关系 | 同一地址、各 500 ms：`CTRL=7`（`SRC=1`）读到 `TXN=14373`、`BEAT=2304000`；`CTRL=5`（`SRC=0`）读到 `TXN=14691`、`BEAT=2355840`，两组增速一致 |
| 探针满负载下的单场水位 | 读负载中三次抽样 `SNAP_MIN` 都是 331，写负载中两次都是 329；探针 `DONE` 时 `ERRS=0` |

第三行给出一个不在规格里的结论：像素侧的弹出判据是 `rd_en = pop_phase & ~rd_empty`，不看 `src_eff`，
所以 `EN=1` 就已经是完整的取数负载，`SRC` 只选择显示哪一路、并给水位与欠载计量开门。
这条结论限定了后面两个程序的配置写法：测量水位的一组必须 `SRC=1`，只读 `MAX_*` 与 `TXN` 的回归程序置 `EN=1` 就够。

前期探针取样还有两笔用于核对压力时长的原始值：display 满速取数时，4096 笔 × 256 拍读用了
1 310 667 周期（每笔 320.0 周期，`LAT_SUM=171349`、`ERRS=0`），同规模写用了
1 337 616 周期（每笔 326.4 周期，`ERRS=0`）；读压力延长到 262144 笔后用了
83 974 272 周期（每笔 320.3 周期），采样期间三次单场水位均为 331 拍。
这组取样只有每种条件两三个点，不能替代后面的连续 120 场判据。按 480 笔/场、60 场/秒换算，
显示扫描约 4 608 000 拍/秒（73.7 MB/s）；探针的 256 拍读约 1.28 GB/s。

### 3.2 测量程序

新增 `Main/sw/apps/probe/displayFifoProbe/`，只在 Ti60 上运行，`Makefile` 直接 include
`../../../mk/target.mk`。三张寄存器表只把用到的偏移复制进 `src/main.c`，文件头指回三个 RTL，
开局用三组 ID/VERSION 拒绝错误的比特流，再核对 guard 的上电配置（`ctrl=3 mask=7 age=64`），
任一项不符就打 `fail 1` 结束，不在程序里替它写回默认值。

这个取舍针对的是接口归属：这些量测寄存器不是跨平台的游戏平台能力，
放进 `sw/bsp/include/board.h` 会迫使 PC 侧实现一批没有语义的空函数，并让一次实验牵动全平台回归；
局部复制的最小寄存器表爆炸半径更小。代价是三处 ID/VERSION 检查必须在程序里显式做，否则表与比特流不同步时读数没有意义。

三个场景除 S1 负载外配置相同：`idle` 不启动探针，`read` 用 `MODE=0` 连续 256 拍读，
`write` 用 `MODE=WRITE` 连续 256 拍写；探针地址固定 `0x0D00_0000`（避开程序区、命令表、帧缓冲与共享区），
`LEN=255` 不递增；display 为 `EN=1, SRC=1`，前缓冲先填一幅八条横向色带的稳定图案；
guard 保持上电默认。`COUNT` 初值 `0x0010_0000`。

### 3.3 固定起点与采样协议

每个场景都从同一个干净状态开始，再去采样，这样三组之间只差 S1 的负载：

```
每个场景的一次尝试（read/write 有探针，idle 没有）

  写 CTRL=0 ──► 等 STATUS 的 started/ar_valid/in_flight 三位全 0（上限 100 ms）
                │  越界 → scan_stop
                ▼
  等 2 个 SNAP_FRAME（像素侧 src_eff 经 CDC 与场起始锁存后关闭）
                ▼
  写 CTRL=CLEAR（此时无在途事务）──► 等一份完整快照，要求触底与欠载都为 0
                │                      不为 0 → warmup_underflow
                ▼
  写 CTRL=EN|SRC ──► 无压力预装 2 场 ──► 再查两个累计值
                ▼
  read/write 在这里启动探针；idle 不启动
                ▼
  丢 2 个压力预热快照 ──► 收 120 个样本 ──► 等探针 DONE
   （帧号 +1、前后帧号相同、每场查完整性）    （DONE、TX_DONE=COUNT、ERRS=0，上限 5 s）
                ▼
  读最新一份完整快照（累计触底与欠载）──► 停扫描 ──► 一次读走 MAX_*/TXN/BEAT/guard
                ▼
  排序后报 min、max、首次最小值的帧号、sorted[59] 与 sorted[60]
```

采样循环对每个样本做四件事：以 `SNAP_FRAME` 变化为节拍、整组读取六个寄存器、
读完再读一次帧号确认没有被下一场快照插入、要求相邻样本的帧号按 16 位模加法恰好加一。
第四件是用来发现软件漏采的：循环次数不等于样本数，重复帧被跳过时不能照样算满 120 次。
每条等待都有周期上限（等快照 100 ms，探针从启动到 DONE 5 s，`ABORT` 后等 10 ms 清 BUSY），
周期差用无符号减法，允许 32 位计数器回绕。采样期不打印串口、不做 CPU 大块拷贝，
结果先落内存，三组跑完统一输出；否则串口发送时间会让程序跳过快照，测到的就不再是连续 120 场。

### 3.4 判据的组成与重跑的边界

判据分三层。每个样本查 `FRAME_BEATS = 76800`、`SNAP_END_LEVEL = 0`、最低水位不低于 160 拍；
每个场景查两个累计欠载计数、display `RESPERR` 与 `SKIP`、探针 `ERRS`、display 与 guard 的 `STATUS`；
整轮查 `TXN × 160 = BEAT`（停扫描后读的同一刻快照）。探针在采样窗内必须一直是 `BUSY`，
中途 `DONE` 说明压力没有覆盖整个窗口，该轮作废。

重跑只允许两种情况：采样窗内探针提前 `DONE`（把 `COUNT` 翻倍后从起点完整重跑一次），
以及帧号跳号（场景无效，同参数重跑一次）。欠载、坏样本、等不到帧、停不下扫描都是真失败，
不能用第二轮把第一次抹掉。这条边界是复核阶段改的，理由见 4.4 节。

### 3.5 回归行：`ddrBurstProbe` 适配真实扫描输出

第 06 章的回归行要求 `ddrBurstProbe` 在端口重排后复跑。扫描输出接管 `0xF810_E000` 之后，
它对扫描窗口的三个假设失效，改了三处：`stage_ident` 的扫描 ID 由 `0x5343_414E`（`"SCAN"`）改为
`0x4449_5350`（`"DISP"`），`VERSION` 仍为 1；两处收尾等待由 1 毫秒改为 20 毫秒，
因为 `EN` 在场起始才生效（最长 16.7 毫秒），1 毫秒停不住扫描，统计还在涨；
另外把四处无界的 `DONE` 轮询统一加上 5 秒总上限与错误/超时 `ABORT`，`age64_rd/wr` 不再忽略返回值。
`S_BASE` 那一项读的是 display 的只读 `FRONT_BASE`，写它被静默忽略，复位值仍是 `0x02000000`，照旧成立。

替换替身前后逐项对照在第 06 章 5.4 节：CPU 拷贝倍数、guard 地址等待与扫描最坏值都在同一量级，
所以 2.3 节的结论可以继续引用。

| --- | --- |

| 引擎交接 | 真实引擎读、写方向各最多一笔在途；接入 S1 后，在最重 FILL/BLIT/ALPHA 命令表下复测帧完整性、水位与欠载，探针结果不能代替。 |
| 上板采集 | 从完整烧写比特流开始，程序加载后的日志须包含完整输出及末行 `fail 0`、`done`；不可用 `--no-program` 复用上次状态，采集终止标记不可提前命中 `probe_done`。 |

## 四、遇到的问题

### 4.1 初版的「停扫描」没有真正停住

第一现场（初版三轮日志，以 `e5_2_4_run1.log` 为例）：

```
SCEN idle scan txn=59040 beat=9446400 max_first=66 max_full=239 max_gap=44 status=00000004
SCEN read scan txn=96960 beat=15513600 max_first=72 max_full=238 max_gap=44 status=00000004
SCEN write scan txn=98880 beat=15820800 max_first=353 max_full=529 max_gap=44 status=00000004
```

解读：`STATUS` 读回 `0x4`，按寄存器表即 `started=1`，说明软件以为「扫描已停」时取数侧仍在运行。
`TXN` 与 `BEAT` 的比值当时是对的，所以这一条不会自己暴露。

定位：`scan_off()` 只等 `STATUS` 的 bit0。bit0 是「有一笔读在途」，它在两笔之间为 0，
于是函数在一笔结束、下一笔还没发出的那一拍就返回了。三个场景的日志全部是 `status=0x4`，
没有例外，说明这是稳定复现的过早返回。

根因与修法：改成等 `started`、`ar_valid`、`in_flight` 三位全清，并对停不下来的情况返回
`scan_stop` 失败码。修完正式日志的 `status` 都是 0，`MAX_*` 与 `TXN/BEAT` 才是真正的收尾值。
原判据没有覆盖到它，因为初版只检查「水位有没有越界」与「帧完整性」，
把 `status` 当成顺带打印的诊断量，没有为它写期望值。

这条缺陷还带走了一个结论。初版据此读到的 guard 累计命中数在写负载下是 613 045，
按它推断「写负载下地址等待长期超过 `AGE_LIMIT=64`」；修正场景边界之后，五个有效会话的末值是 824~835，
那个数量级来自错误的场景边界。用命中数论证写方向保护的说法已撤回，
写方向「guard 只验接线与触发、等待保证靠每方向一笔在途」仍由第 06 章的仿真与注错支撑，不依赖这一组数。

初版 `displayFifoProbe` 的 bin 为 10578 字节（SHA-256 前 16 位 `16a68aa06cca8b55`），
三轮原始日志保存在 `Main/sw/apps/probe/displayFifoProbe/logs/e5_2_4_run{1,2,3}.log`。

### 4.2 清零切在一笔事务中间

第一现场（复核时的诊断轮，打印的是 `SCEN idle scan` 那一行；这一轮没有留下日志文件，
下面这一行按开发日志的记录还原）：

```
SCEN idle scan txn=59039 beat=9446227 status=00000000
```

解读：`59039 × 160 = 9446240`，比读回的 `9446227` 少 13 拍。`BEAT` 比 `TXN` 对应的整笔少，
说明计数是从一笔 160 拍事务的中途开始记的。同一轮里 `status` 已经是 0，
排除「没有停住」这条原因。

定位：`CTRL.CLEAR` 清 core 侧统计是立即生效的，而当时已经有一笔读在途，
它剩下的 13 拍还会写进计数量。软件的清零点落在事务中间，两个计数器的零点就错开了。

根因与修法：把清零挪到停稳之后。修完的顺序是「先停机、再清零」，
正式日志里三组都满足 `TXN × 160 = BEAT`（59520 × 160 = 9523200、97440 × 160 = 15590400、
99360 × 160 = 15897600）。原判据没有覆盖到它，因为初版把这条对账当成顺带验证，
只打印不判定，所以从半笔开始的计数照样能报 `fail 0`。

### 4.3 冷启动叠加满写压力，第一场欠载

第一现场：诊断轮里 `warmup_underflow`，读到第二个预热快照的累计欠载不为 0。

解读：display 刚被使能时 FIFO 是空的，取数侧要一场多的时间才能预装起来；
在这一场里叠加满写压力，像素侧无数据可弹，欠载计数被写进累计量，后面 120 场再干净也过不了这一关。

定位：把起点序列拆开看，缺少「无压力预装」这一段。初版看不到这一条，
因为 4.1 的缺陷让它实际上从未真正停掉 display，每次进入新场景时 FIFO 里还有存数。

根因与修法：在清零之后、启动探针之前，先以 `EN|SRC` 无压力预装 2 场并确认两个累计值为 0，
之后才启动探针，进入正式的 2 个压力预热快照与 120 个样本。
原判据没有覆盖到它，因为初版的重跑规则允许 `warmup_underflow` 用第二轮覆盖第一次（见 4.4），
把这一条压成了偶发现象。

### 4.4 重跑规则过宽，会把第一次失败抹掉

第一现场：初版的 `retryable()` 把 `sample_bad`、`no_frame`、`warmup_underflow` 与 `early_done`、
`frame_jump` 并列，任一情况都可以用第二轮通过后只报第二轮的结果。

解读：规格只允许两种重跑（采样窗内提前 `DONE` 与帧号跳号），其余都是判据本身的结论。
允许第二轮覆盖，等于让「偶发欠载」通过一条报 `fail 0` 的路径。

定位：逐条对照本章 3.3、3.4 节的采样与重跑边界，重跑条件只有那两条；初版把「场景作废重跑」误推到了所有失败原因上。

根因与修法：`retryable()` 只保留 `early_done` 与 `frame_jump`；其余失败直接判该场景失败，
并在第 120 个快照读完之后补一次 `BUSY` 复核，防止探针恰好在这一场内提前结束却被当成覆盖了整个窗口。
原判据没有覆盖到它，因为判据表只写「该组是否通过」，没有规定重跑后如何记账。

### 4.5 对健康满写探针写 `ABORT`，板子停不下来

第一现场（诊断过程中两次遇到）：程序在写负载中途报错后直接写探针 `CTRL.ABORT`，
之后 OpenOCD 报 `Halt timed out, wake up GDB`，`reset halt` 也不能把 CPU 停下来，只能重新烧写比特流恢复。

解读：`ABORT` 会立刻把 `awvalid` 与 `wvalid` 撤销。AXI 规定 `valid` 拉高后必须保持到握手，
在一笔写事务中途撤销会把多路器与控制器留在中间状态，之后调试通路访问不到 CPU。

定位：把「普通判据失败」与「探针故障」分开看。写负载下探针本身健康，只是采样窗内提前 `DONE`，
让它在原 5 秒预算内自然收尾即可；真正需要撤销 `valid` 的只有 `TIMEOUT`/`RESP_ERR`/`LAST_ERR`
与总预算耗尽这两种情况。

根因与修法：失败路径改为先保存现场，再让健康事务自然 `DONE`；只有探针已经不能正常收尾时才写 `ABORT`，
并在 10 毫秒内确认 `BUSY` 清除；本章 3.3 节的失败收尾协议据此定稿。
同一个修法也用到 `ddrBurstProbe` 的四处无界 `DONE` 轮询上。原判据没有覆盖到它，
因为判据只关心测量结果，没有为失败路径本身设一条可观测的期望。

### 4.6 一次 `no_frame`：像素侧快照没有前进

第一现场（复核第 3 轮，`e5_2_4_review_run3.log`）：

```
SCEN idle n=0 min=0 max=0 first=0 med_lo=0 med_hi=0
SCEN idle scan txn=480 beat=76800 max_first=66 max_full=239 max_gap=44 status=00000000
SCEN idle FAIL why=no_frame
...
fail 3
done
```

解读：三个场景都没收到样本（`n=0`），失败原因是等下一份快照超过 100 毫秒；
而 `TXN=480` 说明取数侧正常发了一场的读，`status=0` 说明它已经停了。像素侧的快照没有随场起始更新。

**订正（2026-09-21，后续源码复核、`corerst` 仿真与三次新比特流上板复测）**：
上面“像素侧快照没有前进”是寄存器现象，不能推断像素时钟没有启动。
`TXN=480`、`BEAT=76800` 恰好是一整场：FIFO 已被像素侧弹完；`scan_off()` 成功返回也证明第二次场起始已到 core 侧。
冻结的只有快照寄存器。原先把故障归到板卡/像素时钟、认为原因未定位的判断撤回。

根因在 `display_fetch` 的快照接收侧：它用 `snap_sync[1] ^ snap_sync[0]` 识别翻转沿，
同步链却在 core 复位期间继续移位，接收事件被复位压住。若首次翻转恰在复位窗口内，
撤销复位后同步链已稳定，接收侧永远等不到新的沿；像素侧的 `snap_busy` 又在等确认，双方永久停住。
core 与像素域的复位源不同，完整重烧会同时复位两域，所以曾表现为“重烧即恢复”。
板上三次读回的 `FRAME_CNT/SNAP_FRAME` 分别为 65/64、65/64、66/65，说明两域释放复位只相隔约一场；
`reset halt` 还会单独复位 core 域，使这条边界在加载程序时重复出现。

修法改为比较稳定后的请求与确认电平，并要求同步链两级读数一致：
`snap_new = (snap_sync[1] ^ snap_ack) & (snap_sync[1] == snap_sync[0])`，
再用 `snap_go <= snap_new & ~snap_go` 推后一拍锁存。只比第 1 级的中间写法曾让第 0 级变成死端，
综合网表把两级折成一条 `EFX_SRL8`；加入两级一致条件后，网表恢复为两个独立、带 `async_reg` 标记的触发器。
新增 `sim/display` 的 `corerst` 用例：像素域先启动、以及运行中单独复位 core 域两段，
改前均因 `SNAP_FRAME` 不递增而失败，改后逐场 `+1`。新比特流四步编译 PASS，
`core_clk` hold 仍为 0.026 ns、片上 RAM 71 块不变；三次完整烧写后的压力矩阵全部 `fail 0`，
最低水位均为 347/331/329 拍，与修复前的有效会话一致。完整的时序与回归记录在 display 第 01 章 4.8、5.4 节。

另有一条独立的程序失败清理缺陷：run 3 的探针尚未启动，旧清理路径仍去等待并写 `ABORT`；
加入 `probe_started` 标志后不再误等。run 3 仍作为原始失败现场保留，不混入压力矩阵结果；
旧版 `retryable` 原本可能把这种失败覆盖掉，修正后程序正确报告 `fail 3`。

### 4.7 `--stop-on done` 命中 `probe_done`

第一现场（`ddrBurstProbe` 复核重跑的第一次尝试）：

```
INJECT age1_rd age=1 hits=0x00044008 probe_done
（此后再无输出，日志 3366 字节，没有 fail 也没有 done）
```

解读：程序在 `INJECT` 阶段中途看起来停住了。display 第 01 章 4.6 节记过一个同类现象，
当时归因于探针写通路，后来被反汇编与状态位定义推翻。

定位：上板工具的 `--stop-on` 是子串匹配，`"done"` 落在程序自己打的 `"probe_done"` 里，
采集窗口在一行 `probe_done` 之后关闭，程序后面的输出没有被收进日志。
换成只出现在末行的 `--stop-on "fail "` 之后，两轮都完整跑到 `done`。

根因与修法：采集侧的问题，修法落在用法上：`--stop-on` 取只在末尾出现的标记。
同一个陷阱还有第二个入口：`displayFifoProbe` 的失败现场行里有 `ptxdone=` 字段，也含 `"done"`。
这条同时解释了 display 第 01 章 4.6 留下的疑问，那一节已就地订正。
原判据没有覆盖到它，因为回归判据校验的是程序输出，采集窗口的边界不在判据范围内。

`1 tick = 10 ns`，即一个 `core_clk` 周期。探针 `cycles` 约 `0x1405_xxxx`（3.359 s）与 `0x1467_xxxx`（3.423 s），
分别等于每笔读 320.3 个周期、每笔写 326.4 个周期乘以 `COUNT`，与前期按 E4 模型算的 3.35 s 与 3.42 s 一致，

三组结果的解释：

1. **深度定值维持 512 拍。** 五种有效会话里最低水位分别是 347、331 与 327 拍，
   最坏的一轮仍高于一行 160 拍的下界 167 拍，中位数与最小值相等或只差 2 拍，
   说明 120 场的窗口里水位没有贴近下界。按本章 3.6 节的深度决策，M2 阶段保持 512 拍，
   不因为「看起来还有余量」改浅：改浅会同时改变发行节奏与场末排水窗口，水位不能按差值线性外推。
   与前期 JTAG 单场取样（读 331、写 329）相比，120 场的序列在写方向多采到 2 拍的下探。
2. **负载确实压低水位，方向规律与第 06 章一致。** 满负载读的 `MAX_FULL` 是 237~239 拍，
   水位从 347 降到 331；满负载写把 `MAX_FULL` 推到 521~544、`MAX_FIRST` 从 66 推到 353~378，
   水位最低 327。写方向更差与第 06 章 5.3 节的解释一致：控制器的读写共用 DDR 端口，
   一笔 256 拍写约占 300 个周期。`MAX_R_GAP` 三组都是 44 拍，R 通道的拍间隙没有被负载拉长。
3. **帧完整性与欠载在五个会话里全部为 0。** 每组的 `beats_bad`、`end_bad`、`low_bad` 都是 0，
   每场的 `FRAME_BEATS` 是 76800、`SNAP_END_LEVEL` 是 0，两个累计欠载计数与 `RESPERR`、`SKIP`、
   探针 `ERRS` 都是 0。`BEAT = TXN × 160` 三组都严格成立，这是统计在同一笔事务边界上读出的证据。
4. **guard 命中数只作诊断。** 五个会话的末值是 `idle` 32~37、`read` 251~256、`write` 824~835，
   随负载方向递增，与「读方向保护能改变新授权、写方向掩码生效窗口很窄」一致；
   它们不设阈值，也不再用 4.1 节撤回的那组数论证任何结论。
5. **回归行。** 有界轮询版 `ddrBurstProbe` 两轮六阶段全部 `ok`、末行 `fail 0` 与 `done`
   （`logs/e5_display_review_run{1,2}.log`）：`TRI rd` 扫描 `max_first=78`、`max_full=244`，
   `TRI wr` 为 365 / 531，`mask_s0` 为 `12000 12480 12480 12480 13071`（清位后在途那一笔照常完成、
   之后冻住、恢复后继续增长），`age1` 两个方向命中 278539 / 278538，`ERRS=0`。
   与第 06 章 5.4 节的替身时代对照表同量级。

测量方法与误差来源：水位单位是 128 位拍，一行 160 拍；`SNAP_MIN_LEVEL` 取读侧指针差，
写指针同步有两三级延迟，读数是真实水位的下界；计量窗口是帧缓冲模式下的前 476 行，
末 4 行属于排水段。板上数字由 CPU 经 APB 读取，每组在停扫描之后一次性读走，
所以 `TXN` 与 `BEAT` 是对账的；用 JTAG 逐字读同一段时两者会差几十笔，
那是两次读之间扫描仍在前进，与硬件无关。轮间波动体现在写方向的 `MAX_FIRST` 与 `MAX_FULL`
（353~378、521~544，约 4%），水位随之在 327~329 之间；`idle` 与 `read` 两组的五轮读数完全一致。
`first`（首次最小值的帧号）跟着像素域的 `SNAP_FRAME` 走，与 `FRAME_COUNT` 原点不同、不能相减，
它只回答最小值出现在哪一场。run 3 的 `no_frame` 不计入本表。
