# E4：DDR3 控制器能接受多长的突发，一次事务的固定开销是多少

状态：未开工。设计文档 3.1 节的全部带宽估算都建立在这两个数上。
需要新写一个最小 AXI 主机并接入 `Axi_Mux`，是本仓第一次往 DDR3 上挂第二个主机。

## 1 要解决什么

现在 DDR3 上只有一个主机，即 SoC 的 `io_ddrA`。它发什么样的突发由缓存行和
`memcpy` 的行为决定，测不出控制器本身的上限。引擎要用突发把一整行像素搬进片上缓冲，
搬多少、分几次、够不够 60 帧，取决于三个数：

- 控制器能接受的最大 `arlen` / `awlen`。参数文件里 `BURST_MODE="8"` 指的是颗粒侧的
  突发长度，与 AXI 侧一次事务能有多少个 128 位数据拍是两回事，后者还没有查证。
- 一次事务的固定开销 `t_tx`，即从发出地址到第一个数据拍之间的周期数。
  这个数决定突发切多长才划算。
- 持续读写时每周期能传几个数据拍，用来判断 640x480 的扫描输出与引擎并发时余量还剩多少。

突发上限这一项有一种常见的漏法：上限由从机内部的计数器位宽决定，
而仿真模型里的计数器是理想的整数，不会溢出，于是仿真通过、板上挂死。
这块板上的 DDR3 控制器是加密 RTL，连仿真都没有，这个数只能在板上量。

## 2 怎么切分

**第一步，最小 AXI 读写主机。** 写一个 `axi_probe_master`：APB 配置基址、`len`、
重复次数、读还是写，启动后按配置连续发事务，用 `core_clk` 计数器记录从启动到最后一个
`rlast` / `bvalid` 的周期数，事务计数与错误响应计数各一个寄存器。
它要带超时：控制器不响应时在固定周期后停下并置错误位，否则一次配错就得重新上电。

**第二步，接入 `Axi_Mux`。** `rtl/vendor/axi_mux/Axi_Mux.v` 已经在仓库里，
还没有进工程源文件列表。接入时 SoC 走一个主口，`axi_probe_master` 走另一个，
合成一路进 DDR3 控制器。注意文件开头的 `` `define X2 `` 在单编译单元里对后续文件可见。

**第三步，扫参数。** `len` 取 1、2、4、8、16、32、64、128、255，读写各一轮，
每轮重复足够多次让固定开销被平均掉。记录周期数、事务数、错误响应数。

**第四步，算参数。** 用周期数对 `len` 做线性拟合，截距是 `t_tx`，斜率的倒数是每周期的数据拍数。
超过控制器上限的 `len` 会表现为错误响应或超时，把最大可用值记下来。

**第五步，并发。** 让 `axi_probe_master` 满负载跑，同时用 CPU 跑 memTest，
观察两侧的耗时变化，得到 `Axi_Mux` 仲裁下的实际分配。这一步的数据同时供 E5 使用。

## 3 判据

| 项 | 判据 |
| --- | --- |
| 接入不破坏现有功能 | 接 `Axi_Mux` 之后，memTest 仍然 PASS，HDMI 八色竖条不变，APB 探针四项仍通过 |
| 时序 | 编译四步 PASS，约束告警 0，`core_clk` 与 `sdram_clk` 的 hold 仍为正，与 `../TechReports/platform/01-从零搭起可上板的硬件基线.md` 5.1 节的表逐行对比 |
| 计数器自洽 | 事务数等于配置的重复次数，错误响应数为 0；这一条不成立时，周期数不能用 |
| 注错见红 | 把超时阈值调到小于一次正常事务的时间，错误位必须置起来 |
| 输出 | 一张 `len` 对周期数的表，一个 `t_tx`，一个持续吞吐，一个最大可用 `len` |
| 结论落地 | 替换设计文档 3.1 节的估算数字，并注明测量条件 |

`axi_probe_master` 本身在仿真里要先过：自己写的部分（状态机、计数器、超时）用
一个 AXI 从机行为模型验证，正常用例加两个注错用例。控制器是加密的，这一层只能到板上。
