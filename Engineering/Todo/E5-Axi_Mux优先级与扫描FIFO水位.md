# E5 Axi_Mux 优先级重分配、防饿死与扫描 FIFO 水位

状态：未开工（分两支：端口重分配与防饿死保护是现在就能做的改动，FIFO 水位要等扫描输出存在）。
不阻塞引擎开工，但**阻塞扫描输出接入**——扫描输出接哪个口定不下来，它的带宽与时序就无法验收。
2.1~2.3 节现在就能做，2.4 节要等扫描输出存在。2.2 节的「在途事务不超过 1」是引擎 RTL 的设计约束，引擎开工时必须遵守。

## 1 要解决什么

扫描输出是实时流。640×480@60 的一行共 800 个像素时钟，约 31.7 微秒，
其中可见的 640 像素（160 拍 128 位）在约 25.4 微秒内被消耗，中间不能等。
E4 在板上量过等待的代价：轮询仲裁下，另一个主机持续发 256 拍突发时，
发短事务的一方（CPU）速度降到 **51.5%**
（platform 第 03 章 5.4 节，原始输出在那里）。

而现在的端口分配是反的。`Axi_Mux` 的优先级模式（`Cfg_Arb_Type = 1`）只能让 **S0 最高**
（设计文档 3.3 节的对照表与 platform 第 03 章 3.2 节研究 4 都确认了这一点），
当前 `rtl/top/gfx2d_top.v` 第 647 行起把 **S0 给了 SoC**、S1 给了探针主机。

**优先级模式的实际行为**（`rtl/vendor/axi_mux/Axi_Mux.v` 第 2425 行起的 `Axi_Mux_Addr_Ctrl`）：
每次授权之后扫描指针回到 S0，再按 S0、S1、S2 的顺序每拍前进一格，
所以是**按端口号的严格优先级**，号越大越靠后，而且每往后一个端口多一拍扫描延迟。
仲裁只管**地址握手**：一个主机拿到通道，等它的地址握手完成就重新仲裁；
读写数据则按信息 FIFO 里的授权顺序串行送回（读 AR2R 深 16，写 AW2W 深 8），已经排进去的事务不会被插队。
读与写由两个独立的仲裁器处理（第 1113 行 `Axi_Mux_Wr_Ctrl`、第 1231 行 `Axi_Mux_Rd_Ctrl`），
所以另一个主机的**写**负载在多路器这一级不挡扫描输出的**读**，只可能在控制器内部排队。

端口分配定为引擎排在 CPU 前面：

```
现状（`define X2，轮询）            接入扫描输出与引擎后（`define X3，优先级）
  u_soc        -> S0                   u_scanout -> S0   最高，实时流
  u_axi_probe  -> S1                   u_engine  -> S1   吞吐优先
                                       u_soc     -> S2   最低，由 2.2 节的保护兜底
```

这个顺序让引擎的吞吐不受 CPU 访存打扰，代价是 **CPU 有被饿死的风险**：
严格优先级下，S2 只有在指针走到它的那一拍 S0、S1 都没有请求时才拿得到授权。
引擎若为了吞吐流水发地址（上一笔地址握手的下一拍就拉高下一笔的 valid），
只要信息 FIFO 与控制器还肯收，S2 就一直轮不到。CPU 取指与缓存装填都要访问 DDR，
被饿住就等于整机停住，而且串口也不会有任何输出。所以本实验除了重分配，
必须同时加上 2.2 节的两道防饿死措施，并把它们验证到「注错见红」。

本实验要量出来的副作用：

1. **SoC 从 S0 挪到 S2**，排在扫描输出与引擎之后。目前两个口轮询，没有谁固定优先，
   改成严格优先级后 CPU 每次访存 DDR 的最坏等待有多长，要按 2.2 节的上界算出来再实测。
2. **`Cfg_Cnl_Mask` 的位宽要跟着端口数变**。现在是 2 位：`axi_probe_master` 的
   `ARB` 寄存器 bit[2:1] 给出 `mux_arb_mask`（`rtl/bus/axi_probe_master.v` 第 186 行），
   顶层第 229 行声明为 `wire [1:0]`。三个端口之后掩码要 3 位，
   探针主机是 E4 的临时占用者，将来会撤走，这个配置位需要有正式的归属。

## 2 怎么切分

### 2.1 端口重分配与优先级（现在就能做，不改厂商的仲裁逻辑）

1. `rtl/vendor/axi_mux/Axi_Mux.v` 第 43 行的 `` `define X2 `` 改成 `` `define X3 ``。
   `Axi_Mux_Param.vh` 里 X3 会连带定义 X2，不必两个都写。
   这是厂商文件，改动要按 `rtl/README.md` 的规矩登记；X3 的端口与内部通路在第 164~199、
   552~591、911~936、1373~1386 行，是现成的。多一个端口会给 128 位数据选择器多一路输入，
   数据通路的组合深度会变，所以第 5 步必须看时序。
2. 顶层端口重排：扫描输出（接入前先用 2.3 节的替身 `scanout_stub`）接 S0，
   `u_axi_probe`（引擎接入前的替身）留在 S1，现有 `soc_ddr_*` 从 S0 挪到 S2。
   挪动时不动数据宽度、不动 ID 截断
   （仍按 `rtl/README.md`「关键参数」一节的说明，地址 [27:0]、ID 4 位）。
3. `mux_arb_mask` 声明成 `wire [2:0]`，`axi_probe_master` 的 `ARB` 寄存器改成
   可以用 3 位掩码（bit[3:1]），复位值仍要满足现状：轮询、全部通道打开。
   **探针主机撤走之后，仲裁方式与掩码要有一个不依赖探针的位置**，
   建议放 `rtl/bus/apb_probe.v` 的空闲地址（它已在 APB Slave 0 的 64KB 窗口里），
   这一步在本实验内决定并实现，不留到引擎接入时再补。
   2.2 节保护模块的寄存器放在同一个位置。
4. 接入 2.2 节的 `axi_mux_guard`，送进 `Axi_Mux` 的掩码改为「寄存器掩码 与 保护掩码」。
5. 编译并看时序。这一刀重排的是 128 位数据通路的端口选择，`core_clk` 的 hold
   现在只有 0.026 ns（`outflow/gfx2d_ti60.timing.rpt` 第 71 行），要按
   `../../Main/doc/开发环境.md` 0.4 节的顺序检查时序与资源。

### 2.2 防饿死的两道措施（与端口重分配同一次做）

两道措施分工不同：第一道约束引擎的行为，让正常情况下根本不会饿死；
第二道在顶层强制兜底，即使引擎违反约束或出了 bug，CPU 的等待也有上界。
只做第一道等于把整机能否运行押在引擎 RTL 没有 bug 上；只做第二道，
CPU 虽然不会被饿死，但扫描输出与 CPU 在信息 FIFO 里可能排在一长串引擎事务后面。

#### 措施一：引擎每个方向的在途事务不超过 1（引擎 RTL 的设计约束）

- 读方向：上一笔的 `rlast` 握手完成之前，不拉高下一笔的 `arvalid`；
- 写方向：上一笔的 `bvalid` 握手完成之前，不拉高下一笔的 `awvalid`；
- 引擎 RTL 用参数 `MAX_INFLIGHT` 表达这条约束，默认值 1，大于 1 必须重新做本实验的全部判据。

它解决两件事。其一，引擎的 valid 在每笔数据阶段都是低的，指针会走到 S2，CPU 自然拿得到授权，
探针主机现在就是这样工作的（`axi_probe_master.v` 的 `S_NEXT`→`S_RD`/`S_WR` 状态机，
一笔的 `rlast` 或 `bvalid` 握手之后才回到 `S_NEXT` 发下一笔）。
E4 的并发实验是在轮询模式下做的，不能拿来证明优先级模式下不饿死，这一点由下面的仿真证明。
其二，它把扫描输出与 CPU 在信息 FIFO 里的排队限制在最多一笔引擎事务之后。
控制器会不会在上一笔数据没传完时就提前接受下一个地址，它的总线层
`rtl/vendor/ddr3_controller/axi4_bus_ctl/axi4_bus_ctl.v` 从第 100 行起是加密的，看不到；
有了这条约束，结论就不依赖控制器的这一行为。

代价是引擎放弃地址流水。E4 实测读事务固定开销约 27 个周期，流水能省下多少取决于控制器是否提前接受地址，
这个收益现在没有数，引擎实现时如果要放开，必须先量出收益，并重做本实验。

#### 措施二：顶层老化屏蔽 `rtl/bus/axi_mux_guard.v`（新写，不改厂商文件）

在顶层观察 S2（SoC）的地址通道，SoC 等太久就暂时把引擎从仲裁里摘掉：

```
每个方向一个等待计数器（AR、AW 各一个）
  SoC 的 valid 为高、ready 为低：计数加 1
  地址握手完成，或 valid 为低：计数清零
任一方向的计数达到 AGE_LIMIT：
  保护掩码的 S1 位清 0，保持到该方向的地址握手完成，再恢复为 1
保护掩码的 S0 位、S2 位恒为 1
送进 Axi_Mux 的 Cfg_Cnl_Mask = 寄存器掩码 & 保护掩码
```

为什么这样做是安全的：

- **不违反 AXI 协议。** 引擎已经拉高的 valid 保持不撤，只是暂时不被选中；AXI 只要求 valid 拉高后保持到握手，
  不限制从机或互连让它等多久。
- **不打断正在进行的握手。** `Axi_Mux` 的掩码只参与选通道（第 2491 行 `Effe_S_Val = S_A_Valid & Cfg_Cnl_Mask`），
  已经被选中、正在地址握手的通道走 `Act_Cnl_List`，不受掩码变化影响。
- **影响范围小。** 读写两个仲裁器接的是同一个 `Cfg_Cnl_Mask`（第 1137、1251 行），
  屏蔽期间引擎读写都暂停，但窗口只持续到 SoC 的地址握手完成，量级是几拍。
- **不碰扫描输出。** S0 永远不被屏蔽，保护只在引擎与 CPU 之间起作用。

寄存器（与 2.1 第 3 步的仲裁配置放在一起）：

| 名称 | 读写 | 复位值 | 说明 |
| --- | --- | --- | --- |
| `GUARD_EN` | 读写 | 1 | 0 时保护掩码恒为全 1，只用于注错 |
| `AGE_LIMIT` | 读写 | 64 | 单位是周期。无竞争时 S2 地址授权最多约 3 拍扫描，64 远大于正常等待；又远小于一笔 256 拍突发（E4 实测读约 307~311 个周期），屏蔽能在引擎的下一笔之前生效 |
| `GUARD_HITS` | 只读，写清零 | 0 | 屏蔽触发的次数 |
| `S2_MAX_WAIT_AR` / `S2_MAX_WAIT_AW` | 只读，写清零 | 0 | SoC 读、写地址从 valid 拉高到握手的最大周期数 |

两道措施都在时，CPU 一次 DDR 访存的最坏等待上界（**估算**，按 E4 的 `T(N) = t_tx + k·N`）：

```
地址阶段 ≤ AGE_LIMIT + 3（指针扫描）                        ≈ 67 周期
数据阶段 ≤ 在途的一笔引擎事务 + 插在前面的一笔扫描行读
         ≈ 读 256 拍 (27.41 + 1.086×256 ≈ 305) + 读 160 拍 (27.41 + 1.086×160 ≈ 201)
合计     ≈ 570 周期，约 5.7 微秒
```

扫描输出的最坏等待同理：地址阶段只有扫描延迟，数据阶段最多排在在途的一笔引擎事务与一笔 CPU 事务之后。
这两个上界都要由 2.3 节的板上测量与下面的仿真替换。

#### 仿真验证（板上复现不了饿死，必须在仿真里做）

探针主机一次只发一笔，在板上当引擎替身时**不会**饿死 CPU，所以「没有保护会饿死、有保护不会」
这组对照只能在仿真里构造。`Axi_Mux` 是明文，可以沿用 `sim/axi_probe` 的做法（带 `EFX_SRL8` 厂商模型），
新建 `sim/axi_mux_guard/`：

| 组件 | 做法 |
| --- | --- |
| S1 主机 | 可配置的激进主机：地址握手的下一拍就拉高下一笔 valid，读写各一种，突发 256 拍 |
| S2 主机 | 模仿 CPU：单拍或 4 拍的短读写，间隔随机 |
| S0 主机 | 按行节拍发 160 拍读，可关闭 |
| 从机 | 复用 `sim/axi_probe/axi_ram_model.v`，加一个参数控制是否提前接受地址 |
| 判据 | 统计 S2 每笔的地址等待与总等待，超过上界即 FAIL |

| 用例 | 配置 | 期望 |
| --- | --- | --- |
| `normal` | 激进 S1，保护开启 | PASS，S2 最大地址等待 ≤ `AGE_LIMIT + 3` |
| `inflight1` | S1 在途事务 ≤ 1，保护关闭 | PASS，只靠措施一也不饿死 |
| `inject_noguard` | 激进 S1，保护关闭 | FAIL，S2 超时。这是饿死确实存在、保护确实起作用的证据 |
| `inject_mask_s0` | 注错让保护掩码的 S0 位跟着 S1 一起清零 | FAIL，S0 在屏蔽窗口内拿不到授权，证明判据盖住了「不碰扫描输出」 |
| `inject_midgrant` | 在 S1 地址握手进行中触发屏蔽 | PASS 且无协议违例，验证「不打断正在进行的握手」 |

### 2.3 用探针主机当引擎与扫描负载的替身（现在就能做）

引擎与扫描输出都还没有，但**它们在总线上的正常负载可以用探针主机复现**：
探针主机就是一台能持续发 256 拍突发的 128 位主机，E4 的 `SHARE` 阶段
已经用它复现过「长突发压短事务」。它遵守措施一，所以测到的是「正常引擎」下的数字，
饿死的情形由 2.2 节的仿真覆盖。本实验的替身方案：

| 角色 | 替身 | 怎么配 |
| --- | --- | --- |
| 引擎满负载 | `u_axi_probe` 接 S1，`LEN=255`、`COUNT` 拉满，**读、写各跑一轮**（`MODE` bit0 WRITE 分别取 0 与 1，bit1 INC 按需） | 读与写在多路器里分开仲裁，只跑一种会漏掉另一种的影响；参数与 E4 的 `SHARE` 相同，地址避开程序区 |
| 扫描输出 | 接 S0 的一个只读小主机，按行发 160 拍的读，行周期约 31.7 微秒（`core_clk` 下约 3175 个周期），场周期 525 行 | 新写 `rtl/bus/scanout_stub.v`，自己用 `core_clk` 数周期产生场行节拍，并对每笔读计「`arvalid` 拉高到第一个 `rvalid`」的周期数，记最大值与直方图 |
| CPU 负载 | `sw/ddrBurstProbe` 里的 `cpu_copy()`，逐字拷贝 256KB，接 S2 | 现成 |

在优先级模式下测四件事：CPU 拷贝耗时（与现状 S0/轮询对比）、扫描替身的**最坏等待**
（从发出 `arvalid` 到第一个 `rvalid` 的周期数）、`S2_MAX_WAIT_AR`/`AW` 与 `GUARD_HITS`，
以及三者并发时是否都完成。
这一节的产物是**数字**，不是功能：它把「S0 让给扫描、S1 让给引擎之后 CPU 会慢多少」先钉住，
引擎真接进来时只需要换掉 S1 的驱动源。

注意仲裁不抢占：即使在优先级模式下，扫描输出也要等排在它前面的事务走完。
在措施一成立时，两种模式下的最坏等待**都**约等于一笔 256 拍突发的时长（E4 实测读约 307~311 个周期），
优先级模式的收益在于最多只排在一笔之后，而轮询模式下可能要依次等 CPU 与引擎各一笔。
判据按这个机理写，不要求两种模式的最坏等待必须拉开很大差距。

### 2.4 扫描 FIFO 的最低水位（要等扫描输出存在）

这一节是本实验的正题，也是唯一无法用替身完全替代的部分：**异步 FIFO 的最低水位
取决于扫描输出自己的消耗节奏与突发长度**，替身只能给出上界。

做法是在扫描输出模块里加水位观测。FIFO 两侧在不同时钟域（写侧 `core_clk`，读侧像素时钟），
**不能用一个计数器两边加减**：水位要在读侧用本域的读指针与同步过来的写指针（格雷码）相减得到，
这样看到的是保守值（写指针同步有两三拍延迟，水位只会偏低不会偏高）。
把 **一帧内出现的最小值**（不是平均值）锁存到一个只读寄存器，
场同步时快照一次，再同步回 `core_clk` 经 APB 读出。
判据是**一帧内的最小水位不低于一行 160 拍**（FIFO 若按像素存，折算成 640 像素）。
这条判据假设扫描输出至少提前一行预取；若设计改成「行到才取」，判据要随之改写，并在报告里说明。

同时记录两次「水位触及 0 之后欠载的拍数」。欠载一旦发生，画面会出现一行错位，
肉眼看不出是 FIFO 还是别的问题，所以必须有计数器，不能只靠看屏幕。

### 2.5 结论落地

- 端口分配与两道防饿死措施写进 `../../Main/rtl/README.md` 与设计文档 3.3 节。
  3.3 节现在写的是「扫描输出必须接 S0，SoC 与引擎依次顺延」，与本实验定下的「S1 引擎、S2 SoC」不一致，
  要换成定稿的分配表，并写明措施一是引擎的设计约束；
- FIFO 深度的定值与依据写进设计文档 3.3 节与 platform 或 display 系列的 TechReport；
- 若实测最低水位远高于一行，写明可以把 FIFO 改浅多少、省几块 RAM（与 E1 的 RAM 预算对账）。

本实验**不含**：扫描输出本身的实现（从 DDR 读像素、时序发生、双缓冲切换，
属 display 工作点）、引擎本体的接入（属 engine 工作点，但措施一的约束由本实验定下）、
`Axi_Mux` 写响应码的缺陷（已在 E4 里处理，见
[`E4-未覆盖的判据.md`](E4-未覆盖的判据.md)）。

| CPU 上界 | CPU 访存的最坏总等待给出实测值，并与 2.2 节约 570 周期的估算对比；超出估算时解释多出来的部分 |
| 仲裁生效 | 优先级模式下，引擎替身读、写满负载各一轮，扫描替身的最坏等待不超过「一笔 256 拍突发的实测时长 + 一笔 CPU 事务 + 仲裁延迟」，且直方图里没有「等两笔引擎事务」的样本；轮询模式作对照，同样记录最坏等待与直方图 |
| 反例 | 把寄存器掩码里 S0 那一位清零，扫描替身必须完全拿不到授权（每笔都超时）。拿得到说明配置没送进多路器，前半段结论作废 |
| CPU 代价 | 给出 CPU 拷贝耗时在 S0/轮询（现状）、S2/优先级加保护两种配置下的数字，差值写明 |
| 水位 | 一帧内 FIFO 最低水位不低于 160 拍；给出最低值、中位值与取到最低值的那一帧的帧号 |
| 欠载 | 欠载计数为 0；不为 0 时本实验不通过，先加深度再复测，并把初值记进报告 |
| 配置归属 | 仲裁方式、掩码与保护寄存器有一个不依赖 `axi_probe_master` 的寄存器位置，且上电默认值可用（优先级模式下 `GUARD_EN = 1`） |
| 定值 | FIFO 深度给出定值与理由（最低水位 + 余量），并与 RAM 预算对账 |

「反例」这一条与「仲裁生效」成对，是这一节的自检：配置若没有送进多路器，
单看「最坏等待不大」也能通过（负载不够重时轮询也不会等太久）。
原先写的「改回轮询后最坏等待必须变差」不成立：仲裁不抢占，两种模式的最坏等待都约等于一笔长突发。
改用掩码注错，S0 被屏蔽后必然拿不到授权，能直接证明配置到达了多路器。

「保护注错」与仿真里的 `inject_noguard` 分工不同：仿真证明饿死确实会发生、保护确实能解，
上板这一条只证明保护模块接到了真实的多路器上。板上的替身遵守措施一，本来就不会饿死，
不能用「关掉保护看 CPU 会不会卡住」来做上板注错。
