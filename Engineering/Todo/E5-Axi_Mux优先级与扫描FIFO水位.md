# E5 Axi_Mux 优先级重分配、防饿死与扫描 FIFO 水位

状态：**2.1~2.3 已验收（2026-09-19，用户验收；第二轮复核：guard VERSION 2，仿真 17/17，上板三轮 `fail 0`，回归表与 HDMI 竖条全过）**；
过程、数据与解释已写进 [platform 第 06 章](../TechReports/platform/06-Axi_Mux三端口仲裁与SoC防饿死保护.md)。
2.4 节（真实扫描 FIFO 水位与深度定值）等扫描输出存在后再做，届时本条才能整体验收。方案见下（2026-09-19 确认 D1~D5）。
不阻塞引擎开工，但**阻塞扫描输出接入**——扫描输出接哪个口定不下来，它的带宽与时序就无法验收。
2.1~2.3 节现在做，2.4 节等扫描输出存在。扫描读与引擎读写都约束为每个方向在途事务不超过 1；
引擎开工时必须遵守，任何一项放宽都要重做 E5 全套判据。

## 1 要解决什么

扫描输出是实时流。640×480@60 的一行共 800 个像素时钟，约 31.7 微秒，
其中可见的 640 像素（160 拍 128 位）在约 25.4 微秒内被消耗，中间不能等。
E4 在板上量过等待的代价：轮询仲裁下，另一个主机持续发 256 拍突发时，
发短事务的一方（CPU）速度降到 **51.5%**
（platform 第 03 章 5.4 节，原始输出在那里）。

E5 开工前 `rtl/top/gfx2d_top.v` 把 **S0 给了 SoC**、S1 给了探针主机（`` `define X2 ``，轮询）；扫描输出还不存在。
2.1 节实现之后已改为 S0 扫描替身、S1 探针、S2 SoC。
`Axi_Mux` 把 `Cfg_Arb_Type = 1` 称为优先级模式，注释写 S0 最高，但 2026-09-19 的源码复核与
三端口临时仿真确认，它**不是通常意义的严格优先级**。

**优先级模式的实际行为**（`rtl/vendor/axi_mux/Axi_Mux.v` 第 2425 行起的 `Axi_Mux_Addr_Ctrl`）：
选中一个通道时搜索指针复位到 S0；地址握手后的第一个空闲周期里，刚完成的通道仍留在
`Act_Cnl_List`，而 `Act_Cnl_Hit` 又排除该列表，所以刚完成的通道会被跳过一轮。下游地址通道
恒 ready 时，三路持续请求的 40 周期握手计数为 S0=10、S1=10、S2=0；只有 S1、S2 持续请求时
为 S1=19、S2=0。让 S1 每笔之后空 6 个周期，S2 才能持续取得授权。固定授权序列必须进入仿真判据，
不能再从“优先级”这个名字推导严格顺序。

仲裁只管**地址握手**：一个主机拿到通道，等它的地址握手完成就重新仲裁；
读写数据则按信息 FIFO 里的授权顺序串行送回（读 AR2R 深 16，写 AW2W 深 8），已经排进去的事务不会被插队。
读与写由两个独立的仲裁器处理（第 1113 行 `Axi_Mux_Wr_Ctrl`、第 1231 行 `Axi_Mux_Rd_Ctrl`），
所以另一个主机的**写**负载在多路器这一级不挡扫描输出的**读**，只可能在控制器内部排队。

端口分配定为引擎排在 CPU 前面：

```
现状（`define X2，轮询）            接入扫描输出与引擎后（`define X3，优先级模式）
  u_soc        -> S0                   u_scanout -> S0   实时流，只读在途 ≤ 1
  u_axi_probe  -> S1                   u_engine  -> S1   读、写各自在途 ≤ 1
                                       u_soc     -> S2   由 2.2 节的保护兜底
```

这个分配保留 S0 作为扫描入口，但实时性结论不依赖“严格优先级”，而由在途事务契约、等待统计、
FIFO 水位和欠载计数共同验收。**CPU 仍有被饿死的风险**：S1 若为了吞吐流水发地址，
只要信息 FIFO 与控制器还肯收，实际状态机就可能一直不走到 S2。CPU 取指与缓存装填都要访问 DDR，
被饿住就等于整机停住，而且串口也不会有任何输出。所以本实验除了重分配，
必须同时加上 2.2 节的两道防饿死措施，并把它们验证到「注错见红」。

本实验要量出来的副作用：

1. **SoC 从 S0 挪到 S2**。目前两个口轮询，没有谁固定优先；改成三端口优先级模式后，
   CPU 的地址等待、总等待与吞吐代价要按 2.2 节的仿真口径和板上实测分别给出。
2. **`Cfg_Cnl_Mask` 的位宽要跟着端口数变**。E5 开工前是 2 位：`axi_probe_master` 的
   `ARB` 寄存器 bit[2:1] 给出 `mux_arb_mask`，顶层声明为 `wire [1:0]`。三个端口之后掩码要 3 位，
   探针主机是 E4 的临时占用者，将来会撤走，这个配置位需要有正式的归属
   （2.1 节已改为 3 位，归永久模块 `axi_mux_guard`）。

## 2 怎么切分

### 2.1 端口重分配与优先级（现在就能做，不改厂商的仲裁逻辑）

1. `rtl/vendor/axi_mux/Axi_Mux.v` 第 43 行的 `` `define X2 `` 改成 `` `define X3 ``。
   `Axi_Mux_Param.vh` 里 X3 会连带定义 X2，不必两个都写。
   这是厂商文件，改动要按 `rtl/README.md` 的规矩登记；X3 的端口与内部通路在第 164~199、
   552~591、911~936、1373~1386 行，是现成的。多一个端口会给 128 位数据选择器多一路输入，
   数据通路的组合深度会变，所以第 5 步必须看时序。
2. 顶层端口重排：扫描输出（接入前先用 2.3 节的替身 `scanout_stub`）接 S0，
   `u_axi_probe`（引擎接入前的替身）留在 S1，现有 `soc_ddr_*` 从 S0 挪到 S2。
   挪动时不动数据宽度、不动 ID 截断
   （仍按 `rtl/README.md`「关键参数」一节的说明，地址 [27:0]、ID 4 位）。
3. `mux_arb_mask` 声明成 `wire [2:0]`。仲裁方式、三位用户掩码与保护寄存器全部归永久模块
   `rtl/bus/axi_mux_guard.v`，占 APB Slave 0 的独立窗口 `0xF810_F000~0xF810_FFFF`；
   不放进临时的 `apb_probe` 或 `axi_probe_master`。探针原 `ARB` 寄存器不再驱动多路器，
   `sw/apps/probe/ddrBurstProbe` 随之改读写新窗口。上电默认是优先级模式、三通道全开、guard 开启。
4. 接入 2.2 节的 `axi_mux_guard`，送进 `Axi_Mux` 的掩码改为「寄存器掩码 与 保护掩码」。
5. 编译并看时序。这一刀重排的是 128 位数据通路的端口选择，`core_clk` 的 hold
   现在只有 0.026 ns（`outflow/gfx2d_ti60.timing.rpt` 第 71 行），要按
   `../../Main/doc/开发环境.md` 0.4 节的顺序检查时序与资源。

### 2.2 防饿死的两道措施（与端口重分配同一次做）

两道措施分工不同：第一道约束引擎的行为，让正常情况下根本不会饿死；
第二道在顶层强制兜底，即使引擎违反约束或出了 bug，CPU 的等待也有上界
（这一点仿真只在读方向成立；写方向上 guard 没有可观测的作用，写方向只能靠第一道，见本节末「写方向订正」）。
只做第一道等于把整机能否运行押在引擎 RTL 没有 bug 上；只做第二道，
CPU 虽然不会被饿死，但扫描输出与 CPU 在信息 FIFO 里可能排在一长串引擎事务后面。

#### 措施一：扫描与引擎每个方向的在途事务不超过 1（正式接口契约）

- 读方向：上一笔的 `rlast` 握手完成之前，不拉高下一笔的 `arvalid`；
- 写方向：上一笔的 `bvalid` 握手完成之前，不拉高下一笔的 `awvalid`；
- 扫描输出只有读方向，同样等上一笔 `rlast` 握手之后再发下一笔；
- 引擎 RTL 用参数 `MAX_INFLIGHT` 表达这条约束，默认且当前只允许取 1。扫描或引擎任一项放宽，
  必须重新做本实验的全部判据。

它解决两件事。其一，引擎的 valid 在每笔数据阶段都是低的，指针会走到 S2，CPU 自然拿得到授权，
探针主机现在就是这样工作的（`axi_probe_master.v` 的 `S_NEXT`→`S_RD`/`S_WR` 状态机，
一笔的 `rlast` 或 `bvalid` 握手之后才回到 `S_NEXT` 发下一笔）。
E4 的并发实验是在轮询模式下做的，不能拿来证明优先级模式下不饿死，这一点由下面的仿真证明。
其二，它把扫描输出与 CPU 在信息 FIFO 里的排队限制在最多一笔引擎事务之后，也避免扫描自身
连续排入多笔行读破坏总等待估算。
控制器会不会在上一笔数据没传完时就提前接受下一个地址，它的总线层
`rtl/vendor/ddr3_controller/axi4_bus_ctl/axi4_bus_ctl.v` 从第 100 行起是加密的，看不到；
有了这条约束，结论就不依赖控制器的这一行为。

代价是引擎放弃地址流水。E4 实测读事务固定开销约 27 个周期，流水能省下多少取决于控制器是否提前接受地址，
这个收益现在没有数，引擎实现时如果要放开，必须先量出收益，并重做本实验。

#### 措施二：顶层老化屏蔽 `rtl/bus/axi_mux_guard.v`（新写，不改厂商文件）

在顶层观察 S2（SoC）的地址通道，SoC 等太久就暂时把引擎从仲裁里摘掉：

```
每个方向一个等待计数器和保护锁存（AR、AW 各一组）
  SoC 的 valid 为高、ready 为低：计数加 1
  地址握手完成，或 valid 为低：计数清零
某方向的计数达到 AGE_LIMIT：锁存该方向的 protect
  protect_ar 保持到 SoC 的 AR 地址握手完成或 ARVALID 撤销
  protect_aw 保持到 SoC 的 AW 地址握手完成或 AWVALID 撤销
guard_allow_s1 = ~(protect_ar | protect_aw)
只有两个方向的 protect 都清除，S1 才恢复
保护掩码的 S0 位、S2 位恒为 1
送进 Axi_Mux 的 Cfg_Cnl_Mask = user_mask & {1'b1, guard_allow_s1, 1'b1}
```

为什么这样做是安全的：

- **不违反 AXI 协议。** 引擎已经拉高的 valid 保持不撤，只是暂时不被选中；AXI 只要求 valid 拉高后保持到握手，
  不限制从机或互连让它等多久。
- **不打断正在进行的握手。** `Axi_Mux` 的掩码只参与选通道（第 2491 行 `Effe_S_Val = S_A_Valid & Cfg_Cnl_Mask`），
  已经被选中、正在地址握手的通道走 `Act_Cnl_List`，不受掩码变化影响。
- **读写保护不会互相提前解除。** 读写两个仲裁器接的是同一个 `Cfg_Cnl_Mask`（第 1137、1251 行），
  所以任一方向触发时引擎读写都暂停；用 `protect_ar | protect_aw` 合并，先完成的方向不能让另一个方向失去保护。
- **不碰扫描输出。** S0 永远不被屏蔽，保护只在引擎与 CPU 之间起作用。

永久 APB 窗口为 `0xF810_F000~0xF810_FFFF`，寄存器如下：

| 偏移 | 名称 | 读写 | 复位值 | 说明 |
| ---: | --- | --- | ---: | --- |
| `0x000` | `ID` | 只读 | `0x4D555847` | ASCII `MUXG` |
| `0x004` | `VERSION` | 只读 | 2 | 寄存器接口版本；2 = 两个 MAX 改为每拍更新（2026-09-19 复核） |
| `0x008` | `CTRL` | 读写 | 3 | bit0 `ARB_TYPE`，bit1 `GUARD_EN`；guard 关闭只用于注错 |
| `0x00C` | `CHANNEL_MASK` | 读写 | 7 | 三位 `user_mask`，S0/S1/S2 全开 |
| `0x010` | `AGE_LIMIT` | 读写 | 64 | 单位为 `core_clk` 周期，只是保护触发阈值，不是绝对等待上界 |
| `0x014` | `STATUS` | 只读 | 0 | bit0 `protect_ar`，bit1 `protect_aw` |
| `0x018` | `GUARD_HITS` | 只读 | 0 | 两个 protect 的 0→1 次数之和 |
| `0x01C` | `S2_MAX_WAIT_AR` | 只读 | 0 | SoC ARVALID 高、ARREADY 低的最长连续周期数，每拍更新，含尚未握手的那一笔 |
| `0x020` | `S2_MAX_WAIT_AW` | 只读 | 0 | 同上，AW 方向 |
| `0x024` | `CLEAR` | 只写 | — | bit0 写 1 清三个统计寄存器，不改配置与当前保护状态 |

掩码只参与新通道搜索，不能撤销已经锁存在 `Act_Cnl_List` 的授权：S1 已获授权且下游持续不 ready 时，
中途屏蔽 S1，S2 仍要等 S1 的地址握手。这条**已由仿真实测**（`inject_midgrant`：S1 未撤销 valid，
释放后 S2 恢复），不再写成 `AGE_LIMIT + 3` 那样的硬件绝对保证。

**地址等待的验收口径（2026-09-19 按实测改）**。原写 `S2 地址等待 ≤ AGE_LIMIT + ADDR_STALL_MAX + 4`，
整机仿真证明它不成立：`Axi_Mux` 的 AR2R（深 16）与从机读队列会先收下一批**已授权**的地址，
S2 要等这些排队事务走完；实测 ARREADY 连续为低 307~309 拍，远大于 `ADDR_STALL_MAX=4`，
说明限制地址通道的是队列深度，这一项作不了上界。改为按配置分两种口径，都只报口径不声称形式上界：

| 配置 | 口径 | 仿真实测 |
| --- | --- | --- |
| 遵守措施一（引擎每方向一笔在途） | `AGE_LIMIT + 一笔 256 拍读 + 搜索余量`，仿真阈值 414 | 读 301（197 笔）；写 311（65 笔），写队列 4 时 271（311 笔） |
| 引擎不守契约（激进发地址） | 按实测取阈值 700，并与保护关闭时对比 | 读：保护开 590、关 889，完成 55 / 30 笔；写：保护开、关都是 607（33 笔），写队列 4 时都是 590（50 笔） |

读方向上保护起作用（关掉后超阈值）；写方向上保护开关结果逐项相同，写方向的等待只由措施一约束，
guard 在写方向只验接线与触发，不计为写方向的等待保证。原因见下面「写方向订正」一段。

板上的 DDR3 控制器加密且没有公开地址反压上界，所以板上只报告 `S2_MAX_WAIT_AR/AW` 的实测最大值、
guard 命中数、是否超时与三方是否完成。数据阶段的一笔 256 拍引擎读约 305 周期、
一笔 160 拍扫描读约 201 周期，只作容量设计参考。

**饿死只在「下游地址通道恒 ready」时成立**。整机多路器里，地址反压（AR2R 或从机队列）给了仲裁
指针旋转并停在 S2 上的时间：`Act_Cnl_Hit` 命中会阻止继续旋转（`Axi_Mux.v` 第 2554 行），
指针停在 S2 上时它下一轮必然拿到授权。所以保护关闭 + 激进 S1 时 S2 也没饿死（实测完成 30 笔），
`inject_noguard` 因此改成**对照判据**：同一阈值下保护关闭必须不通过（实测 889 > 700），
而恒 ready 的饿死由 `grant_sequence` 逐字复现（仅 S1/S2 持续请求时 S1=19、S2=0）。

#### 仿真验证（板上复现不了这组对照，必须在仿真里做）

探针主机一次只发一笔，在板上当引擎替身时不会复现这组对照，所以对照只能在仿真里构造。
`Axi_Mux` 是明文，沿用 `sim/axi_probe` 的做法（带 `EFX_SRL8` 厂商模型），`sim/axi_mux_guard/`：

| 组件 | 做法 |
| --- | --- |
| S1 主机 | 可配置主机：读或写满负载（256 拍突发），激进（地址握手后下一拍就再拉高 valid）或遵守措施一（写方向等 `bvalid`）；W 通道的 `wvalid`/`wlast` 用组合逻辑 |
| S2 主机 | 模仿 CPU：4 拍读、单拍写交替，间隔随机；读、写最大地址等待分开统计，每拍更新，含未握手的那一笔 |
| S0 主机 | 按行节拍发 160 拍读，可关闭，量首拍等待与整笔时间 |
| 从机 | 复用 `sim/axi_probe/axi_ram_model.v`，用 `RD_QUEUE`、`WR_QUEUE`（默认都是 1）与 `ADDR_STALL_MAX`、`hold_ar/hold_aw` 构造条件；WLAST 与突发长度不符时计 `wlast_err` |
| 判据 | 固定授权序列、S2 完成笔数与最大地址等待、S1 的 valid 是否被撤销、从机 `wlast_err` 为 0、S0 是否拿到授权 |

| 用例 | 配置 | 期望 |
| --- | --- | --- |
| `grant_sequence` | 下游恒 ready，三路持续请求及仅 S1/S2 请求 | PASS，分别复现 S0/S1 交替且 S2 饿死、S1 独占的固定序列 |
| `dual_direction` | AR、AW 同时超限且分时完成 | PASS，两个 protect 都清除之前 S1 不恢复；同拍触发 HITS=2；未握手时两个 MAX 已经在涨（版本 1 的 RTL 在这一项读到 0，报 FAIL） |
| `normal` | 读，激进 S1，保护开启 | PASS，S2 读全部完成且最大地址等待 ≤ 700（实测 590） |
| `inflight1` | 读，S1 每方向一笔在途，保护关闭 | PASS，只靠措施一也满足更严的口径 ≤ 414（实测 301） |
| `inject_noguard` | 读，激进 S1，保护关闭 | FAIL，最大地址等待超过同一阈值（实测 889 > 700），保护在读方向起作用的对照 |
| `inject_mask_s0` | 注错让保护掩码的 S0 位跟着 S1 一起清零 | FAIL，S0 在屏蔽窗口内拿不到授权，证明判据盖住了「不碰扫描输出」 |
| `inject_midgrant` | S1 已获授权后保持下游不 ready，再触发屏蔽 | PASS 且无协议违例；S2 等待包含既有授权的反压，证明 guard 不伪造抢占 |
| `wr_aggr_guard` / `wr_aggr_noguard` | 写，激进 S1，保护开 / 关，`WR_QUEUE=1` | 都 PASS（≤ 700，实测 607），且 `run.sh` 比对两者的扫描、引擎与 CPU 统计必须逐项相同 |
| `wr_contract` | 写，措施一，保护关，`WR_QUEUE=1` | PASS（≤ 414，实测 311） |
| `wr_q4_aggr_guard` / `wr_q4_aggr_noguard` | 同上，`WR_QUEUE=4`（与读方向条件对等） | 都 PASS（实测 590），逐项相同 |
| `wr_q4_contract` | 写，措施一，`WR_QUEUE=4` | PASS（实测 271） |
| `inject_wlast` | 复原引擎替身打一拍的 WLAST | FAIL 且 `wlast_err` 非零，证明从机协议检查进了判据 |

共 14 个用例，加两项逐项比对与一项「inject_wlast 的 FAIL 来自 wlast_err」检查，`run.sh` 输出 `SIM OK: 17/17 checks as expected`。

### 2.3 用探针主机当引擎与扫描负载的替身（现在就能做）

引擎与扫描输出都还没有，但**它们在总线上的正常负载可以用探针主机复现**：
探针主机就是一台能持续发 256 拍突发的 128 位主机，E4 的 `SHARE` 阶段
已经用它复现过「长突发压短事务」。它遵守措施一，所以测到的是「正常引擎」下的数字，
饿死的情形由 2.2 节的仿真覆盖。本实验的替身方案：

| 角色 | 替身 | 怎么配 |
| --- | --- | --- |
| 引擎满负载 | `u_axi_probe` 接 S1，`LEN=255`、`COUNT` 拉满，**读、写各跑一轮**（`MODE` bit0 WRITE 分别取 0 与 1，bit1 INC 按需） | 读与写在多路器里分开仲裁，只跑一种会漏掉另一种的影响；参数与 E4 的 `SHARE` 相同，地址避开程序区 |
| 扫描输出 | 接 S0 的一个只读小主机，按行发 160 拍的读，行周期约 31.7 微秒（`core_clk` 下约 3175 个周期），场周期 525 行，最多一笔读在途 | 新写 `rtl/bus/scanout_stub.v`，记录 `arvalid` 到首个 `rvalid`、到 `rlast` 的完整时间，以及相邻 R 拍最大间隙；三项都记最大值与直方图 |
| CPU 负载 | `sw/apps/probe/ddrBurstProbe` 里的 `cpu_copy()`，逐字拷贝 256KB，接 S2 | 现成 |

在优先级模式下测五件事：CPU 拷贝耗时（与现状 S0/轮询对比）、扫描替身的首拍等待与整笔完成时间、
扫描 R 通道最大拍间隙、`S2_MAX_WAIT_AR`/`AW` 与 `GUARD_HITS`，以及三者并发时是否都完成。
这一节的产物是**数字**，不是功能：它把「S0 让给扫描、S1 让给引擎之后 CPU 会慢多少」先钉住，
引擎真接进来时只需要换掉 S1 的驱动源。

注意仲裁不抢占，而且本多路器的优先级模式有 1 节所述的完成通道排除行为；不能假定 S0 每次都先于
S1、S2。措施一成立时，扫描最多只在信息 FIFO 中排到一笔引擎事务之后；实际首拍、整笔和拍间隙
仍以直方图为准。轮询模式只作性能对照，不要求两种模式的最坏等待必须拉开固定差距。

### 2.4 扫描 FIFO 的最低水位（要等扫描输出存在）

这一节是本实验的正题，也是唯一无法用替身完全替代的部分：**异步 FIFO 的最低水位
取决于扫描输出自己的消耗节奏与突发长度**，替身只能给出上界。

做法是在扫描输出模块里加水位观测。FIFO 两侧在不同时钟域（写侧 `core_clk`，读侧像素时钟），
**不能用一个计数器两边加减**：水位要在读侧用本域的读指针与同步过来的写指针（格雷码）相减得到，
这样看到的是保守值（写指针同步有两三拍延迟，水位只会偏低不会偏高）。
只在 FIFO 完成预装之后的有效显示区更新 **一帧内出现的最小值**（不是平均值）；复位、预装和场消隐
期间不参与，否则空 FIFO 会把最小值固定为 0。场同步时把帧号、最小值与欠载统计锁存在一组保持寄存器，
通过 toggle/ack 握手同步回 `core_clk`，接收侧确认之前源侧保持多位快照不变，不能逐位直接同步二进制值。
判据是**一帧内的最小水位不低于一行 160 拍**（FIFO 若按像素存，折算成 640 像素）。
这条判据假设扫描输出至少提前一行预取；若设计改成「行到才取」，判据要随之改写，并在报告里说明。

同时记录两项：有效显示区内水位触及 0 的次数 `FIFO_ZERO_HITS`，以及没有有效像素可读的拍数
`FIFO_UNDERFLOW_BEATS`。欠载一旦发生，画面会出现一行错位，
肉眼看不出是 FIFO 还是别的问题，所以必须有计数器，不能只靠看屏幕。
连续采集 120 帧的每帧最小水位，由软件计算最低值与中位值，并登记最低值对应的帧号。

### 2.5 结论落地

- 端口分配、实际仲裁行为、两道防饿死措施与永久 APB 窗口先写进设计文档 3.3 节；
  RTL 实现完成后再把当前状态登记进 `../../Main/rtl/README.md`，不能提前把计划写成现状；
- FIFO 深度的定值与依据写进设计文档 3.3 节与 platform 或 display 系列的 TechReport；
- 若实测最低水位远高于一行，写明可以把 FIFO 改浅多少、省几块 RAM（与 E1 的 RAM 预算对账）。

本实验**不含**：扫描输出本身的实现（从 DDR 读像素、时序发生、双缓冲切换，
属 display 工作点）、引擎本体的接入（属 engine 工作点，但措施一的约束由本实验定下）、
`Axi_Mux` 写响应码的缺陷（已在 E4 里处理，见

「反例」这一条与「仲裁生效」成对，是这一节的自检：配置若没有送进多路器，
单看「最坏等待不大」也能通过（负载不够重时轮询也不会等太久）。
原先写的「改回轮询后最坏等待必须变差」不成立：仲裁不抢占，两种模式的最坏等待都约等于一笔长突发。
改用掩码注错，S0 被屏蔽后必然拿不到授权，能直接证明配置到达了多路器。

「保护注错」与仿真里的 `inject_noguard` 分工不同：仿真里的对照是**同一阈值判据在保护关闭时不再成立**
（实测最大地址等待从 590 涨到 889），而不是「一定会饿死」——整机多路器里饿死复现不出来（原因见 2.2 节），
上板这一条只证明保护模块接到了真实的多路器上。板上的替身遵守措施一，本来就不会饿死，
不能用「关掉保护看 CPU 会不会卡住」来做上板注错。

**写方向订正（2026-09-19 第二轮复核）**：`Axi_Mux` 的读、写走两个独立仲裁器，读方向的数字不能替代写方向，
所以补了写方向用例。第一轮补记曾写「激进写引擎把 CPU 的写停住（20000 与 60000 周期都只完成 7 笔，保护开、关逐项相同 610/7），
guard 挡不住，措施一是写方向唯一有效的约束」，并把两个激进写用例的期望定成 FAIL。**这条结论是测试台自己的错，已撤回**：

- 测试台的引擎替身 `master_aggr` 把 `wlast` 写成打一拍的寄存器，连续握手时末拍漏掉 WLAST、下一笔第 0 拍带上；
  从机每个写用例都报了 27~37 次 `MODEL: wlast mismatch`（包括判为 PASS 的 `wr_contract`），但没有判据检查它。
  W 错位后写通路死锁：多路器已把 AW 授权给 S2，从机 `awready` 恒 0，W 指针停在已经发完数据的 S1。
  「7 笔之后一笔不涨」是死锁的特征，饿死会让笔数慢慢涨。
- CPU 替身与 guard 的最大地址等待当时只在握手时更新，卡死的那一笔永远不进统计；报出来的 610 是已完成那 7 笔的最大值，
  那一刻 S2 的 AW 已连续等待 16051 拍。

修正测试台（`wvalid`/`wlast` 组合逻辑、写方向措施一按 `bvalid`、`wlast_err` 进判据、等待每拍更新）之后：

| 写方向用例 | 从机写队列 | S2 写完成 | S2 最大写地址等待 | 结果 |
| --- | ---: | ---: | ---: | --- |
| `wr_aggr_guard`（激进，保护开） | 1 | 33 | 607 | PASS |
| `wr_aggr_noguard`（激进，保护关） | 1 | 33 | 607 | PASS，逐项相同 |
| `wr_contract`（措施一，保护关） | 1 | 65 | 311 | PASS |
| `wr_q4_aggr_guard` / `_noguard` | 4 | 50 | 590 | PASS，逐项相同 |
| `wr_q4_contract` | 4 | 311 | 271 | PASS |

1. **写方向没有饿死。**
2. **写方向上 guard 不起作用，但原因与第一轮写的不同**：在 `WR_QUEUE=4`、激进写、保护开启的用例上统计
   `protect_aw` 为 1 的 16105 个周期，写地址仲裁器 68% 的时间是 S1 的授权已锁存、在等下游收地址，32% 是已授权给 S2 在等下游，
   处于搜索新通道（掩码唯一能起作用的时刻）只有 49 个周期。写数据 256 拍把地址通道压成「一个授权挂着等下游」，
   屏蔽 S1 的新授权无从生效。
3. **措施一把写方向的最大等待减半**（607 到 311、590 到 271），与读方向同一规律。

所以判据表的写法是：写方向以措施一为准，guard 在写方向只验接线与触发、不计入写方向的等待保证；
这条结论依赖从机模型，真控制器在写方向接受多少个地址是黑盒，板上的替身又都守契约，写方向 guard 的有效性在板上没有证据。
上板程序 `ddrBurstProbe` 的 TRI 与 INJECT 都是读、写各一轮，统计值在停扫描之后一次性读取（同一时刻快照）。
过程的四段记述见 platform 第 06 章 4.4、4.5 节。

  | 用例 | 保护 | S1 在途 | S2 读完成 | S2 最大地址等待 | ARREADY 连续为低最大 |

  | `inflight1` | 关 | ≤1 | **197** | **301** | 309 |
  | `normal` | 开 | 激进 | 55 | **590** | 309 |
  | `inject_noguard` | 关 | 激进 | 30 | **889** | 307 |

  1. **整机多路器里复现不出饿死。** 保护关闭加激进 S1 时 S2 仍完成 30 笔读。根因是地址反压
     （从机队列 + `Axi_Mux` 的 AR2R）给了仲裁指针旋转并停在 S2 上的时间：`Act_Cnl_Hit` 命中会
     阻止继续旋转（`Axi_Mux.v` 第 2554 行），只要下游不是「恒 ready」，指针就会停在 S2 上，
     它下一轮必然拿到授权。1 节记录的饿死条件是裸仲裁器（`M_A_READY` 恒 1）才成立的极限情形，
     `grant_sequence` 用例已经把它逐字复现（仅 S1/S2 持续请求时 S1=19、S2=0）。
     所以 `inject_noguard` 的期望要改成**对照判据**：同一负载下保护关闭的 S2 最大等待（889）
     与完成笔数（30）必须明显差于保护开启（590 / 55），而不是「必须饿死」。
  2. **措施一是主力，不是兜底。** 保护关闭时，把 S1 约束成每方向一笔在途，S2 完成 197 笔、
     最大等待 301；不约束时只有 30 笔、889。这条差值（约 3 倍等待、6.5 倍完成数）
     正好是「引擎在途事务不超过 1」这条契约的价值，比原来只有机理说明的写法有力。
  3. **`S2 地址等待 ≤ AGE_LIMIT + ADDR_STALL_MAX + 4` 不成立，要改口径。** 保护开启、
     S1 激进时实测 590，而上界算出来是 72。原因有两层：已授权的事务（含 `Act_Cnl_List` 里
     在途的一笔）本来就不受掩码影响；更主要的是 `Axi_Mux` 的 AR2R（深 16）与从机队列
     （`RD_QUEUE`）会先收下一批地址，S2 要等这些**已授权**的排队事务走完。
     实测还显示 ARREADY 连续为低 307~309 拍，远大于 `ADDR_STALL_MAX=4`——真正限制地址通道的
     是队列深度，所以上界公式里 `ADDR_STALL_MAX` 这一项没有意义。改法：
     该公式只对遵守措施的配置（实测 301，可用 `AGE_LIMIT + 一笔 256 拍读 + 搜索延迟` 表达）
     保留形式；引擎不守契约时写成「实测最大值并与保护关闭时对比」，不再声称形式上界。

**2026-09-19 前期研究复核**（未开发；只读源码、临时仿真、现有回归与设备枚举）：

1. **“按端口号严格优先级”的解读不成立，规格正文与总体设计暂不据此改动，待下一轮确认。**
   临时测试台直接例化 `Axi_Mux_Addr_Ctrl`，设三端口、优先级模式、下游地址通道恒 ready：
   三路持续请求 40 个周期，握手计数为 S0=10、S1=10、S2=0；只让 S1、S2 持续请求，
   计数为 S1=19、S2=0；让 S1 每次握手后空 6 个周期，计数为 S1=26、S2=52。
   原因是地址握手后的第一个空闲周期里，刚完成的通道仍留在 `Act_Cnl_List`，
   `Act_Cnl_Hit` 又显式排除该列表（`Axi_Mux.v` 第 2573~2607 行）。选择一个通道时虽然把
   `Channel_List` 复位到 S0，但刚完成的通道会被跳过一轮。因此它不是通常意义的严格优先级：
   三路持续请求时 S0、S1 交替，S2 仍会饿死；只有 S1、S2 请求时 S1 独占。
   S0=扫描、S1=引擎、S2=SoC 仍可作为候选分配，但 2.1、2.2、2.3 节及总体设计 3.3 节的
   仲裁机理、等待上界和仿真期望必须按上述实际序列重写，并增加固定授权序列用例。

2. **老化掩码不能给出正文所写的 `AGE_LIMIT + 3` 严格地址等待上界。**
   临时仿真先让 S1 获得地址授权、保持下游 ready=0，再清除掩码中的 S1 位；连续 20 个周期内
   `Act_Cnl_List` 始终为 S1，S2 的 ready 始终为 0；恢复下游 ready 后，S2 再过 3 个周期握手。
   这与源码一致：掩码只参与新通道搜索，已锁存在 `Act_Cnl_List` 的授权保持到地址握手完成。
   所以上界至少应写成“`AGE_LIMIT` + 已获授权地址的剩余反压时间 + 搜索延迟”；真 DDR3
   控制器的地址反压上界当前没有测量，不能先写成常数。`inject_midgrant` 应同时验证“不撤销
   valid、不破坏协议”和“等待计数包含既有授权的反压”，不能把后者判成 `AGE_LIMIT + 3`。

3. **保护状态还缺少读写同时触发时的合并规则。** `Cfg_Cnl_Mask` 同时送入读、写仲裁器，
   但 AR、AW 有两个等待计数器。实现时应分别锁存 `protect_ar`、`protect_aw`，S1 只有在两者都
   清除后才能恢复，即保护位按 `~(protect_ar | protect_aw)` 生成；否则一个方向先握手会提前
   恢复 S1，让另一个方向继续挨饿。仿真需补一项 AR、AW 同时超限且分时完成的用例。

4. **扫描替身和 FIFO 判据还缺四项边界。** `scanout_stub` 除 `arvalid` 到首个 `rvalid` 外，
   还要记录整笔完成时间与最大相邻 R 拍间隙；扫描读也要约束为最多一笔在途，否则“前面最多
   一笔扫描事务”的总等待估算不成立。真实 FIFO 的帧内最低水位只在完成预装后的有效显示区
   统计，否则复位和场消隐期的空 FIFO 会把最小值固定为 0；跨时钟返回帧快照要用保持寄存器
   加 toggle/ack 握手，不能把多位二进制值直接逐位同步。判据里的中位值由软件采集固定数量的
   连续帧后计算，并补上样本数；2.4 节“记录两次”疑为“记录两项/同时记录”，下一轮一并订正。

5. **仲裁配置不宜继续归属临时探针。** `apb_probe` 在 `rtl/README.md` 中被定义为占位模块，
   `axi_probe_master` 也会在引擎接入后撤走。为满足“不依赖探针”，建议让永久的
   `axi_mux_guard` 自己拥有仲裁方式、寄存器掩码、`GUARD_EN`、`AGE_LIMIT` 和统计寄存器，
   顶层给它划一个独立、稳定的 APB 子窗口；不要先塞进 `apb_probe` 再二次迁移。

   3.3 节正文则写扫描必须接 S0；E5 选择的是 S0 扫描、S1 引擎、S2 SoC。下一轮确认仲裁方案后
   同时修图、3.3 节分配表与 E5 正文，避免先把未确认方案写成定稿。
