# E7 软件执行器的板上像素吞吐

状态：未开工。前置是 2.1 节的规格补全，补规格不依赖别的条目，可以立刻开始。
本条产出的软件执行器是赛题基础要求 3（实时对比软硬件帧率）与 M1「软件画方块的帧率打到串口」的前提，
也是引擎像素流水线的金标准；它不阻塞引擎 RTL 开工，但规格定稿之前引擎的像素级不要写。
与 [`E8-CPU每弹幕开销与缓存大小.md`](E8-CPU每弹幕开销与缓存大小.md) 互不阻塞：E8 量的是生成命令，本条量的是执行命令。

## 1 要解决什么

赛题基础要求 3 要「Demo 在屏幕上实时对比软件渲染与硬件渲染的帧率」。
要做这个对比，必须有一个在 CPU 上逐像素执行同一份命令表的软件执行器。
它的用途有三处，缺了它三件事都做不了：

1. **对比基线。** 同一帧命令表、同一台板子，软件画一遍、硬件画一遍，
   时间差的倍数就是加速比的原始数字。
2. **金标准。** 设计文档 3.8 节要求「同一帧命令表软硬各跑一次，比较后缓冲 CRC」。
   CRC 对不上时，是硬件错还是软件错，要靠一份可信的软件实现来判。
3. **开发载体。** PC 版游戏与仿真测试台都用同一份软件执行器，
   游戏逻辑与素材流水线可以在没有板子的情况下先做完。

现在没有这东西。`sw/` 下三个程序（`bootSizeTest`、`ddrAliasTest`、`ddrBurstProbe`）
都是诊断程序，没有一行像素代码；`sdk/` 里的官方示例也没有任何显示或游戏例程
（设计文档 4.2 节已经检索过）。

**本实验要量的是它的像素吞吐**：每种混合方程各能画多少像素每秒，
折成一帧 16.67ms 能画多少像素、多少个指定尺寸的 Sprite。
这个数字是软件基线的定义值，也是判断「墙什么时候从硬件移到 CPU」的依据。

## 2 怎么切分

### 2.1 先把规格钉死（本实验的前置，也是硬件实现的前置）

软件执行器与硬件必须实现同一份逐像素规格，否则 CRC 对不上时无法判断谁错。
规格在设计文档 3.5 节已经写了一半，本实验要把它补成可以实现的程度，
补完的部分写进 3.5 节，**两边都照改**：

| 待钉死的项 | 设计文档现状 | 本实验要补 |
| --- | --- | --- |
| 混合方程 | `out = src × Fs + dst × Fd`，5 行表 | 每行的 `Fs`/`Fd` 取值表已全，确认无遗漏 |
| 舍入 | 除以 255 用 `q = (x + 128 + ((x + 128) >> 8)) >> 8` | 全量穷举 0~65025 验证，给出通过的结论 |
| 舍入与饱和的顺序 | 「结果饱和到 255」 | 写清是两项各自 ÷255 舍入后再相加饱和，还是先相加再统一 ÷255 舍入。两种写法在 ALPHA、CONST 下结果可能差 1；ADD 两项系数都是 1，不经过舍入，两种写法结果相同，只有饱和 |
| 色键 | 「源像素等于色键颜色时不写目的像素」 | 比较的是三通道还是含 alpha、是否在预乘前比较 |
| 裁剪 | 3.4 节命令表允许目的坐标部分出屏 | 写清边界取闭区间还是开区间、宽高为 0 时的行为 |
| alpha 为 0 | 未写 | ALPHA 方程下 alpha=0 的像素是否仍写目的像素（决定能否省一次写） |
| 字节序 | 帧缓冲 XRGB8888，纹理预乘 ARGB8888 | 写清每个字节在内存里的位置与端序 |

判据是**同一份输入在 C 参考实现与仿真里的逐像素结果一致**，
所以规格里每一条都要能用一段可穷举的代码表达。这也是 `sim/` 里金标准测试台的输入。

### 2.2 写 `sw/execSwTest`

新程序 `../../Main/sw/execSwTest/src/main.c`，骨架照 `sw/ddrBurstProbe`：
固定测试区、`clint_getTimeLow(BSP_CLINT)` 打点、逐行打印、末尾 `fail <n>` 与 `done`。

实现按设计文档 4.4 节的软件分层，只做 `exec_sw/` 这一层，不写游戏：

```
表面表：本实验只用 4 个表面（3.4 节的格式允许 16 个），每个 {base, stride_log2, width, height, space, format}，space 只实现 0（DDR）
命令解释：NOP / FILL / BLIT / SET_CLIP / END，32 字节定长记录，字段按 3.4 节的位域（BAND 属引擎条带模式，不做）
像素核心：5 个混合方程各一个函数 + 色键判定
```

要覆盖的用例，每个都要有可比对的输出（整块 CRC32 或逐像素校验和）：

| 用例 | 内容 | 为什么要它 |
| --- | --- | --- |
| FILL 全屏 | 一个 640×480 纯色填充 | 最简路径，量写带宽上限 |
| BLIT COPY 不透明 | 256×256 图块拷到指定位置 | 量读+写 |
| BLIT 色键 | 同尺寸，色键命中约 50% | 量色键分支的代价 |
| BLIT ALPHA 预乘 | 2000 个 12×12 弹幕 | 场景 S1 的主力用例（设计文档 4.5 节） |
| BLIT ALPHA 非预乘 | 同上，走赛题公式 `fg*a + bg*(1-a)` | 对照赛题原文，报告里要这组 |
| BLIT ADD | 200 个 16×16 粒子 | 量饱和加 |
| CONST | 全屏淡出 | 量常数混合 |
| 裁剪 | 目的坐标负值与部分出屏 | 量边界分支，并与硬件的裁剪判据对齐 |
| 舍入穷举 | `x = 0..65025` 的 ÷255 | 规格验证，不做像素搬运 |

### 2.3 三种编译配置各测一遍

像素核心的写法直接决定数字，只报一个数没有意义。三种配置：

| 配置 | 编译选项 | 想回答的问题 |
| --- | --- | --- |
| 基线 | `-O2` | 正常使用的数字 |
| 省空间 | `-Os` | 代码放不进 512KB 时的代价 |
| 按行处理 | `-O2`，内层循环按行而非按像素，逐行处理 4 像素一组 | 手工展开能省多少 |

三份 ELF 的 SHA256、bin 大小、编译命令都要记下来。**所有数字必须标注是哪一份**。

### 2.4 定义并测量吞吐口径

统一口径，否则数字之间不可比：

- **像素吞吐**：每秒处理的目的像素数。色键命中的像素算不算，两种口径都报，
  分别记 `pixel_total`（命令覆盖的像素总数）与 `pixel_written`（真正写入的像素数）。
- **每像素周期数**：`cycles / pixel_written`，这是与硬件对比时唯一可比的量
  （硬件是每周期 4 像素，设计文档 3.5 节）。
- **打点范围**：只包住执行循环，不含命令表生成与 CRC 校验；命令表生成的开销在 E8 里量。
- **数据规模**：每个用例至少跑 10 帧或 100 万像素，取较大者，避免打点本身成为主要开销。

### 2.5 折成帧预算

把数字折成 M1 要的那条判据与后续判断：

```
一帧的周期预算：16.67ms = 166.7 万周期（100MHz）
  软件一帧最多画的像素数 P = 166.7 万 ÷ 每像素周期数
  整屏等效帧率 = 1 亿 ÷ (每像素周期数 × 307200)，即 P ÷ 307200 × 60
  场景 S1 的帧率 = 1 亿 ÷ (按 S1 各类像素加权的每像素周期数 × 68 万)
```

设计文档 4.5 节的场景 S1 是现成的对照输入，本实验的结论要直接对着它写。
CPU 侧的估算在设计文档 3.1 节是「每弹幕约 100 条指令、5000 个弹幕约 5ms」，
本实验给出的是**像素侧**的数字，正是那个估算缺的另一半。

本实验**不含**：游戏逻辑、弹型、碰撞（属 sw 工作点）、
命令表按条带分桶（属引擎的条带模式）、
硬件引擎的实现与 CRC 对比判据的硬件侧（属引擎工作点）、
PC 版与 SDL2 的显示部分（本实验只要能在板上跑并打点，
PC 版是同一份源码的另一个编译目标，等游戏开发需要时再做）。

## 3 判据

| 项 | 判据 |
| --- | --- |
| 规格 | 第 2.1 节七项逐条写进设计文档 3.5 节；舍入的穷举用例在板上跑过并通过 |
| 金标准 | 每个用例给出 CRC32 与逐像素校验和两个值，重复运行一致 |
| 注错见红 | 每个方程一个注错宏，只改该方程的输出（例如 `-DINJECT_EQ_ALPHA` 让 ALPHA 结果最低位取反）。打开某一个宏时，只有用到该方程的用例 CRC 变化，其余用例不变。逐个方程各验一次 |
| 三配置 | 基线、省空间、按行处理各给出数字，并写明是哪一份 ELF |
| 吞吐表 | 每个方程一行，含 `pixel_total`、`pixel_written`、周期数、每像素周期数、每秒百万像素 |
| 折帧 | 给出软件一帧能画的像素数与等效帧率，并与场景 S1 的 68 万像素对比 |
| 口径 | 明确写出打点范围与数据规模；`-O2` 与 `-Os` 的包体大小一起报 |
| 复现 | 串口原始输出整段贴进 TechReport；三个 ELF 的 SHA256 与编译命令行记录在案 |
| 文档 | `../../Main/sw/README.md` 登记期望输出、bin 大小与工具链版本 |

「注错见红」这一条针对的是这类测量最常见的问题：CRC 只盖住了命令表的解析结果、
或者像素核心被编译器优化成了一个不做事的循环，量出来的「很快」是假的。
每个方程单独注错，「该变的变、不该变的不变」两边都符合，才说明 CRC 盖住的确实是像素结果，
并且各用例确实走到了各自的方程。
原先写的「对调 Fs 与 Fd」不能用：按 3.5 节的表，COPY 是 Fs=1、Fd=0，对调后结果变成目的像素，CRC 会变；
ADD 是 Fs=Fd=1，对调后结果不变，CRC 不会变，与原期望正好相反。
