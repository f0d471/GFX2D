# E4 已验收项的未覆盖判据

状态：未开工（本条尚未动手；E4 主体已于 2026-09-17 完成并验收，见
[`../TechReports/platform/03-DDR3上的第二个主机与突发预算.md`](../TechReports/platform/03-DDR3上的第二个主机与突发预算.md)）。
本文件只收 E4 留下、当前判据没有覆盖的边界，不重述已验收的结论。
它不阻塞引擎开工，但引擎的错误通路照抄 E4 的做法，先查清更省事。

## 1 要解决什么

platform 第 03 章的验收结论是硬的：突发上限 256 拍、读固定开销 27.4 周期、
写 7.3 周期、持续吞吐 0.85~0.92 拍/周期、CPU 与第二个主机交叉读一致。
这些结论都由 `sw/ddrBurstProbe` 的四个阶段与 `sim/axi_probe` 的五个用例支撑。

留下的是**错误响应的通路**。第 03 章 3.2 节研究 6 查出 `Axi_Mux` 的一个缺陷：

> 对照端口表逐个检查 AXI 信号时发现，读方向有 `I_M_R_RESP` 与各主机的 `O_Sn_R_RESP`，
> 写方向却**没有任何 `B_RESP` 端口**。写响应码告诉主机这笔写是否成功，缺了它，
> 控制器报告的写错误在多路器这一级就消失了，主机永远看到成功。

修法是在顶层把控制器的 `bresp` 直接并接给所有主机。查 `../../Main/rtl/top/gfx2d_top.v`
能看到已经这么做了：`ddr_bresp`（第 170 行声明）是 **DDR3 控制器**的写响应码
（第 339 行 `.s_axi_bresp (ddr_bresp)`），它不经过 `u_axi_mux`，
直接接到 `u_soc` 的 `.io_ddrA_b_payload_resp`（第 431 行）与 `u_axi_probe` 的 `.bresp`（第 630 行）。
读方向的响应码则经过 `Axi_Mux` 的 `I_M_R_RESP` 送回，两个方向的通路不同，要分开验证。

**但这条修法在板上没有被验证过。** 它只在仿真里由 `inject_maxlen` 用例覆盖过一次，
而从机模型是自己写的 `sim/axi_probe/axi_ram_model.v`——按仓库规矩，
测试台里的从机不能比真从机强，所以那次通过证明的是「连法正确」，
不能证明「真从机的写错误能送到主机」。

另外两处同类缺口：

- 探针主机 `rtl/bus/axi_probe_master.v` 的 `ERRS` 分两个字段：[15:0] 是非 OKAY 响应计数，
  [31:16] 是读比对失配拍数；`STATUS` 的 bit3 `RESP_ERR` 表示本轮出现过非 OKAY 响应，
  bit4 `LAST_ERR` 表示读突发的 `rlast` 位置不对，与响应码无关。
  真控制器返回一次非 OKAY 时，`ERRS[15:0]` 会不会动、`RESP_ERR` 会不会置位，没有实测过。
- 设计文档第 6 节第 2 条要求「突发超时、`RRESP`/`BRESP` 非 OKAY、命令越界，
  都要置粘滞错误位和序号，发中断」。引擎的错误通路要照这个做，
  而它依赖的第一环——从机能给出非 OKAY 响应，且这个响应确实到达主机——现在是空白。

## 2 怎么切分

### 第一步，找出这块板上的真从机会在什么条件下报错

这一步是研究，先读后测。DDR3 控制器加密，能做的是读资料包里的手册与网表，
再从外部试着逼它报错。可试的方向按代价从低到高：

| 试法 | 期望现象 | 代价 |
| --- | --- | --- |
| 突发跨 4KB 边界（AXI4 协议禁止） | 可能被截断、可能挂死、可能报错 | 低，只改探针的 `ADDR` 与 `LEN` |
| 访问 256MB 以外的地址 | 顶层截 28 位，实际会回绕，**大概率不报错** | 低，只改 `ADDR` |
| `AxSIZE` 大于 4（一拍超过 16 字节，与 128 位数据宽度不符） | 协议非法 | 中，探针的 `awsize`/`arsize` 在 RTL 里固定为 4（`axi_probe_master.v` 第 193~194 行），要改 RTL 加寄存器并重编比特流 |
| `AxBURST` 用 FIXED 或 WRAP | 控制器可能不支持 | 中，`arburst` 同样固定为 INCR，要改 RTL |
| 控制器校准未完成时访问 | 上电早期 DONE 未置位 | 中，要控制加载时机 |

「突发长度超过上限」无法在板上构造：`AxLEN` 只有 8 位，最多 256 拍，而 E4 已实测 256 拍可用。
仿真里的 `inject_maxlen` 是把从机模型的上限改成 16 拍，真控制器上没有对应的条件。

先做前两项，因为只改探针主机的寄存器、不重编比特流。**任何一项让板子挂死都是结果，
要按第一现场记录**：探针主机超时后不撤销已拉高的 valid，
CPU 也会访问不了 DDR，只能 ABORT 或重新加载比特流恢复（第 03 章 3.3 节）。

### 第二步，把错误响应测出来

在 `sw/` 下新增一个诊断程序（或扩展 `sw/ddrBurstProbe` 加一个 `ERR` 阶段），
用第一步找到的非法条件发一笔事务，然后读回三处并逐行打印：

| 位置 | 应当表现 |
| --- | --- |
| 探针主机 `ERRS[15:0]` | 非 OKAY 响应计数增加 |
| 探针主机 `STATUS` bit3 `RESP_ERR` | 置位 |
| 探针主机 `TX_DONE` | 与 `COUNT` 对照 |

探针的 `RESP_ERR` 是整轮的粘滞位，不记录是第几笔出错。要定位到笔，就把 `COUNT` 设为 1，
一笔一轮地发，每轮读一次 `STATUS` 与 `ERRS`。

同时做一次对照组，**只对写方向有效**：把 `u_axi_probe` 的 `.bresp` 改接常量 `2'b00`
（`u_soc` 那一路不动），重编译一次比特流，同一程序下写错误必须不再被看到。
读方向的响应码走 `Axi_Mux` 内部，对照组改为把 `u_axi_probe` 的 `.rresp` 接常量。
**对照组是这一条的关键**：没有它，「主机看到了错误」和「主机永远乐观」这两种情况在串口上都表现为一行计数。
如果第一步没有找到任何能让控制器报错的条件，对照组无从做起，按判据「不留白」处理。

### 第三步，把结论分派到该去的地方

- 如果写错误确实送到了主机：`../Bugs/README.md` 不必开条目，
  在第 03 章相应位置补一条订正，写明验证日期与对照组，
  并把这条判据加进 `../../Main/doc/开发环境.md` 0.6 节的回归表。
- 如果没送到：按 `../Bugs/README.md` 的单条结构开一条，第 7 节必须回答
  「现有判据为什么没有覆盖到它」——答案已经在第 1 节里，
  即 E4 的五个仿真用例里只有一个是错误响应用例，而它用的是自建从机模型。
- 两种情况都要把「引擎错误通路的判据怎么写」写清楚，
  因为引擎的错误位、序号、中断要照同一套判据验收。

本实验**不含**：引擎错误通路的实现（属引擎工作点）、
`apb_probe` 读未映射地址时 PSLVERROR 是否传到调试通路
（另一条，写在 platform 第 01 章 6 节末与 `../Bugs/README.md`，
用的是 APB 而不是 AXI，与本条没有共用判据）。

## 3 判据

| 项 | 判据 |
| --- | --- |
| 第一步 | 每种非法条件给出「报错 / 挂死 / 正常返回」三选一的结论，并保留串口原文与最后一行 |
| 可复现 | 每个结论至少跑两次；挂死要写明恢复方式（重新加载比特流） |
| 错误可见 | 非法事务后 `ERRS[15:0]` 增加、`STATUS` 的 `RESP_ERR` 置位；按 `COUNT = 1` 逐笔发送时能指出是第几笔 |
| 对照组 | 写方向把 `u_axi_probe` 的 `.bresp`、读方向把 `.rresp` 改接 `2'b00` 后，同一程序看不到该错误。对照组仍能看到错误，说明错误来自别处，结论作废 |
| 恢复 | 超时或挂死之后，ABORT 命令或重新加载比特流能让 CPU 重新访问 DDR，两条路各验一次 |
| 文档 | 第 03 章加订正或 `../Bugs/` 开条目，二者必居其一，并同步 `开发环境.md` 0.6 节的回归表 |
| 不留白 | 「真从机在什么条件下报错」如果最终查不出来，要明写查不出来，不得用仿真的 `inject_maxlen` 代替 |
