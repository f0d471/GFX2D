## 1 要解决什么

引擎是 DDR3 上的第二个 AXI 主机，它直接改 DDR。CPU 的数据缓存
（1 路直接映射，64 行 × 64 字节，行号取地址 [11:6]，标签取 [31:12]）
不会因为 CPU **经别名地址**改了同一块内存而失效，这一点已在这一块板上观测到
（`../../Main/sw/apps/probe/ddrAliasTest` 的 `CACHE_NOEVICT` 一项，原始输出见 platform 第 02 章）。
那次改写是 CPU 自己经 `0x1000_0000` 别名写的，**不是另一个 AXI 主机写的**。
platform 第 02 章第六节据此推知「引擎写 DDR3 时缓存副本同样不会失效」，但这是推论，
另一个主机写入的情形还没有在板上测过，这是本实验要补的第一件事。

设计文档 2.1 节据此写下一条约定，靠它绕开一致性问题：

> 共享区单向使用：命令表和素材 CPU 只写不读回，帧缓冲 CPU 只在软件渲染模式下写。

这条约定很贵。它意味着：命令表写完不能读回校验、素材上传完不能复核、
调试时不能用 CPU 读帧缓冲查画面对不对、软件执行器读自己的命令表也要小心。
赛题要的「软硬件同帧 CRC 对比」恰好要在 CPU 侧读回后缓冲的内容，
如果缓存会给旧值，这条判据就不成立，必须改成先失效再读。

**经别名写入后能看到旧值，platform 第 02 章已经确认**（`sw/apps/probe/ddrAliasTest` 的 `CACHE_NOEVICT`
一项读到 `11`，`../../Main/sw/README.md` 的期望值里写明了这一点）。
要回答的是四件驱动写法直接依赖的事：

0. 另一个 AXI 主机写入之后，CPU 是否同样读到旧值（把第 02 章的推论变成实测）；
1. 失效指令（`data_cache_invalidate_all()` / `data_cache_invalidate_address()`）
   能不能让 CPU 读到外部主机刚写的值，以及要多久、失效多大的范围才够；
2. 外部主机写入后，CPU 的第一次读、第二次读、命中与未命中路径是不是**都**给旧值——
   若某些路径给新值而另一些给旧值，这比统一给旧值更危险，因为回归会随机通过；
3. 结论对「另一个主机」的具体身份是否敏感。现在这个主机是探针主机
   `rtl/bus/axi_probe_master.v`，接在 `Axi_Mux` 的 S1，与将来的引擎走同一条通路。

顺带把 2.1 节那条单向约定从「已被观测到」升级成「已按判据验证过」，
并把失效指令的用法写进 `../../Main/sw/README.md`，让写驱动的人有章可循。

## 2 怎么切分

### 第一步，把「外部主机改写」这一步做出来

不需要引擎，现成的探针主机就能当外部写入者。它的寄存器在 APB Slave 0 的
`0x1000~0x1FFF`（CPU 地址 `0xF810_1000`），寄存器表与数据图样见
`../../Main/rtl/bus/axi_probe_master.v` 文件头。写方向把 `MODE`（偏移 `0x14`）的 bit0 WRITE 置 1，
`ADDR` 必须是 16 的倍数；一笔 128 位拍按地址派生图样 `{v^A5A5A5A5, v^5A5A5A5A, ~v, v}`，
其中 `v = SEED + a`。也就是说探针写到地址 `a` 的四个 32 位字可以精确预测：
CPU 在 `a` 读到 `v`，在 `a+4` 读到 `~v`。

新程序 `../../Main/sw/apps/test/cacheCoherencyTest/src/main.c`，按 `sw/apps/probe/ddrAliasTest` 的骨架写：
固定的测试区（建议 `0x0C80_0000` 附近，与 `ddrAliasTest` 一致，远离程序与栈）、
`hex8` 十六进制输出、每项一行 `ok`/`FAIL`、末尾 `fail <n>` 与 `done`。

缓存是 1 路直接映射，**程序自己的栈、全局变量、APB 访问之外的 DDR 读写，只要落在与测试地址相同的行号上，
就会把测试行挤出缓存**，A 组会随机读到新值。测试地址的行号（地址 [11:6]）要避开程序热数据所在的行，
并在每组测试的「CPU 读进去」与「CPU 再读」之间不调用会访问 DDR 的函数（包括 `bsp_printf`），
打印一律放到该组测完之后。

### 第二步，四种顺序各测一遍

每一组都在同一地址上做「CPU 先读进去 → 外部主机改写 → CPU 再读」，
区别只在中间与最后一步怎么走：

| 组 | 顺序 | 预期（若约定成立） |
| --- | --- | --- |
| A 基线 | CPU 读 → 探针写 → CPU 直接读 | 读到**旧值** |
| B 失效全部 | CPU 读 → 探针写 → `data_cache_invalidate_all()` → CPU 读 | 读到**新值** |
| C 失效单地址 | CPU 读 → 探针写 → `data_cache_invalidate_address(a)` → CPU 读 | 读到**新值** |
| D 未缓存 | 探针写 → CPU 驱逐后读（先读 `a ^ 0x2000_0000`） | 读到**新值** |

D 组是判据的自检，手法照抄 `sw/apps/probe/ddrBurstProbe/src/main.c` 的 `evict_rd32`：
读一个行号相同、标签不同的地址把目标行挤出缓存，再读目标。
D 组读不到新值说明地址译码或探针写入本身有问题，A 组的「旧值」就没有意义。

A 组还要多测几种命中路径，因为它们不一定同时给旧值：

- 读进来之后立刻改写（缓存行刚装填）；
- 读进来之后先访问几百个别的地址再改写。这些地址的行号必须都与测试行不同，否则测试行已被挤出，
  测到的是 D 组的情形（行仍在缓存，但访问历史不同）；
- 先写后读（CPU 写过这一行，缓存里是脏行）；
- 以字节、半字、字三种宽度读回。

`data_cache_invalidate_all()` 与 `data_cache_invalidate_address()` 都在
`../../Main/sdk/software/standalone/driver/vexriscv.h` 第 25~35 行，
`.word(0x500F)` 是 VexRiscv 的私有失效指令。要用哪个由本实验的结论决定：
单地址失效够用就不必每次全清，全清一次的开销也要量出来（用 `clint_getTimeLow(BSP_CLINT)` 打点，
CLINT 按 `SYSTEM_CLINT_HZ = 100000000` 计数，一格 10 ns，`sw/apps/probe/ddrBurstProbe` 里有现成用法）。

### 第三步，量失效的代价

失败的写法是「每个命令表提交前全清一次缓存」，一旦每帧清几次，
开销会进帧时间。这一步量三件事：`data_cache_invalidate_all()` 一次多少周期、
`data_cache_invalidate_address()` 一次多少周期、清完之后紧接着读同一片区域要多花多少。

### 第四步，把结论写成驱动规则

结论落地的位置：

- `../../Main/sw/README.md` 登记新程序与期望输出；
- `../../Main/doc/赛题二总体设计.md` 2.1 节末的「Cache 一致性」一段，
  按实测改写单向约定（保留、放宽、或换成「读回前必须失效」）；
- `../TechReports/platform/` 新增一章，记录过程与原始输出（本实验用探针主机，属平台系列；引擎侧复跑时再写进引擎系列）；
- 若结论是「某些路径给新值」，同时在 `../Bugs/` 开一条，写明现有判据为什么没有覆盖到它。

本实验**不含**：引擎侧同款判据的最终版本（引擎存在后重跑，判据不变）、
硬件侧的一致性机制（不加 snoop，本设计不打算做）、
指令缓存（引擎不改指令，不涉及）。

## 3 判据

本节是**开工前写的计划判据**。实际执行时判据的构造被改过三次，改动与理由见第 4 节开发日志
与 platform 第 05 章第四节；下表保留原样，便于对照「计划」与「实际」的差别，
对照结论在第 4 节最后一条「实测结果」里。

| 项 | 判据 |
| --- | --- |
| 前置 | 带 `u_axi_probe` 的比特流（2026-09-17 起）；串口先开再 `resume` |
| 输出 | 每项一行，格式 `<组> <子项> expect=<8 位 hex> got=<8 位 hex> ok\|FAIL`，末尾 `fail 0` 与 `done` |
| A 组 | 全部子项都读到旧值。任一子项读到新值，都要单独列出该路径，并在报告里说明它为什么安全或不安全 |
| B、C 组 | 都读到新值；若 C 组失效单地址不生效而 B 组生效，结论里必须写明「只能用全清」 |
| D 组 | 读到新值。这一组读不到新值时不继续，先查地址与探针 |
| 注错见红 | 编译时加 `-DINJECT_NO_INVALIDATE`（`make INJECT=1`），挡住四处失效调用的后果：A3 两行（A 组跑两遍）与 B、C 共四行打 `FAIL (inject)`，而 `fail` 计数仍为 0。A2 不在其中，它原本就没有失效调用。正常版这四行读新值，注错版读旧值，两者对照即见红 |
| 反复性 | 整个程序连跑三次，除计时数字外每次输出完全一致。A 组出现时好时坏要记为结论，不能取一次正常值了事 |
| 代价 | 两种失效指令各自的周期数：一次打点包住 1000 次调用，再减去同样 1000 次的空循环，写明计时用的是 `BSP_CLINT`。单条指令只有几个周期，与读计时器本身的开销同量级，不能逐次打点 |
| 结论 | 2.1 节的单向约定给出明确的「保留 / 放宽 / 改成读前失效」，并说明对同帧 CRC 判据的影响 |

「注错见红」这一条是本实验的关键，理由与 platform 系列一致：
失效指令是一句没有返回值的汇编，写错了（写错地址、写错寄存器、被编译器优化掉）
不会有任何编译期提示，只有在它必须生效的地方报 FAIL，才能证明它真的生效了。

**已实测的结果（2026-09-17）。** 这一节的判据都跑过了，原始输出、三次判据构造失败的过程、
每一次的关键数据与解读见
[`../TechReports/platform/05-CPU数据缓存与第二个主机写入的一致性.md`](../TechReports/platform/05-CPU数据缓存与第二个主机写入的一致性.md)。
几条与本节原计划不同的地方（2026-09-18 定稿口径）：

- 建立旧值的序列是：读 `a ^ 0x2000_0000` 挤出该行、别名写旧值、读一次装行并核对 `armed`。
  本构型没有写缓冲，不需要排空；写之后读一次也会装行（`cacheMechTest` T2），
  选别名写是为了让 DDR 与缓存里都是旧值。
- 判据从「A 组四项」变成 A1/A2/A3 三项加 P、B、C、D，原计划的 `A read_byte` 与 `A word1` 两项没有进入最终版本。
- 三种失效方式各占一个函数：紧跟在跳走的分支之后的失效指令即使没执行也会清缓存（T10）。
- 注错：`INJECT=1` 下 A3 两行加 B、C 共四行 `FAIL (inject)`、`fail 0`；
  `INJECT=2` 自检版失效调用保留，同四行 `NOT_RED (inject)`、`fail 4`。
- 代价实测：失效指令本身全清约 67 个周期、单地址约 4 个周期（T11）；
  判据程序里测到的「全清约 135 个周期」含栈那一行重新装入的约 69 个周期。
  1 tick = 10 ns = 1 个 `core_clk` 周期。
- 判据在 `-Og` 与 `-O0` 两种编译档下结果相同。实际默认编译档是 `-Og`（BSP `soc.mk` 的 `DEBUG_OG?=yes`），原先写的 `-O0` 是错的。

**2026-09-17 第 4 次上板：结论成立，跑反复性与注错。**

正常版连跑三次，除计时的最后几位外输出完全一致，三次都是 `fail 0`：

```
P cpu_to_prb expect=c0de00f1 got=c0de00f1 ok
A armed=1 ok
A immediate          expect=c0de00a1 got=c0de00a1 ok
A after_loads        expect=c0de00a1 got=c0de00a1 ok
A invalidated_after  expect=1fd7a5c0 got=1fd7a5c0 ok
B armed=1 ok
B invalidate_all  expect=1fd7a640 got=1fd7a640 ok
C armed=1 ok
C invalidate_addr expect=1fd7a680 got=1fd7a680 ok
D evicted expect=1fd7b5c0 got=1fd7b5c0 ok
D word1   expect=e0284a3f got=e0284a3f ok
fail 0
done
```

`armed=1` 每次都成立，说明旧值确实装进了缓存，A 组那两项的「旧值」才有意义。
A 组两项读到 `c0de00a1`（CPU 经别名放进去的旧值），失效之后读到探针的新值。

注错版（`OBJDIR=build_inject INJECT=1`）`fail 0`，A3 两行加 B、C 共四行打 `FAIL (inject)`：

```
A after_loads       expect=c0de00a1 got=c0de00a1 ok   (inject)
A invalidated_after expect=1fd7a5c0 got=c0de00a1 FAIL (inject)
B invalidate_all    expect=1fd7a640 got=c0de00b1 FAIL (inject)
C invalidate_addr   expect=1fd7a680 got=c0de00c1 FAIL (inject)
fail 0
```

A2 在注错模式下是 `ok (inject)`：它调用时就带 `APPLY_NONE`，本来就没有失效调用，
两种模式下行为相同，因此不参与见红。打 `FAIL (inject)` 的是 A3（A 组跑两遍所以两行）与 B、C，共四行。

代价三次的数据：

```
empty=000032e4  all=00024212/00024270/0002422b  addr=000046f0/000046b0  all_plus_read=00035278/00035268/00035278
```

换算：1 tick = 10 ns = 1 个 `core_clk` 周期。空循环单次 13.1 个周期，
全清单次约 135 个周期（1.35 µs），单地址单次约 5 个周期（50 ns，低于 13.1 的分辨率），
全清加一次读合计约 218 个周期。

> 订正（2026-09-17 复核）：本节原先写「全清 13.5 ns」，单位换错 10 倍，
> 实际是 135 个周期 = 1.35 µs。同时原先写「注错时 A2、A3、B、C 四处报 FAIL」，
> 与实测不符，实际是 A3 两行加 B、C 共四行。见 platform 第 05 章 5.2、5.4 节。

产物：正常版 4370 字节（`sha256:2d1dd6374739269c…`）、注错版 4450 字节（`sha256:048431a4a0294ca7…`）。
`.word(0x500f)` 的出现次数正常版 3 处、注错版 2 处。计数看不出是哪几处被去掉，
另用反汇编逐处核对：正常版里 `coherency_read` 内的两处（`.word(0x500f)` 与带地址的
`.word(0x4500f)`）在注错版里都不在了，剩下的两处在计时函数里，与 `A2` 无关。

**2026-09-17 判据第三版：修输出格式，第一次跑出「正常版全过」。**

前两次上板暴露的最后一个问题是输出格式把注错结果说反了：`expect=` 一栏取的是
「注错模式的期望值」，而那个值被填成旧值，于是 B、C 两行打成
`expect=c0de00b1 got=c0de00b1 ok`——读到旧值被判成通过。同一份程序里 A3 却报了 FAIL，自相矛盾。

改的时候走了两次弯路：

1. 把「注错时判定取反」放进公共的 `report_all`，结果**所有**行都取反，
   连 P、D 这两种不做失效的判据也一起报 FAIL（写出 `fail 5`）。这是错的：
   取反只对真正跳过失效的那几条成立。
2. 改成给每条记录加一个取反标志，仍然把「读到旧值」当作通过的理由，输出还是矛盾的。

最终修法：参考值只能有一个，`expect=` 一栏两种编译模式都打**正常模式**的期望值，
判定统一为 `got == expect`；注错模式下预期要红的四条用一个 `inject_fail` 标志标出，
它们的 FAIL 计入输出但不计入 `fail` 计数。改完之后正常版 `fail 0`、注错版 `fail 0` 且四处标 `FAIL (inject)`。

同时把判据里 `expect_inject` 这个字段整个删掉了，只留一个期望值，从结构上消除这种反向填法的可能。

**2026-09-17 判据第二版：改成「先读一次再写」，A 组变成稳定读新值。**

第一版的 A 组用「CPU 写入旧值 → 读一次（以为装进了缓存）→ 探针写 → CPU 读」。
看到 `dbded39e` 这种上电垃圾值之后，我以为问题是「行没进缓存」，于是把序列改成
「先读一次 → 写 → 探针写 → 读」：

```c
(void)*(volatile uint32_t *)a;   /* 先读一次，让测试行进缓存 */
wr(a, stale);
spin(SPIN);
*st_out = probe_write(a);
return *(volatile uint32_t *)a;
```

结果 A 组从「随机」变成**稳定地全部读到新值**：

```
A just_loaded expect=c0de0001 got=1fd7a5c0 FAIL
A after_loads expect=c0de0001 got=1fd7a5c0 FAIL
A dirty_line expect=c0de0004 got=1fd7b5c0 FAIL
A read_byte expect=00000003 got=000000c0 FAIL
A read_word expect=c0de0003 got=1fd7c5c0 FAIL
A word0 expect=c0de0005 got=1fd7d600 FAIL
A word1 expect=3f21fffa got=e02829ff FAIL
fail 16
```

`1fd7a5c0` 就是探针写进去的值（`SEED + a`），说明外部写入与地址译码都是对的，
CPU 读到的却是新值。这一版的价值是排除了「时序抖动」这个解释：
输出从随机变成确定，说明缓存里在任何一次探针写之前就**没有**旧副本，
问题在装行那一步，而不在竞争窗口。

还额外改掉了一处自己写的缺陷：A2 里制造「别的地址」的那段循环原先用
`LINE_ALIAS + (k+1)*PAGE`，每个页的偏移为 0 意味着行号都是 0，与测试行同号，
等于自己把测试行挤掉了。改成固定 `A_STRESS` 页内偏移让那批访问只落在行号 1。

**2026-09-17 最小实验 `cacheMinTest`：判定缓存留不留行。**

A 组两版都失败之后，需要一个不含外部主机的实验把问题限定在「缓存本身」，
于是新写 `Main/sw/apps/probe/cacheMinTest`，只问三个互不依赖的问题（同一地址连读两次；写之后读回；
CPU 经别名写入之后原地址读到什么）。地址贴近 `sw/apps/probe/ddrAliasTest` 用过的那一片，
那是已知能观测到缓存遮蔽的地方。

原始输出：

```
S1 no_ddr_between      expect=c0de00a1 got=c0de00a1 ok
S1 other_ddr_between   expect=c0de00a1 got=c0de00a1 ok
S1 evicted_same_line   expect=c0de00a1 got=c0de00a1 ok
S2 write_then_read     expect=c0de00a1 got=c0de00a1 ok
S2 alias_no_evict      expect=c0de00a1 got=c0de00a1 ok
S2 alias_then_evict    expect=c0de00b2 got=c0de00b2 ok
S3 CACHE_NOEVICT expect=00000011 got=22 FAIL
S3 CACHE_EVICT   expect=00000022 got=22 ok
```

读出两条：

1. **先写后读算不出「这一行在缓存里」。** `S3` 与 `sw/apps/probe/ddrAliasTest` 的 `CACHE_NOEVICT`
   是同一手法，`ddrAliasTest` 得到旧值 `11`，这里的 `S3` 得到新值 `22`。
   差别在 `ddrAliasTest` 在读 `Q` 之前先做过 `rd8_fresh(CACHE_Q)`（一次真读），
   而 `S3` 之前只有写。这一条直接判掉前两版判据的假设。
2. **先读后写能算出旧值。** `S2 write_then_read` 在写入后读一次得到 `V_A`，
   而 `S3` 的同样一步没有把值留住。能稳定复现的是「写 → 读」这一对操作，
   它不保证旧值在后续还留在缓存里。最终判据因此不依赖它，
   改用「别名写入 → 等排空 → 读一次并核对 `armed`」。

有一点没有结论：`S1 evicted_same_line`（用同一行号、别的标签的读去驱逐，结果仍读到 `V_A`，
说明驱逐没成功）与 `S2 alias_no_evict`（`spin` 之后读到旧值）这两项，
可能是写缓冲转发、也可能与标签比较有关，本实验没有把两者分开，
因此不把这两项当作证据，只留在程序里作为可复现的现象。

这一条是本实验的关键：原判据把「写入之后紧跟一次读」当成了「这一行在缓存里」，
这两件事在这块板上不等价。补上的那一步是**先读一次装行并核对**（`armed`）。

**2026-09-17 注错宏的加法试错。**

第一版 makefile 把注错宏写成「include 之后 `CFLAGS += -DINJECT_NO_INVALIDATE`」，
编译出来的注错版与正常版 **SHA256 完全相同**（都是 `c1018147a5265efd…`），
说明宏根本没进编译命令。用 `$(info CFLAGS_AT_END=[$(CFLAGS)])` 打印，宏确实在变量里。

根因在 `standalone.mk` 第 54 行：它用 `$(foreach …)$(eval …)` 在**解析期**就把编译 rule 固化了，
那时命令行上的 `CFLAGS` 还没有赋值。修法是在 include 之前经 `CFLAGS_ARGS` 带进去
（`standalone.mk` 第 10 行会把它追加进 `CFLAGS`）。
改完之后两版 SHA256 不同、注错版里 `500f` 的出现次数由 3 降到 2。

同一件事还踩过一次：第一次验证时用 `make clean` 清目录，但当时 makefile 里没有 `clean` 目标，
`make clean` 静默失败（错误被 `2>&1 | tail` 吞掉），`build_inject/` 里留着正常版的 `.o`，
make 只做了链接，于是两版又"相同"。后来改成显式 `rm -rf build build_inject` 才看清。

判据与产物稳定下来之后，两块新增的 `clean` 需求补进了 makefile 说明。
