E1 已验收（结论见 platform 第 04 章）：**保留 Standard 构型**，65 块片上 RAM 不再变，
所以 E8 的缓存对比要按这条结论重排——它的对照组不再是 Lite。

它解开的两个问题：驱动与软件执行器可以在读回共享区之前失效一次就安全使用，

整帧读回约 13 ms（估算），适合逐帧调试时开启。

## 搭车与顺序建议

1. **E8 的缓存对比在仓库外的复制工程里做，主线只按结论重新生成一次 IP。**
   E8 本身要生成好几个变体（4KB、8KB 与 2 路、16KB 与 4 路），
   每个变体都是一次独立生成，而且每次只改一个变量，不能并成一次；
   但它不动主线，也就不涉及主线的提交与登记项恢复。
   结论出来之后，[`soc资源裁剪.md`](soc资源裁剪.md) 在主线上**只生成一次**，把裁剪项与缓存大小一起定下。
   按 [`README.md`](README.md) 的搭车规则第 2 条，主线每次生成都要单独提交并逐条恢复 `sdk/README.md` 的登记项，
   分开做就是两次恢复、两次全套回归。
   E1 已确认不换构型，所以那一次生成不必再考虑构型变量。
2. **E5 的端口重分配与引擎接入分两次做。** 端口重分配会动 128 位数据通路的选择器，
   而 `core_clk` 的 hold 只有 0.026 ns，混在引擎接入那一次里，时序一旦变负就分不清是谁造成的。
3. **E3 与 E6 可以并行，且都不需要编译比特流**（E6 的双线版除外），
   适合放在等编译结果的时间里做。
4. **E4 的遗留判据与 E5 的第一半共用探针主机与同一个诊断程序骨架**，
   两个一起做可以只写一次 APB 配置与串口输出部分。
5. **E7 的规格补全先做**（2026-09-18 已完成并经用户确认）。它是引擎像素流水线与软件执行器共同的前置，
   拖到引擎开工之后再补，两边都要改。

## 每一份 spec 的共同结构

按 [`README.md`](README.md) 的单条结构，节序固定：

| 节 | 内容 |
| --- | --- |
| 状态 | 一行，写明未开工 / 进行中 / 待验收，以及它阻塞什么（验收之后文件删除，不存在「已验收」状态） |
| 1 要解决什么 | 现在是什么样，不做会导致什么 |
| 2 怎么切分 | 拆成哪几步，每一步的产物；不做什么也写在这里 |
| 3 判据 | 怎样算做完；可量化的写数字，上板项写清对照组与注错用例 |
| 4 开发日志 | 开工后逐次追加，最新的在最前 |
