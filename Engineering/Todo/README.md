各条目的当前状态以文件顶部为准；已验收工程的结果查对应TechReport，不在本索引重复登记。

## 收录与流转

- 排版、文案清理、文件移动、目录整理和索引修复等日常维护静默处理，不建立条目或开发日志。

- 开工登记改动、消费者、检查项、档位与板测需求；按 `../../Main/doc/验证流程.md` 选择范围。
  quick 通过、正式验收通过与缺项分别记录，不把旧工作点的全套复跑要求扩展成日常默认。

- 收录硬件及配套软件未开工的 spec、进行中的开发日志，以及已实现但未验收的事项。
- 应用内容迭代不强制立项。用户撤销维护范围时可撤条目，按范围撤销记录，不登记为验收通过。
- 已完成项先补齐 TechReports 的开发记录（前期研究与实验取样的过程、数据和解释写在那里），
  再同步受影响目录的 README，然后把状态改为「待验收」。**验收之后**才删除本目录的文件。
- 跨会话的停点与续接状态记在本条目的开发日志，来源与借鉴边界直接写 TechReports 正文；
  不在代码目录另立 STAGE、notes 等阶段文件；Engineering 不新增或保留 evidence 等独立输出层。
- 部分完成按工作点写清剩余验收；「代码已有」「仿真通过」「上板通过」分开记录。
- 已明确不做、延期或被其它任务覆盖的方案，不当成已实施。
- 正文保留开发过程时，以文件顶部最新状态为准。

## 单条结构

| 节 | 内容 |
| --- | --- |
| 状态 | 一行，写明未开工 / 进行中 / 待验收，以及它阻塞什么 |
| 1 要解决什么 | 现在是什么样，不做会导致什么 |
| 2 怎么切分 | 拆成哪几步，每一步的产物 |
| 3 判据 | 怎样算做完。可量化的写数字，上板项写清对照组 |
| 4 开发日志 | 开工后逐次追加，最新的在最前 |
