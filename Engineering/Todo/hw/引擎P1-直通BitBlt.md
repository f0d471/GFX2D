# 引擎 P1：直通 BitBlt（填充、拷贝、色键与 Alpha 混合）

状态：**未开工，可以开工**。spec 首稿写于 2026-09-26；开工前的取舍 D1~D14 与前期研究带出的 D15~D23
都已于同日定案（2.1 节），前期研究（2.2 节十个问题）与复核也已完成（第 4 节），代码未开始。
从 2.8 节的开工顺序第 1 步开始。
它阻塞的东西最多：赛题基础要求 1~3 与高阶要求 1、2 的上板演示，SW9 的后半（硬件后端与软硬件对比），
SW8 在板上求 `N_max`，E3 与 E5 的引擎侧复测，以及后续 P2 条目。
对应设计文档第 8 节里程碑 M2「直通引擎」。

## 1 要解决什么

**现在是什么样。** 引擎一行 RTL 都没有。`Axi_Mux` 留给引擎的 S1 口由探针主机
`rtl/bus/axi_probe_master.v` 占着（APB 第 1 页 `0xF810_1000`）；设计文档 3.4 节给引擎的寄存器页
`0xF810_0000~0xF810_0FFF` 目前落在 `rtl/bus/apb_probe.v` 上（顶层按 `paddr[15:12]` 分页，第 0 页是默认分支）；
SoC 给引擎预留的中断 B 在 `rtl/top/gfx2d_top.v` 里接的是 `1'b0`。
软件这一侧已经全部就位：命令 ABI v1 定稿（spec 第 02 章），逐像素规格定稿（spec 第 01 章），
软件执行器与 159 条一致性向量、十一个整帧用例都在 `sw/lib/gfx/`，SW6 的基础 Demo 已在板上用软件执行器跑通。

**不做会怎样。**

1. 赛题的六项要求里有五项落在引擎上：基础 1 的指令解析、块拷贝与纯色填充，基础 2 的突发与 FIFO，
   基础 3 里「硬件加速帧率」那一半，高阶 1 的 DSP Alpha 混合，高阶 2 的色键。
2. 软件执行器画一帧场景 S1 要约 805 ms（E7，platform 第 09 章），SW8 已写明软件后端下 `N_max` 不存在；
   高阶 3 的 `N_max` 只能来自硬件。
3. E5 的 FIFO 水位与 SoC 等待只在探针负载下量过，platform 第 08 章写明换成真实引擎要按同一判据复测。

**已经定下、本工作点必须遵守的约束**（出处都已验收，不在本条重新讨论）：

| 约束 | 值 | 出处 |
| --- | --- | --- |
| 总线端口 | `Axi_Mux` 的 S1，读写都用 | E5，platform 第 06 章 |
| 在途事务 | 每个方向最多一笔：读方向上一笔 `rlast` 握手之前不拉高下一笔 `arvalid`；写方向上一笔 `bvalid` 握手之前不拉高下一笔 `awvalid`。写方向没有 guard 兜底 | platform 第 06 章 3.2 节措施一；放宽要重做 E5 全套判据 |
| 地址 | CPU 地址就是控制器地址，有效范围 `0x0000_1000~0x0FFF_FFFF`；AXI ID 截成 4 位 | E2，platform 第 02 章 |
| 突发 | 上限 256 拍；读 `t_tx = 27.41`、`k = 1.086`，写 `t_tx = 7.25`、`k = 1.183`（周期，N 为拍数） | E4，platform 第 03 章 |
| 帧缓冲 | 两面 `0x0200_0000`、`0x0240_0000`，行跨 4096 字节；缓冲切换只归扫描输出（`BACK_BASE`/`SWAP_REQ`） | 设计文档 2.1 节；扫描输出 D2 |
| 像素规格 | 六个方程、除以 255 的舍入、饱和、通道范围、色键、裁剪与坐标、字节序 | spec 第 01 章，设计文档 3.5 节 |
| 命令语义 | 32 字节记录、表面表、十步检查的顺序、首错停止、错误三元组 | spec 第 02 章，设计文档 3.4 节 |
| 缓存一致性 | CPU 读回引擎写过的区域之前必须失效，失效晚于写入完成 | E3，platform 第 05 章 |
| 时钟 | 引擎挂 `core_clk`（100MHz），与 SoC、DDR3 控制器的 AXI 同域，没有跨时钟 | 设计文档 2.5 节 |
| 时序余量 | `core_clk` 的 hold 余量只有 0.026 ns（4KB 与 16KB 缓存两种构型相同） | platform 第 06、10 章 |
| 片上 RAM | 现用 71 块（4KB 缓存）或 89 块（16KB 缓存），总共 256 块 | platform 第 10 章 |

**每颗弹幕要多少周期，用 E4 的板上数先算一遍**（估算，引擎上板后用计数器替换）。
标准弹是 16×16、预乘 ALPHA（SW8 的 K2）；目的 x 不按 4 像素对齐时一行 5 拍，按最坏情况算：

| 量 | 算式 | 周期 |
| --- | --- | --: |
| 读源一行 | 27.41 + 1.086 × 5 | 32.8 |
| 读目的一行 | 同上 | 32.8 |
| 写目的一行 | 7.25 + 1.183 × 5，与下一行的读分属两个方向，可以重叠 | 13.2（不计入） |
| 每行 | 读源加读目的 | 65.6 |
| 每颗弹幕 | 16 行，加命令取数分摊与流水线填充 | 约 1100 |
| 每帧固定开销 | 游戏区 400 宽加 HUD 240 宽的整屏 FILL：480 × (125.6 + 78.2) | 约 9.8 万 |
| 扫描输出占用 | 480 笔 × 最坏整笔 236（E5 实测 `MAX_FULL_TXN`） | 约 11.3 万 |
| 可用 | 166.7 万减去上面两项 | 约 145 万 |
| 硬件侧上限 | 145 万 ÷ 1100 | **约 1300 颗** |

前期研究在校准到 E4 板上数的事务模型上用真实的两个 DMA 核与 `Axi_Mux` 复算（第 4 节第 10 问）：
每颗 1092~1124 周期，取决于源、目的 x 是否按 4 像素对齐；整屏 FILL 的 400 像素一行 126.0 周期；硬件侧上限约 1310 颗。

这个数没有计入 CPU 写命令时对 DDR 的争用。它说明两件事：瓶颈是每行两笔读事务的固定开销
（每行 65.6 周期里有 54.8 是固定开销），而不是带宽；P2 把纹理放到片上、去掉「读源」那一笔，
每行降到约 32.8 周期，硬件侧上限约翻一倍。这是 D1 把 P2 排在 P3 前面的依据。

## 2 怎么切分

### 2.1 开工前的取舍（D1~D23，2026-09-26 定案）

D1~D14 是 spec 首稿时定的；D15~D23 是前期研究带出的，同日按推荐项定案，并据此订正了 D2、D3、D5~D8、D10、D13 的原文。
订正前后的依据都在第 4 节。

**D1 路线：P1 → P2 → P3（有条件）。** 本条只做 P1：命令 ABI v1 的全部操作（NOP、FILL、BLIT、SET_CLIP、END），
源表面三种格式，目的只有 XRGB8888，`space` 只有 DDR。
P2 是「直通模式加片上纹理」：只把 SW7 的标准圆弹、小圆弹与火花（合计不到 16 KiB）放进片上，
米弹（约 100 KiB）与 Boss（约 432 KiB）仍从 DDR 读；它在 P1 上板之后另开条目。
P3 条带模式以「P1 在 10 月中旬之前上板」为条件，做的话与 ABI v2 的实例列表一起做
（每颗弹幕的提交从 32 字节降到约 8 字节；sw 第 06 章 3.6 节的批量提交接口 `gfx_blit_run()` 就是它的入口，
接口的输入保持「一串目的坐标与源帧」，换成 v2 时调用处不用改）。
P4 弹幕运动卸载不做：E8 的阶段性建议是 N=2000 时运动只占一帧的 5.6%。

**D2 引擎的分层。** 五层，从上到下：

| 层 | 内容 | 本条的文件（2.3 节） |
| --- | --- | --- |
| 控制层 | APB 寄存器、命令表取数、十步检查、首错定位、`SET_CLIP` 状态、中断、性能计数器、软复位请求 | `engine_regs.v`、`engine_cmd.v` |
| 几何层 | 目的矩形、游戏区、裁剪框、目的表面、源表面五者求交；矩形拆成行；每行拆成按 16 字节对齐、不跨 4KB 的读写描述符 | `engine_geom.v` |
| 搬运层 | 一个 AXI 主机：读写两个厂商无关的 DMA 核、读侧多个请求方的仲裁、在途门控、W 通道带内掩码、排空与超时 | `engine_mover.v` |
| 计算阵列与片上缓冲 | 源行缓冲、目的行缓冲（各放两行乒乓）、命令缓冲；像素旋转器；一条像素通路，每拍 4 像素 | `engine_pix.v` |
| 计算核心 | 单通道混合（乘、除以 255 舍入、饱和）与色键比较 | `engine_blend.v` |

五者里的源表面一项来自 spec 第 01 章 3.6 节第 5 步：「源越界只跳过该像素」等价于再交一个矩形
`[dst_x − src_x, dst_x − src_x + src_w − 1] × [dst_y − src_y, dst_y − src_y + src_h − 1]`，
在矩形级做掉，像素通路不逐像素判源越界；整帧用例 `blit-clip-partial` 的第三条就是这种情形。
FILL 没有源，只交前四个（前期研究订正，首稿写四者）。

像素通路的输入输出一律是流接口，不直接连 AXI；输出里「这个像素不写」用 X 字节的带内标记表示（D16），
不用流的 `tkeep`（首稿写「数据加有效字节掩码」，写核中间拍不看 `tkeep`，前期研究订正）。
P2、P3 只换搬运层与片上缓冲（DDR 行缓冲换成纹理缓存或条带缓冲）和几何层的迭代顺序，像素通路与计算核心不动。

**D3 搬运层直接用 verilog-axi 的 `axi_dma_rd.v` 与 `axi_dma_wr.v`，源码一字不改。**
来源：[alexforencich/verilog-axi](https://github.com/alexforencich/verilog-axi)，MIT 许可，
取仓库归档前最后一个提交 `516bd5dadc3365b7f9e225d2af8fe0b8d804fe53`（2025-02-27）。
仓库已归档，后继项目 taxi 是 CERN-OHL-S（强传染）许可，不用。
两个文件放 `rtl/vendor/verilog-axi/`，连同 LICENSE 原样入库，登记进 `rtl/README.md` 的 vendor 表。

已核对（2026-09-26，首稿与前期研究两轮）：

- 两个文件都是 Verilog-2001，不例化任何子模块；WSL 里 iverilog 12 用 `-g2005` 单独编译都通过
  （`axi_dma_wr.v` 有五条 `@*` 敏感整个数组的告警，不影响功能）。Efinity 2026.1 整机编译四步通过，
  两个核合计 1515 XLR、16 块 RAM，合计 59 条厂商代码常见的告警（第 4 节第 1 问）。
- 接口是描述符（地址、字节长度、标签）进、AXI-Stream 出（读）或进（写），状态从独立的状态口回来；
  写状态的 `error` 字段来自 `bresp`，读状态的 `error` 字段来自 `rresp`。
- 参数取：`AXI_DATA_WIDTH = 128`、`AXI_ADDR_WIDTH = 32`、`AXI_ID_WIDTH = 4`、`AXI_MAX_BURST_LEN = 192`、
  `AXIS_KEEP_ENABLE = 1`、`AXIS_LAST_ENABLE = 1`、`AXIS_ID/DEST/USER_ENABLE = 0`、`LEN_WIDTH = 12`、`TAG_WIDTH = 4`、
  `ENABLE_SG = 0`、**`ENABLE_UNALIGNED = 0`**（D15；首稿取 1，前期研究量到三处代价之后改成 0）。
  前期研究的仿真与编译用的就是这一组。
- 写核中间拍的 `wstrb` 恒为全 1、不看流的 `tkeep`（`axi_dma_wr.v` 第 556 行），只有最后一拍看 `tkeep`；
  按像素跳过写走 W 通道带内掩码（D16）。
- 两个核复位时不收尾：读核把 `rready` 清 0（第 612 行），写核清空输出 FIFO（第 933~937 行）；复位分域与排空见 D17。
  两个核都没有中止功能：`axi_dma_wr` 的 `abort` 只在端口表里，`axi_dma_rd` 没有这个端口。
- 两个核内部各有一个 32 深的输出 FIFO，各占 8 块 RAM；深度写在模块体内的 `parameter` 里，
  Efinity 当它是 localparam，不改源码缩不了（D23 的 RAM 账算进去了）。
- **一个描述符如果要拆成多笔突发（跨 4KB，或超过 `AXI_MAX_BURST_LEN`），读核在上一笔地址握手之后就发下一笔，
  不等数据回完**（`axi_dma_rd.v` 第 362~404 行的 `AXI_STATE_START`）；读核在地址发出后就可以接下一个描述符。
  写核同样：拆出的第二笔 `awvalid` 不等第一笔的写响应（`axi_dma_wr.v` 第 509 行 `!first_cycle_reg` 分支；
  第 4 节的整屏 FILL 注错用例在写方向量到 9120 个违例周期）。
  所以在途契约不能交给核自己保证，定为两条规矩：
  1. 几何层保证每个描述符按 16 字节对齐、不跨 4KB、不超过 `AXI_MAX_BURST_LEN` 拍，核内永不拆分，一个描述符恰好一笔突发；
  2. 搬运层在上一个描述符的状态回来之前不发下一个（读、写各自门控），状态在数据全部交接之后才出。
- 已知缺陷（上游 issue #12）：`AXI_MAX_BURST_LEN × 16 >= 4096` 时 4KB 判断的一个表达式恒真。
  行最长 161 拍，所以取 `AXI_MAX_BURST_LEN = 192`，不触发这个表达式；加上规矩 1，核内的 4KB 分支也不会走到。

**D4 其余自己写，但都有现成的蓝本。** 十步检查照 `sw/lib/gfx/check.c` 的 `gfx_cmd_check()` 逐步翻成组合逻辑加状态机，
检查顺序与错误码按 spec 第 02 章 §5；像素运算照 spec 第 01 章与 `tools/check/check_round255.c`。
软件执行器 `sw/lib/gfx/exec_sw.c` 是逐像素的行为模型，也是测试台的期望值来源。

**D5 寄存器页与寄存器表。** 引擎占 APB 第 0 页（`0xF810_0000~0xF810_0FFF`），`apb_probe` 撤下（D21）。
设计文档 3.4 节的寄存器表删三组：`FRONT`/`SWAP_REQ`（缓冲切换只归扫描输出，扫描输出 D2 留下的「别名还是改表」在这里定为改表，
引擎页不设别名）、`OSD_TEXT`（归显示端，属后续 display 条目）、`PALETTE`（INDEX8 不做）。
保留 `ID`、`CAPS`、`CTRL`、`STATUS`、`IRQ_EN`/`IRQ_STAT`、`ERROR_INDEX`/`ERROR_TAG`、
`LIST_BASE`/`LIST_COUNT`/`DOORBELL`、`SURF[0..15]`、`PERF_*`，偏移不变。
`SURF` 窗口与 `sw/lib/gfx/gfx_abi.h` 的 `gfx_surf_raw` 三个字逐位同构，驱动直接按原始三字写。

**D6 S1 从探针换成引擎。** 引擎接入的同一次编译里，`axi_probe_master` 从顶层撤下，源文件与 `sim/axi_probe/` 留着。
E5 引擎侧复测的负载是引擎的整屏 FILL 与整屏 BLIT。用到 S1 探针的四个板上程序、撤之前要在现行比特流上做完的事
与撤之后的改法见 D22（首稿只列了 `ddrBurstProbe`、`displayFifoProbe` 两个）。

**D7 行级调度与读写避让。** 每一行按「读源 → 读目的 → 写目的」走，写目的与下一行的读并行（两个方向各一笔，不违反契约）。
按 spec 第 01 章第 6 条允许的读写避让，只做结果逐像素不变的三种：

| 情况 | 省掉什么 | 依据 |
| --- | --- | --- |
| FILL 且方程为 COPY | 读源、读目的 | 常量源；COPY 不看目的 |
| BLIT 且方程为 COPY（含色键） | 读目的 | COPY 不看目的；色键命中的像素打 W 通道带内标记不写（D16），目的原值不动 |
| FILL 的其余方程 | 读源 | 常量源 |

其余情况（ALPHA、ALPHA_STRAIGHT、ADD、CONST、MUL）都要读目的。SW7 的背景、HUD 底图、机体与文字都落在前两行。
第二行首稿写「用写掩码跳过」，照原样用写核的 `tkeep` 做不到（D3 已核对的写核 `wstrb` 一条），前期研究改成带内标记。

**D8 命令表批量取数。** 一次读若干条记录进命令缓冲，取数与像素读共用同一个读核、同一条在途门控，读侧按「命令取数优先」仲裁。
每批 16 条，出错时退回逐条取，见 D18。

**D9 像素通路与乘法器。** 一条通路，每拍 4 像素。六个方程都写成 `x = 基数 × 255 + m1 × m2`
（例如 `src×a + dst×(255−a) = dst×255 + (src−dst)×a`），整数恒等，与 spec 第 01 章的 V 顺序逐位相同，
所以每通道只要一个有符号乘法器，一条通路 12 个。乘法先让综合推断 DSP，时序不够再按厂商原语例化。

**D10 错误通路。** 十步检查的九个错误码照 spec 第 02 章；取命令时 `rresp` 非 OKAY 报 `FETCH`。
像素数据读写的总线错误与超时是硬件独有的，spec 第 02 章没有编码；码值与语义见 D19，完成时补进第 02 章的错误表（软件执行器不产生这几种）。
所有错误置粘滞位、锁存首错的三元组、发中断 B。E4 的遗留判据不做：错误通路在仿真里用从机注错验收，上板只验检查类错误。

**D11 中断与交换。** 命令表完成与错误走中断 B（17）；缓冲切换只归扫描输出。驱动在完成之后调用现有的 `board_present()`。

**D12 在途不放宽。** 每个方向一笔。放宽到两笔能不能省下读的固定开销，取决于加密的 DDR 控制器会不会提前接受地址，
这件事没有数；要放宽得先量、再重做 E5 的判据，本条不做。

**D13 验证与流程。** 仿真沿用仓内做法：WSL 里 iverilog，Verilog 测试台，每个子目录一个 `run.sh`，不引入 cocotb。
从机复用 `sim/axi_probe/axi_ram_model.v`，它已有随机反压、响应延迟、`SLVERR` 与永不响应两种注错，
缺四样要补（前两样首稿列出，后两样前期研究补上）：
存储只有 4096 拍，整帧用例的设备内存是 `0x0021_0000` 字节（纹理基址 `0x0020_0000`），要扩到 4 MiB；
不支持写掩码 `wstrb`；按地址区间回 `SLVERR`（159 条向量的 FETCH 一组靠它截断可读条数）；
定时模式（前期研究的校准值 `RD_LAT=23 RD_BUB=12 WR_BUB=6 B_LAT=1`，性能判据用）。
新增参数的默认值保持现有行为，`sim/axi_probe/` 与 `sim/axi_mux_guard/` 的判据不变。
流程：前期研究与复核已于 2026-09-26 完成；判据与注错见红一条不少。

**D14 SoC 基线。** E8 条件性推荐的 16KB/4 路数据缓存若在引擎上板前满足 [platform 第 10 章](../../TechReports/platform/10-CPU每弹幕开销与缓存对照的复现.md) 第六节维护的采用条件，就先单独换进主线，
引擎在换过的 SoC 上收敛时序；条件没满足就在 4KB 上做，缓存以后单独换。两次都按搭车规则分开编译、分开提交。

#### 前期研究带出的取舍 D15~D23（2026-09-26 提出并定案）

每项先列事实，再写定案与没有采用的做法；依据与原始数据在第 4 节「2026-09-26 前期研究」。

**D15 对齐方式：`ENABLE_UNALIGNED = 0`，像素通路自带旋转器。** 首稿取 1，前期研究量到三处代价：
一行跨 4KB 拆成两个描述符时，第二段的流又从 0 号通道开始，两段在像素位置上接不上，像素通路仍要按像素重排；
起始地址的低 4 位原样发上总线（随机用例 800 笔突发里 578 笔非 16 字节对齐），而 E4 的探针只发过对齐地址，
控制器对这种地址的行为没有数据；两个核的字节移位器让搬运层从 1515 XLR 涨到 3198 XLR，周期数不变。

定案：描述符一律按 16 字节对齐的覆盖区间发，总线地址恒对齐；行首、行尾拍里不属于本行的像素按 D16 不写；
源与目的 x 对 4 的余数不同时，像素通路用一个两拍窗口、4 个位置的像素旋转器把源拍对齐到目的拍；
4KB 边界本身是 16 字节的整数倍，拆开的两段按拍直接拼接。
没有采用：维持 1 并另加 4KB 拆分时的像素重排与一条控制器接收非对齐地址的上板验证。

**D16 按像素跳过写：W 通道带内标记。** 需要按像素不写的有三处：色键命中、行首行尾不属于本行的像素、
排空时补的哑拍（D17）。写核中间拍不看 `tkeep`（D3 已核对）。

定案：像素通路输出像素的 X 字节（spec 第 01 章规定写回时恒为 0）最高位置 1 表示「不写」；
写核与 `Axi_Mux` 之间加一层组合逻辑，按每个像素 X 字节的最高位把该像素的 4 位 `wstrb` 清零，再把 X 字节清零后上总线。
核的源码不改；前期研究的仿真覆盖了中间拍、首末拍与整行全跳过。
没有采用：改 `axi_dma_wr.v` 第 556 行让中间拍也与 `tkeep` 相与（违反 D3「源码一字不改」，`tkeep` 在核里还参与帧尾判断，
第 358、571、838 行要重验）；色键 BLIT 也读目的、在像素通路里换回原值（D7 第二行的避让失效，机体类每行约多 35 周期）。

**D17 复位分域与排空。** 两个核复位时不收尾（D3 已核对）。引擎在事务中途被复位时，读方向迟到的 R 拍没人接，
写方向的突发断在半截，`Axi_Mux` 按信息 FIFO 的顺序一直等这一笔，扫描输出与 SoC 跟着停住。
`soc_system_reset` 在每次 `reset halt` 时都会拉起（display 第 01 章第四节）；扫描输出不受影响，
是因为它的 `r_ready` 恒为 1（`display_fetch.v` 第 207 行）。

定案：搬运层（两个核、门控、排空、W 通道带内掩码）的复位接 `ddr_rstn` 取反，与 `Axi_Mux` 同源，只在上电与 PLL 失锁时复位；
控制层挂 `soc_system_reset` 与软复位。控制层复位或软复位时向搬运层发「排空」：读方向收完在途那一笔并丢弃数据，
写方向用带内标记的哑拍把欠的拍补完、再等写响应；两个方向的状态都回来之后，控制层才清状态、接受新提交。
`STATUS` 里给一位「排空中」。
像素通路与行缓冲挂在控制层复位下，所以两个核的流接口前各有一个归搬运层的二选一：
平时接像素通路；排空期间读流恒 ready、数据丢弃，写流由搬运层自己按「描述符拍数减已送拍数」补上全打「不写」标记的哑拍。
搬运层要为此记住在途写描述符的拍数与已送拍数（复核时补）。
没有采用：全部挂 `soc_system_reset`，约定引擎忙时不做 `reset halt`，违反时只能重新加载比特流。

**D18 命令取数：每批 16 条，出错退回逐条取。** 每批 4 条以上时批量大小对每颗弹幕的周期数几乎没有影响
（不取命令 1104.1，每批 4/8/16/32/64 条为 1113.6/1110.0/1108.3/1107.6/1107.5 周期，每条单取 1136.1），
决定它的是存储与出错定位：128 位宽的存储在 Ti60 上深 512 以内一律 7 块，16 条放寄存器要 4096 个触发器；
读核对一笔读只报一个错误码，看不出是哪一拍，而 spec 第 02 章要求 `ERROR_INDEX` 精确到那一条，
159 条向量的 FETCH 一组就是在表中间截断可读条数；批里还可能含 END 之后的记录，规范条款 §5 要求它们不读取，读到错误也不能报。

定案：命令缓冲是专用的一块 128 位 RAM（7 块），两批乒乓，执行当前批时预取下一批；批长截到 `LIST_COUNT` 剩余条数；
整批报错时丢掉这一批，从这一批的第一条起改为逐条取（每条一笔 2 拍），第一条出错的就是 FETCH 的位置，
END 先到则正常结束，逐条取到这一批的末尾再回到整批取。
当前批里执行到 END 时，已经预取的下一批不论成败都丢掉，出错也不报（复核时补）；
批里的记录只在整批数据与状态都回来之后才开始执行，所以整批出错时这一批没有任何一条已经执行。
没有采用：每条单取（没有批与回退路径，每颗弹幕多 27.8 周期，约 2.5%）。

**D19 错误码、超时与排空的语义。** 两个核没有中止功能；读核照常把出错那笔的数据推出来，写核的错误随写响应回来。
按门控，每个方向的状态都在下一个描述符发出之前回来，所以写方向出错时，下一条命令的第一笔写还没有发出。

定案：

- 码值：10 `BUS_READ`（像素数据读回的 `rresp` 非 OKAY），11 `BUS_WRITE`（写响应非 OKAY），12 `TIMEOUT`；
  命令取数出错仍是 9 `FETCH`。错误归属用描述符随带的命令索引，因为写方向的状态可能晚于下一条命令的读。
- 语义：检查类错误维持「失败命令没有像素副作用」；总线类错误时失败命令可能已写了部分行，不回滚，
  读错的那一行不写，之后的命令没有像素副作用；已经发出的下一条命令的读由排空收掉。完成时补进 spec 第 02 章。
- 超时只报告、不放弃：某方向有描述符在途且连续 `T` 个周期没有任何握手时，置 `TIMEOUT` 粘滞位、发中断 B，之后照常等状态；
  欠总线的拍由 D17 的排空补齐。从机真的不再响应时整条总线已经停住，CPU 也访问不了 DDR，只能重新加载比特流，
  与 `axi_probe_master` 的超时相同。`T` 做成寄存器，复位值按一笔 192 拍的读在扫描输出满负载下的最坏耗时留足余量，开工时定数。

**D20 `PERF_*`：不做硬件快照。** 计数器累计，`CTRL` 里一位清零；引擎空闲时计数器不动，驱动在命令表完成之后读，
按帧做差在软件里做（SW8 的统计本来就在软件里）。
没有采用：从扫描输出引一根场起始脉冲（`display_fetch` 里已有同域的 `fs_event`），场起始时把计数器锁进一组影子寄存器。

**D21 `apb_probe` 撤下，默认分支常量应答。** 它现在应答第 0 页与其余未映射页，按完整 16 位地址译码，
引擎占第 0 页之后它的三个寄存器再也访问不到；它还挂在 `doc/开发环境.md` 回归表的「APB 探针」一行
（ID、VERSION、SCRATCH 图案、`0xF810_8008` 读回 0）。未映射页必须有模块回 `PREADY`，否则 CPU 访问会停住。

定案：`apb_probe` 从顶层撤下，源文件与 `sim/apb_probe/` 留着（同 D6 对探针主机的处理）；顶层默认分支改成常量应答
（`PREADY = 1`、`PSLVERR = 1`、`PRDATA = 0`）；回归表那一行改成读引擎的 `ID`、写读一个无副作用的读写寄存器
（`LIST_BASE`），`0xF810_8008` 照旧读回 0。
没有采用：保留并加基址参数挪到空页（要改 `apb_probe.v` 与它的测试台，回归表只改地址）。

**D22 撤探针主机之前与之后要做的事。** 用到 S1 探针的板上程序有四个：

| 程序 | 用探针做什么 | 撤下之后 |
| --- | --- | --- |
| `sw/apps/probe/ddrBurstProbe` | E4 突发扫描，E5 并发与注错 | 4KB/16KB 回归已于 2026-09-27 完成，两档均 `fail 0`/`done`（platform 第 10 章 5.9）；后续相关硬件改动的验证须在撤探针前安排 |
| `sw/apps/probe/displayFifoProbe` | E5 2.4 节的满负载读、满负载写 | 引擎没有纯读命令，「满负载读」一组造不出来（platform 第 06 章第六节已记） |
| `sw/apps/probe/cacheMechTest` | E3 机理实验 T1~T11 的外部写入者 | 结论已归档 platform 第 05 章 |
| `sw/apps/test/cacheCoherencyTest` | E3 回归：外部写入者与第二个读者 | 回归程序要留下，随引擎改写 |

定案：照 D6 在引擎接入的同一次编译里撤探针。撤之前在现行比特流上做完三件事：E8 的两份 DDR 探针
（`ddrAliasTest`、`ddrBurstProbe`）在 4KB/16KB 上复跑（2026-09-27 已完成，四次均通过，见 platform 第 10 章 5.9），`cacheCoherencyTest` 与 `displayFifoProbe` 各留一份基线日志。
撤之后 `cacheCoherencyTest` 改写：外部写入者换成引擎 FILL COPY，第二个读者换成引擎 BLIT 读 CPU 写过的表面、
CPU 失效后读回；另外三个在 `sw/README.md` 标成「需要撤探针之前的比特流」。
没有采用：顶层加编译宏让 S1 在引擎与探针之间二选一，两种比特流并存（测量程序不用改，但要两套编译与回归）。

**D23 行缓冲：源、目的各一块，不设输出行缓冲。** 128 位宽的存储深 256 与深 512 都是 7 块（6 块 512×20 加 1 块 1024×8），
一行 161 拍的缓冲与两行乒乓的缓冲一样贵；2.2 节第 3 问原先估的「各 3 块」不成立。
写核只在第一笔突发的流数据到了之后才拉起 `awvalid`（`axi_dma_wr.v` 第 509 行），之后流一断 W 通道就挂在总线上，
所以要保证的是「写一开始就能每拍给一拍」。

定案：源、目的各一块 128 位 RAM，每块放两行乒乓；源、目的两行都在片上之后，像素流水线每拍出 1 拍直接喂写核，
写核自带的 32 深 FIFO 吸收总线反压。读描述符只在目标缓冲那一半空出来之后发，读流的消费者恒 ready，
S1 的 `rready` 不会因为引擎自己拉低（`Axi_Mux` 按读地址顺序回数据，S1 一停，扫描输出与 SoC 的读数据跟着停）。
片上 RAM 合计：行缓冲 14 块、两个核 16 块、D18 的命令缓冲 7 块，共 37 块；加上现行 71 块（4KB 缓存）是 108 块，
加上 89 块（16KB 缓存）是 126 块，总共 256 块。
没有采用：首稿的三个行缓冲（21 块），写描述符等输出行整行算完再发。

### 2.2 前期研究要回答的十个问题

1. Efinity 2026.1 能否综合 `axi_dma_rd.v`/`axi_dma_wr.v`：资源、有没有推断出 RAM、`core_clk` 下的时序；两者的 `rst` 是高有效同步复位，与顶层复位的接法。
2. 描述符门控在仿真里的实测：随机反压下读、写各自的在途笔数最大值是否恒为 1；去掉门控的注错版必须见红。
3. 行缓冲的深度与片上 RAM：源行、目的行、输出行各最多 161 拍 × 128 位，估算各 3 块、合计约 9~10 块；
   输出行要整行缓冲完再发写描述符，写核拿不到数据时会把 W 通道挂在总线上，占住 S1。
4. 读侧最后一拍的 `tkeep` 与行内像素的对应关系；宽度不是 4 的倍数时，像素通路怎么丢弃多余像素。
5. 命令批量的条数与命令缓冲的存放（寄存器还是片上 RAM）；`PERF_*` 的快照时机
   （设计文档原写「场同步时快照」，场同步归扫描输出，引擎这边要么接一根场起始信号，要么改成按命令表快照）。
6. 数据通路总线错误与超时的错误码；超时之后怎么排空：两个核都没有中止功能，
   参考 `axi_probe_master` 的 `ABORT` 实测（platform 第 03 章 3.3 节）与龙芯 MTX 的「写侧等响应超时不排空」结论，定出不破坏协议的恢复方式。
7. `apb_probe` 的去留：挪到空页，还是撤下（它的 PSLVERR 判据还挂在 `Bugs/README.md`）。
8. 用到 S1 探针的板上程序清单，以及各自改成引擎负载的写法。
9. 测试台的期望值怎么进 Verilog：159 条向量与十一个整帧用例导出成 `$readmemh` 能读的格式，写一个小转换脚本。
10. P1 每颗 16×16 ALPHA 弹幕的周期数，用 E4 的事务模型在仿真里预估，与第 1 节的约 1100 对照。

十个问题已于 2026-09-26 全部回答，做法与原始输出在第 4 节「2026-09-26 前期研究」；
第 3 问的「各 3 块」与第 2 问「在途笔数最大值」的问法都被研究订正了（D23、2.4 节第 4 条）。

   `tools/check/` 新写一个链接 `sw/lib/gfx` 的主机小程序，把每个用例的表面表、命令表与初始内存导出成同样的记录；
   测试台跑完把帧缓冲导出，按 sw 第 03 章 3.6 节的口径算 CRC32，与 `sw/lib/test/golden.txt` 相同。
4. **协议**：契约按原文判——上一笔没结束（读看 `rlast` 握手、写看 `bvalid` 握手）时下一笔的 `arvalid`/`awvalid` 拉高一个周期即违例，
   违例恒为 0；不按握手次数数在途笔数（从机一次只收一个地址时那个数恒为 1，是空转判据，第 4 节第 2 问）。
   另外：每笔地址 16 字节对齐、不跨 4KB、每个描述符恰好一笔突发；`WLAST` 与 `AWLEN` 对得上；
   读数据阶段 S1 的 `rready` 恒为 1；随机反压下不死锁。
5. **几何定向用例**：159 条向量与十一个整帧用例都没有一行跨 4KB，源、目的 x 对 4 的余数组合也不成体系，所以另加：
   表面基址不按 4KB 对齐、行跨 4KB（拆成两个描述符）；源、目的 x 对 4 的余数 4×4 种；宽度对 4 取余 4 种；
   源矩形越出源表面（五者求交的第五项）。结果逐像素与软件执行器相同。
6. **错误**：每个检查类错误码一例；FETCH 落在一批中间（退回逐条取后定位到那一条）与 END 之后的记录不可读（不报错）各一例；
   像素读回 `SLVERR`（`BUS_READ`）与写响应 `SLVERR`（`BUS_WRITE`）各一例，失败命令之后的命令没有像素副作用；
   从机迟到超过门限一例：报 `TIMEOUT` 并发中断，迟到的响应到达后引擎排空回到空闲、能再次提交，迟到的响应不被新命令认领。
7. **复位**：读突发中途、写突发中途各做一次软复位与一次控制层复位（模拟 `reset halt`）：排空完成，总线上没有断掉的突发
   （R 拍全部收完、`WLAST` 对账、写响应全部收到），之后能再次提交。
8. **注错**：去掉在途门控、改错一个方程、跳过色键、W 通道带内掩码旁路（`wstrb` 直通）、排空旁路（复位时直接清核），各自必须见红。
9. **性能**：定时从机下 16×16 ALPHA 每颗的周期数，与第 4 节第 10 问的 1092~1124 对账。

两份都是 map、interface、pnr、pgm 四步 PASS，没有 error。

  事务中途复位两个核会把 `Axi_Mux` 留在等这一笔的状态。

#### 第 2 问：门控与在途契约

测试台每次跑 400 个操作：从低 512 KiB 随机取源地址（4 字节对齐）、1~640 个像素（每 7 个操作里有一个只有 1~6 个像素），
截到不跨 4KB；目的在高 512 KiB，同样截断；每个像素以约 3/8 的概率打「不写」标记，每 5 个操作里有一个全不打、一个全打。
读、写两个方向并发：写第 k 个操作时，读已经在取第 k+1 个。从机每个 ready/valid 以 3/8 的概率拉低；
`rndready` 两档让读流的消费者只有 1/4 的周期 ready。判据：读回的像素逐个对影子内存，结束后目的区 131072 个字逐字对影子内存；
每个描述符恰好一笔突发、不跨 4KB、`WLAST` 位置对；契约按原文判，上一笔没结束时下一笔的 valid 拉高一个周期记一次违例。

读法：

- 五个正常配置全过，门控下两个方向的违例都是 0。
- 去掉门控的两个注错版，读方向 2.8 万多个违例周期、写方向 8 千多个，判据见红。
- **但 `max_inflight` 在注错版里仍然是 1。** 从机一次只收一个地址，第二个 `arvalid` 拉起来了也握不上手，

- `inj_tkeep_u1` 把「不写」从带内标记改成在写流的 `tkeep` 上挖洞，结束比对报 `22825 dst words differ, first at 0x00081188 got 00c7e87f want c7205dca`：

- `rndready` 两档总周期从 3.3 万涨到 7.2 万、数据仍全对：消费者慢时读核在输出 FIFO 半满后拉低 `rready`。
  到了真总线上，`Axi_Mux` 按读地址的顺序回数据，S1 的 `rready` 一低，排在后面的扫描输出与 SoC 的读数据也跟着停，

- `unal_addr`：`ENABLE_UNALIGNED = 1` 时 800 笔突发里 578 笔（另一个种子 602 笔）的起始地址不按 16 字节对齐，直接发上总线；
  `= 0` 时是 0。

#### 第 3 问：行缓冲与片上 RAM

综合探针里深 256 与深 512 的两个 128 位行缓冲各占 7 块（6 块 512×20 加 1 块 1024×8，14 块合计，见第 1 问 30 块的拆分：
两个核 16 块、两个行缓冲 14 块）。原先「各 3 块」的估算按 10 Kbit 一块折算，没有考虑位宽：Ti60 的 RAM 块在这里最宽只取到 20 位，
128 位就要 7 块并排，深 512 以内不再增加。

写核只在第一笔突发的流数据 `tvalid` 到了之后才拉起 `awvalid`（`axi_dma_wr.v` 第 509 行），之后流一断，W 通道就挂在总线上。
所以要保证的是「写一开始就能每拍给一拍」，不一定要整行输出缓冲：源、目的两行都已在片上时，像素流水线是定长流水，
每拍出一拍，写核自带的 32 深 FIFO 吸收总线反压。输出行缓冲可以省掉，见 D23。

#### 第 4 问：`tkeep` 与宽度不是 4 的倍数

- `ENABLE_UNALIGNED = 1`：读流第一个像素在 0 号通道，最后一拍 `tkeep` 恰好是低 `len mod 16` 个字节（测试台逐个操作核对过）；
  写核只在最后一拍看 `tkeep`。宽度不是 4 的倍数时，最后一拍多余的通道由 `tkeep` 截掉。
- `ENABLE_UNALIGNED = 0`：每拍 `tkeep` 全 1，拍内像素位置与地址一致；几何层知道 `x0 mod 4` 与宽度，
  像素通路按拍号算出哪几个通道属于本行，其余通道打「不写」标记。测试台里这一步按下标换算，相当于像素通路的旋转器，两个种子都过。
- 拆行：一行跨 4KB 时几何层要拆成两个描述符。`= 1` 时第二段的流又从 0 号通道开始，
  第一段最后一拍只有 `(len1 / 4) mod 4` 个像素，两段要按像素重新拼；`= 0` 时 4KB 边界是 16 字节的整数倍，两段按拍直接接上。

#### 第 5 问：命令批量与 `PERF_*` 快照

批量大小的数据在第 10 问的矩阵里（`FETCH_B` 一列），结论与存储、出错定位的分析写进 D18；快照时机写进 D20。
这里补一条事实：命令记录 32 字节正好 2 拍，一批 16 条是一笔 32 拍的读；向量里 FETCH 一组靠 `reads`（可读条数）截断，
测试台的从机要对 `LIST_BASE + reads × 32` 以后的地址回 `SLVERR`，这正是 D18 担心的「整批报错看不出是哪一条」。

#### 第 6 问：错误码、超时与排空

- 两个核都没有中止：`axi_dma_wr` 的 `abort` 只出现在端口表（第 139 行），`axi_dma_rd` 没有这个端口。
  `enable` 只挡新描述符，不影响在途的一笔。
- 错误上报：读核把一笔里见到的 SLVERR/DECERR 记下，在最后一拍输出时随状态给出（码 4/5，第 518~533 行），出错那笔的数据照常推出来；
  写核的错误随写响应回来（码 6/7，第 755~784 行）。读状态在最后一个输出拍给出，所以门控按状态放行，
  等价于「`rlast` 握手之后才发下一笔」，只晚一两个周期。
- 参考：`axi_probe_master` 超时后不撤 valid，只能 `ABORT`（撤 valid）或重新加载比特流救场（platform 第 03 章 3.3 节）；
  龙芯仓 MTX 的做法是读方向吃到 `rlast`、写方向用字节使能全 0 的哑拍补完，写响应超时不放弃，
  否则迟到的写响应会被下一条命令认领。本仓的门控保证下一个写描述符在状态回来之前不发，只要从不放弃，迟到的响应就只会配给原来那一笔。
- 由此得到 D19 的码值、语义与超时处理，以及 D17 的排空；2.4 节第 5 条要改写。

#### 第 7 问：`apb_probe`

顶层按 `paddr[15:12]` 分页，第 1、E、F 页以外全部落到 `apb_probe`（顶层第 536~580 行）；它按完整 16 位地址译码，
只认 `0x0000`/`0x0004`/`0x0008`，其余读回 0 并置 PSLVERROR。`doc/开发环境.md` 回归表的「APB 探针」一行用它，
`Bugs/README.md` 记着「PSLVERROR 有没有传到调试通路没查过」。取舍写进 D21。

- 16×16 ALPHA 每颗 1092~1124 周期，取决于源、目的是否对齐；第 1 节手算的「约 1100」（两边都 5 拍）落在这个区间里，
  实测 5+5 拍比手算多 2%。不取命令那一档每行 69.0 周期，两笔读（4 拍与 5 拍）按 E4 的拟合是 31.75 + 32.84 = 64.6，
  余下约 4.4 个周期，是两个核「描述符到地址」与「最后一拍到状态」的延迟加门控的一拍，每笔读约 2.2 个周期。
- `ENABLE_UNALIGNED` 取 0 或 1 周期数完全相同，D15 的选择不影响性能。
- `CMD_GAP` 0 与 2 结果相同，`PIX_LAT` 4 与 12 结果相同：命令之间几个周期的几何层开销被读的门控等待（每笔约 28 周期）盖住，
  像素流水线的延迟被「写与下一行的读并行」盖住。
- 命令批量：每条单取 1136.1，每批 2 条 1121.1，4 条以上都在 1107~1114。
- 整屏 FILL 一行 126.0 周期，第 1 节的 125.6 是它的手算值。
- 硬件侧上限按第 1 节的算法：145 万 ÷ 1108 ≈ 1310 颗，与原估算的约 1300 一致。

**注错：一行跨 4KB。** 同一个测试台把整屏 FILL 的起点挪到 x = 700，每行 1600 字节跨过 4KB 边界，写核把它拆成两笔：

```text
UNAL=0 MODE=3 SRC_OFF=0 DST_OFF=0 FETCH_B=0 PIX_LAT=4 CMD_GAP=2: cmds=480 rows=480 reads=0 cycles=63360 per_cmd=132.0 per_row=132.0 viol=0/9120
```

写方向 9120 个违例周期：拆出的第二笔 `awvalid` 在第一笔写响应回来之前就拉起了。这条补进了 D3 的第 3 点，
也说明 D3 规矩 1（几何层保证不跨 4KB）对写核同样必要。
