# 引擎 P1 · B5：控制层（寄存器、命令取数与十步检查）

状态：**未开工**。命令取数要 B2（I7）；端到端的错误判据要 B1~B4 的数据通路。
本批写出引擎对外的顶层 `engine_top.v`，B6 把它接进 SoC。路线、层间接口与批次顺序见 [引擎P1总览.md](引擎P1总览.md)。

## 1 要解决什么

**这一层做什么。** 引擎与 CPU 之间的全部约定：

1. **寄存器**：APB 第 0 页的寄存器表（D5），表面表 `SURF[0..15]`，`DOORBELL` 受理，软复位与「排空中」，
   粘滞错误、错误三元组与中断 B（D10、D11），`PERF_*` 累计计数与清零（D20），超时门限 `T`（D19）。
2. **命令取数**：每批 16 条、两批乒乓、整批出错退回逐条取（D18），经 B2 的读核（I7）。
3. **十步检查**：照 `sw/lib/gfx/check.c` 的 `gfx_cmd_check()` 逐步翻成硬件（D4），首错定位，`SET_CLIP` 状态，
   `LIST_COUNT` 与 END 的结束规则；通过的 FILL、BLIT 按 I1 下发给几何层。
4. **引擎顶层** `engine_top.v`：APB 从口、S1 的 AXI 主机口、中断 B、两路复位（D17）。

**现在是什么样。** 没有 RTL。行为的权威是 spec 第 02 章（规范条款 §1~§5）与 `sw/lib/gfx/check.c`；
159 条一致性向量由 `tools/check/check_cmd_semantics.py --emit` 导出；寄存器表在设计文档 3.4 节，
已按 D5、D19、D20 于 2026-09-26 同步。

**不做会怎样。** 赛题基础要求 1「引擎解析指令」就是这一层；驱动（B6）与 SW9 都按它的寄存器表写。

## 2 怎么切分

### 2.1 已定的取舍

**D4 其余自己写，但都有现成的蓝本。** 十步检查照 `sw/lib/gfx/check.c` 的 `gfx_cmd_check()` 逐步翻成组合逻辑加状态机，
检查顺序与错误码按 spec 第 02 章 §5；像素运算照 spec 第 01 章与 `tools/check/check_round255.c`。
软件执行器 `sw/lib/gfx/exec_sw.c` 是逐像素的行为模型，也是测试台的期望值来源。

**D5 寄存器页与寄存器表。** 引擎占 APB 第 0 页（`0xF810_0000~0xF810_0FFF`），`apb_probe` 撤下（D21）。
设计文档 3.4 节的寄存器表删三组：`FRONT`/`SWAP_REQ`（缓冲切换只归扫描输出，扫描输出 D2 留下的「别名还是改表」在这里定为改表，
引擎页不设别名）、`OSD_TEXT`（归显示端，属后续 display 条目）、`PALETTE`（INDEX8 不做）。
保留 `ID`、`CAPS`、`CTRL`、`STATUS`、`IRQ_EN`/`IRQ_STAT`、`ERROR_INDEX`/`ERROR_TAG`、
`LIST_BASE`/`LIST_COUNT`/`DOORBELL`、`SURF[0..15]`、`PERF_*`，偏移不变。
`SURF` 窗口与 `sw/lib/gfx/gfx_abi.h` 的 `gfx_surf_raw` 三个字逐位同构，驱动直接按原始三字写。

**D8 命令表批量取数。** 一次读若干条记录进命令缓冲，取数与像素读共用同一个读核、同一条在途门控，读侧按「命令取数优先」仲裁。
每批 16 条，出错时退回逐条取，见 D18。

**D10 错误通路。** 十步检查的九个错误码照 spec 第 02 章；取命令时 `rresp` 非 OKAY 报 `FETCH`。
像素数据读写的总线错误与超时是硬件独有的，spec 第 02 章没有编码；码值与语义见 D19（[engine 第 02 章](../../TechReports/engine/02-AXI事务层.md) 3.9 节），完成时补进第 02 章的错误表（软件执行器不产生这几种）。
所有错误置粘滞位、锁存首错的三元组、发中断 B。E4 的遗留判据不做：错误通路在仿真里用从机注错验收，上板只验检查类错误。

**D11 中断与交换。** 命令表完成与错误走中断 B（17）；缓冲切换只归扫描输出。驱动在完成之后调用现有的 `board_present()`。

**D18 命令取数：每批 16 条，出错退回逐条取。** 每批 4 条以上时批量大小对每颗弹幕的周期数几乎没有影响
（不取命令 1104.1，每批 4/8/16/32/64 条为 1113.6/1110.0/1108.3/1107.6/1107.5 周期，每条单取 1136.1，engine 第 02 章 3.8 节），
决定它的是存储与出错定位：128 位宽的存储在 Ti60 上深 512 以内一律 7 块，16 条放寄存器要 4096 个触发器；
读核对一笔读只报一个错误码，看不出是哪一拍，而 spec 第 02 章要求 `ERROR_INDEX` 精确到那一条，
159 条向量的 FETCH 一组就是在表中间截断可读条数；批里还可能含 END 之后的记录，规范条款 §5 要求它们不读取，读到错误也不能报。

定案：命令缓冲是专用的一块 128 位 RAM（7 块），两批乒乓，执行当前批时预取下一批；批长截到 `LIST_COUNT` 剩余条数；
整批报错时丢掉这一批，从这一批的第一条起改为逐条取（每条一笔 2 拍），第一条出错的就是 FETCH 的位置，
END 先到则正常结束，逐条取到这一批的末尾再回到整批取。
当前批里执行到 END 时，已经预取的下一批不论成败都丢掉，出错也不报（复核时补）；
批里的记录只在整批数据与状态都回来之后才开始执行，所以整批出错时这一批没有任何一条已经执行。
没有采用：每条单取（没有批与回退路径，每颗弹幕多 27.8 周期，约 2.5%）。

**D19 的码值一侧**：10 `BUS_READ`、11 `BUS_WRITE`、12 `TIMEOUT` 由 B2 带命令索引报上来，本层落到粘滞位、三元组与中断（原文见 engine 第 02 章 3.9 节）。

**D20 `PERF_*`：不做硬件快照。** 计数器累计，`CTRL` 里一位清零；引擎空闲时计数器不动，驱动在命令表完成之后读，
按帧做差在软件里做（SW8 的统计本来就在软件里）。
没有采用：从扫描输出引一根场起始脉冲（`display_fetch` 里已有同域的 `fs_event`），场起始时把计数器锁进一组影子寄存器。

**计数器按「能对账」设计**（设计文档 3.4 节）：`CMD`、`PIXEL`、`KEY_SKIP`、`RD_BURST`、`WR_BURST`、`RD_BEAT`、`WR_BEAT`、
`WAIT_DDR`、`BUSY`；`RD_BEAT` 必须等于各读突发长度之和。`FRAME_DROP` 不在引擎里做，掉帧由 SW8 的场数减切换数算。

### 2.2 开工前要补的研究

第 4 节的第 5 问只定了批量与快照，十步检查的硬件结构没有研究过。结果写进 TechReports `engine/` 第 05 章。

1. **十步检查的结构。** 一拍组合逻辑（十个条件并行算、按顺序取首个）还是多拍状态机：比较面积与 100MHz 下的余量。
   最长的几项是表面末像素的溢出判断（`base + (h−1) << stride + (w−1) × 4 + 3` 要 33 位）与 BLIT 的重叠判断（32 位有符号区间）；
   另一个候选是在写 `SURF` 时就把每个表面的结构合法性算好存成一位，检查时只查表，要核对它与 spec 第 02 章「软复位清 valid、valid 最后置位」的时序是否相容。
2. **命令处理器的参考。** 至少读两份：CV1000 blitter 在 MAME 里的命令循环（总览 2.7 节）；ORGFX 的命令接口；
   iDMA 的寄存器前端。
3. **寄存器表的单一真源。** 寄存器偏移与位域要同时进 RTL、C 驱动（B6）与设计文档，三处手抄容易漂移；
   评估用一份表生成 Verilog 常量与 C 头文件（手写小脚本，或 PeakRDL 一类工具，要看它的输出 iverilog 与 Efinity 能不能吃）。
4. **取数状态机。** D18 的整批、预取、回退逐条、END 丢预取批四种路径画成状态图；与 B3 一起定命令完成的判定与零面积命令的通知（总览 2.4 节末段）。
5. **实验。** 单独综合 2.2 节第 1 项的两三种结构，登记 XLR 与余量。
6. **跨命令的写后读（B4 验收查出，2026-10-01）。** 几何层发完一条命令的最后一个写描述符就空闲，
   下一条命令的读描述符照常发出；下一条读到上一条最后一行的区域时会读到旧值。B1~B4 不挡，
   `sim/engine/pix` 的 `path_hazard_nowait`（几何层一空闲就提交）必须见红、`path_hazard_wait`（等末行写状态）必须对
   （[engine 第 04 章](../../TechReports/engine/04-计算阵列与片上缓存.md)第四节）。三种处理：
   ① 控制层等上一条命令的末行写状态（I2 的 `wr_last_row` 回来的那个写状态）再发下一条，16 颗 16×16 ALPHA 实测 17668 对 17304 周期，多 2.1%；
   ② 几何层每条命令开头等写方向空闲，同价，改在 B3；③ 只在新命令的源或目的矩形与上一条的目的矩形相交时才等，省下大部分 2.1%，多一组 32 位矩形比较。
   推荐 ①：最省事，`row_free` 在命令开始时恒为空闲。命令下发的结构与它一起定。

研究之后要定的（编号 D24 起）：检查的结构、寄存器表的真源、完成判定、跨命令写后读的处理。

### 2.4 仿真

新目录 `sim/engine/ctrl/`。被测是 `engine_top.v`（B1~B5 全部），从机是补齐之后的 `axi_ram_model.v`，测试台经 APB 提交。

1. **十步检查**：159 条向量逐条喂进引擎，错误三元组与 spec 第 02 章的期望逐条相同。
   `tools/check/` 新写一个转换脚本，把 `check_cmd_semantics.py --emit` 的标签文本展开成 `$readmemh` 能读的定长记录
   （B4 条目第 4 节第 9 问）；命令表放在向量不用的地址，`LIST_BASE + reads × 32` 以后由从机回 `SLVERR`。
2. **取数的边界**：FETCH 落在一批中间（退回逐条取后定位到那一条）与 END 之后的记录不可读（不报错）各一例。
3. **总线错误与超时（端到端）**：像素读回 `SLVERR`（`BUS_READ`）与写响应 `SLVERR`（`BUS_WRITE`）各一例，三元组正确、中断 B 置位，
   失败命令之后的命令没有像素副作用；从机迟到超过门限一例：报 `TIMEOUT` 并发中断，迟到的响应到达后引擎排空回到空闲、能再次提交。
4. **软复位**：经 `CTRL` 软复位，排空完成后所有表面的 `valid` 清零、裁剪框恢复全游戏区（spec 第 02 章 §5）。
5. **跨命令写后读**：`pix_cases_dump --hazard` 那组用例经 APB 连续提交，目的内存与软件执行器逐字相同（2.2 节第 6 项）。
6. **注错**：检查顺序对调相邻两步、关掉逐条回退，各自必须见红。

### 2026-09-26 前期研究（原条目 2.2 节第 5 问）

原来的问题：

5. 命令批量的条数与命令缓冲的存放（寄存器还是片上 RAM）；`PERF_*` 的快照时机
   （设计文档原写「场同步时快照」，场同步归扫描输出，引擎这边要么接一根场起始信号，要么改成按命令表快照）。

#### 第 5 问：命令批量与 `PERF_*` 快照

批量大小的数据在 engine 第 02 章 3.8 节的矩阵里（`FETCH_B` 一列），结论与存储、出错定位的分析写进 D18；快照时机写进 D20。
这里补一条事实：命令记录 32 字节正好 2 拍，一批 16 条是一笔 32 拍的读；向量里 FETCH 一组靠 `reads`（可读条数）截断，
测试台的从机要对 `LIST_BASE + reads × 32` 以后的地址回 `SLVERR`，这正是 D18 担心的「整批报错看不出是哪一条」。
