## 搭车与顺序建议

1. **E8 的缓存变体在仓库外的复制工程里做。** 现行 4KB 基线已就位，
   8KB 与 16KB 各生成、编译、回归一次；复制工程也要恢复并核对 `sdk/README.md` 的登记项。
   SoC IP 定型已于 2026-09-19 完成，未等待 E8。若 E8 推荐改缓存，
   主线再单独生成一次 IP，只引入选定的缓存配置，按 [`README.md`](../README.md)
   的搭车规则独立提交并做全套回归。三档同时改变容量与路数，结论不可单独归因于路数。
2. **E5 的端口重分配已经单独完成。** 引擎接入另做一次编译；`core_clk` 的 hold 只有 0.026 ns，
   需在引擎接入后重新核对时序，并按第 08 章复测扫描 FIFO。
3. **E6、E7 与 E8 的 4KB 探针可以并行。** E7 的像素规格已完成，
   软件执行器由 SW3 提供，不需要等引擎；E8 的缓存变体随后单独编译。
4. **P4 不因 E8 合成探针单独定案。** E8 给阶段性建议，
   SW8/SW9 在真实游戏和板上测完整帧及 `N_max` 后再作最终取舍。

## 每一份 spec 的共同结构

按 [`README.md`](../README.md) 的单条结构，节序固定：

| 节 | 内容 |
| --- | --- |
| 状态 | 一行，写明未开工 / 进行中 / 待验收，以及它阻塞什么（验收之后文件删除，不存在「已验收」状态） |
| 1 要解决什么 | 现在是什么样，不做会导致什么 |
| 2 怎么切分 | 拆成哪几步，每一步的产物；不做什么也写在这里 |
| 3 判据 | 怎样算做完；可量化的写数字，上板项写清对照组与注错用例 |
| 4 开发日志 | 开工后逐次追加，最新的在最前 |
