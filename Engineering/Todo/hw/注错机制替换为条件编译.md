## 1 要解决什么

生产 RTL 里的注错（变异测试）开关做成了 `parameter integer INJECT`，由仿真脚本用
`-P<实例>.INJECT=n` 在例化处覆盖。这带来三件事：

1. **功能与注错在同一行语句里耦合**。典型形态是
   `wire signed [17:0] c_stage = INJ_UNREG_C ? $signed(c255_comb) : $signed(r_c);`
   ——真实数据通路上带着一个仿真用的选择器。`engine_blend.v` 里 5 处、`engine_geom.v` 里 5 处、
   `engine_mover.v` 里 7 处、`engine_pix.v` 里 5 处、`display_fetch.v` 里 4 处、`display_out.v` 里 3 处，
   形态相同。
2. **它的「零开销」依赖综合器的常量折叠真的发生**，而这件事没有被验证过。
3. **位号（`INJECT & 1`）不是自解释的**：读代码要回文件头查位定义，读日志要回 `run.sh` 对号。

不做会导致：功能代码里长期带着仿真语义；替换或重构数据通路时，注错分支容易与新逻辑打架；
审查者无法从代码本身判断某一行是功能还是注错。

这条做法在业界的原型是**变异测试**（硬件验证领域叫 mutation analysis 或 functional
qualification，商业工具代表是 Synopsys Certitude），与安全标准里的 fault injection
（stuck-at、位翻转这类物理缺陷模型，服务诊断覆盖率）不是一回事。

## 3 判据

1. **全部仿真套件符合预期**：正常用例 PASS、注错用例 FAIL 且红在对应判据上。
   清单见 `Main/sim/README.md` 的注错表。
2. **正常用例结果不变**：用同一个用例比较「替换前」与「替换后」的正常构建结果。
   这一项必须显式做，不能只看注错见红。
3. **开关生效性**：同一用例编两次（带与不带 `-DINJ_xxx`）结果不同。取不到差异说明开关没生效，
   此时注错用例的 PASS 会被误读成「判据有漏洞」。
4. **干净构建对账**：工作区版本与原版（`--rev c156fe5`）综合出的 XLR、Memory Blocks、
   DSP Blocks 与 setup、hold slack 一致，差异能用注释与文件头改动解释。
5. **上板**：干净版比特流跑 `开发环境.md` 0.6 节回归表：调试通路两项 PC 可读、
   APB 回归四个读数符合登记值、`engineTest` 与 `cacheCoherencyTest` 的 `fail 0`、HDMI 八色竖条。

### 2026-10-08 干净构建对账：两种形态综合出的网表不同（0.8%），但可复现

对账要回答的是「把注错从 parameter 换成 `ifdef` 之后，综合出的东西变没变」。
编译三次，每次四步 PASS：

| 次 | 源码形态 | XLR | RAM | DSP | `core_clk` setup | hold |
| --- | --- | --- | --- | --- | --- | --- |
| A1 | 工作区（`ifdef`） | 36716 | 121 | 16 | +0.591 ns | +0.026 ns |
| A2 | 工作区（`ifdef`），同一份源码 | 36716 | 121 | 16 | +0.591 ns | +0.026 ns |
| B | `--rev c156fe5` 原版（parameter） | 36237 | 121 | 16 | +0.826 ns | +0.026 ns |

- **A1 与 A2 的 `map.rpt`、`place.rpt`、`timing.rpt` 逐行相同**，说明这台机器上的综合与布局
  布线对同一份源码是可复现的。（`.bit` 的 SHA256 不同，那是比特流里带的生成时间戳。）
- **A2 与 B 的 `map.rpt` 差 483 行，XLR 差 479（占器件 0.79%）**，`u_blend:engine_blend`
  是差异最集中的模块（22 行）。逐通道看，两种形态在 12 个通道上的映射资源**有增有减**
  （如 `pixel[2].channel[0]` 是 69 对 66，`pixel[0].channel[2]` 是 87 对 86），
  不是单向变差，也不是少了常量折叠——注入分支在两种形态下都已经不在了。
- B 的另一处旁证：B 的比特流与改动前那次编译（2026-10-08 00:08，同为 parameter 形态）
  **逐字节相同**（2376780 字节），说明对照组的构造是对的。

**结论**：`ifdef` 形态与 parameter 形态是逻辑等价的（预处理器展开后源码相同），
但**综合映射不保证给出逐位相同的网表**。因此对账的判据不能写成「两次数字必须完全相等」，
只能写成「差异可解释、且两版都过各自的判据」；真正的等价证据是
「`--rev` 还原出的原版与改动前备份逐行一致」＋「A1↔A2 可复现」这两条。
后面的 `ifdef` 替换不必再重建对账，理由是同样的：形态差异本来就可能影响映射。

代价是要记下来的：本批让设计多占 479 个 XLR（60.39% → 59.60% 的反向读法即
B 比 A 少 0.79 个百分点），`core_clk` setup 从 +0.826 降到 +0.591 ns，仍为正、仍有余量。
如果需要把这 0.79% 挣回来，那是独立的优化工作点，不属于本次替换。

### 2026-10-08 上板回归：非 TEX 项全过，TEX 项为既有失败

干净版（`-DINJ_*` 一个都不定义）的比特流，`outflow/gfx2d_ti60.bit`，
SHA256 `CE05F1F8...D36F40E`，四步 PASS，资源 XLR 36716 / 121 RAM / 16 DSP，
`core_clk` setup +0.591 / hold +0.026 ns。

| 项 | 结果 |
| --- | --- |
| 调试通路（两次 OpenOCD 各读一次 PC） | 两次都 `Target successfully examined`，PC 一致 |
| APB 回归四个读数 | 引擎 ID `0x47465801`、CAPS `0x0000044F`、`LIST_BASE` 写入 `0x12345678` 回读一致、`0xF810_8008` 读回 0；与 `开发环境.md` 0.6 节登记值逐项相同 |
| `engineTest`（正常版） | `fail 17`，其中非 TEX 的全部 `ok`：十一帧金标准两面 CRC、`COUNT32`、`DIR` 两项、`INJ-COH`、`PERF-BUSY`、`STRESS`、`TEX-CAPS`、`TEX-LOAD`、`TEX-PERF` |
| `cacheCoherencyTest` | `fail 0`，IDENT 与 A1/A2/A3/B/C/D 全 `ok`；自检版另按登记要求跑，结论同上 |

**TEX 渲染项 17 项 FAIL 是既有问题，不是本次改动引入的。** 判据采用对照实验：
把**改动前的比特流**（`outflow/gfx2d_ti60.bit` 于 2026-10-08 00:08 编出，SHA256
`58073AE5...58DEEDE`）烧回板上，跑同一个 `engineTest-O2.bin`，得到**逐行相同**的 17 项 FAIL
与相同的 `6ab1aca3` 实测 CRC。两版比特流都是同一结果，所以这 17 项与注错机制的形态无关。
`TEX-LOAD ok` 而全部 TEX 渲染项退回同一个 CRC，指向 TEX 渲染通路或它依赖的素材是问题所在，
需要单独立项排查（另见下一条「对账中查到的两处既有账」）。
