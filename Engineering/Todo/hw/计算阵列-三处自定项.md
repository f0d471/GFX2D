# 计算阵列的三处自定项

状态：**未开工（条件启动）**（2026-10-17 立项）。三处都是现行实现里成立的做法，
不是缺陷，也不阻塞作品提交与任何已验收工作点。本条目只做记录与备选分析，
触发条件出现时才立项动手。

触发条件（任一成立即重开本条）：

- 目的表面要支持 ARGB8888（需要 alpha 写回）；
- 混合核级数 `L`、流水级数或排空拍数其一变更；
- 读流改成允许多行预取（读描述符先于边带发出）；
- 需要把「这三处为什么这么写」写进对外材料（报告、答辩、开源文档）。

## 1 要解决什么

计算阵列的数据通路是标准结构的组合，来源在
[engine 第 04 章](../../TechReports/engine/04-计算阵列与片上缓存.md) 3.1 与 3.4 节：
两拍窗口与旋转器照 Amiga blitter 的 node011F/node0127 先例，首末拍掩码照它的首尾字掩码
（改成按目的拍在旋转后打），常量源走同一混合核照 STM32 DMA2D 的 R2M，色键命中不写回照 ORGFX，
行缓冲乒乓、每拍 4 像素、延迟像与时钟使能都是通行做法。

另有三处是本项目自定的，没有文献或先例可引，只有本仓实验与判据背书：

1. **带内「不写」标记**：把逐像素掩码编在像素的 X 字节最高位，而不是走流的 `tkeep`。
2. **开环排空**：状态机固定等 8 拍再换行，没有从流水取「已空」反馈。
3. **每行一条边带、跨 4KB 两段共用写指针**：靠「边带先于读描述符发出」的顺序成立。

不做会怎样：这三处看起来都像可以随手改的实现细节，而改动后的错法都是静默的
（错一拍、抹掉一段数据），不是编译报错。同时它们既不该在对外材料里被写成创新，
也不该被当成缺陷要求返工，需要一条写清「为什么必须这样、什么条件下才会破」的记录。

## 2 怎么切分

### 2.1 带内「不写」标记

现状：`engine_pix` 在周期 7 把 `no_write`（色键命中或首末拍掩码外）写进每个像素的
X 字节最高位，其余 24 位放混合结果；搬运层在写核与 `Axi_Mux` 之间按这个标记清
`wstrb` 的对应 4 位，`ws_tkeep` 因此恒为全 1。

为什么必须这样：

- 写核中间拍 `wstrb` 恒全 1、不看 `tkeep`，只有最后一拍才看 `tkeep`，
  逐像素「打洞」无法用 `tkeep` 表达。研究轮做过 `tkeep` 挖洞注入，22825 个字写错。
- 核内 32 深 FIFO 是数据唯一的通路，任何旁路掩码线都要另配一份同深度、同延迟的
  FIFO 才能与数据对齐，代价与风险都大于收益。
- 目的表面是 XRGB8888，X 字节按规范恒为 0，用最高位当标记不损失任何信息。

现在靠什么判据：一行一行的测试台每行查 `tkeep` 恒全 1（与拍数、行内不断拍、
停顿数据保持并列）；首末拍掩码与色键有各自注错位。

崩溃条件：目的表面改 ARGB8888、需要用 X 字节存 alpha 时，标记没有位置，
必须重新设计并通过规范层（写帧缓冲高字节为 0 的要求同时要改）。

### 2.2 排空拍数

现状：`PS_RUN` 发完最后一拍后进 `PS_DRAIN`，`drain_count` 从 7 数到 0 共 8 拍再回
`PS_IDLE`。7 是流水级数，多出的 1 是余量。`en` 停时 `drain_count` 也停，
所以等的是 8 个有效拍而不是 8 个物理时钟。

备选：流水里有现成的 valid 链（`r_v1`/`r_v2`/`v_d1~v_d4`/`ws_tvalid`），
`pst == PS_DRAIN` 且这一串全 0 即「已空」，逻辑更少、还省掉那 1 拍。

现在为什么不改：8 是整套拍数判据的基线，418 行逐槽对照、乒乓台拍数账、真实通路周期数、
每行固定开销都按它算；改小 1 拍要重跑全部证据，而收益是每行 1 拍，
在 8×8 精灵一行 2~3 拍注入的量级上约占固定开销 3%，进不了整机关键路径。

崩溃条件：混合核级数或流水级数变化而排空未跟着改，新行参数会追到上一行的拍上。

可选的小改（零行为变化）：把「7 拍延迟」与「8 拍排空」的隐式耦合写成派生关系，
例如 `localparam [7:0] PIX_LAT = 8'd7;` 后 `drain_count <= PIX_LAT;`，
让改级数时编译期就暴露，而不是静默错拍。改动只涉及常量声明与一处赋值，
但仍需一次完整的统一跑。

### 2.3 每行一条边带与跨段共用写指针

现状：一行的写指针是 `{半, 该半读入计数}`，只在该半的边带握手时清零；
一行跨 4KB 拆成两段读时两段之间不清，读齐按总拍数判、不看 `rs_tlast`
（一行有两个 `tlast`）。

为什么不算额外的绕：读流的数据要落进行缓冲的某一半，就必须先把那一半占上，
而占上只能由边带握手完成，所以「边带先于读描述符」是结构决定的，不是本层新加的约束。
在这个前提下，写指针在一行内单调递增是事实，两段共用只是把它照实写出来。

崩溃条件：读流改成允许多行预取（读描述符先于边带发出）时，下一行的边带握手
会把写指针清零，抹掉本行第一段的数据。

现在靠什么判据：拆段 4 行的用例（每行两个描述符）在 25 项常态覆盖内；
`row_free`/`sb_ready` 的先后有专门断言检查。

### 2.4 相邻的两处同类简化（一并记录，同样不动）

- **半号不跨命令翻转**：每条命令第 0 行都用第 0 半，奇数行命令边界多等约 15 拍，
  一颗 16×16 弹幕的 1092 拍里约 1.4%。改成跨命令翻转要加一位翻转寄存器并改动几何层。
- **不设输出行缓冲**：靠写核 32 深 FIFO 吸收反压，代价是每个写描述符首拍至少停 1 拍；
  换掉要 8 深以上 × 128 位，约 1000 个 FF 或 7 块 RAM。

## 3 判据

任一处决定要改时，按下列顺序取证，缺项按未完成记：

1. 结论与依据：保留或改动，写清对应触发条件与代价数字（拍数、带宽、RAM 块数）。
2. 等价性或差异证据：只挪声明与注释的改动用去注释 token 多重集；涉及行为的改动
   必须重跑 `sim/engine/pix/` 的 25 项、B1~B4 真实通路 512 KiB 逐字比对、
   以及整机四步（RAM/DSP/slack 与登记值比，XLR 只报同轮读数）。
3. 拍数账：若动 2.2，重新给出「行周期 = 读拍数 + 注入拍数 + 排空拍数」的算式与实测值。
4. 板测：只在改动影响部署对象时做，按 [验证流程](../../../Main/doc/验证流程.md) 选范围。
