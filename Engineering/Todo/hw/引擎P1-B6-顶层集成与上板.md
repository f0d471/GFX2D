# 引擎 P1 · B6：顶层集成与上板

状态：**正式开发完成，转待验收（2026-10-02）**。前置 B1~B5；第 0 步（撤探针前基线）已于 2026-10-02 闭环。
顶层接入、整帧仿真、整机编译、驱动与两个板上判据程序、上板判据与回归全部完成，
证据见第 4 节 2026-10-02 开发条目与 [engine 第 06 章](../../TechReports/engine/06-顶层集成与上板.md)。
路线、层间接口与批次顺序见 [引擎P1总览.md](引擎P1总览.md)。

## 1 要解决什么

**这一批做什么。** 把 B5 写好的 `engine_top.v` 接进 SoC 顶层：S1 从探针主机换成引擎，APB 第 0 页从 `apb_probe` 换成引擎，
接上中断 B；引擎级跑十一个整帧用例与性能，整机一次编译，写最小驱动与 `engineTest`，按 2.6 节上板。

**现在是什么样。** 顶层的 S1、第 0 页与中断 B 的现状见总览第 1 节；用到 S1 探针的板上程序有四个（D22）；
E8 的两份 DDR 探针已于 2026-09-27 在 4KB/16KB 上复跑通过；`cacheCoherencyTest` 与 `displayFifoProbe`
已于 2026-10-02 在现行 4KB 比特流上补齐基线日志。S1、第 0 页和中断 B 仍待本批接入引擎。

**不做会怎样。** 引擎在仿真里全对也不能上屏：赛题基础 1~3 与高阶 1、2 的上板演示、SW9 的硬件后端、E3 与 E5 的引擎侧复测都等这一批。

## 2 怎么切分

### 2.1 已定的取舍

**D6 S1 从探针换成引擎。** 引擎接入的同一次编译里，`axi_probe_master` 从顶层撤下，源文件与 `sim/axi_probe/` 留着。
E5 引擎侧复测的负载是引擎的整屏 FILL 与整屏 BLIT。用到 S1 探针的四个板上程序、撤之前要在现行比特流上做完的事
与撤之后的改法见 D22（首稿只列了 `ddrBurstProbe`、`displayFifoProbe` 两个）。

**D14 SoC 基线。** E8 条件性推荐的 16KB/4 路数据缓存若在引擎上板前满足 [platform 第 10 章](../../TechReports/platform/10-CPU每弹幕开销与缓存对照的复现.md) 第六节维护的采用条件，就先单独换进主线，
引擎在换过的 SoC 上收敛时序；条件没满足就在 4KB 上做，缓存以后单独换。两次都按搭车规则分开编译、分开提交。

**D21 `apb_probe` 撤下，默认分支常量应答。** 它现在应答第 0 页与其余未映射页，按完整 16 位地址译码，
引擎占第 0 页之后它的三个寄存器再也访问不到；它还挂在 `doc/开发环境.md` 回归表的「APB 探针」一行
（ID、VERSION、SCRATCH 图案、`0xF810_8008` 读回 0）。未映射页必须有模块回 `PREADY`，否则 CPU 访问会停住。

定案：`apb_probe` 从顶层撤下，源文件与 `sim/apb_probe/` 留着（同 D6 对探针主机的处理）；顶层默认分支改成常量应答
（`PREADY = 1`、`PSLVERR = 1`、`PRDATA = 0`）；回归表那一行改成读引擎的 `ID`、写读一个无副作用的读写寄存器
（`LIST_BASE`），`0xF810_8008` 照旧读回 0。
没有采用：保留并加基址参数挪到空页（要改 `apb_probe.v` 与它的测试台，回归表只改地址）。

**D22 撤探针主机之前与之后要做的事。** 用到 S1 探针的板上程序有四个：

| 程序 | 用探针做什么 | 撤下之后 |
| --- | --- | --- |
| `sw/apps/probe/ddrBurstProbe` | E4 突发扫描，E5 并发与注错 | 4KB/16KB 回归已于 2026-09-27 完成，两档均 `fail 0`/`done`（platform 第 10 章 5.9）；后续相关硬件改动的验证须在撤探针前安排 |
| `sw/apps/probe/displayFifoProbe` | E5 2.4 节的满负载读、满负载写 | 引擎没有纯读命令，「满负载读」一组造不出来（platform 第 06 章第六节已记） |
| `sw/apps/probe/cacheMechTest` | E3 机理实验 T1~T11 的外部写入者 | 结论已归档 platform 第 05 章 |
| `sw/apps/test/cacheCoherencyTest` | E3 回归：外部写入者与第二个读者 | 回归程序要留下，随引擎改写 |

定案：照 D6 在引擎接入的同一次编译里撤探针。撤之前在现行比特流上做完三件事：E8 的两份 DDR 探针
（`ddrAliasTest`、`ddrBurstProbe`）在 4KB/16KB 上复跑（2026-09-27 已完成，四次均通过，见 platform 第 10 章 5.9），`cacheCoherencyTest` 与 `displayFifoProbe` 各留一份基线日志。
撤之后 `cacheCoherencyTest` 改写：外部写入者换成引擎 FILL COPY，第二个读者换成引擎 BLIT 读 CPU 写过的表面、
CPU 失效后读回；另外三个在 `sw/README.md` 标成「需要撤探针之前的比特流」。
没有采用：顶层加编译宏让 S1 在引擎与探针之间二选一，两种比特流并存（测量程序不用改，但要两套编译与回归）。

### 2.2 开工前要补的研究

这一批以集成为主，要补的研究少，结果写进 TechReports `engine/` 第 06 章。

1. **驱动的形状。** 最小驱动放 `sw/bsp/ti60/`，它的接口怎么与 SW9 的硬件后端、SW1 的分层判据（`tools/check/check_sw_layers.sh`）对上；
   寄存器偏移取自 B5 定下的单一真源，生成的 C 头文件已迁至 BSP 可见的 `sw/bsp/include/`。B5 的 P1 命令取数要求非空表 `LIST_BASE` 按 32 字节对齐（未对齐报 `FETCH`）；驱动分配/复制命令表时要保证该对齐，不能只依赖 C 结构体的默认对齐。
2. **编译前后的对照口径。** 搭车规则第 1 条：进网表的改动一次编译，`core_clk` hold 余量只有 0.026 ns；
   定出这次编译与 2026-09-25 的 `outflow`（XLR 21935、RAM 71 块、setup 3.516、hold 0.026）逐项对照的表。
3. **D14 的前提。** 开工时重读 platform 第 10 章第六节，确认 16KB/4 路的采用条件满没满足，决定引擎在哪个 SoC 基线上编译。

三项已于 2026-10-02 研究完毕，过程与结论在第 4 节；产出一条候选定案 D55（头文件产物位置），
并确认已有 D14 取 4KB 分支。D55 的路径冲突已在前期研究复核时先行修复并验证。

### 2.3 RTL

顶层改动：S1 换成引擎、`axi_probe_master` 撤下（D6、D22）；第 0 页换成引擎、`apb_probe` 撤下、默认分支改成常量应答（D21）；
中断 B 接上；引擎搬运层的复位接 `ddr_rstn` 取反（D17）。进网表的改动攒成一次编译（搭车规则第 1 条）；
不改管脚，`gfx2d_ti60.peri.xml` 不动。

### 2.4 仿真

新目录 `sim/engine/frame/`。被测是 `engine_top.v`，从机是补齐之后的 `axi_ram_model.v`。

1. **整帧**：引擎加从机模型（随机反压），跑十一个整帧用例与 SW6 的若干帧命令表。
   表面表、命令表与初始内存由 B4 写的导出小程序给出；测试台跑完把帧缓冲导出，按 sw 第 03 章 3.6 节的口径算 CRC32，与 `sw/lib/test/golden.txt` 相同。
2. **计数器对账**：同一批用例下 `RD_BEAT` 等于各读突发长度之和、`WR_BEAT` 同理、`PIXEL` 等于软件执行器的 `pixel_total − src_oob`。
   **订正（2026-10-01，B3 前期研究复核）**：原文写「等于 `pixel_total`」，但 `pixel_total` 含源越界的像素，五者求交（D2）在矩形级把它们裁掉，硬件见不到；十一整帧里差 5904 个（`blit-clip-partial`）。
3. **性能**：定时从机下 16×16 ALPHA 每颗的周期数，与 engine 第 02 章 3.8 节的 1092~1124 对账。

### 2.5 编译与时序

四步全过、无负 slack；`core_clk` 的 hold 余量登记，与 0.026 ns 比较；片上 RAM、DSP、LUT 登记，
RAM 增量以 35 块预算对账并解释实际差额（B4 的 D46 之后：行缓冲 12、两个核 16、命令缓冲 7；D23 原估 37），
两个核与 B2 单独综合的数对账；35 不是必须精确命中的通过线。
B3 几何层单独综合（裁剪框接变量）setup 余量只有 +0.572 ns，关键路径是求交的比较链到首行锁存寄存器的时钟使能；
整机里若这条路径 setup 不过，按 [engine 第 03 章](../../TechReports/engine/03-几何层.md) 3.8 节末段把求交拆成两拍（加 `S_CALC`，每条命令多 1 拍）。
B2 单独综合（主线参数）量到两个核 897 XLR（读核 361、写核 536）、16 块 RAM（每核 8 块）；
RAM 与整机编译里的 16 块对上，写核 XLR 比整机里记的 1126.5 少 590。
B4 的 D48（搬运层自己打写流 `tlast`）之后重跑：两个核 900 XLR（读核 353、写核 547），RAM 不变，写核与整机的差是 579.5，对账按这一版。
整机那次的工程与报告已经不在，B2 无法归因
（[engine 第 02 章](../../TechReports/engine/02-AXI事务层.md) 3.1 节与第五、六节）。
本批的整机编译里把两个核的 XLR 登记一次，与这两组数对照，写核的差距在这里有结论。
两个核在 B2 单独综合时每份约 59 条厂商告警（位宽截断与「模块体内的 parameter 变成 localparam」等类型）。
B6 进整机网表后若出现，相对 B5 主工程属于新增告警，应对照 B2 的已知清单逐条归因；
不把已知第三方告警误记为本仓自写 RTL 的新问题，也不把数量差异自动放过。

### 2.6 上板

0. **撤探针之前**（现行比特流，D22）：E8 的 `ddrAliasTest`、`ddrBurstProbe` 在 4KB/16KB 上复跑已于 2026-09-27 完成（platform 第 10 章 5.9）；
   `cacheCoherencyTest` 与 `displayFifoProbe` 的现行 4KB 比特流基线已于 2026-10-02 留档（第 4 节最新条目）。
   **第 0 步已完成**；这两份程序使用 S1 探针，B6 接入引擎后不能再以原样复跑。
1. 新程序 `sw/apps/test/engineTest`：同一张命令表，软件执行器画一份、引擎画一份，比较两面的 CRC；
   十一个整帧用例与几何定向用例（engine 第 03 章 3.4 节）全部一致；注错：读回之前跳过失效，CRC 必须不一致（设计文档 3.8 节，E3 的规则）。
2. 写掩码：目的 x 对 4 取余为 1、2、3 的窄矩形（首末拍的部分掩码）与色键棋盘（中间拍按像素跳过的稀疏掩码），
   验证 S1 发出的这两种掩码在真控制器上生效（探针只发过全掩码，这一条板上从没验过）。
   总线地址恒按 16 字节对齐（D15），不需要验非对齐地址。
3. E5 引擎侧复测：最重的 FILL、BLIT、ALPHA 命令表连续跑，扫描 FIFO 最低水位、欠载与 SoC 的最大地址等待按 platform 第 08 章的口径登记。
4. E3 引擎侧复测：改写后的 `cacheCoherencyTest`（引擎当外部写入者与第二个读者，D22）按 platform 第 05 章的判据验证失效规则，
   与第 0 步的探针基线对照。
5. 复位：引擎连续执行命令表时 `reset halt`、重新加载程序，引擎能再次提交，`displayTest` 照常通过（D17）。
6. APB 回归：`doc/开发环境.md` 回归表的 APB 一行按 D21 改成读引擎 `ID`、写读 `LIST_BASE`、`0xF810_8008` 读回 0。
7. 性能：16×16 ALPHA 弹幕每颗的周期数由 `PERF_BUSY` 与计数器给出，与总览第 1 节的估算、engine 第 02 章 3.8 节的模型对照；整帧 `N_max` 由 SW8/SW9 出。

驱动：`sw/bsp/ti60/` 写最小驱动（登记表面、提交命令表、等完成、读错误三元组与计数器、软复位并等排空结束），`engineTest` 用它；
中断驱动的帧节拍、游戏接入与软硬件切换属 SW9。

**驱动的 API 与位置。** 接口头文件放 `bsp/include/`（与 board.h 同层，应用可见），实现放 `bsp/ti60/`

设计文档 3.4 节与 B5 第 05 章 6.1 节的协议直接约束写法：

- 提交只在 `EN=1` 且空闲时被 DOORBELL 受理，忙/排空中/`EN=0` 写它回 PSLVERR（D54）；受理清旧错误定位与 DONE。
- DONE/ERR 置位即引擎已静止（D54），「等完成」轮询 STATUS 即可，置位后不必再查 BUSY，
  PERF 可以立刻读（D20 的「完成后读、软件按帧做差」直接成立）。
- 非空表 `LIST_BASE[4:0]` 必须为 0，违例报 `FETCH`（索引 0、TAG 0）（D53）。命令表落
  `REGION_CMDLIST_A/B`（基址 `0x0040_0000`/`0x0050_0000`，本身 1MB 对齐），表在分区内的偏移由调用方决定，
  驱动在入口断言 32 字节对齐，不能依赖 C 结构体的默认对齐。
- 轮询要有上界。board.c 的 `DISP_POLL_LIMIT` 教训：比特流里没有该模块或通路没起来时，
  无上界轮询的表现像死机。驱动先读 `ID` 判模块在不在比特流里（与 `disp_present_in_bitstream()` 同一手法），
  不在则各接口直接返回「无引擎」错误码；等待完成另设按 `BOARD_HZ` 折算的轮询上界。
- 软复位：写 `SOFT_RST`（写 1 自清），等 `DRAINING`/`BUSY` 落下再返回；表面表 `valid` 全被清，
  重新提交前要重新登记；复位期间 DOORBELL 不可用。
- 中断留给 SW9：最小驱动不使能 `IRQ_EN`（复位值 0，纯轮询），API 不含中断注册。
  缓存失效不进驱动 API：`board_dcache_invalidate_*` 已在 board.h（E3 规则），
  读回共享区之前由调用方失效，时机在「等完成返回」之后（失效晚于写入完成），
  顺序由 engineTest 的注错判据（跳过失效 CRC 必须不同）固定。

#### 第 3 项：D14 的前提

重读 platform 第 10 章第六节与 5.5 节。16KB/4 路的正式采用条件是三件事：
单独生成 IP 并同步 SDK 配置与必要回归；两份 DDR 探针在 4KB/16KB 复跑通过（2026-09-27 已完成，5.9 节）；
在 SW9 的真实游戏与扫描压力下确认资源、时序和帧预算。第三件以引擎上板为前提（SW9 后半等引擎 P1），
构成依赖环：引擎等缓存裁决，缓存裁决等 SW9，SW9 等引擎。前两件里引擎上板前能做的都已完成
（合成负载收益 2026-09-27 重现，同产物九组降低 17%~44%）。

结论：D14 取后半——**引擎在 4KB/1 路主线上编译**；16KB 缓存留作引擎上板之后的独立改动
（改一个参数的一次 IP 生成加 sdk 同步，按搭车规则第 2 条单独提交，按 platform 第 10 章第六节
维护的采用条件验收，真实游戏验证归 SW9）。资源余量不构成反方向的理由：
4KB 加引擎约 106 块（全片 41%），16KB 加引擎约 124 块，都在 256 块以内；裁决依据是采用条件，
资源数另行登记在案。
