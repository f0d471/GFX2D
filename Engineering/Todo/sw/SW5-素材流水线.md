## 1 要解决什么

主路径纹理以 **ARGB8888_PREMULT** 存放；赛题原式的对照素材以 **ARGB8888_STRAIGHT** 存放
（设计文档 3.4、3.5 节）。板上启动时从 Flash 素材区（`0x400000` 起 4 MiB）
把完整素材包拷到 DDR 素材区（`0x0100_0000` 起 16 MiB）；PC 版从文件读同一包、
放到模拟的同一分区。目录偏移以包起点为基准，像素数据在 DDR 中不再重排，
绘图表面的设备地址是 `g_mem_regions[REGION_ASSET].offset + 条目偏移`。
没有这条流水线，游戏里的每张图都得手写成数组，改一张图要重编程序，而且预乘的量化偏差没有地方记录
（spec 第 01 章：预乘路径最大偏差 254/255，「偏差要在素材工具里记着」）。

本条负责打包、两平台的装载入口、共用解析与一次板上装载验收；
SW9 只调用现成入口并验证游戏帧，不再另写一套素材装载。

## 2 怎么切分

### 2.1 工具：`Main/tools/assets/pack_assets.py`

WSL 里的 python3 + Pillow（2026-09-22 复测：python 3.14.4、Pillow 12.2.0、zlib 1.3.1）。
`tools/` 按用途分三类，素材打包不属于 `board/`、`soc/`、`check/` 任何一类，
按 `tools/README.md`「加新工具的规则」新开 `tools/assets/` 并在那张表里登记；
镜像合成属「写 Flash 前」一类，放 `Main/tools/board/make_flash_image.py`。理由见第 4 节 R1。

```
输入   Main/assets/manifest.txt        UTF-8 TSV：显式 ID、名字、相对 PNG 路径、用途、
                                       alpha_mode(premult/straight/xrgb)、色键、切片宽高
输出   Main/assets/build/assets.pak    素材包
       Main/assets/build/assets.h      稳定编号、包版本与 CRC、宽高/行跨/格式、图集子矩形
```

- manifest 路径只相对 `Main/assets/`，规范化后仍须落在该目录内，不接受
  `..` 跳出素材根或绝对路径；显式 ID 和名字均不得重复，重排行不改变编号，
  相同输入逐字节产出相同的包与头文件。生成头里的包 CRC 由程序在装载时比对，
  防止单独更新 Flash 素材区后程序仍按旧编号解释新包。
- `premult`：各通道用整数式 `(c × a + 127) / 255` 取整，与 spec 第 01 章同口径；
  校验 `R/G/B <= A`，并统计每张图因预乘改变的像素数与最大偏差。
- `straight`：保留 PNG 的 RGB 与 A，供 ALPHA_STRAIGHT 对照；与同一素材的预乘副本使用不同条目和格式号。
- `xrgb`：高字节写 0，不预乘。带色键的 PNG 只接受 A=0/255：A=0 的像素写成
  manifest 指定的 `0x00RRGGBB` 色键字，A=255 的可见像素不能与该字撞色；
  无色键的 xrgb 要求全部 A=255。ARGB 色键按转换后的 32 位存储字指定，
  与 spec 第 01 章的比较域一致。
- **输入只接受可按规格展开为 8 位 RGBA 的 PNG 模式**
  （`1`、`L`、`LA`、`P`、`RGB`、`RGBA`；其中 `1` 是 1 位二值图，
  `P` 的索引位深也不一定是 8 位）。Pillow 12.2.0 对
  16 位灰度 `I;16` 的 `convert("RGBA")` 是**截断到 255**（1000 → 255、65535 → 255），
  不是按比例缩放，静默转换会产出近全白的图；`I`、`F`、`CMYK` 等模式同样一律报错退出，不猜。
  取像素用 `tobytes()`，不用 Pillow 12.2 已弃用（14 移除）的 `getdata()`。
- 预乘**必须用 65536 项查表**（`(c << 8) | a` 索引），不能用 `ImageChops.multiply` 图快：
  实测它等于 `floor(c × a / 255)`，与规格口径在 65536 组里有 31,770 组不同（48.5%）。
- **色键只与 `xrgb` 搭配**：spec 第 01 章 3.5 节的色键比较域是源表面的 32 位存储字，
  预乘/直通条目的存储字已被改过；manifest 里给 `premult`/`straight` 配色键一律报错。
- v1 不产出 `INDEX8`（格式 3）：`gfx_surface_set()` 结构上收它，但 `gfx_cmd_check()`
  只让 XRGB/ARGB_PM/ARGB_ST 当 BLIT 源，用了会报 `GFX_E_BAD_FORMAT`。
- 每项的像素字按小端存储，字节顺序 B、G、R、A（xrgb 最后一字节为 0）。
  每行行跨取不小于 `width × 4` 的最小 2 的幂，行尾填 0；目录记录 `stride_log2`，
  数据长必须等于 `height × (1 << stride_log2)`。例如 640×480 整图的行跨为
  4096 字节，占 1,966,080 字节，即 1.875 MiB；不能按紧凑排列的约 1.17 MiB 预算。
  `stride_log2 = max(2, ceil(log2(width × 4)))` 且不超过 31：`gfx_surface_struct_ok()`
  的下限是 2（check.c 第 103 行），`gfx_surface_set()` 拒 31 以上；目录里它是 u8，
  解析器要把越界当结构错误拒掉。
- 图集：同尺寸小图可按网格拼在一个表面里。**目录是一项对一个表面**，
  图集成员不是独立条目——它们与图集条目共用同一段数据区，各自成条目会互相重叠，
  而 2.2 节要求解析器把重叠当结构错误拒掉。成员以「图集条目号 + 子矩形」的形式
  进 `assets.h`，绘图时用 `gfx_blit()` 的源坐标 `(sx, sy)` 取，不额外占表面槽
  （v1 只有 16 槽）。背景按本条首版方案：优先复用图块和程序生成的画面，
  需要独立整图时也按行跨与包大小实算。

### 2.2 素材包格式

```
头       固定 32 字节：magic "G2DP"、版本 u32=1、头长 u32=32、条目数 u32、
         总长 u32、整包 CRC32 u32、目录字节数 u32、保留 u32=0
目录     每项固定 32 字节：ID u32、偏移 u32、长度 u32、宽/高各 u16、
         stride_log2 u8、格式 u8、标志 u16、色键字 u32、数据 CRC32 u32、保留 u32=0
数据     每项起点按 64 字节对齐；条目数据包括逐行的 0 填充
```

所有多字节字段固定小端；目录紧跟头，`目录字节数 = 条目数 × 32`，
偏移相对包起点，未使用的包间隙填 0。v1 最多 256 项；标志的 bit 0 表示启用色键，
其余位必须为 0，未启用色键时色键字必须为 0。格式编号照 `gfx_abi.h` 的 v1 定义。
CRC32 与 `sw/lib/core/crc32.h` 同参（同 zlib.crc32）：每项覆盖其完整数据区，
整包覆盖 `总长` 字节，计算时把头内的整包 CRC 字段当作 0。

解析与校验放 `sw/lib/core/assetpak.c` + `assetpak.h`（**是文件，不是目录**）：
`mk/host.mk` 与 `mk/target.mk` 都只按 `lib/<库名>/*.c` 一层取源文件，
`check_sw_layers.sh` 也按 `lib/*/*.o` 扫目标文件，放进子目录既不会被编、也不会被判据扫到。
PC 与板子共用这一份。先检查头、版本、数量、
偏移与乘法溢出、重叠、行跨（`stride_log2 ∈ [2, 31]` 且 `width × 4 <= 1 << stride_log2`，
目录里它是 u8，能存到 255）和 16 MiB DDR 边界，再按 ID 逐项检查数据 CRC，
最后检查整包 CRC；单项数据被改坏时要报对应 ID，头或目录坏掉时报结构错误。
任何失败都不返回可用于绘图的素材表面，不静默使用。

生成的 `assets.h` 落 `Main/assets/build/`（`.gitignore` 的 `build/` 模式已覆盖它），
要能把 ID/图集子矩形映射到上述目录项，并参与 PC 与板上构建：
两个 `mk/*.mk` 给**应用**那一层的编译规则加 `-I$(ASSETS_BUILD)`
（`ASSETS_BUILD ?= $(SW)../assets/build`），lib/ 与 bsp/ 那一层不加，分层不变。
`lib/core/assetpak.h` 只放通用格式与解析器、不认识具体 ID；
本项目的 ID 与子矩形只在 `assets.h` 里，只有应用包含它。
包目录最多 256 项，但 `gfx_surface_table` 只有 16 槽：包 ID 不是表面槽号，
解析器不得按 ID 一次登记全部条目；应用按当前画面需要选择、登记至多 16 个表面
（包括帧缓冲），图集成员继续共用图集槽。超出可用槽数时明确报错，不静默覆盖。
装载后用现有 `gfx_surface_set()` 实际登记表面、由软件执行器 BLIT 一个已知图块，
不能只证明打包与解包互相一致。
该 BLIT 的 `gfx_mem` 必须同时覆盖源素材区和目标帧缓冲：以
`REGION_ASSET` 起点作 `dev_base`，`host` 指向 `board_region(REGION_ASSET).ptr`，
`bytes` 覆盖到测试目标帧缓冲末端；两平台均先核对相邻分区指针与
`g_mem_regions` 偏移的一致性。只把 `board_region(REGION_ASSET).size`
填进 `gfx_mem.bytes` 会使帧缓冲落在窗口外，BLIT 按 `GFX_E_BAD_SURFACE` 失败。

### 2.3 两平台装载

- 装载分两半，**应用把两半接起来**（sw 第 01 章 3.2 节的分层：bsp 不依赖 lib、lib 不依赖 bsp）：
  - `sw/bsp/` 出「读字节」的能力，`board.h` 里定成
    `int board_asset_read(uint32_t offset, void *dst, uint32_t bytes);`（0 或负错误码）：
    offset 相对素材分区起点，host 从 `assets.pak` 文件读
    （`GFX2D_ASSETS_PAK` 环境变量，不给时用 `mk/host.mk` 编进去的绝对路径），
    ti60 用现有 SPI Flash 驱动从 `0x400000` 读。
  - `lib/core/assetpak` 出「装载策略」：`assetpak_load(pk, rd, dst, dst_bytes, lim, out_len)`
    先读 32 字节包头校验总长，再按总长读进 `dst` 并完整解析。`dst` 由应用从
    `board_region(REGION_ASSET)` 取——应用只经这个接口拿到分区，不出现物理地址。
  包头校验放在 lib 里而不是 bsp 里，是为了让「读正文之前先校验总长」这条规则只有一份；
  bsp 只负责读，不认识包格式。
- ti60 装载入口独立完成 SPI 初始化、Flash 唤醒及退出 4 字节地址模式
  （与 bootloader 的 `spiFlash_init`、`spiFlash_wake`、`spiFlash_exit4ByteAddr`
  调用顺序一致），不假设启动后外设仍保持 bootloader 的状态。
  单线（`spiFlash_f2m`）为默认；双线留 `BOARD_ASSET_SPI_DUAL` 一个宏，由 E6 决定是否切换。
- 装载是 CPU 经驱动逐字节写 DDR，**不是外部主机写**，所以 E3 的「读回前必须失效」
  在这一段不适用：本构型没有写缓冲，CPU 的写返回前已落到 DDR，写后立刻读回也不会读到旧值
  （platform 第 05 章 T1、T3、T6）。这条 Flash → DDR → 解析的路径**不加**失效调用，
  免得照抄 E3 规则白付 16 MiB 逐行失效的代价。若以后改成由外部主机搬素材，必须再加回来。
- 板上启动先读固定 32 字节包头，在继续读取前先核验 magic、版本、头长、条目数、
  目录字节数与总长的基本关系，且 `总长 <= 4 MiB`、`总长 <= REGION_ASSET.size`；
  不能先信任未校验的总长去写 DDR。头部通过后再按总长读取完整包，
  由共用解析器完整校验目录、条目与整包 CRC，并与编译时生成头的版本、
  整包 CRC 比对，之后才允许使用素材。host 文件路径也按同一容量界限检查。
  出错时串口明确报包级原因或条目 ID，并拒绝使用。
- 一次板上验收要覆盖 Flash → DDR → 解析 → 软件绘制器绘图，和 PC 对同包同图的 CRC 对账。
  JTAG 预装 DDR 可以作调试捷径，但不能替代 Flash 启动路径的验收。

### 2.4 Flash 镜像合成

`Main/tools/board/make_flash_image.py`：比特流 + 程序（`0x380000`）+ 素材包（`0x400000`），按设计文档 2.2 节的分区合成一个 hex。
比特流输入是 `fpga/gfx2d_ti60/outflow/gfx2d_ti60.hex`，**不是 `.bit`**：
同一编译的两份输出解码后长度差 20 字节，差异全在 ASCII 头部（`.bit` 写 `Mode: passive`，
`.hex` 写 `Mode: active` 并多一行 `4Byte: 0`），头部之后 698,623 字节逐字节相同；
写 Flash 要 active 那一份。四个分区起点（`0x0`、`0x200000`、`0x380000`、`0x400000`）
都是 4 KiB 扇区边界，工具要断言这一点。
输入先还原为真实字节，输出为 Efinity Programmer 接受的每字节一行 hex（不是编译器的 Intel HEX）；
空洞填 `0xFF`，逐分区检查容量、起点与互不重叠，解回字节后与三份输入逐字节比对。
输出默认覆盖到三份输入中最高的「分区起点 + 输入实际字节数」，
再向上取整到扇区；不能按最后一个非 `0xFF` 字节截断，有效输入本身可以以
`0xFF` 结尾。`--full` 出整片 8 MiB。
物理上限始终是 4 MiB，参数只能把运行预算收紧，不能放宽到越过 Flash 分区。
本工具只生成与校验镜像，不自动烧录；需要上板写 Flash 时按 `Main/doc/开发环境.md`
第 8 节先备份；烧录与回读由独立的上板流程完成。

### 2.5 占位素材与许可

- 占位：`Main/assets/placeholder/` 下由脚本生成的纯色方块、圆形弹幕、渐变背景、棋盘格，许可无问题，先用它们把全流程跑通。
- 字库：8×16 点阵、95 个 ASCII 字形。**自绘**，字形以文本形式（每字 16 行、每行 8 位十六进制）
  入库 `Main/assets/font/ascii8x16.txt`，打包工具把它渲染成图集；
  `LICENSES.md` 登记为「项目自绘，无第三方来源」。查过本仓与厂商资料包，
  两边都没有可用的点阵/矢量字库（`Efinix/` 下没有 `.ttf`/`.bdf`/`.fnt`），
  而选外部 CC0 字库要额外核许可、也要离线可得，自绘把这两件事一起去掉。
  字库不在流水线的关键路径上：用占位图块就能验完整条流水线，SW6 的 HUD 才需要它。
  （**订正**：自绘版有几个字形残缺，2026-09-27 定案换成开源点阵字体 Spleen 8x16（BSD-2-Clause），由 `Main/tools/assets/gen_font_txt.py` 转换成同一格式的 `ascii8x16.txt`，见 `Main/assets/LICENSES.md`。）
- 本条只准备能证明流水线和 SW6 画面的占位、字库与许可台账；
  正式角色、弹幕和背景的美术生产随 SW7 的主题选择另排。
  **没有登记许可的非生成素材不入库**。

### 2.6 检查脚本

`Main/tools/check/check_sw5_assets.sh` 把本条的结构判据串成一条命令，与 `check_sw4_pc.sh` 同构：
打包占位素材 → 主机侧 C 侧解包并逐项对 CRC → 六类推错输入（改数据一字节、改头、改目录、截断、
重叠、越界）各自报出指定的错误码 → 镜像合成后按 Programmer 格式解回逐分区比对 →
一次注错构建必须见红。全部通过时末尾 `fail 0` 与 `done`、退出码 0。

本条**不含**：游戏逻辑与正式美术、8 位索引加调色板格式、RLE 压缩；
若路线改变而需要后两者，先另开工作点，不悄悄扩进本条。

## 3 判据

| 项 | 判据 |
| --- | --- |
| 格式 | 预乘结果与 C 侧对 256×256 组 `(c, a)` 全部一致且满足 `c_pm <= a`；STRAIGHT 打包往返后 RGBA 逐字节不变；不在允许解码模式列表内的 PNG、带色键的预乘/直通条目、`INDEX8` 条目一律报错且退出码非 0 |
| 布局 | 每项满足 2 的幂行跨、行尾 0、64 字节起点对齐；`stride_log2` 落在 `[2, 31]`，越界按结构错误拒；640×480 整图按 1.875 MiB 计；`gfx_surface_set()` 接受生成的宽高/行跨/格式，图集子矩形不越界 |

### 4.17 实现过程里踩到的坑

按时间顺序，每条写现象、定位、修法。

1. **`assetpak_probe_header` 用 32 字节去比头里的总长，必然失败。** 主机侧单测第一次跑，
   A1 报 `expect=ok got=bad_total`。根因：probe 的调用者手里**只有**包头，
   正文还没读，拿 `total > len` 去比永远不成立。修法：`check_header()` 加一个
   `have_body` 参数，probe 只校容量预算（`total <= lim->max_total`），
   parse 才比 `total` 与传入长度。这一条如果没写单测，会在板上表现成「任何包都装不进来」。
2. **单测自己写错了一处**：B09「总长超过传入长度」把 `len` 传成了头里写的那个总长，
   等于没有截断，于是报的是 `pack_crc`。修法：`len` 取「调用方手里最多有多少字节」
   （`min(total, BUF_BYTES)`）。判据写错与实现写错一样要留档。
3. **`need(cond, msg)` 的消息是立即求值的**，重复 ID/名字那两处的 `%` 格式化在没重复时
   也会算，`seen.get()` 返回 `None` 直接抛 `TypeError`。修法：那两处写成显式 `if`。
4. **字库图集的第 96 格没有字形，alpha 留在 0**，而 xrgb 不带色键要求全 255，
   打包在 `(120,80)` 报错退出。修法：整个图集按 `[0,0,0,255]` 初始化，
   未用到的格子是不透明的黑（BLIT 时靠色键 `0x00000000` 跳过）。
5. **独立校验工具自己错了**：`check_sw5_pak.py` 对字库那一项把第 4 个字节算成 `0xFF`，
   而规格是 xrgb 高字节写 0。它报「第 3 项像素字节不符，包 00 期望 FF」，
   查下来是**校验工具**错、打包工具对。这正是要两份实现的原因：错的那一份会先被另一份抓住。
6. **`assetTest` 的 C1 自检写错**：把一串返回值（全 0）的和与 `list.used` 比，
   恒不相等。修法：数「返回码非 0 的调用次数」。
7. **判据脚本对「文件比总长短」的期望码写错**：PC 从文件读，读不满声明的长度，
   报的是板级 `board_read`(-2)，不是解析器的 `bad_total`(6)。解析器自己那一条由
   主机侧单测（B09/B26）与「头写 6 MiB 总长」那一组覆盖，脚本注释里写清了分工。
8. **`board_run.py` 的 `--flash-boot` 与 `--dry-run` 的顺序**：新分支插在了 `--dry-run`
   之前，`--flash-boot --dry-run` 会真的去烧板子。修法：分支条件加 `and not args.dry_run`，
   落到下面原来的 dry-run 打印里。改完用 `--dry-run` 验过一遍。

### 4.21 实现复核与修正（2026-09-23）

软件侧总判据通过后，另用最小反例复核输入边界，发现并修正八处：

1. 字库解析原先把所有 `#` 开头的行当注释，导致 `#.......` 这类合法像素行被吞掉；
   注释现限定为 `#` 后跟空白，行首像素可正常打包。
2. PNG 入口原先只检查 Pillow 解码后的模式，扩展名伪装的 JPEG 也会被接受；
   现同时要求 `Image.format == "PNG"`，独立校验器使用同一输入约束。
3. 素材名只检查原字符串唯一，`foo` 与 `FOO` 会在 `assets.h` 里生成同名宏；
   现按最终的大写宏名检查碰撞。
4. 镜像工具能按十六进制行解码 passive `.bit`，但不会发现模式错误；
   现检查头部 `Mode: active`，并把 `--app` 改为必填、禁止输出覆盖任一输入。
5. 解析器原先只检查色键标志与键值，没有限制色键只能用于 XRGB；

### 4.2 PNG 解码行为（问题 1）

把各模式的图存成 PNG 再读回，走真实的解码路径，`Image.open(f).convert("RGBA")`：

| PNG 模式 | 读回模式 | 转 RGBA 的结果 |
| --- | --- | --- |
| `1`（二值） | `1` | 黑/白，alpha 全 255 |
| `L`（8 位灰度） | `L` | 灰度复制到 RGB，alpha 全 255 |
| `LA` | `LA` | 灰度 + alpha，**alpha 保留** |
| `P`（调色板） | `P` | 调色板展开，alpha 全 255 |
| `P` + `tRNS` | `P` | `info["transparency"]` 保留；透明索引的 alpha 为 **0**，其余 255 |
| `RGB` | `RGB` | 原样，alpha 全 255 |
| `RGBA` | `RGBA` | 原样，RGBA 逐字节不变 |
| `I;16`（16 位灰度） | `I;16` | **截断到 255**：原值 `[0, 255, 1000, 65535]` → R 通道 `[0, 255, 255, 255]` |

**结论（R4）**：manifest 只接受上表前七种可展开为 8 位 RGBA 的模式；
`1` 原图是 1 位，`P` 的索引位深也可能低于 8 位；`I;16`、`I`、`F`、
`CMYK` 等一律报错退出。
`I;16` 那一行是关键：它不是缩放而是截断，静默转换会产出近全白的图，
而这种错在打包环节看不出、要到画面上才发现。

### 4.3 预乘：口径必须自己实现，且已经与 C 侧对账（问题 1、2）

**先试了 Pillow 的现成快路径，不能用。** `ImageChops.multiply` 对 65536 组 `(c, a)` 逐一比对：

```
ImageChops.multiply(L,L) 取 65536 组 (c,a)
与 floor(c*a/255) 不同: 0 处
与 round((c*a+127)/255) 不同: 31770 处，首个 (1, 128, 0, 1)
```

它是 `floor`，不是规格的 `(c × a + 127) / 255`，**48.5% 的组合不同**（最小反例 `c=1, a=128`：
floor 给 0，规格给 1）。用它会与板上硬件、与 spec 第 01 章的校验全面对不上。

**改用 65536 项查表**（索引 `(c << 8) | a`），按 4 字节一组处理 RGBA：

```
640x480 = 307200 像素，纯 python 预乘 0.047 s（660.23 万像素/秒）
违反 c_pm <= a 的像素: 0
```

**与 C 侧逐字节对账**（表按 `c` 外层、`a` 内层生成，共 65536 项）：

| 量 | C 侧（`(c*a+127)/255`） | python 侧 | 一致 |
| --- | --- | --- | --- |
| 表 CRC32 | `71CE34F8` | `71CE34F8` | 是 |
| `c=1, a=128` | 1 | 1 | 是 |
| 65536 字节逐字节 | — | — | 是 |

`round` 口径下 `c_pm > a` 的组合数 **0**，与 spec 第 01 章「素材侧的预乘要满足 `src_pm ≤ a`」
自洽（可证：`c ≤ 255` 时 `(255a + 127)/255` 向下取整仍是 `a`）。

**结论**：R2 用查表，速度不是问题（一张 640×480 只要 47 毫秒，一张图集的构建时间可忽略）；
R3 在工具的实现注释里写明「不要换成 `ImageChops.multiply`」并给出上面这组数，
避免后续把查表替换成舍入规则不同的图像乘法操作。

### 4.4 打包参数与表面表：全部收下（问题 2）

写了一个 C 探针，用 `sw/lib/gfx/` 的真实源码，把打包工具会生成的那一组参数喂给
`gfx_surface_set()`，读回返回值与 `gfx_surface_struct_ok()`：

| 条目 | w×h | `stride_log2` | 格式 | `gfx_surface_set()` |
| --- | --- | --- | --- | --- |
| 640×480 背景 | 640×480 | 12 | XRGB8888(0) | `rc=0 struct_ok=1` |
| 图集 | 128×96 | 9 | ARGB8888_PM(1) | `rc=0 struct_ok=1` |
| 字库图集 | 128×96 | 9 | XRGB8888 | `rc=0 struct_ok=1` |
| 弹幕 | 32×32 | 7 | ARGB8888_PM | `rc=0 struct_ok=1` |
| 直通对照 | 64×64 | 8 | ARGB8888_ST(2) | `rc=0 struct_ok=1` |
| 小图块 | 8×8 | 5 | XRGB8888 | `rc=0 struct_ok=1` |
| 极限小图 | 1×1 | 2 | XRGB8888 | `rc=0 struct_ok=1` |

边界（`rc=-3` 即 `GFX_BUILD_BAD_ARG`）：

```
sl 太小(640 宽用 2^11=2048<2560)      rc=-3
1x1 sl=2                              rc=0
1x1 sl=1（低于下限 2）                rc=-3
base 未 4 对齐                        rc=-3
INDEX8 表面                           rc=0
```

**结论**：

- R5：`stride_log2` 由 `max(2, ceil(log2(width × 4)))` 算。下限是 **2**，不是 0
  （`check.c` 第 103 行 `if (sl < 2u) return 0;`）；上限 31 由 `gfx_surface_set()` 把住。
  目录里这个字段是 u8、能存到 255，所以**解析器必须把 `>31` 当结构错误拒掉**，
  不能等到 `gfx_surface_set()` 那里才发现。
- R6：`INDEX8`（格式 3）`gfx_surface_set()` 收，但 `gfx_cmd_check()` 的 `fmt_eq_ok()`
  只让 XRGB / ARGB_PM / ARGB_ST 当 BLIT 源，用它做纹理会在执行时报 `GFX_E_BAD_FORMAT`。
  v1 打包工具不产出格式 3，manifest 写 `index8` 直接报错。
- 「base 顶到 0xFFFFFF00 后越界」的边界算例返回 `rc=0` 是**对的、不是漏判**：
  `0xFFFFFF00 + 7×32 + 7×4 + 3 = 0xFFFFFFFF`，正好落在界内。真正的越界判据在
  `gfx_surface_struct_ok()` 的 64 位算式里（`check.c` 第 112~115 行），
  实现时按 64 位边界公式构造真正越界的注错用例。

### 4.5 图集：一项对一个表面，成员不是独立条目（问题 2）

用真实源码验「从一张图集表面上取一块来 BLIT」：

```
图集登记 128x96 ARGB8888_PM sl=9      rc=0
帧缓冲登记 640x480 XRGB8888 sl=12      rc=0
BLIT 子矩形 16x16 COPY                rc=0
BLIT 子矩形 16x16 ALPHA(预乘)          rc=0
BLIT 子矩形 16x16 带色键               rc=0
BLIT ALPHA_STRAIGHT 源是预乘           rc=6（GFX_E_BAD_FORMAT，符合预期）
```

子矩形靠 `gfx_blit()` 的源坐标 `(sx, sy)` 取，**不占第二个表面槽**；v1 只有 16 槽，
这正是图集方案要的效果（128×96 的图集放 48 个 16×16 的小图，只花 1 槽）。

**顺带定下一条本来会写错的**（R7）：图集成员**不能各占一个目录条目**。
它们与图集条目共用同一段数据区，各成条目时 `[offset, offset+len)` 必然互相重叠，
而 2.2 节要求解析器把重叠当结构错误拒掉——两处要求会互相打架。
所以：**目录是一项对一个表面**，成员以「图集条目号 + 子矩形」的形式进 `assets.h`，
由应用在 BLIT 时给源坐标。manifest 的「切片宽高」就按这个口径理解：
一组等尺寸小图归到一条图集条目下，条目数是表面数，不是小图数。

### 4.6 容量预算：4 MiB 到底能放什么（问题 4）

按 2.1 节的布局规则（头 32 字节 + 每项目录 32 字节 + 每项起点 64 字节对齐 +
行跨取 2 的幂 + 行尾填充）实算三组：

| 方案 | 内容 | 合计 | 占 4 MiB |
| --- | --- | --: | --: |
| A（不作为首版） | 2 张 640×480 整图 + 图集 + 字库 + 两种弹幕 | 4,035,840 = 3.849 MiB | **96.2%**，只剩 158,464 字节 |
| B（首版） | 1 张 640×480 整图 + 图集 + 字库 + 两种弹幕 | 2,069,696 = 1.974 MiB | 49.3% |
| C（全程序生成） | 256×256 图集 + 字库 + 弹幕 + 粒子 | 316,864 = 0.302 MiB | 7.6% |

- 一张 640×480 整图 = `480 × 4096` = **1,966,080 字节 = 1.875 MiB**；
  4 MiB 分区最多 **2 张**整图，且放 2 张就吃掉 96% 的预算。
  这组容量预算排除了「3~4 张独立整图」；2 张虽然装得下，但余量过小，
  不作为首版素材配置。
- 目录开销：头 32 + 256 项 × 32 = **8,224 字节**；256 项在 16 MiB DDR 里平均上限 65,536 字节/项。
- 方案 B/C 的余量足够给正式美术留出替换空间，**不必**现在动 INDEX8 或 RLE。

### 4.7 装载时间：物理上限不等于运行预算（问题 4）

按 [E6](../hw/E6-SPI装载速度.md) 已有的两个口径算（E6 还没开工，这两个是它的起点数字）：

| 包大小 | 按手册口径 0.41 MB/s | 按单线纯搬移上限 2.1 MB/s |
| --- | --: | --: |
| 4 MiB（物理上限） | ≈ 10.2 s | ≈ 2.0 s |
| 方案 B 1.974 MiB | ≈ 5.0 s | ≈ 0.99 s |
| 方案 C 0.302 MiB | ≈ 0.77 s | ≈ 0.15 s |

**结论（R8）**：4 MiB 是「**能放多少**」的上限，不是「**该放多少**」的依据。
方案 A 那种接近上限的包，即使 E6 证明双线有效，启动也要等好几秒的黑屏。
所以本条把两件事分开写：物理上限 4 MiB 固定在工具里（越过就报错），
「运行预算」是另一个参数，**默认就等于物理上限、等 E6 出数之后再收紧**，
首版素材按方案 B/C 控制在约 2.1 MiB；当前占位包实测 2.044 MiB。
判据里「E6 定下更小运行预算后同样拒绝超预算包」
这一句就是为它留的口子。

### 4.8 Flash 镜像：输入是 `.hex`，不是 `.bit`（问题 3）

一开始用「两份文件按行比对」的办法看 `outflow/gfx2d_ti60.bit` 与 `.hex`，
得到「最佳偏移 20、632,541 行不同 / 699,027 行」，看起来像是两份不同的比特流。
换成**最长公共前缀/后缀**再看，结论完全不同：

```
本项目 gfx2d_ti60（2026-09-21 编译）
  len(bit)=699027 len(hex)=699047 diff=20
  LCP=156 LCS=698623  差异窗口: bit[156:404] (248 字节)  hex[156:424] (268 字节)
  窗口之后逐字节相同: True（698623 字节）
  bit 头: '...Mode: passive\nDie Name: Ti60_MP\nPADDED_BITS: 0...'
  hex 头: '...Mode: active \nDie Name: Ti60_MP\n4Byte: 0\nPADDED_BITS: 0...'
```

官方那一对 `ddr_demo_ti60.bit/.hex` 是同一个形状（差 20 字节、窗口之后 651,020 字节相同）。
两份文件都是「每字节一行十六进制」的文本（文件大小约为实际比特流的 3 倍，
与 `bit/README.md` 一致），差别**全部**在那 248/268 字节的 ASCII 头部里：
`.bit` 写 `Mode: passive`，`.hex` 写 `Mode: active` 并多一行 `4Byte: 0`。

**结论（R9）**：镜像合成与上板用的是 **`.hex`**（active，给 Flash 用），
`.bit` 是 JTAG 加载用的 passive 流；两者不能互换，也不能从一份推出另一份。
当前 `.hex` 解码 **699,047 字节 = 0.667 MiB**，2 MiB 分区余 1,398,105 字节。

分区算术（脚本里断言过，四个区间连续且恰好覆盖整片 8 MiB，无洞无重叠）：

| 分区 | 范围 | 大小 |
| --- | --- | --: |
| 比特流 | `0x000000`–`0x1FFFFF` | 2 MiB |
| 空闲 | `0x200000`–`0x37FFFF` | 1.5 MiB |
| 应用 | `0x380000`–`0x3FFFFF` | 512 KiB |
| 素材包 | `0x400000`–`0x7FFFFF` | 4 MiB |

四个起点（`0x0`、`0x200000`、`0x380000`、`0x400000`）都落在 4 KiB 扇区边界上，
满足 `开发环境.md` 第 8 节「写入地址必须落在扇区边界上」。
**R10**：工具要断言这件事；输出默认覆盖到三份输入中最高的实际末端地址，
再向上取整到扇区，输入末尾即使是 `0xFF` 也必须算进去。
方案 B 大约到 `0x600000`，比整片省 2 MiB 的写入时间；`--full` 出整片。
Programmer hex 的格式本轮也从既有的 `bin2hex.py` 与 `bit/flash_backup/` 那份备份确认过：
每字节一行、两位大写十六进制、LF 换行，长度恰好是字节数 × 3。

### 4.9 启动路径的缓存问题：E3 规则在这里不适用（问题 4）

2.3 节的路径是 Flash `0x400000` → SPI 驱动 → DDR 素材区 → 解析 → 画图。
看起来像 E3 说的「外部主机写、CPU 读」，但**不是**：
搬素材的是 CPU 自己经 `spiFlash_f2m_*` 逐字节写内存，不是引擎或扫描输出那种外部主机。
platform 第 05 章的实测支持这一点：本构型**没有写缓冲**（网表是 `dBus_Bridge_withoutWriteBuffer`，
CSR `0x810` 读写都触发非法指令，T6），CPU 的写返回前已经落到 DDR（T3），
T1 在 4096 个地址上「写后立刻读回」**0 次不符**，T2 只写不装行、写后读一次会装行。

**结论（R11）**：这条路径**不加** `board_dcache_invalidate_range()`。
追加失效不是「保险」，代价是每次 16 MiB / 64 = 262144 行、按 T11 的约 4 周期/行算
是百万级周期，而收益为零。实现说明明确区分 CPU 写入与外部主机写入。
若以后改成由外部主机搬素材（例如引擎做 DMA 预取），那时必须再加回来。

### 4.10 CRC32 口径对账（问题 2）

| 输入 | C 侧 `crc32_ieee` | python `zlib.crc32` |
| --- | --- | --- |
| 空 | `00000000` | `00000000` |
| `"123456789"` | `CBF43926` | `CBF43926` |
| fox 那句话 | `414FA339` | `414FA339` |
| 4 MiB 图案（`byte i = (i*31+7) & 0xFF`） | `91DFD9F8` | `91DFD9F8` |

4 MiB 那一行另做了「分 4096 字节喂」的流式对照，与一次算完相同（`91DFD9F8`），
首/末 16 字节也逐字节相同。所以 2.2 节的「整包 CRC 覆盖 `总长` 字节」可以用
`crc32_begin/update/end` 分块算，不必把整包先拷成一块连续内存。

### 4.11 字库来源（问题 4）

查过本仓与厂商资料包：`Main/` 下没有任何点阵或矢量字库；
`Efinix/` 下也没有 `.ttf` / `.bdf` / `.fnt`（文件名里带 `8_16` 的只有
`par2ser_128_16_v1.v`，是并串转换，与字库无关）。

**结论（R12）**：字库自绘，95 个 ASCII 字形以文本形式（每字 16 行、每行 8 位十六进制）
入库 `Main/assets/font/ascii8x16.txt`，打包工具把它渲染成图集，
`LICENSES.md` 登记为「项目自绘，无第三方来源」。
这样不必引入外部依赖、也不必在离线环境里找 CC0 字库。
字库不在流水线的关键路径上：占位图块就能验完整条流水线，SW6 的 HUD 才需要它。
