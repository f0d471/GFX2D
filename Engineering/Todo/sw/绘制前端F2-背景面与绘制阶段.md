# 绘制前端 F2 背景面与绘制阶段

状态：**待验收（候选未采用）**。前置：[F1](绘制前端F1-成本分解与基线.md) 的背景/固定项实测。
范围：纯软件组织与调度，复用现有背景 LOAD，不修改 RTL。共同契约见
[总览](绘制前端总览.md)。

决策依据：engine 第 11 章 D67、D72、D73；背景初值、画序与资源租用一起成立。

## 1 要解决什么

当前 LOAD 从 dst 自身取初值，再用跨 30 桶的全高 FILL 重画背景与 HUD。
独立背景面可移走重复记录，但动态背景/HUD 的生成仍有成本。不能通过冻结星点、
滚动或 HUD 获得性能，也不能把 HUD 在画序中的位置随意改变。

## 2 怎么切分

### 2.1 先明确三种候选

| 候选 | 实际工作 | 采用风险 |
| --- | --- | --- |
| B0 基准 | bg=dst，全部绘制进入现有 v2 | 保留为运行时对照 |
| B1 真静态缓存 | 只缓存证明跨帧不变且在该区域构成连续绘制前缀的内容；变化时重建 | 静态竖线位于动态横线之后，不能直接提到前面 |
| B2 动态预合成 | 每帧以直通/TEX 将完整背景块和 HUD 合成到离屏面，再 BAND LOAD | 增加 DDR 写、一次执行/完成边界和表面更新；须完整计入 |

B1 若只能缓存底色，仍如实报告小收益；不为了凑“静态层”改变原画序。
B2 是默认研究候选，完成 F1 后再决定是否采用；一次性静态层与每帧动态背景分开计账。
全屏初始化确保每个 LOAD 像素有定义，不能让未覆盖区域读取前帧或上电残值。

### 2.2 通用 pass 与资源接口

增加 CPU 侧 `gfx_frame_plan` / `gfx_pass`，字段至少包含：

```text
frame_id, target descriptor, initial attachment(base/stride/format/generation),
draw range, reads[], writes[], dependency pass_id, completion ticket,
command/instance/PB leases, first_error, published
```

首版 API 为 `gfx_frame_begin(plan, leases)`、`gfx_frame_add_pass(plan, pass)`、
`gfx_frame_seal(plan)`、`renderer_submit_plan(plan, ticket)`。最多三 pass，依赖
只能指向更小的 pass_id；add/seal 返回 GFX_BUILD_BAD_ARG/FULL 或既有语义错误，
失败不发布任何 doorbell。seal 后计划只读，提交成功后 ticket 绑定整帧资源；
只有成功完成或错误排空后才能 `gfx_frame_release(ticket)`。单 pass 旧入口保持。

首版最多三阶段：直通背景 prepass → 动态 BAND pass → 交换。
所有参数是表面与 draw 区间；通用库不出现游戏名称、kind、网格/星点规则。
不增加任意递归依赖：按提交序给出有向无环依赖，首版调度器按拓扑序串行提交同一引擎。
初值操作首版只支持现有 LOAD；CLEAR/DONT_CARE 不伪装成当前硬件已支持的能力。

每个待呈现帧有独立的背景页 lease。动态背景初版准备 A/B 两页，每页大小由
stride×height 算得并检查范围/对齐；模式 1 的三张预合成图与游戏背景页按模式
互斥租用。游戏槽 15 作背景描述符，切换映射只在 engine 完成并排空后执行；
帧计划保存物理 base，不依赖可被下一帧改写的单个全局表项。

### 2.3 保持当前画面与统计

应用适配把 `draw_background` 发往 prepass；敌机、自机、各粒子池、banner、flash
仍按原序发往动态 pass。HUD 与游戏区经 clip 限定为不相交的 x 区间，可在动态
命令已构造、active 计数已确定后发往 prepass；prepass 完成之后才执行 BAND。
这是读写集合不相交的调度，不能推广到有重叠的通用 HUD。

通用情况的后置 overlay 与动态区域相交时，保留在 BAND 序列末尾，或单独形成
有完成依赖的后置 pass；禁止用“HUD”标签绕过依赖检查。若读背景或读取目的结果，
必须在资源集合中表达，不能擅自移动。

逻辑 draw/by_eq/active 总数仍按原输入统计；另报各 pass 的物理命令、像素与 DDR
字节。原游戏 HUD 读取哪些帧率/活动数保持一致，不更改统计时间点。

### 2.4 调度与缓存一致性

CPU 可构造下一帧的命令，但不能写 GPU 正在消费的背景页或改硬件 SURF。
每帧依次：构造两个命令范围 → 收尾上一帧 → 设置本帧背景 SURF → 提交并等待
prepass → 提交 BAND → 后续按原 present 路径请求交换。初版不宣称 prepass 与
BAND 在同一引擎上并行；依赖造成的 CPU/GPU 空泡是性能账的一部分。

CPU 发布前按现 BSP 的写顺序/内存屏障契约完成；CPU 读回 GPU 写结果前失效。
只在需要消费读回的诊断路径做缓存检查，不每帧增加无用途的 CRC/hash。
prepass 失败、版本不匹配、资源不足或 BAND 失败都阻止本帧交换；已发布后不原地
修改计划、不静默回退。启动前发现不支持时可选择 B0 并重新构造完整帧。

### 2.5 实现位置

| 文件/层 | 动作 |
| --- | --- |
| `Main/sw/lib/gfx` | 通用帧计划、pass 描述与依赖/范围检查 |
| `stg_draw.c` / `stg_modes.c` | 绘制阶段适配；复用原绘制函数，保持背景内部顺序 |
| `renderer.c` / BSP 驱动 | 多阶段完成票据、SURF 绑定、失败不呈现、切换 flush |
| `main.c` 的模式/表面初始化 | 离屏资源 lease 与槽 15 映射；恢复基础 Demo |
| `sim/engine/frontend` | pass 的独立直通像素对照与生命周期反例 |

## 3 判据

- 所有候选与原直通逐像素、可见区 CRC 一致；背景横/竖线交叉、星点跨屏、HUD
  更新、flash、标题、通关、切后端/切模式全部覆盖，padding 保持原契约。
- 资源页越界/相交、未初始化像素、缓存失效遗漏、SURF 提前切换、旧 generation、
  prepass 未完成即 LOAD 各有反例；共享页被下一帧覆盖的注错必须见红。
- 至少 10000 张场景与完整宿主回放；板上同帧验证及采用门槛沿总览。
- 同状态 B0/B1/B2 计 CPU、prepass、BAND、额外 DDR 和依赖空泡；不能只报
  BAND 命令数下降。若总关键路径不下降或扫描压力恶化，候选不转正。
- 不承诺固定减少 40%；报告实际比例随 K/场景变化的曲线及每次缓存重建的代价。
