## 1 要解决什么

把三维管线变成看得见的演示:同一块板、同一位流上,评委先看到 2D 弹幕指标(压力模式),
再切到 3D 模式看到真 3D 场景;cup3d 提供同负载软硬件对照。游戏本体 MYRIAD 与三个既有
演示模式不动,3D 是新增模式。

## 2 怎么切分

### 2.1 模式框架

  TechReports,不得静默删除。

### 2.2 场景与渲染分工(按阶梯分级,评审定案)

后画的 2D 精灵只能保证覆盖世界背景,**不能表达世界遮挡**(敌机会「穿墙」),
且旧 BitBlt 无实时缩放。因此世界内物体一律走 3D 通路,2D 层只放无遮挡语义的东西:

- **弹幕全部是世界空间物体(2026-10-22 二次修订,用户质询成立)**:评审对敌机的遮挡
  论证同样适用于敌弹——有世界位置的东西画在 2D 层就会「穿门框」。敌弹=色键抠底的
  billboard(FLAGS.KEY_EN,两三角形,来自敌机与门框炮台,飞到门框后面由 z 测试正确挡住);
  自机弹=纵向小条,向走廊深处飞行(纵深变小);L1 平涂下敌弹为纯色小方块
  (TEX_EN=0,同样走 RAST——L1 也有真 3D 弹幕),原「画面边缘 2D 阵地」方案废除。
  命中判定=敌弹逼近相机面时与自机屏幕位置比对,过近面即移出世界。
  原“场景 ~500 + 弹幕 ~300×2≈1100 tri，CPU 约 6ms”已被 2026-10-23 板测推翻：
  当前通用 view→setup 1100 条约 504.453ms，独立分桶约 48.318ms（合成探针，非真实场景）。
  **首版从 16～32 个动态三角形起测**，减少走廊段/模型面数和弹幕数，保留世界空间遮挡；
  32 条探针两项约 15.378ms，但还不含模型变换、逻辑、硬件和显示，不能视为 30fps 证据。
  1100 条改为压力/优化目标；恢复该规模须 CPU 快路/缓存经 R1 数值对拍与真实板上剖析后再定。
- **L1(平涂)**:程序化走廊——立方体隧道段沿 z 推进、循环,门框障碍(撞上扣护盾);
  世界内**不放敌机精灵**(场景约束,规避遮挡问题);自机=世界空间平涂/线框机体
  (相机前固定深度,横移带倾斜,弹从机首出,命中/擦弹/门框判定全部用世界距离);HUD 2D。
- **L2(纹理)**:敌机改为**世界空间纹理 billboard**(面向相机的两三角形四边形,
  走 RAST_TEX):距离缩放与深度遮挡由 3D 管线自然给出,不依赖 2D 缩放。
- 渲染路径(两级同构):CPU(R1 §2.3:S3L 到视图空间→近面裁剪→除法→映射→guard band
  →setup→条带子表分桶)→ 引擎 RAST;2D 层只剩 HUD,在同条带 2D 相位叠加。
  **TEX 窗口所有权:3D 模式独占 TEX**(2D 热纹理集不装载;N_max 模式反之,3D 空闲)——
  窗口 16KiB 定为 64×64 atlas，包含 4 个 32×32×32bpp 区块：走廊墙面、门框、敌机、敌弹。
  CPU 按 64 词行距装载，UV 加区块原点 (0,0)/(32,0)/(0,32)/(32,32)，不增加 128B 记录字段；
  原点单位为 texel，Q12.4 raw 偏移乘 16；各块局部 UV 限在 [0,31]，不把端点 32 采到相邻区块。
  切回二维模式前等引擎完成，写 TRI_COUNT=0 并重装其纹理工作集；恢复3D时再完整发布
  参数快照和列表。不能把四张线性拼接数据当作 atlas。
- 素材全部脚本生成,走现有 PNG→预乘图集流水线。

### 2.3 cup3d 硬件版(同分辨率同语义对照,评审定案)

- cup3d(396 三角形茶杯)加渲染开关,软件/硬件两路:
  - 软件=rast_ref(R1 同一数值契约)在 **320×240** 渲染;
    small3dlib 原路径保留为「历史第三方软件渲染」参照,不进加速比对照
    (其减量 z 与分辨率与硬件版不同构,历史约 20fps 数字只作背景引用);
  - 硬件=同一几何出口转 setup 记录走 RAST,同一 **320×240 视口 1:1**(与软件版同窗;
    原「×2 放大铺满」选项删除——放大是新路径,不属本工作点)。
- 物理帧仍是 640×480、30 带的 R3 ABI，320×240 是其中的视口，两路都生成 30 个子表头，
  视口外背景一致。当前 `rast_setup_view` 固定 640×480 映射，R4 须通过共同的 320×240
  视口映射接 `rast_setup_polygon` 或扩展软件视口接口并做数值验证，不能只缩 LSTRIPS。
- 演示口径:同 app、同模型、同分辨率、同数值语义下软件 fps vs 硬件 fps 同屏对照。

### 2.4 软件对照模式

- 3D 模式内一键切「软件光栅」:rast_ref 整帧软件画(预期秒级/帧),
  HUD 并排显示软硬件 fps——复现赛题「实时对比软硬件渲染」的 3D 版。

### 2.5 性能与调参

- 帧预算分解(板上 CLINT 打点,同本条目第 3 节及开发日志 §4.6 口径):游戏逻辑/几何+setup/分桶/命令提交/
  引擎执行;瓶颈若在 CPU 几何+setup,先降三角形数再谈优化。
- 输入三角形数、裁剪后记录数、总条带引用数、bbox 扫描点数分别统计；不能用“光栅每拍一点”
  或 307200 个最终像素替代实际工作量。30fps 先以小规模实测闭合，再扩负载。
  软件优化若修改 setup/分桶，须同向量同数值语义对拍，缓存只复用本帧确实未变的几何/setup。
  降到L1只关硬件纹理不能解决通用CPU setup成本，仍须降低动态几何量或另做经验证的快路。
- STRIP_H=16 起步;纹理 4 张 32×32 起步,不够再议 TEX 扩容(R3 资源账另估,不在本工作点内)。

## 3 判据

1. 轨道射击:B7 位流上 **30fps 判据**(评审修正口径)——连续 60 秒(约 3600 场)内:
   呈现节拍=每两场一次缓冲切换(±1 场抖动内),以「本该呈现的场次未呈现」计掉帧,
   **掉帧=0**;逐帧渲染时间(CLINT)≤33.3ms,迟到帧=0。
   (60fps 的「场数−切换数=0」公式不适用于 30fps:正常即 3600 场/约 1800 次呈现。)
2. 画面分层正确:世界(3D,含弹幕)→ HUD(2D)次序稳定;L2 下敌机/敌弹被门框遮挡
   由深度测试给出(设计「敌弹没入门框后消失」「敌机绕到门框后」两个演示瞬间,
   目检+帧 CRC 双判)。
3. cup3d 硬件版:同负载、同语义帧 CRC 与 PC 侧 rast_ref 一致，软硬 fps 同屏；
   396 面经当前通用 setup 不能直接承诺满帧。满帧列为优化目标，须板上整帧数据证明，
   未达到时如实报告实际帧率与 CPU/光栅分项，不用减面模型冒充同负载加速比。
4. 板上逐帧对账:3D 帧的 PC 期望(R1 参考导出)与板上硬件帧 CRC 一致,≥60 帧;注错见红沿用 R3 组。
5. 2D 零回退:模式 1/2/3 在同一位流行为与既有判据逐项不变(3D 模式独占 TEX 不影响
   其它模式——模式切换时装载策略随模式走)。
6. PC(host)与板上(target)同源构建零告警;`check_sw_layers.sh` 过(rast_ref/rast_setup
   属 lib/gfx,应用不越层)。

### 4.2 实测：CPU 与 bbox 两个预算必须分别控制

探针直接调用未修改的 `fx16_mat_vec/rast_setup_view/rast_setup_polygon/rast_bin` 和
`gfx_engine_submit_raster/wait`。小三角形组每个输入顶点先经过通用单位矩阵变换，
再做近远裁剪/投影/setup/分桶；全屏组从屏幕坐标开始，因此两组 CPU 时间不能当同工作量
相除。每组 3 次，以下列出各分项中位数，单位 ms；合计是两分项中位数之和。

| 合成输入 | 记录数 | CPU（含分桶） | 提交到完成 | 其中 RAST | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小三角形网格 | 16 | 9.638 | 2.176 | 0.030 | 11.814 |
| 小三角形网格 | 32 | 19.232 | 2.201 | 0.054 | 21.433 |
| 小三角形网格 | 64 | 39.810 | 2.250 | 0.106 | 42.061 |
| 小三角形网格 | 396 | 245.910 | 2.772 | 0.623 | 248.681 |
| 全屏 bbox | 1 | 0.337 | 5.235 | 3.097 | 5.572 |
| 全屏 bbox | 16 | 4.569 | 51.412 | 49.260 | 55.981 |
| 全屏 bbox | 32 | 9.021 | 100.647 | 98.504 | 109.667 |

这里的“提交到完成”含整帧 30 带 LOAD、z clear、RAST、每带 8 像素 FILL 代用 HUD 与
FLUSH，RAST 是其子集，**不能再次相加**。不含游戏逻辑、真实 HUD 构造、纹理采样、
输入处理或 CRC；CPU 分项包含探针约定的变换，但不是任意模型的真实变换成本。

32 个小三角形只有 3916 个 bbox 候选点、48 个条带引用；16 个全屏 bbox 为
4915200 个候选点、480 引用，32 个为 9830400 点、960 引用。相同深度的重叠三角形
最终大部分被 LESS 拒绝，仍要扫描各自 bbox；不能按最终可见像素估算 RAST。
小负载约 2.15ms 的整帧固定部分也不能用纯 RAST 计数替代。

另跑 **32 条动态生成记录的 120 帧两场节拍取样**：每帧都执行通用变换→setup→分桶→
真实引擎→呈现。渲染时间 p50=21.42058ms、p99=21.44428ms、max=21.45422ms；
120/120 在预定场次呈现，迟到及超过 33.333ms 的帧均为 0，交换计数逐帧 +1。
窗口以固定起始场锚定，不按实际晚到场重新计时。原始逐帧数据在串口中，分位数按最近秩计算。
日志先存内存、取样后输出，不把 UART 阻塞混入热循环。

全部 8 组板上整帧 CRC 与 host `rast_ref` 相同，主/子表 CRC 与引用/bbox 统计也一致；
采集器另拒绝缺加载边界、串口丢失、缺帧、CRC 篡改和显示错误 5 类坏日志。
清统计后的显示累计 ZERO/UNDER/RESPERR 均为 0，末次 SNAP_MIN=347。
`SNAP_FRAME` 是像素域 16 位快照，`board_frame_count` 是 core 域场计数，两者复位纪元不同，
不拿它们的绝对值相减；呈现节拍只用后一计数。

**解释与限制：**120 帧约四秒只证明该合成工作量下两场呈现机制可行；它不是完整走廊、
L2 纹理、60 秒/1800 帧或 R4 30fps 验收。396 组也只是重复网格三角形，不能称为茶杯实测。
这轮与 R3 的 32 条/15.378ms 探针输入不同，并新增通用模型矩阵阶段，二者不构成性能回退比较。
下一轮从 16～32 条**裁剪后记录**起步，同时记录总 bbox 点数、总引用和真实整帧时间。
首版暂以约 40 万 bbox 点/帧作取样目标，留待真实场景验证；它不是已证明的通用 30fps 容量。

通用矩阵每顶点调用 16 次 `fx16_mul`，每个输入三角形额外 3 次通用模型矩阵与 3 次投影矩阵；

确实不变的记录才缓存；再研究常量除数精确舍入、简单模型/同深度 billboard 快路与保序分桶。

不能把多个逐项乘法舍入合成一次点积舍入，或直接以倒数乘法替换精确除法。
本轮没有编写/采用这些生产优化。

### 4.4 视口、场景与纹理预算

1. **视口必须作为软件接口明确表达。**走廊按预览采用左400×480、右240像素HUD；
   cup3d 为居中的320×240，原点(160,120)。现有 `rast_setup_view` 固定640×480，
   `rast_setup_polygon` 只裁全帧 guard band，没有子视口 scissor。
   单改投影比例或 LSTRIPS 不成立；建议在 lib/gfx 增加共享的显式视口入口，旧入口保持原语义。
   映射原型为 `x_raw=16*x0+fx16_viewport(ndc_x,width,0)`，y同理（flip=1）；
   子视口四边先裁到最大 Q12.4 格点形成的半开矩形，再进入现有 setup。
   新接口在实现前把裁剪顺序、扩顶点容量、像素四边与属性舍入补入数值契约并独立对拍。
   两种执行者消费**同一份最终记录**，硬件仍提交完整640×480/30带。
2. **最小场景从构图倒推成本。**首发只放一段走廊、一个门框、自机、少量世界弹；
   L2 再加一个敌机。一个四边形需2条，四面走廊约8条、四边门框约8条、自机约4条，
   一对敌弹/自机弹再4条，L2敌机再2条：未裁剪示意约24/26条，已接近32条起测上限。
   该账只是拓扑预算，近面/视口裁剪拆分后按实际记录数判限。
   循环段、多个敌机、密集弹幕、模型细分逐项增加，每次同时看bbox/引用与整帧时间；
   不能直接照搬 HTML 的对象数量或照抄“约500面走廊”。
3. **世界规则保持确定性。**坐标用既有定点约定，逻辑固定每 tick=1/30秒、显式种子，
   不从墙钟取位置/随机数；软件慢时同一逻辑帧仍产生同一场景，不能按耗时追帧。
   敌弹/自机弹/自机/敌机均有世界位置和深度，擦弹/命中先在同一世界/相机空间判断，
   再做投影。近面后移除物体的次序与录像一致。预算超限按固定优先级限出生/省装饰，
   不能静默截断主表或用2D弹替代世界遮挡。
4. **L1/L2 在同一 B7 上切换。**L1 使用 TEX_EN=0、VCOLOR_EN=1；不重综合。
   L2 为原有仿射 UV、nearest/CLAMP、原始ARGB色键、严格LESS，没有透视校正或半透明混合。
   面向相机且同深度的 billboard 适合该插值；长墙会有仿射扭曲，先用平涂几何/短分段，
   不能未经预算靠大量细分掩盖它。线框、辉光和粒子不是 RAST 原生能力，需几何/素材成本。
5. **atlas 固定16KiB。**四区块仍按第2节的64词行距交错装载；每块局部 UV=0..31 texel，
   再加0/32 texel原点并乘16。采用二值透明：透明像素经素材流水线变为原始ARGB全0，
   全atlas共用 RAS_KEY=0；可见像素alpha=255，墙体不放全0 texel。
   RAST忽略alpha合成，PNG半透明边缘/发光不能当已支持。生成后导出atlas原始词与CRC，
   帧测试覆盖区块边缘、键色前后深度和敌弹没入门框的瞬间。
6. **预览只作构图参考。**HTML 使用 Canvas 渐变、阴影、描边和深度排序；
   FPS有 `30+sin(t)*0.3` 模拟值，软件画面有约0.8fps的定时冻结。它不是R1参考器、
   深度验收或板上性能证据。保留原文件，正式演示HUD必须显示实际测量值。

### 4.5 资源所有权、模式切换与软件对照

共享池现为10MiB，命令A/B各1MiB，帧缓冲保持4096字节行跨。建议给模式4显式租用
两个独立64KiB槽（32B对齐主表，随后16B包络子表），可各容纳256记录及全跨30带的子表：
32768+15480=48248B，补齐到48256B。**这是存储容量，不是可达30fps规模**。
不得与 `frontend_game` 的实例/分桶 arena 同时存活；进出模式先释放原租约，检查活对象为0。
首版串行路径只用一个槽，第二槽留给后续经验证的流水；对软件参考器另租用
640×16×(4+2)=61440B的颜色/z条带暂存。cup3d若裁剪后超过256条，应申请另一个更大租约，
不能把396面输入塞进该固定槽或以容量不足时减面冒充同负载。

进入3D的顺序：flush旧renderer并确认在途present→释放旧arena→失效旧TEX热集状态→
装完整atlas→登记3D/HUD/背景表面→发布主/子表与参数→submit。
离开则wait/drain并完成或丢弃待呈现帧→释放3D槽→**重新装载**旧热集并重新登记覆盖层→
renderer_prepare→首张2D帧；旧submit在新门铃前负责清TRI_COUNT。
现有 `s_tex_ready` 只表示曾装过热集，3D覆盖窗口后必须失效，不能凭旧标记跳过重装。
SW/HW或L1/L2切换也只在帧边界完成；不修改生产默认后端来绕过切换测试。

模式4软件路径使用 `rast_ref` 按30条带执行相同记录、相同背景、相同HUD；CPU只维护
条带z，不另造低精度整帧z语义。两路功能对拍包含padding和视口外背景；整帧CRC、
回读与双参考执行在功能判据中做，正式性能窗口关闭这些操作并保持同一场景输入。
慢速软件模式继续提供输入轮询，允许在条带间记下退出请求，在安全帧边界丢弃未呈现帧。
HUD上的另一后端FPS用最近一次有效测量并注明；未测显示 `--`，不填估计数字。

cup3d有207顶点/396面，原路径使用 S3L 的8位压缩z且两面着色，与R1背面剔除/16位z不同。
新同构SW/HW路须共用视空间出口、显式320×240映射、绕序/背面策略、光照和最终记录，
按同一个逻辑帧逐帧CRC；记录输入面数与剔除/裁剪后数。
先计算一次207个唯一顶点的模型/视图变换，再按396个索引组面，避免重复变换1188个顶点。
旧 small3dlib 演示原样保留为历史第三方路径，不能与新路计算加速比。
本轮396网格组CPU约246ms只证明通用CPU成本需警惕，不推算实际茶杯FPS。

### 4.7 来源与收尾

仓内事实以上述代码、数值契约、R3第18章及本次原始日志为准。外部只查机制的一手资料，
没有移植外部实现：

- [RISC-V M扩展](https://docs.riscv.org/reference/isa/v20240411/unpriv/m-st-ext.html)：DIV/REM按XLEN操作，RV32的64位算术不能等同一条DIV；具体成本由本机反汇编和板测确定。
- [GCC整数运行库](https://gcc.gnu.org/onlinedocs/gcc-13.2.0/gccint/Integer-library-routines.html)：核对 `__divdi3/__moddi3` 的含义；并未将“存在库调用”直接当成耗时占比证明。
- [Khronos GLSL 4.60 §4.5](https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.4.60.html)：核对线性屏幕插值与透视校正插值的区别；本项目仍以R1仿射契约为准，不宣称GL一致性。

取样后重新构建并加载当前生产 `gfx2dGame`（O2/PERF、启动模式2/HW-TEX），恢复正常游戏。
首次15秒采集只有素材包输出，不能据退出码0判恢复成功；随后不复位被动采集12秒，
明确收到连续 `game,hw-tex` 统计行才确认恢复。
该步骤只检查启动/模式/后端输出与部署身份，不算2D全量回归或新的N_max记录；
[恢复确认](../../TechReports/engine/evidence/19-r4-research-20261023/restore.json)、
[后续串口](../../TechReports/engine/evidence/19-r4-research-20261023/restore-followup.serial.log)
与BIN身份随同归档。本轮研究完成，下一轮从A批进入正式开发；若真实场景
预算超限，先减装饰/弹数并测量，再决定是否启动经数值验证的CPU快路。
