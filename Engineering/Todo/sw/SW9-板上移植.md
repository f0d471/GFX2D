## 1 要解决什么

PC 版证明的是逻辑与画面正确，板上要回答三件事：同一份代码在 RV32 上结果是否逐位相同、
软件渲染在板上有多快、切到硬件后快多少。第三件是赛题基础要求 3 的「实时对比」，
也是 `N_max` 的来源。

## 2 怎么切分

### 2.1 前半：无显示运行（现在就能做到的部分）

- 补全 `sw/bsp/ti60/` 的输入（KEY0~3 + 串口），映射按 SW7 的 G3 定案（2026-09-25）：
  KEY0~3（丝印 SW0~SW3）依次映射到 `BOARD_KEY_LEFT`、`DOWN`、`UP`、`RIGHT`，低有效，`board_keys()` 每帧读一次；
  和弦（上+下切模式、左+右切软硬件）是 SW8 应用侧的事，bsp 只给原始位图。
  串口转发：`tools/board/board_run.py` 加一个选项，在同一进程里用 `ctypes` 调 Windows 的 `GetAsyncKeyState`、
  `XInputGetState` 读键盘与手柄，按键位图变化时经串口发出（两字节即可，格式在本条定）；
  板上从 UART 接收 FIFO 非阻塞地取，与 KEY0~3 按位或。按键的物理排布以实物为准，映射只是一张表。
  正式素材由 SW5 已验收的板级装载入口从
  Flash 读入 DDR 素材区，再由 `sw/lib/core/assetpak` 解析；本条只调用，不重写装载器。
  JTAG 预装 DDR 仅作调试捷径，不代替 SW5 的 Flash 启动判据。占位画面的无素材测试仍可先做。
  计时与日志在 SW1 已有。
- 录像回放：把 PC 录的一段按键序列编进程序（或经串口送入），板上跑同样的帧数，
  每帧用软件执行器画进 DDR 帧缓冲 0（`0x0200_0000`），算整帧 CRC32 打到串口。
  CRC 口径按 [sw 第 03 章](../../TechReports/sw/03-PC平台层与帧节拍.md) 3.6 节：逐行取前 `width × 4` 字节、跳过行跨的间隙，
  两边都用 `lib/core/crc32.h` 的流式接口。把行跨的空隙算进去，板上 DDR 的上电残值与
  PC 上的零必然不同，比对会在与渲染无关的地方全线报错。
  （2026-09-28：SW7 D 批入库了 9208 帧的工具辅助通关录像 `replay/stg_clear.g2dr` 与回放入口
  `-DSTG_FIELD=4 -DSTG_JUDGE_REPLAY=1`，录像在构建时转成 C 数组、板上构建编得进去，逐帧 `g` 行带整帧 CRC，
  可以直接当这一步的输入，见 [sw 第 06 章](../../TechReports/sw/06-游戏本体.md) 3.15 节。
  板上的 `N_max` 用模式 3 的 `-DGFX2D_PRESS_CLOCK=1`，S1 规模用 `-DGFX2D_PRESS_KNOB=1744`，见 [sw 第 07 章](../../TechReports/sw/07-演示模式与统计埋点.md)。）
- 与 PC 无窗口回放的 CRC 序列逐帧比对。这一步验证的是 ILP32 与 LP64、gcc 8.3 与 gcc 15 之间没有行为差异。
- 顺带测出板上软件渲染每帧的三段耗时（逻辑、构造命令、执行），这是软件基线帧率的第一个真实数字；
  执行段的细分吞吐以 E7 为准。

### 2.2 后半：上屏与硬件引擎（等 display、engine）

- display 就绪后：`sw/bsp/ti60/` 的 `board_present` 与 `board_wait_frame` 已在扫描输出验收时接上
  （写 `BACK_BASE`/`SWAP_REQ`、轮询 `SWAP_COUNT` 与 `FRAME_COUNT`）；
  `board_frame_count`/`board_swap_count` 由 [sw 第 03 章](../../TechReports/sw/03-PC平台层与帧节拍.md)
  补齐并已于 2026-09-21
  上板验过（600 帧 `dfield=dswap=600`、每帧恰一场、掉帧减法 2 减 1），本条不必再验一遍。
  本条要补的是把帧节拍从轮询改成场起始中断驱动。
- 引擎就绪后：引擎 P1 已在 `sw/bsp/ti60/` 写好最小驱动（登记表面、按设计文档 3.4 节提交命令表、等完成、读错误三元组与计数器，
  见 [引擎 B6 条目](../hw/引擎P1-B6-顶层集成与上板.md) 2.6 节）；本条在它上面接中断 B、完成后调用 `board_present()` 请求交换；
  按 sw 系列 README 的一致性规则，读回共享区之前失效。
- 软硬件切换按 [sw 第 07 章](../../TechReports/sw/07-演示模式与统计埋点.md) 3.7 节：板上左+右和弦、PC 端串口转发的 Tab；一次只跑一个后端，
  HUD 两个帧率都填实数（另一个显示最近一次实测）；硬件计数器（`PERF_*`）并入 SW8 的 CSV。
- 同帧软硬件 CRC 对比：同一张命令表，软件执行器画一份、引擎画一份，CRC 必须相同；
  注错：跳过读回前的失效，CRC 必须不同（设计文档 3.8 节）。
- 在板上跑 SW8 的压力测试，软件与硬件各得一个 `N_max`。

最小驱动随引擎 P1 一起写；本条的中断与游戏接入代码在引擎就绪之前就可以按寄存器表写好并编过，只是无法验证。

### 2.3 候选缓存与最终性能（2026-09-27 分工）

E7/E8 的固定产物实验按定案的缩减范围收尾，维护记录在
[platform 第 09 章](../../TechReports/platform/09-软件执行器像素吞吐的板上复现.md)与
[第 10 章](../../TechReports/platform/10-CPU每弹幕开销与缓存对照的复现.md)。
本条负责真实游戏的完整帧预算、软硬件加速比、扫描压力与最终缓存选择。
4KB 是当前主线，16KB/4 路是候选；采用候选前确认第 10 章的 DDR 回归证据，
配置变更单独生成并核对资源、时序及相关回归。在实际选定的构型上完成本条集成判据，
不要求每次软件更新重跑 E7/E8，也不为已不参与选型的 8KB 补齐新版矩阵。

## 3 判据

| 项 | 判据 |
| --- | --- |
| 前半：逐帧一致 | 一段不少于 600 帧的录像，板上每帧 CRC 与 PC 逐帧相同；注错：板上把某个方程的注错宏打开，从第一次用到该方程的那一帧起 CRC 开始不同 |
| 前半：耗时 | 三段耗时每秒一行打到串口，原始日志入 `sw/apps/game/gfx2dGame/logs/` |
| 前半：体积 | bin 小于 512KB，登记 SHA256 与编译命令 |
| 后半：上屏 | 三种模式在 HDMI 上显示，交换无撕裂 |
| 后半：同帧 CRC | 软硬件同帧 CRC 一致，跳过失效的注错版必须不一致 |
| 后半：对比 | 软件与硬件的帧率、`N_max` 同屏显示，并写进 CSV |
